# Архитектура геймплея RH

> **Владеет:** устройством авторского слоя пакета `rh` (раскладка, слои, связи между файлами, соглашения), моделью игровых данных, механиками (характеристики, условия и эффекты, взаимодействия, сознание, перемещение, ход, роли, персонажи, модели NPC, процессы, квесты, реакции), их связями и стратегией проверки.
> **Не владеет:** механизмами движка (`core`, `textsystem`), командами, событиями и состоянием как таковыми — их семантику задают [Commands and Events](../Architecture/CommandsAndEvents.md) и [Canonical State and Save](../Architecture/CanonicalStateAndSave.md).
> **Статус:** `draft` — принятая архитектура до реализации первых механик; становится `normative`, когда механики реализованы и проверены.

## 1. Назначение и границы

`rh` — однопользовательская текстовая RPG: мир из связанных переходами локаций; у каждой локации картинка, описание и меню взаимодействий. Игра пошаговая: игрок тратит выносливость на взаимодействия, завершает ход, мир реагирует. Целевой масштаб — сотни NPC; в игре есть квесты, сюжет и песочница.

- Весь геймплей пишется в `GameData/rh/` на authoring surface ([Authoring Surface](../Architecture/AuthoringSurfaceContract.md)): код — только в `scripts/authoring/`, данные — в `definitions/`, `schemas/` и `localization/`. Из `game.*` используется только `game.random` ([Lua Gameplay Reference](../Authoring/LuaGameplayReference.md#детерминированный-генератор-случайных-чисел-gamerandom)).
- Единственный файл вне authoring — мост старта новой игры: он вызывает стартовую команду и не содержит логики. Мост остаётся, пока движок не даст authoring-объявление стартовой команды ([GAP-015](../Status/EngineGaps.md#gap-015-старт-новой-игры-из-authoring)).
- Общие механизмы, которых не хватает, относятся к `textsystem` и `core` и записываются в [Engine Gaps](../Status/EngineGaps.md); обход через `game.*` или сырое `game.state` запрещён.
- Экраны и UI-поля, которых не хватает, записываются в [Screen Requests](../Status/ScreenRequests.md).
- Тексты и картинки контента заводятся заглушками ID в Definitions, их содержание описывается заявками на ресурсы.
- Пакет пишется с нуля. Текущая заглушка удаляется, когда тесты движка перестанут на неё опираться ([GAP-017](../Status/EngineGaps.md#gap-017-тесты-движка-опираются-на-заглушку-rh)).

## 2. Устройство пакета

### 2.1. Раскладка

```text
GameData/rh/
  package.json5
  definitions/        <kind>[_<группа>].json5, без подкаталогов
  schemas/            schemas собственных kinds и расширения kinds других пакетов
  localization/
  scripts/
    manifest.lua
    runtime/start_bridge.lua     мост старта новой игры (GAP-015)
    authoring/
      model/          набор характеристик, формулы, поля и методы сущностей
      rules/          механики: Services, их Commands и Events
      modes/          оболочки временных режимов
      content/        поведение конкретного контента
```

Движок читает только верхний уровень `definitions/`, поэтому Definitions одного kind группируются префиксом имени файла (`locations_city.json5`), а не подкаталогами. Каждый authoring-файл объявляется в `scripts/manifest.lua`.

### 2.2. Слои

| Слой | Каталог | Содержит | Обращается к |
|---|---|---|---|
| Данные | `definitions/`, `schemas/` | Definitions и schemas `rh`, расширения Definitions других пакетов | к коду — только через договорные имена: тип условия или эффекта, Service фазы |
| Модель | `authoring/model/` | набор характеристик, формулы, поля и методы `Actor`, `Item`, `Location`, `World` | только к модели |
| Механики | `authoring/rules/` | условия, эффекты, взаимодействия, переходы, ход, роли, генерация NPC, реакции, меню, чистые ядра режимов | к модели |
| Режимы | `authoring/modes/` | оболочки режимов: `start`, `view`, команды режима | к механикам и модели |
| Контент | `authoring/content/` | уникальное поведение конкретной локации, NPC, квеста | ко всем слоям |

Нижний слой не обращается к верхнему. Модель, механики и режимы не содержат ID конкретного контента. Появление контентного скрипта — сигнал, что не хватает механики, типа условия или эффекта.

### 2.3. Связи между файлами

Authoring-файлы не вызывают `require` друг друга. Связи между файлами:

| Связь | Назначение | Правило |
|---|---|---|
| Методы `Actor`, `Item`, `Location` | операции одной сущности над своим состоянием | без проверок правил игры и без других сущностей; из механик используют только формулы |
| Services `rh:service.<имя>` | механика: правила, формулы, несколько сущностей | без состояния; имя — один сегмент; вне своего файла — по полному ID (`services["rh:service.interactions"]`), короткий key виден только в файле объявления |
| Commands | вход из UI и отложенные реакции | тонкие: аргументы → `check` → `fail` → `apply` |
| Events | факты после выполнения команды | подписчик только ставит команду в очередь (`:later`) |

- Command, связка Semantic Action с ней и публикуемые Events объявляются в файле механики, которой принадлежат.
- Методы prototype — общее пространство имён всех пакетов. `rh` не переобъявляет методы `textsystem` (`is_player`, `is_npc`, `require_location`, `move_to`, `travel`, `Location:is_connected`, `Location:require_connected`): конфликт объявлений отклоняется при загрузке.

### 2.4. Проверка отдельно от записи

Механика, которая меняет состояние, — Service с двумя методами:

- `check(ctx)` → `nil` или причина `{ key, params }`; только чтение;
- `apply(ctx)` — запись; вызывается только после успешного `check`.

```lua
commands.perform = function(args)
    local ctx = services.interactions.context(args)
    local reason = services.interactions.check(ctx)
    if reason then
        fail(reason.key, reason.params)
    end
    services.interactions.apply(ctx)
end
```

Одна причина даёт и typed refusal `rh:error.<key>`, и подсказку у неактивного пункта меню: ошибке соответствует текст `rh:text.error.<key>` ([Authoring Surface](../Architecture/AuthoringSurfaceContract.md#execution-scope-and-attribution)). Так правило «все проверки до первой записи» держится формой кода.

**Термин «взаимодействие».** [Glossary](../Architecture/GlossaryAndNaming.md#запрещённые-неоднозначности) запрещает «gameplay action»: изменение мира — Command, а kind `action` — Semantic Action ([Semantic Input](../UI/SemanticInput.md)). То, что игрок выбирает в меню, в `rh` — взаимодействие: Definition kind `interaction` (стоимость, условия, эффекты), которое исполняет Command `rh:command.perform`.

## 3. Инварианты

- Правило получает персонажа параметром; набор характеристик у игрока и NPC одинаковый.
- У NPC нет собственных ходов: NPC действует только в ответ на взаимодействие игрока (в том числе по его приказу) или в фазе конца хода.
- Фаза конца хода обращается к конкретным NPC через роли и списки участников; перебор всех NPC мира запрещён.
- В canonical state хранится только то, что нельзя вычислить. Итоговые характеристики, доступность взаимодействия и причина недоступности не сохраняются.
- Механика проверяет всё в `check` до первой записи в `apply`: `fail()` после записи запрещён ([Authoring Surface](../Architecture/AuthoringSurfaceContract.md#execution-scope-and-attribution)).
- Взаимодействие, переход, ветка диалога, реакция, фаза и сценарий старта описываются данными; Lua нужен для нового типа условия или эффекта, новой механики или уникального поведения контента.
- Данные `rh` хранятся в собственных kinds; расширения kinds других пакетов минимальны.
- Бой, торговля и диалог — временные режимы; их промежуточное состояние не сохраняется ([Temporary Game Modes](../Proposals/TemporaryGameModesProposal.md)).
- Модель, механики и режимы не содержат ID конкретного контента.

## 4. Модель данных

### 4.1. Kinds

| Kind | Schema | Содержит |
|---|---|---|
| `interaction` | `rh` | текст, стоимость в выносливости, условия, эффекты, источник меню (игрок, спутник, локация, переход) |
| `location` | `textsystem` + расширение `rh` | заголовок, экраны, переходы; в расширении — стоимость входа, взаимодействия локации, варианты описания и картинки с условиями |
| `actor` | `core` + расширение `rh` | имя, портрет, теги; у уникального NPC — значения базовых характеристик; у шаблона типового NPC — параметры генерации |
| `item` | `rh` | название, цена, иконка, категория и свойства для оценки |
| `shop` | `rh` | торговец, ассортимент, тексты |
| `dialogue` | `rh` | граф: шаги, реплики, картинки, варианты ответа с условиями и эффектами |
| `appraisal` | `rh` | оценка при продаже: принимаемые предметы, параметры формулы, исходы с условиями |
| `reaction` | `rh` | событие, условия, шанс, запускаемое взаимодействие |
| `dance` | `rh` | параметры сцены и движения |
| `turn_phase` | `rh` | `order`, Service фазы |
| `quest` | `rh` | стадии и условия переходов |
| `flag` | `rh` | объявление флага |
| `scenario` | `rh` | стартовое состояние: игрок, уникальные NPC и их размещение, генерация типовых NPC, предметы, роли, флаги |
| `config` | `rh` | длительность хода (в `rh` — 6 часов), параметры формул |

Новый kind пакета добавляется вместе со schema ([Stable ID Specification](../Architecture/StableIDSpecification.md#kind-registry)). Поля Definitions собственных kinds читаются через `def.<kind>(name)`; поля расширений kinds других пакетов — после [GAP-012](../Status/EngineGaps.md#gap-012-поля-definition-из-блока-расширения-пакета).

### 4.2. Что где хранится

| Сущность | Definition (статично) | Canonical state (сохраняется) | Вычисляется |
|---|---|---|---|
| Персонаж | имя, портрет, теги; базовые характеристики уникального NPC; параметры генерации шаблона | базовые характеристики сгенерированного или изменённого персонажа, HP, выносливость, оставшиеся ходы без сознания, локация, флаги, поля-роли, имя экземпляра | итоговые характеристики, максимум выносливости |
| Локация | заголовок, варианты описания и картинки с условиями, стоимость входа в выносливости, взаимодействия, объекты взаимодействия, переопределение меню | изменения состояния локации (по мере появления) | выбранный вариант описания и картинки |
| Взаимодействие | `rh:interaction.*`: текст, стоимость, условия, эффекты, источник | — | доступность и причина недоступности |
| Фаза конца хода | `rh:turn_phase.<name>`: `order`, Service фазы | — | — |
| Процесс | рецепт: требуемый объём, затраты, результат | экземпляр процесса с прогрессом | — |
| Квест | стадии и условия переходов | стадия и флаги — runtime-state поля Definition квеста | — |
| Конфигурация | `rh:config.*`: длительность хода, параметры формул | номер хода и время мира в `world` | время суток |

Стоимость перехода задаётся одна на локацию: переход в локацию стоит её стоимости входа.

### 4.3. Характеристики

Набор характеристик объявлен в коде модели: одна таблица имён порождает поля `Actor`. Значения конкретного персонажа — из данных: у уникального NPC — из его Definition, у типового — генерируются из шаблона при создании и хранятся в экземпляре. Базовое значение — значение экземпляра, если оно задано, иначе значение Definition.

### 4.4. Соглашения об ID

| Что | Форма | Пример |
|---|---|---|
| Definition | `rh:<kind>.<группа>.<имя>` | `rh:location.city.market`, `rh:interaction.tavern.rest` |
| Текст поля Definition | `rh:text.<kind>.<группа>.<имя>.<поле>` | `rh:text.interaction.tavern.rest.title` |
| Причина отказа | error `rh:error.<механика>.<причина>`, текст `rh:text.error.<механика>.<причина>` | `rh:error.interaction.no_stamina` |
| Ресурс | `rh:resource.<kind>.<группа>.<имя>.<назначение>` | `rh:resource.location.city.market.background` |
| Service | `rh:service.<механика>`; типы условий и эффектов — `rh:service.condition_<тип>`, `rh:service.effect_<тип>` | `rh:service.condition_has_item` |
| Имя экземпляра | `<группа>.<имя>` внутри пакета-создателя | `dog.rex` |

## 5. Механики

### 5.1. Характеристики и формулы

База — значение персонажа ([4.3](#43-характеристики)); модификаторы — от предметов, эффектов и ролей; итог вычисляется при чтении. Формулы (максимум и восстановление выносливости, выход из бессознательного состояния, урон, оценка) — именованные функции модели; параметры — в Definition `config`.

### 5.2. Словари условий и эффектов

Тип условия — Service `rh:service.condition_<type>`:

```lua
services.condition_has_item = {
    check = function(ctx, params) ... end,   -- true | false
    reason = function(ctx, params) ... end,  -- причина недоступности { key, params }
}
```

Тип эффекта — Service `rh:service.effect_<type>` с методом `apply(ctx, params)`; эффект с собственным предусловием добавляет `check(ctx, params)` → причина. `ctx` — `{ actor, location, target }`.

В данных условия и эффекты задаются коротким типом:

```json5
requires: [
  { type: "stamina_at_least", amount: 3 },
  { type: "has_item", item: "rh:item.tool.mortar" },
],
effects: [
  { type: "give_item", item: "rh:item.potion.healing" },
  { type: "set_flag", flag: "rh:flag.met_alchemist", value: true },
],
```

Список условий или эффектов в schema — `union` по полю `type` ([Definition Envelope and Schema Rules](../Architecture/DefinitionEnvelopeAndSchemaRules.md)): параметры каждого типа проверяются при сборке repository, а не в Lua. Один словарь используют взаимодействия, переходы, фазы конца хода, квесты, диалоги и реакции. Причина недоступности формируется типом условия, а не пишется для каждого взаимодействия.

### 5.3. Конвейер взаимодействия

Service `rh:service.interactions`, `ctx` — исполнитель, взаимодействие, цель:

- `check(ctx)` → `nil` либо причина: `performer:can_act()` → условия → выносливость → предусловия эффектов;
- `apply(ctx)` → списать выносливость → эффекты по порядку → `rh:event.interaction_completed`.

Все кнопки взаимодействий связаны с одной Semantic Action `rh:action.interact` → Command `rh:command.perform` с аргументами `{ interaction, target, performer? }`. Новое взаимодействие — только Definition, без Lua. Приказ спутнику — та же Command с `performer` = спутник: тратится его выносливость. Меню получает доступность и причину из `check`.

### 5.4. Сознание

`actor:can_act()` — первый шаг конвейера. Потеря сознания блокирует все взаимодействия, кроме завершения хода; то же правило действует для NPC: бессознательный NPC не исполняет приказы и не участвует в фазах конца хода. Выход из бессознательного состояния вычисляется формулой в фазе конца хода и может занять больше одного хода.

### 5.5. Перемещение

Переход проходит тот же конвейер с эффектом перемещения; источник «переходы» меню строится из связей локации. Стоимость — стоимость входа целевой локации; условия перехода — из словаря условий. После перехода публикуется `rh:event.travel_completed`.

### 5.6. Ход

Command `rh:command.turn.end` доступна всегда, в том числе без выносливости и без сознания. Одна транзакция:

1. Фазы — Definitions kind `turn_phase` — исполняются по возрастанию `order` (при равенстве — по Stable ID). Мод добавляет фазу новой Definition и отключает её переопределением. Требует [GAP-010](../Status/EngineGaps.md#gap-010-перебор-definitions-по-kind-в-authoring).
2. Фаза — Service `run(ctx)`; возвращает список записей отчёта `{ resource_id?, text }` (возможно, пустой).
3. Время мира сдвигается на длительность хода; публикуется `rh:event.turn_ended`.
4. Если записи есть, запускается режим отчёта `rh:mode.turn_report`: отдельный экран в основном слое, записи по одной ([SR-002](../Status/ScreenRequests.md#sr-002-отчёт-о-конце-хода)).

Рекомендуемый шаг номеров `order` — 100, чтобы моды могли вставлять фазы между существующими.

### 5.7. Модели NPC

Модель NPC — фаза конца хода. Её участники заданы ролями (`player.dog`) или списком участников; участие меняется той же командой, что и флаг («отправить собаку на охоту»). Модель исполняет взаимодействие участника с его характеристиками и выносливостью и возвращает записи отчёта.

### 5.8. Роли

Роль — поле-ссылка на конкретный экземпляр (`Actor.dog = field.ref_instance("actor", { nullable = true })`) на персонаже или мире. Общие обработчики работают с ролью, а не с конкретным ID. Роли-списки, ограничение кандидата и контроль висячих ссылок требуют [GAP-008](../Status/EngineGaps.md#gap-008-поля-коллекции-и-целостность-ссылок-на-экземпляры).

### 5.9. Персонажи: уникальные и типовые

- **Уникальный NPC** — Definition `actor` и ровно один экземпляр, созданный сценарием старта; код обращается к нему по Definition: `actor("npc.merchant")`.
- **Типовой NPC** — экземпляр, сгенерированный из шаблона: Definition `actor` с параметрами генерации (диапазоны характеристик, наборы имён и портретов). Генерация — Service `rh:service.npc_generation`: на старте по сценарию и во время игры эффектом `spawn_npc`. Броски идут из потока `rh:random_stream.generation`, результат хранится в экземпляре.
- **Обращение к конкретному экземпляру из кода:**
  - через роль — когда правило работает с тем, кто сейчас занимает роль (`player.dog`);
  - через имя экземпляра — постоянную ссылку, заданную при создании в сценарии или эффекте генерации (`{ template: "rh:actor.dog", instance_name: "dog.rex" }`), когда контент или квест заранее ссылается на конкретного персонажа. Требует [GAP-018](../Status/EngineGaps.md#gap-018-имя-экземпляра-и-удаление-персонажа-из-authoring).
- Ненужный сгенерированный NPC удаляется ([GAP-018](../Status/EngineGaps.md#gap-018-имя-экземпляра-и-удаление-персонажа-из-authoring)); ссылки на него обрабатываются по политике [GAP-008](../Status/EngineGaps.md#gap-008-поля-коллекции-и-целостность-ссылок-на-экземпляры).

### 5.10. Процессы

Процесс — рецепт (Definition) и экземпляр с прогрессом. Вклад — взаимодействие «работать над процессом» игрока или спутника по приказу: тратятся ресурсы исполнителя (выносливость, материалы), прогресс растёт по формуле от характеристик. Когда вложено достаточно, результат выдаётся в той же команде. Конец хода процессы не продвигает. Экземпляр процесса требует [GAP-004](../Status/EngineGaps.md#gap-004-операции-с-runtime-instance-не-actor-kind).

### 5.11. Квесты

Квест — уникальная Definition; стадия и флаги — runtime-state поля этой Definition, поэтому экземпляры не нужны. Объявление таких полей через prototype `Quest` требует [GAP-014](../Status/EngineGaps.md#gap-014-поля-и-методы-prototype-на-definitions). Переходы между стадиями описываются словарём условий. Продвижение — по Events (подписчик ставит в очередь команду проверки квеста) и в фазе конца хода. Сюжет — квесты и флаги мира; песочница — процессы и модели NPC.

### 5.12. Временные режимы

Торговля, продажа, диалог, танец, бой и отчёт о ходе — режимы из [Temporary Game Modes](../Proposals/TemporaryGameModesProposal.md). Режим делится на две части:

- **чистое ядро** в `rules/` — функции без состояния: оценка при продаже, расчёт танца, навигация по графу диалога, бой. Ядро получает значения участников и возвращает результат; canonical state не читает и не пишет;
- **оболочка** в `modes/` — `start`, `view`, команды режима и его временное состояние.

Бой не сдвигает время мира и по завершении возвращает изменения одной командой.

### 5.13. Events и реакции

Словарь фактов `rh`: `rh:event.interaction_completed`, `rh:event.travel_completed`, `rh:event.actor_lost_consciousness`, `rh:event.actor_regained_consciousness`, `rh:event.turn_ended`, `rh:event.process_completed`, `rh:event.quest_stage_changed`. На них строятся квесты, реакции и отчёт; моды используют их как точки расширения.

Реакция — Definition `reaction`: событие, условия, шанс, запускаемое взаимодействие. Подписчик `rh` на событие только ставит в очередь команду реакции, а она проверяет условия, бросает шанс и запускает взаимодействие: подписчик работает при закрытом mutation window ([Commands and Events](../Architecture/CommandsAndEvents.md)). Перебор реакций события требует [GAP-010](../Status/EngineGaps.md#gap-010-перебор-definitions-по-kind-в-authoring).

### 5.14. Случайность

Отдельный поток `game.random` на подсистему: `rh:random_stream.combat`, `rh:random_stream.loot`, `rh:random_stream.npc_models`, `rh:random_stream.generation`, `rh:random_stream.reactions`. Изменение одной подсистемы не сдвигает броски другой.

### 5.15. Старт новой игры

Мост старта вызывает `rh:command.game.start`. Команда читает Definition `scenario` и создаёт игрока, уникальных NPC и их размещение, генерирует типовых NPC, выдаёт предметы, назначает роли и флаги. Состав стартового мира — данные.

## 6. Основные сценарии

```text
Кнопка взаимодействия → rh:action.interact → rh:command.perform(interaction, target, performer?)
  interactions.check: performer:can_act()? → условия? → выносливость? → иначе fail(причина)
  interactions.apply: списать выносливость → эффекты → rh:event.interaction_completed
  → presentation перестраивает экран локации

Кнопка «Завершить ход» → rh:command.turn.end
  для каждой turn_phase по order: run(ctx) → записи отчёта
    (сознание, эффекты, модели NPC, квесты, восстановление выносливости)
  время мира += длительность хода → rh:event.turn_ended
  записи есть → режим rh:mode.turn_report

Переход → rh:event.travel_completed → подписчик ставит команду реакции
  команда: реакции события → условия? → шанс? → запуск взаимодействия
```

## 7. Экран

- Основной экран — `textsystem:screen.location`. Меню собирается из четырёх источников: взаимодействия игрока, спутников, локации и её объектов, переходы; локация может переопределить сборку ([GAP-006](../Status/EngineGaps.md#gap-006-сборка-меню-локации-из-источников-действий)).
- Недоступное взаимодействие показывается неактивным с причиной при наведении ([SR-001](../Status/ScreenRequests.md#sr-001-неактивный-пункт-меню-с-подсказкой-о-причине)); до реализации — скрывается.
- Значения панелей статуса задаёт `rh` ([GAP-007](../Status/EngineGaps.md#gap-007-данные-панелей-статуса-из-пакета-игры)).
- Отчёт о ходе — отдельный экран ([SR-002](../Status/ScreenRequests.md#sr-002-отчёт-о-конце-хода)).

## 8. Расширяемость и эволюция

- Сначала данные: новая локация, NPC, взаимодействие, рецепт, реакция или фаза добавляются без кода.
- Точки расширения для модов: семейства Services `condition_*` и `effect_*`, Definitions `turn_phase` и `reaction`, Events.
- Definition переопределяется только целиком ([GameDataRepository Contract](../Architecture/GameDataRepositoryContract.md)); поэтому расширяемые наборы — отдельные Definitions, а не списки внутри одной.
- `union` в schema закрыт: тип условия или эффекта из мода требует расширения schema `rh`. Механизм выбирается, когда появится первый такой мод.
- Механизмы проектируются без перебора всех NPC, хотя при сотнях NPC перебор допустим.

## 9. Проверка

Число тестов растёт с числом механик, а не с объёмом контента.

| Уровень | Что проверяет | Объём |
|---|---|---|
| Schemas данных | каждую Definition при сборке repository: обязательные поля, типы, параметры условий и эффектов, ссылки на локации, тексты, ресурсы | schemas `rh`, без тестов |
| Обходы контента | один spec на точку расширения перебирает весь контент: у каждого взаимодействия существуют Services типов условий и эффектов, стоимость неотрицательна; переходы ведут в существующие локации; каждый `condition_*` имеет `check` и `reason`, каждый `effect_*` — `apply`; каждая `turn_phase` ссылается на существующий Service | около 10 |
| Specs механик | конвейер взаимодействия, сознание, конец хода, роли, генерация, процессы — каждая с отрицательным случаем | 3–5 на механику |
| Specs чистых ядер | оценка, танец, граф диалога, бой — без механизма режимов | 3–5 на ядро |
| Эталонные прогоны | headless-последовательность команд → эталонный state hash ([Regenerate Golden](../Guides/RegenerateGolden.md)) | 3–5 |
| Контентные скрипты | только сложный уникальный Lua | по необходимости |

Перечислитель обходов — repository (все Definitions kind) и registry Services, а не рукописный список. Массовые прогоны боя для баланса — инструмент, а не тест. Место specs пакета требует [GAP-016](../Status/EngineGaps.md#gap-016-место-specs-пакета-игры).
