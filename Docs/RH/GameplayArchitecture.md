# Архитектура геймплея RH

> **Владеет:** слоями пакета `rh`, моделью игровых данных, механиками (характеристики, условия, действия, сознание, перемещение, ход, роли, модели NPC, процессы, квесты), их связями и стратегией проверки.
> **Не владеет:** механизмами движка (`core`, `textsystem`), командами, событиями и состоянием как таковыми — их семантику задают [Commands and Events](../Architecture/CommandsAndEvents.md) и [Canonical State and Save](../Architecture/CanonicalStateAndSave.md).
> **Статус:** `draft` — принятая архитектура до реализации первых механик; становится `normative`, когда механики реализованы и проверены.

## 1. Назначение и границы

`rh` — однопользовательская текстовая RPG: мир из связанных переходами локаций; у каждой локации картинка, описание и меню действий. Игра пошаговая: игрок тратит выносливость на действия, завершает ход, мир реагирует. Целевой масштаб — сотни NPC; в игре есть квесты, сюжет и песочница.

- Весь геймплей пишется в `GameData/rh/` на authoring surface ([Authoring Surface](../Architecture/AuthoringSurfaceContract.md)).
- Общие механизмы, которых не хватает, относятся к `textsystem` и `core` и записываются в [Engine Gaps](../Status/EngineGaps.md); обход через `game.*` или сырое `game.state` запрещён.
- Экраны и UI-поля, которых не хватает, записываются в [Screen Requests](../Status/ScreenRequests.md).
- Тексты и картинки контента заводятся заглушками ID в Definitions, их содержание описывается заявками на ресурсы.

## 2. Слои пакета и связи

| Слой | Где | Содержит | Ограничение |
|---|---|---|---|
| Данные | `definitions/`, `schemas/` | Definitions и schemas `rh`, расширения Definitions других пакетов | — |
| Механики | `scripts/authoring/mechanics/` | Общие правила `rh` | Не содержат ID конкретного контента |
| Контент | `scripts/authoring/content/` | Поведение конкретных локаций, NPC, квестов | Использует механики; появление скрипта — сигнал, что не хватает механики или типа условия |

Authoring-файлы не вызывают `require` друг друга. Связи между файлами:

- методы сущностей (`function Actor:...`) — общие для пакета;
- Services и Commands — по полному Stable ID (`services["rh:service.actions"]`): короткий key виден только в файле, где объявлен; имя Service — один сегмент (`condition_has_item`);
- Events.

**Термин «действие».** [Glossary](../Architecture/GlossaryAndNaming.md#запрещённые-неоднозначности) запрещает «gameplay action»: изменение мира — Command, а kind `action` — Semantic Action ([Semantic Input](../UI/SemanticInput.md)). В этом документе «действие» — Definition Semantic Action с расширением `rh` (стоимость, условия, эффект) и Command, которую она вызывает.

## 3. Инварианты

- Правило получает персонажа параметром; набор характеристик у игрока и NPC одинаковый.
- У NPC нет собственных ходов: NPC действует только в ответ на действие игрока (в том числе по его приказу) или в фазе конца хода.
- Фаза конца хода обращается к конкретным NPC через роли и списки участников; перебор всех NPC мира запрещён.
- В canonical state хранится только то, что нельзя вычислить. Итоговые характеристики, доступность действия и причина недоступности не сохраняются.
- Все проверки действия выполняются до первой записи: `fail()` после записи запрещён ([Authoring Surface](../Architecture/AuthoringSurfaceContract.md#execution-scope-and-attribution)).
- Бой, торговля и диалог — временные режимы; их промежуточное состояние не сохраняется ([Temporary Game Modes](../Proposals/TemporaryGameModesProposal.md)).
- Механики не содержат ID конкретного контента.

## 4. Модель данных

| Сущность | Definition (статично) | Canonical state (сохраняется) | Вычисляется |
|---|---|---|---|
| Персонаж | базовые характеристики, теги, имя, портрет | HP, выносливость, оставшиеся ходы без сознания, локация, флаги, поля-роли | итоговые характеристики, максимум выносливости |
| Локация | заголовок, варианты описания и картинки с условиями, стоимость входа в выносливости, действия, объекты взаимодействия, переопределение меню | изменения состояния локации (по мере появления) | выбранный вариант описания и картинки |
| Действие | Semantic Action + расширение `rh`: текст, стоимость, условия, эффект, источник (игрок, спутник, локация, переход) | — | доступность и причина недоступности |
| Фаза конца хода | `rh:turn_phase.<name>`: `order`, Service фазы | — | — |
| Процесс | рецепт: требуемый объём, затраты, результат | экземпляр процесса с прогрессом | — |
| Квест | стадии и условия переходов | стадия и флаги — runtime-state поля Definition квеста | — |
| Конфигурация хода | длительность хода (в `rh` — 6 часов), параметры формул | номер хода и время мира в `world` | время суток |

Стоимость перехода задаётся одна на локацию: переход в локацию стоит её стоимости входа.

## 5. Механики

### 5.1. Характеристики и формулы

База — в Definition персонажа; модификаторы — от предметов, эффектов и ролей; итог вычисляется при чтении. Формулы (максимум и восстановление выносливости, выход из бессознательного состояния, урон) — именованные функции одного модуля механик; параметры — в данных конфигурации хода.

### 5.2. Словарь условий

Тип условия — Service `rh:service.condition_<type>`:

```lua
services.condition_has_item = {
    check = function(ctx, params) ... end,   -- true | false
    reason = function(ctx, params) ... end,  -- TextSpec причины недоступности
}
```

`ctx` — `{ actor, location, target }`. Условия записываются в данных:

```json5
requires: [
  { type: "stamina_at_least", amount: 3 },
  { type: "has_item", item: "rh:item.tool.mortar" },
]
```

Один словарь используют действия, переходы, фазы конца хода, квесты и диалоги. Новый тип условия, в том числе из мода, — новый Service; поиск по полному ID во время игры поддерживается authoring surface. Причина недоступности формируется типом условия, а не пишется для каждого действия.

### 5.3. Конвейер действия

Service `rh:service.actions`:

- `check(performer, action_id, target)` → доступно либо причина недоступности;
- `perform(performer, action_id, target)` → `performer:can_act()` → условия → выносливость → эффект → Event.

Игрок вызывает конвейер одной Command `rh:command.perform` (`action_id`, `target`, необязательный `performer`). Приказ спутнику — та же Command с `performer` = спутник: тратится его выносливость. Меню получает доступность и причину из `check`.

### 5.4. Сознание

`actor:can_act()` — первый шаг конвейера. Потеря сознания блокирует все действия, кроме завершения хода; то же правило действует для NPC: бессознательный NPC не исполняет приказы и не участвует в фазах конца хода. Выход из бессознательного состояния вычисляется формулой в фазе конца хода и может занять больше одного хода.

### 5.5. Перемещение

Переход — действие с эффектом перемещения; источник «переходы» меню строится из связей локации. Стоимость — стоимость входа целевой локации; условия перехода — из словаря условий.

### 5.6. Ход

Command `rh:command.turn.end` доступна всегда, в том числе без выносливости и без сознания. Одна транзакция:

1. Фазы — Definitions kind `turn_phase` — исполняются по возрастанию `order` (при равенстве — по Stable ID). Мод добавляет фазу новой Definition и отключает её переопределением. Требует [GAP-010](../Status/EngineGaps.md#gap-010-перебор-definitions-по-kind-в-authoring).
2. Фаза — Service `run(ctx)`; возвращает список записей отчёта `{ resource_id?, text }` (возможно, пустой).
3. Время мира сдвигается на длительность хода; публикуется `rh:event.turn_ended`.
4. Если записи есть, запускается режим отчёта `rh:mode.turn_report`: отдельный экран в основном слое, записи по одной ([SR-002](../Status/ScreenRequests.md#sr-002-отчёт-о-конце-хода)).

Рекомендуемый шаг номеров `order` — 100, чтобы моды могли вставлять фазы между существующими.

### 5.7. Модели NPC

Модель NPC — фаза конца хода. Её участники заданы ролями (`player.dog`) или списком участников; участие меняется той же командой, что и флаг («отправить собаку на охоту»). Модель исполняет действие участника с его характеристиками и выносливостью и возвращает записи отчёта.

### 5.8. Роли

Роль — поле-ссылка на конкретный экземпляр (`Actor.dog = field.ref_instance("actor", { nullable = true })`) на персонаже или мире. Общие обработчики работают с ролью, а не с конкретным ID. Роли-списки, ограничение кандидата и контроль висячих ссылок требуют [GAP-008](../Status/EngineGaps.md#gap-008-поля-коллекции-и-целостность-ссылок-на-экземпляры).

### 5.9. Процессы

Процесс — рецепт (Definition) и экземпляр с прогрессом. Вклад — действие «работать над процессом» игрока или спутника по приказу: тратятся ресурсы исполнителя (выносливость, материалы), прогресс растёт по формуле от характеристик. Когда вложено достаточно, результат выдаётся в той же команде. Конец хода процессы не продвигает. Экземпляр процесса требует [GAP-004](../Status/EngineGaps.md#gap-004-операции-с-runtime-instance-не-actor-kind).

### 5.10. Квесты

Квест — уникальная Definition; стадия и флаги — runtime-state поля этой Definition, поэтому экземпляры не нужны. Переходы между стадиями описываются словарём условий. Продвижение — по Events (подписчик ставит в очередь команду проверки квеста) и в фазе конца хода. Сюжет — квесты и флаги мира; песочница — процессы и модели NPC.

### 5.11. Временные режимы

Торговля, диалог и бой — режимы из [Temporary Game Modes](../Proposals/TemporaryGameModesProposal.md). Бой — чистая функция: получает значения участников, не сдвигает время мира и по завершении возвращает изменения одной командой. Отчёт о ходе — тоже режим.

### 5.12. Events

Словарь фактов `rh`: `rh:event.action_completed`, `rh:event.actor_lost_consciousness`, `rh:event.actor_regained_consciousness`, `rh:event.turn_ended`, `rh:event.process_completed`, `rh:event.quest_stage_changed`. На них строятся квесты и отчёт; моды используют их как точки расширения.

### 5.13. Случайность

Отдельный поток `game.random` на подсистему: `rh:random_stream.combat`, `rh:random_stream.loot`, `rh:random_stream.npc_models`. Изменение одной подсистемы не сдвигает броски другой.

## 6. Основные сценарии

```text
Кнопка действия → rh:command.perform(action_id, target, performer?)
  performer:can_act()? → условия? → выносливость? → иначе fail(причина)
  списать выносливость → эффект → rh:event.action_completed
  → presentation перестраивает экран локации

Кнопка «Завершить ход» → rh:command.turn.end
  для каждой turn_phase по order: run(ctx) → записи отчёта
    (сознание, эффекты, модели NPC, квесты, восстановление выносливости)
  время мира += длительность хода → rh:event.turn_ended
  записи есть → режим rh:mode.turn_report
```

## 7. Экран

- Основной экран — `textsystem:screen.location`. Меню собирается из четырёх источников: игрок, спутники, локация и её объекты, переходы; локация может переопределить сборку ([GAP-006](../Status/EngineGaps.md#gap-006-сборка-меню-локации-из-источников-действий)).
- Недоступное действие показывается неактивным с причиной при наведении ([SR-001](../Status/ScreenRequests.md#sr-001-неактивный-пункт-меню-с-подсказкой-о-причине)); до реализации — скрывается.
- Значения панелей статуса задаёт `rh` ([GAP-007](../Status/EngineGaps.md#gap-007-данные-панелей-статуса-из-пакета-игры)).
- Отчёт о ходе — отдельный экран ([SR-002](../Status/ScreenRequests.md#sr-002-отчёт-о-конце-хода)).

## 8. Расширяемость и эволюция

- Сначала данные: новая локация, NPC, действие, рецепт или фаза добавляются без кода.
- Точки расширения для модов: Services с договорными именами (`condition_*`), Definitions `turn_phase`, Events.
- Definition переопределяется только целиком ([GameDataRepository Contract](../Architecture/GameDataRepositoryContract.md)); поэтому расширяемые наборы — отдельные Definitions, а не списки внутри одной.
- Механизмы проектируются без перебора всех NPC, хотя при сотнях NPC перебор допустим.

## 9. Проверка

Число тестов растёт с числом механик, а не с объёмом контента.

| Уровень | Что проверяет | Объём |
|---|---|---|
| Schemas данных | каждую Definition при сборке repository: обязательные поля, типы, ссылки на локации, тексты, ресурсы | schemas `rh`, без тестов |
| Обходы контента | один spec на точку расширения перебирает весь контент: у каждого действия существуют типы условий и Command-эффект, стоимость неотрицательна; переходы ведут в существующие локации; каждый `condition_*` имеет `check` и `reason`; каждая `turn_phase` ссылается на существующий Service | около 10 |
| Specs механик | конвейер действия, сознание, конец хода, роли, процессы, бой — каждая с отрицательным случаем | 3–5 на механику |
| Эталонные прогоны | headless-последовательность команд → эталонный state hash ([Regenerate Golden](../Guides/RegenerateGolden.md)) | 3–5 |
| Контентные скрипты | только сложный уникальный Lua | по необходимости |

Перечислитель обходов — repository (все Definitions kind) и registry Services, а не рукописный список. Массовые прогоны боя для баланса — инструмент, а не тест.
