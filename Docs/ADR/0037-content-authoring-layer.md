# ADR-0037: Content Authoring Layer and Atomic Storage Operations

> **Решение:** Authoritative-реализация авторинга контента выносится в переносимую C++ библиотеку `GV2ContentAuthoring`, операции записи становятся строго атомарными, а запись защищается от внешних изменений файла через оптимистичную блокировку по штампу состояния.
> **Нормативный текст:** [DefinitionEnvelopeAndSchemaRules](../Architecture/DefinitionEnvelopeAndSchemaRules.md), [BuildAndTooling](../Architecture/BuildAndTooling.md).

## 1. Контекст и проблема

Для интеграции встроенного редактора контента в Unreal Editor и развития инструментов авторинга (`gv2-content`) необходим надёжный backend для мутаций канонических JSON5-определений:

1. **Разделение логики и интерфейсов:** Ранее `Json5AstRewriter` и обработчики команд создания, модификации, удаления и переименования определений находились внутри исполняемого файла `gv2-content`. Использование CLI в роли подпроцесса для редактора создавало бы лишнюю IPC-границу, проблемы с производительностью, платформенными путями и обработкой ошибок.
2. **Атомарность операций:** Ранее каждая модификация поля или шага дублирования выполнялась как отдельная независимая перезапись файла. Сбой на промежуточном шаге оставлял файл на диске в частично изменённом и потенциально невалидном состоянии.
3. **Обнаружение внешних изменений:** Файлы `GameData/` находятся под управлением системы контроля версий и могут быть изменены внешним процессом (`git pull`, ручная правка в IDE). Без контроля версии файла существовал риск тихой перезаписи актуальных данных устаревшим состоянием из редактора.

## 2. Решение

### 2.1. Переносимая библиотека `GV2ContentAuthoring`

* Логика мутаций определений выносится в библиотеку `GV2ContentAuthoring` (`Source/GV2ContentAuthoring/`), компилируемую как через CMake (`gv2_content_authoring`), так и через Unreal Build Tool (UBT).
* Библиотека не зависит от Unreal Engine и может использоваться в CLI-инструментах, headless-окружении, автоматических тестах и редакторских плагинах.
* CLI `gv2-content` и `GV2Editor` становятся тонкими клиентами (frontend-ами) поверх одной и той же библиотеки авторинга.

### 2.2. Атомарность операций записи

* Пакетное сохранение полей (`BatchSetFields`), создание (`CreateDefinition`), удаление (`DeleteDefinition`), переименование (`RenameDefinition`) и дублирование (`DuplicateDefinition`) реализуются как одиночные атомарные транзакционные операции.
* Операция следует принципу:
  1. Выполнить все AST-мутации в памяти над строковым представлением файла.
  2. Выполнить полную in-memory валидацию полученного JSON5 против схемы и контрактов определений.
  3. При успехе атомарно заменить файл на диске (запись во временный файл + атомарный `rename`).
* При ошибке на любом шаге файл на диске остаётся байт-в-байт нетронутым.

### 2.3. Оптимистичная блокировка по штампу файла (`FFileStateStamp`)

* При чтении файла или определения формируется непрозрачный штамп состояния `FFileStateStamp` (хэш содержимого файла).
* Все операции записи принимают опциональный `ExpectedStamp`.
* Если `ExpectedStamp` передан, сервис перед модификацией сверяет его с текущим состоянием файла на диске. При расхождении операция отклоняется с типизированной ошибкой `stale_file_state`, предотвращая потерю внешних правок.

## 3. Отвергнутые альтернативы

* **CLI как подпроцесс для редактора:** отвергнуто, так как создает искусственный межпроцессный барьер для кода, который должен быть общей библиотекой в одном адресном пространстве.
* **Серия независимых `set`-записей при сохранении формы:** отвергнуто из-за отсутствия гарантий транзакционности при сбоях в середине набора полей.
* **Оркестрация дублирования определения на стороне UI:** отвергнуто, так как оставляет полускопированные данные при ошибках.
* **Вторая параллельная модель контента в памяти редактора:** отвергнуто для предотвращения семантического расхождения с каноническим JSON5.

## 4. Последствия

* Единая, детерминированная реализация мутаций контента для всех инструментов проекта.
* Безопасное сохранение сложных форм в редакторе с гарантией сохранения целостности файлов при любых ошибках.
* Защита от конфликтов при параллельной работе с Git и внешними редакторами.
