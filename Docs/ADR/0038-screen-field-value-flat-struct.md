# ADR-0038: Screen Field Value Stays a Flat Struct

> **Решение:** `FGV2ScreenFieldValue` остаётся плоской структурой со всеми payload'ами полей одновременно; переход на размеченное объединение отклонён на этом этапе.
> **Условие пересмотра:** добавление следующего (14-го) payload — рефакторинг делается до, а не после него.

## Context

`FGV2ScreenFieldValue` хранит по одному `UPROPERTY` полю на каждый вид значения поля экрана (`InteractiveRichTextValue`, `ButtonListValue`, `CheckboxValue`, ..., `TabContainerValue`) и использует всегда ровно одно. На момент внешнего ревью их было пять с рекомендацией «пока приемлемо, но запланировать ADR при 8–10 типах». Сегодня их 13 ([EXT-AF-03](../Status/Archive/PlanAudit2026-08.md)); порог пройден без решения.

Каждый новый тип виджета/composite поля добавляет ещё один payload. Несколько payload'ов содержат `TArray`/вложенные структуры, поэтому размер экземпляра растёт не линейно по числу полей.

## Decision

Оставить плоскую структуру. Переход на размеченное объединение (`FInstancedStruct` из `StructUtils` — наиболее вероятный кандидат в UE, поскольку сохраняет reflection и BP-редактируемость активного payload'а через runtime-полиморфизм) не выполняется в рамках этого плана и решения.

Причины остаться:

1. `FGV2ScreenFieldValue` — internal view-model bridge type между Lua-декодированием и виджетами, не design-time BP asset: `BlueprintReadWrite` на нём используется для программного построения значений в C++/тестах, а не для ручного редактирования дизайнером в BP Editor. Экономия памяти на неиспользуемых payload'ах реальна, но не является измеренной проблемой производительности — ни один находка ревью не указывает на конкретный memory/perf regression, только на архитектурную неопрятность.
2. Рефакторинг в `FInstancedStruct` меняет форму типа во всех 15+ адаптерах (`GV2ScreenFieldAdapterRegistry.cpp`), во всех виджетах (`ApplyScreenField_Implementation`/`CaptureScreenField_Implementation`) и в тестовом корпусе одновременно — это работа масштаба отдельного плана, а не задачи внутри `SceneAndVerificationCorrection`, где сама структура не является предметом остальных 11 задач.
3. Порог «8–10 типов» был эвристикой на момент, когда пять schema-полей уже покрывали весь baseline UI. Рост до 13 отражает добавление composite location-виджетов (`LocationTopBar`, `LocationPlayerStatus`, `LocationScene`), которые появились предсказуемо в рамках `LocationScreen`/`UiFoundationHardening` — то есть рост оказался line item по фиче, а не признаком забытого рефакторинга.

## Consequences

`FGV2ScreenFieldValue` продолжает расти на один payload с каждым новым типом поля. Размер экземпляра и стоимость копирования увеличиваются с каждым новым composite виджетом (сейчас — самый крупный вклад: `TArray`-содержащие `LocationPlayerStatusValue`, `TabContainerValue` через `TSharedPtr`).

Новое **наблюдаемое** условие пересмотра: добавление 14-го payload'а. К этому моменту рефакторинг в `FInstancedStruct` должен быть запланирован **до** добавления нового поля, а не после — чтобы 13-й порог не повторился ещё раз без реакции.

## Rejected alternatives

- **Рефакторинг сейчас в рамках SVC-11.** Отклонён: задача плана — принять решение, а не провести миграцию через всю кодовую базу; см. Decision п.2.
- **Ручной `TVariant<...>` вместо `FInstancedStruct`.** Отклонён предварительно как менее подходящий кандидат: `TVariant` не даёт `UPROPERTY`-reflection и BlueprintReadWrite активного payload'а, которые сейчас используются программным кодом для построения/чтения значений; `FInstancedStruct` сохраняет reflection ценой runtime-полиморфизма. Финальный выбор конкретного механизма откладывается до момента реализации по итогам следующего ADR.
- **Полное игнорирование порога без нового условия пересмотра.** Отклонён: это ровно то, что уже произошло однажды (порог 8–10 пройден молча) и что этот ADR обязан не повторить.
