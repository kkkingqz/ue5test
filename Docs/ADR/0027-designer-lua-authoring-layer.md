# ADR-0027: Designer Lua Authoring Layer

> **Решение:** ввести designer-facing слой в Lua поверх фасада `game`, отложить регистрацию команд и событий до фазы `register`, связать семантику `fail()` со счётчиком `write_revision` окна мутации, изолировать сырое состояние и выделить единый примитив переносимого значения.

## 1. Контекст и проблема

Рантайм GV2 (`game.commands`, `game.instances`, `game.repository`, Stable ID, DTO конвертов, схемы) спроектирован с упором на строгие границы, неизменяемость снимков, детерминизм и изоляцию. Однако прямое использование низкоуровневых интерфейсов в игровом коде пакетов (например, `rh`) перегружает геймдизайнеров и моддеров техническим бойлерплейтом (выписывание полных Stable ID, ручная сборка DTO запросов, вызовы внутренних реестров).

Требуется предоставить выразительный, лаконичный слой написания геймплея на обычном Lua 5.4, сохранив все архитектурные инварианты GV2 без создания альтернативного пути мутации состояния.

## 2. Решение

### 2.1. Граница слоёв и неизменяемость канонического рантайма
- Designer Lua — это фасад над каноническим API (`game.*`), а не отдельный рантайм.
- Определения сущностей (`definitions`) не создаются из Lua; они заводятся в контенте пакетов (`.json5`) до создания Lua VM и неизменяемы в сессии.
- Programmer API (`game.*`, реестры, валидаторы, декораторы) остаётся в полном объёме для расширений и модов.

### 2.2. Идентичность команд и отложенная регистрация
- Команда идентифицируется ключом в дескрипторе модуля (`commands["shop.buy"]` $\rightarrow$ `<package_id>:command.shop.buy`), а не именем функции. Опубликованный Stable ID не зависит от рефакторинга локальных функций.
- Дескриптор накапливает команды и подписки во время загрузки модуля (`load`), а адаптер регистрирует их на фазе `register`, после чего реестры замораживаются.

### 2.3. Семантика `fail()` и счётчик `write_revision`
- Вызов `fail(code, params)` до первой мутации состояния в теле команды возвращает нормализованный типизированный отказ (`{ ok = false, error = { code, params } }`).
- Вызов `fail()` после хотя бы одной мутации состояния расценивается как ошибка программиста (`AuthoringFailAfterMutation`) и бросает исключение, требуя вынести проверки выше мутаций.
- Монотонный счётчик `write_revision` ведётся в `mutation_window` и увеличивается в `__newindex` guarded-прокси канонического состояния при любой записи.

### 2.4. Три категории свойств в схемах
Схема объявляет для каждого свойства хранилище и политику доступа:
1. **Definition**: чтение из снимка репозитория, запись запрещена (`Cannot modify definition field`).
2. **Plain state**: чтение и прямая запись в каноническое состояние с валидацией по схеме.
3. **Managed state**: чтение из состояния, запись только через зарегистрированную доменную операцию.

### 2.5. Обратное превращение и disposable-обёртки
- Экземпляры акторов представляются одноразовыми (`disposable`) обёртками, разрешаемыми на каждое обращение.
- Ссылки на сущности типизируются в схеме: `ref_definition` возвращает definition-обёртку, `ref_instance` — свежую runtime-обёртку.

### 2.6. Универсальная секция runtime-состояния
- Динамические свойства статических определений хранятся в единой универсальной секции состояния, ключуемой по `definition_id`.
- Значения материализуются по sparse-политике (чтение отсутствующего возвращает default из схемы, запись материализует поле в состоянии).

### 2.7. Изоляция сырого состояния
- Функция `unwrap_state` исключается из публичного экспорта `mutation_window`.
- Ни один геймплейный модуль, доменный метод или сервис не получает прямого доступа к сырой таблице канонического состояния.

### 2.8. Единый примитив переносимого значения
- Создаётся общий модуль ядра `core:module.runtime.portable_value`, обеспечивающий проверку переносимости типов (числа, строки, булевы значения, плотные массивы 1..N, строковые словари, отсутствие метатаблиц, функций, userdata, циклов).
- Примитив используется в событиях (`event_envelope`), аргументах синхронных команд (`command_dispatcher.dispatch`) и отложенной очереди (`command_dispatcher.enqueue`).

### 2.9. Политика совместимости до релиза 1.0
- До версии 1.0 обратная совместимость структуры сохранений и внутренних хэшей скриптов не поддерживается.

## 3. Отвергнутые альтернативы

- **Внешний DSL с кастомным парсером**: отвергнут, так как требует отдельного интерпретатора/отладчика и уступает обычному Lua 5.4.
- **Объявление определений из Lua**: отвергнуто, так как снимок репозитория строится до инициализации Lua VM.
- **Откат состояния при ошибке в теле команды**: отвергнут, так как нарушает прозрачность детерминированного выполнения и маскирует логические дефекты.
- **Автоматический выбор `:run` vs `:later`**: отвергнут, так как скрывает границы окон мутации и создаёт неявный контекст выполнения.

## 4. Последствия

- В `mutation_window.lua` добавляется монотонный счётчик `write_revision` и удаляется экспорт `unwrap_state`.
- Создаётся модуль `portable_value.lua`, исключающий утечку непереносимых объектов через аргументы команд и очередь.
- Подготовлен фундамент для реализации дескрипторов команд, моделей свойств и миграции геймплея пакета `rh`.
