# ADR-0026: Core and Gameplay Ownership

> **Решение:** `core` владеет механизмами, пакет — семантикой; наличие kind в ядре не означает владения его схемой.
> **Нормативный текст:** [Modding](../Architecture/Modding.md), [Stable ID Specification](../Architecture/StableIDSpecification.md).

## Context

После выделения игрового пакета `rh` появился вопрос, которого раньше не было: куда класть **новую** сущность. Правило «конкретная вещь — в пакет, возможность — в ядро» работало для definitions, но не отвечало на вопрос о схемах, командах, событиях и сервисах.

Практический риск — накопление в `core` понятий одной игры: HP, инвентарь, торговля, квесты, бой. Каждое по отдельности выглядит общим, вместе они превращают GV2 в движок ровно под текущую игру.

Действующие формулировки оставляли зазор в трёх местах:

- `StableIDSpecification` перечисляет core kinds (`item`, `actor`, `quest`, `location`, …). Из этого молча следовало, что и схемы этих kind принадлежат ядру — вывод, который нигде не был записан и не был проверен.
- План RhGamePackage зафиксировал «схемы остаются в `core`, схема объявляет, что такое предмет» — решение, принятое до появления критерия ниже. План заархивирован и нормативным не является, но формулировка успела разойтись по документам.
- `Modding` требует «мод не переопределяет основную schema существующего kind», что читается как запрет пакету вообще определять схему для kind, объявленного ядром.

Одновременно `actor_registry.lua` держит `get_gold`/`add_gold` — экономику конкретной игры внутри ядра. Убрать их некуда: точки расширения обёртки не существует.

## Decision

**Критерий владения.** Сущность принадлежит `core` только если она нужна более чем одной игре на GV2 **с тем же смыслом**. Проверочный вопрос: если заменить текущий gameplay package совершенно другой игрой, останется ли сущность необходимой? Нет — она принадлежит пакету.

**Формула.** `core` определяет, *как* исполняется игра; пакет определяет, *что* в ней существует, что означает и что разрешено.

**Kind и schema разделяются.** Наличие Stable ID kind в реестре ядра означает только категорию пространства имён. Оно **не** означает, что ядро владеет схемой этого kind. Схема принадлежит `core` только тогда, когда её структура необходима самому runtime или host boundary; иначе — пакету.

**Пакет может привязать схему к существующему kind.** Разрешается объявить schema binding для kind, объявленного ядром, при условии что ядро само для этого kind схему не привязывает. Конфликт двух bindings для одной пары `(definition_type, schema_version)` остаётся fatal. Правило «мод не переопределяет основную schema существующего kind» относится к перекрытию существующего binding, а не к заполнению пустого.

**`discriminator` актора — framework-требование.** Ядро выбирает обёртку runtime instance по discriminator, поэтому без него не может собрать инстанс. Это единственное поле актора, которое остаётся в схеме ядра; остальные (`base_hp`, `name_text_id` и прочие) — семантика игры и уезжают в пакет.

**Точка расширения обёртки — фабрика-декоратор.** Ядро строит базовую обёртку и удерживает в ней инварианты идентичности (неизменяемость `instance_id`, `definition_id`, `discriminator`, делегирование в состояние инстанса). Пакет регистрирует декоратор, надстраивающий поведение:

```lua
game.instances.actors.register_type("rh:npc", function(base)
    return setmetatable({ add_gold = … }, { __index = base })
end)
```

Форма повторяет `require_base()` из [ADR-0025](0025-lua-module-replacement-and-export-freezing.md): один приём на оба случая расширения.

**Namespace `core` принадлежит framework.** Он используется только для сущностей, смысл которых не зависит от конкретной игры: механизмов, протоколов, framework-ошибок и диагностик. Игра использует собственный namespace.

**Направление зависимостей.** `core` ← feature packages ← gameplay package ← mods. Обратное запрещено: ядро не импортирует игровые Lua-модули, не ссылается на их ID и не предполагает наличия инвентаря, торговли, боя или квестов.

## Consequences

- Появляется ответ на вопрос «куда класть новое», не зависящий от вкуса, и он проверяем: достаточно спросить, требуется ли сущность самому runtime.
- `actor_v1`, `item_v1`, `location_v1` в текущем виде принадлежат игре, а не ядру, и подлежат переносу. Для актора в ядре остаётся минимальная схема с `discriminator`.
- Доменные методы (`get_gold`, `add_gold`) получают легальное место — декоратор пакета, — и обязаны уйти из `actor_registry.lua`.
- Незарегистрированный discriminator обязан давать типизированный отказ, а не молча собранную неподходящую обёртку. На время переноса допускается базовая обёртка плюс список известных нерегистраций, который может только сокращаться.
- Demo content (`core:screen.test`, `Scripts/debug/start.lua`) перестаёт быть частью ядра.
- Реестр kind в `StableIDSpecification` перестаёт быть заявлением о предметной модели и становится списком категорий пространства имён.
- Замороженный корпус `Tests/Fixtures/PortableContentCore/valid/core` под правило не подпадает: он изображает пакет по имени `core`, а не движок, и остаётся как есть.
- Стоимость переноса схем высока — затрагивает реестр ссылочных полей состояния, боевые фикстуры, UE-провайдер и разметку замещаемости. Решение фиксирует направление, а не требует одного change set.

## Rejected alternatives

- **Оставить схемы в ядре, считая kind заявлением о предметной модели.** Именно так было записано в плане RhGamePackage. Отвергается: тогда `core` обязан заранее знать, что у предмета есть цена, а у актора здоровье, — то есть содержать модель одной игры.
- **Реестр фабрик без базовой обёртки** (пакет строит обёртку целиком). Отвергается: инварианты идентичности пришлось бы воспроизводить в каждом пакете, что гарантирует расхождение.
- **Реестр методов вместо декоратора.** Меньше и проще, но выражается через декоратор без остатка, а обратное неверно; заводить два механизма ради одного случая незачем.
- **Жёсткий отказ на незарегистрированный discriminator сразу.** Склеивает перенос схем и введение точки расширения в один неделимый change set вопреки принципу малых шагов.
- **Выносить общие подсистемы (инвентарь, диалоги, квесты) в `core` по мере надобности.** Отвергается: повторная применимость доказывается второй игрой, а не ожиданием. Такие подсистемы выносятся в отдельный feature package, отсутствие которого не мешает работе ядра.
