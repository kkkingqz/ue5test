# ADR-0031: Entity Authoring Extensions

> **Решение:** ввести в authoring-окружение управляемые прототипы доменных сущностей (`Actor`, `Location`, `Quest`, `Item`), перехватывающие декларации методов через `__newindex` и регистрирующие их в централизованном `EntityExtensionRegistry`; собирать неизменяемые эффективные таблицы методов (`effective method tables`) на фазе `register`; квалифицировать дубликаты методов между независимыми пакетами как фатальную ошибку конфигурации.

## 1. Контекст и проблема

После выделения слоев `core` $\leftarrow$ `textsystem` $\leftarrow$ `rh` ([ADR-0030](0030-textsystem-layer-and-data-driven-package-set.md)) ответственность подсистем разделена корректно, однако синтаксис расширения поведения сущностей оставался низкоуровневым:
- требовалось создание дескриптора модуля и ручная регистрация фабрики-декоратора (`register_type("player", decorator)`);
- ручное конструирование обёрток через `setmetatable` и замыкания;
- знание внутреннего устройства runtime-реестров дискриминаторов в игровом коде;
- дублирование привязки методов для каждого дискриминатора (`player`, `npc`).

В то же время авторский слой команд и событий ([ADR-0027](0027-designer-lua-authoring-layer.md), [ADR-0028](0028-simplified-authoring-surface.md)) успешно избавил геймплейный код от инфраструктурного шума. Требуется предоставить аналогичный декларативный и лаконичный механизм для расширения доменных сущностей.

## 2. Решение

### 2.1. Управляемые прототипы в авторском окружении (`_ENV`)
- В лексическое окружение authoring-скриптов (`scripts/authoring/*.lua`) инжектируются управляемые прокси-объекты для зарегистрированных категорий сущностей: `Actor`, `Location`, `Quest`, `Item`.
- Синтаксис объявления метода:
  ```lua
  function Actor:add_gold(amount)
      self.gold = (self.gold or 0) + amount
  end

  function Location:is_safe()
      return (self.danger_level or 0) <= 0
  end
  ```
- Метаметод `__newindex` прокси перехватывает присвоение функции, валидирует типы аргументов и регистрирует метод в централизованном реестре `core:module.runtime.entity_extension_registry` с атрибуцией `(source_module, package_id, entity_kind, method_name, fn)`.

### 2.2. Централизованный реестр и разрешение конфликтов
- `EntityExtensionRegistry` накапливает объявленные расширения во время загрузки модулей.
- **Правило разрешения конфликтов:** если два независимых пакета объявляют метод с одинаковым именем для одной сущности, сессия завершается фатальной ошибкой `entity_extension.method_conflict` при инициализации. Неявный override по порядку загрузки строго запрещен ([INV-010](../Architecture/Invariants.md)).
- На фазе жизненного цикла `register` реестр финализируется, валидирует отсутствие конфликтов, собирает композитные неизменяемые таблицы методов (`effective method table`) для каждого вида сущности и замораживается (`INV-006`).

### 2.3. Контракт `self` для различных категорий сущностей
Механизм разделяет категории сущностей по их онтологической природе:
1. **Экземпляры сущностей (Instances, например `Actor`, `Item Instance`)**:
   - `self` передается как `ActorWrapper` / `InstanceWrapper`.
   - Доступ к полям (`self.gold`) проходит через валидацию свойств и окно мутации канонического состояния.
2. **Определения контента (Definitions, например `Location`)**:
   - `self` передается как `DefinitionWrapper`.
   - Чтение полей (`self.danger_level`) читает неизменяемый снимок репозитория (`def.data`) с fallback на динамическую секцию состояния `state.definitions[def_id]` (по правилам ADR-0027 sparse-материализации).
   - Запись полей материализует динамические свойства в каноническом состоянии `state.definitions`.

### 2.4. Контекст пакета и вызовы `fail()`
- Метод сущности при выполнении проверок сохраняет контекст пакета своего объявления (`declaration package_id`).
- При вызове `fail(key, params)` из тела метода генерируется канонический Stable ID отказа в пространстве имён пакета, объявившего данный метод (например, `rh:error.economy.insufficient_gold`), независимо от того, из какого вызывающего контекста или команды был запущен метод.

### 2.5. Изоляция состояния и инварианты мутаций
- Методы расширений не вводят собственных структур данных и не сериализуются в save-контейнер ([INV-001](../Architecture/Invariants.md), [INV-008](../Architecture/Invariants.md)).
- Мутации канонического состояния внутри методов сущностей разрешены только при вызове внутри открытого окна мутации командного пути ([INV-003](../Architecture/Invariants.md)). Попытка прямой мутации вне окна мутации отклоняется рантаймом.

## 3. Отвергнутые альтернативы

- **Полноценная иерархия классов ООП в Lua (Class Inheritance)**: отвергнута, так как вводит избыточную сложность, метатабличные накладные расходы и противоречит компонентно-ориентированной модели данных контента и схем.
- **Неявное переопределение методов по порядку загрузки (Last-writer-wins)**: отвергнуто, так как маскирует коллизии имен между модами и нарушает принцип детерминизма.
- **Сохранение ручных декораторов типов (`register_type`) в игровом коде**: отвергнуто, так как вынуждает игровые пакеты содержать низкоуровневый инфраструктурный бойлерплейт.

## 4. Последствия

- Игровые пакеты (`textsystem`, `rh`, моды) освобождаются от низкоуровневого кода регистрации декораторов и метатаблиц.
- В ядро добавляется модуль `core:module.runtime.entity_extension_registry` и интеграция прототипов в `_ENV`.
- Валидация managed-операций (DLA-12) переводится на инспекцию `effective method table`.
- Сохраняются гарантии детерминизма, чистоты границ слоев и неизменяемости канонического состояния.
