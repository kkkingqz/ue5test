# ADR-0034: Gameplay Service Authoring

> **Решение:** авторский синтаксис `services.<name> = { … }` для stateless-процессов, координирующих несколько сущностей, атомарное объявление, контракт «только функции», неизменяемость после регистрации, наследование execution scope вызывающего, атрибуция `fail()` и `emit()` к пакету объявления и обязательное введение механизма вместе с потребителем.
> **Нормативный текст:** [Authoring Surface](../Architecture/AuthoringSurfaceContract.md), [Commands and Events](../Architecture/CommandsAndEvents.md), [Runtime Facade](../Architecture/RuntimeFacadeAndRegistries.md).

## Context

В runtime GV2 существует реестр игровых сервисов `game.services` (`register`, `get`, `require`, `exists`, `list`, `freeze`). Однако:
1. В авторском слое отсутствовал декларативный синтаксис для объявления сервисов, и пакеты были вынуждены обращаться к низкоуровневому устройству реестра.
2. В реестре kinds ([Stable ID Specification](../Architecture/StableIDSpecification.md)) отсутствовал kind `service`, а `service_registry.register` проверял лишь непустую строку вместо строгой формы Stable ID.
3. После удаления `core:service.location` планом TextSystemLayer у `game.services` не осталось ни одного потребителя. Согласно [ADR-0026](0026-core-and-gameplay-ownership.md), введение механизмов без потребителя («заранее») запрещено.
4. Отсутствовали четкие архитектурные правила разграничения между методами сущностей и сервисами, а также правила наследования execution scope при вызове сервисов из валидаторов или команд.

## Decision

1. **Критерий разделения «метод сущности vs сервис»**:
   - Критерий основан на **естественном владении операцией**:
     - Операция, имеющая одного естественного владельца, является **методом сущности** (`actor:spend_gold(10)`, `actor:move_to(location)`).
     - Процесс, координирующий несколько равноправных сущностей, назначение которого одной из них было бы искусственным, является **Gameplay Service** (`services.trade.buy(buyer, seller, item)`).
   - Вспомогательные односущностные действия (проверка наличия, изъятие и получение предметов) остаются методами сущностей.

2. **Атомарное объявление и синтаксис вызова**:
   - В авторское окружение `_ENV` предоставляется прокси `services`.
   - Сервис объявляется атомарно присваиванием таблицы:
     ```lua
     services.trade = {
         buy = function(buyer, seller, item) … end,
     }
     ```
   - Распределённое объявление `services.trade.buy = …` запрещено.
   - Вызов осуществляется через точку (`services.trade.buy(...)`), так как сервис не является сущностью и не имеет состояния/`self`.

3. **Контракт таблицы и неизменяемость**:
   - Таблица сервиса обязана содержать исключительно функции (`ServiceFieldNotFunction`). Поля-значения запрещены.
   - Константы через лексическое замыкание разрешены конвенцией; изменяемое захваченное состояние запрещено конвенцией.
   - После регистрации реализация сервиса защищается метатаблицей от модификации (`ServiceImmutableAfterRegistration`).
   - Повторное объявление с тем же Stable ID отклоняется `ServiceDuplicateDeclaration`.
   - Объявление после заморозки отклоняется `ServiceDeclarationAfterFreeze`.
   - Обращение к необъявленному локальному имени отклоняется `UnknownServiceKey`.

4. **Идентичность и kind `service`**:
   - Kind `service` вносится в реестр kinds спецификации Stable ID.
   - Канонический Stable ID локального сервиса: `<package_id>:service.<name>`.
   - `service_registry.register` строго проверяет соответствие ID каноническому Stable ID kind `service` (`InvalidServiceId`).

5. **Наследование Execution Scope**:
   - Сервис выполняется в execution scope вызывающего и не создаёт собственного.
   - При вызове из валидатора (`validator` scope) все охранники побочных эффектов (`AuthoringValidatorSideEffectDisallowed`) применяются к телу сервиса.
   - При вызове из команды (`command` scope) сервис может мутировать состояние внутри открытого окна мутации.
   - Вызов сервиса с мутацией состояния вне команды отклоняется закрытым окном мутации.
   - Вложенный вызов сервиса не создаёт нового окна мутации и отдельного commit.

6. **Атрибуция `fail()` и `emit()`**:
   - Вызовы `fail()` и `emit()` внутри методов сервиса атрибутируются к **пакету объявления сервиса** (через замыкание `_ENV` сервиса), независимо от того, какой пакет вызвал сервис.

7. **Разрешение межпакетных ссылок**:
   - Межпакетное обращение вида `services["other_pkg:service.calc"]` разрешается при заморозке авторской фазы (`freeze`).
   - Отсутствующий целевой сервис вызывает ошибку сборки `ServiceTargetMissing` с указанием вызывающего пакета и запрошенного ID.

8. **Обязательная связь с потребителем (ADR-0026)**:
   - Механизм принимается строго вместе с первым потребителем — торговцем в пакете `rh` (M2 плана GameplayServices), где покупка переходит от бесконечной генерации предметов из воздуха к реальному обмену товаром и золотом между игроком и NPC-торговцем.

## Consequences

- Авторский слой получает лаконичный и безопасный инструмент для многосущностных процессов.
- Сохраняются строгие инварианты детерминизма, отсутствия скрытого состояния и изоляции ядра от понятий конкретной игры.
- Отсутствует дублирование инфраструктуры: используется существующий реестр `game.services`.

## Rejected alternatives

- **Распределённое объявление `services.trade.buy = …`**: размывает владение, усложняет валидацию и заморозку.
- **Вызываемый сервис `services.trade(...)`**: сервис концептуально является пространством операций, а не отдельной функцией.
- **Форма `service("trade", { … })`**: нарушает сложившийся декларативный синтаксис `commands.foo`, `actions.foo`.
- **Расширение чужого сервиса модом**: нарушает инварианты владения пакетов; расширение поведения выполняется через валидаторы, подписчики событий или собственные сервисы.
- **Введение сервисов без реального потребителя**: прямо отвергнуто ADR-0026.
