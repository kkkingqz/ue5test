# ADR-0041: UI Commit Rollback Model

> **Решение:** Commit-фаза на каждой границе, где применяется последовательность fallible-мутаций к переиспользуемому live-состоянию, обязана перед применением очередной единицы захватывать состояние, необходимое для отмены уже применённых, и при отказе — откатить их в обратном порядке той же обычной Prepare/Commit-машиной (replay предыдущего значения), прежде чем вернуть failure. После успешного physical inverse она обязана вернуть захваченный committed tuple. Наблюдаемый результат — ровно два состояния: «предыдущая ревизия, физически и учётно нетронута» или «новая ревизия, применена целиком»; третьего (частично применённой новой ревизии) не существует.

## Context

`REM-02` — самая глубокая архитектурная недоработка внешнего ревью: `CommitUiHostProperties` и все его вызывающие применяют подготовленные мутации последовательно и выходят по первому отказу без отката. Для свежего off-tree кандидата это безопасно (виджет ещё не опубликован). Для **переиспользуемого** живого экземпляра отказ в середине оставляет логически старую ревизию физически частично новой.

Ревизия кода в рамках `GBH-09` нашла эту границу воспроизведённой на **пяти** уровнях, а не на одном:

1. **Свойство одного host'а.** `CommitUiHostProperties` (`GV2UiMutationPlan.cpp:506-566`) идёт по `Plan.GetMutations()` подряд и возвращает `false` на первом отказе консьюмера — свойства, закоммиченные раньше в этом же вызове, остаются на новом значении.
2. **Host одного экрана.** `UGV2ScreenWidgetBase::CommitScreenFields` (`GV2ScreenWidgetBase.cpp:202-233`) идёт по `Plan.FieldPlans` подряд; комментарий в коде прямо признаёт отсутствие механизма: «Every plan above already prepared cleanly... there is nothing to roll back to (no compensating capture exists any more)».
3. **Экран одного документа.** `FGV2LayeredUiReconciler::CommitReconcile`, шаг 1 (`GV2LayeredUiReconciler.cpp:150-173`) коммитит **все** экраны подряд до какого-либо attach/detach. `Docs/UI/UIDocumentAndReconciliation.md:220` уже документирует это как «все остальные слои... остаются буквально нетронутыми» — но это верно только для слоёв, до которых цикл не дошёл; уже закоммиченный в этом же вызове экран A, если B откажет, лежит на новом значении, пока `ActiveScreens` ниже не продвигается.
4. **Элемент keyed collection.** `FGV2KeyedCollectionPropertyConsumer::Commit` (`GV2PropertyConsumers.cpp:1268-1324`) идёт по `PreparedItems` подряд, вызывая `CommitUiHostProperties` для каждого хоста-элемента. Если элемент 2 откажет, `Panel`/`ActiveWidgetsByKey` не обновляются (return до этого места) — но переиспользуемый widget элемента 1 это тот же самый объект, что уже стоит в `Panel`, и его собственные под-свойства уже физически замьютированы на новое значение. Видимый результат: контейнер логически на старой ревизии, но первый его переиспользуемый элемент — визуально на новой.
5. **Вложенный экран в табе.** `FGV2TabContainerTabsPropertyConsumer::CommitWithFailureInjector` (`GV2PropertyConsumers.cpp:1773-1834`) — тот же паттерн уровнем глубже: коммитит `PreparedTabs` подряд через `Item.ScreenWidget->CommitScreenFields(...)`; отказ таба 2 оставляет вложенный экран таба 1 (если он переиспользуемый) физически замьютированным, пока `TabContainer->ApplyTabEntries(...)` не вызывается.
6. **Shell attach publication.** `CommitReconcile`, шаг 3 (`GV2LayeredUiReconciler.cpp:200-213`). `GBH-01` уже перенёс в `PrepareReconcile` каждую *предсказуемую* причину отказа `AttachScreenToLayer`, поэтому отказ здесь — по определению непредсказуемый engine-level. `UIDocumentAndReconciliation.md:222` называет остаточный разрыв прямо: «неудача присоединения экрана B после успешного присоединения A оставляет A физически в дереве Shell, хотя `ActiveScreens` ниже не обновляется... ни один тест не воспроизводит отказ `AttachScreenToLayer`».

Отдельно фиксируется, почему это не было найдено раньше: `PCC-07` закрывался инъекцией отказа на уровне экрана (пункт 3 выше — но только между разными экранами, ни разу — внутри одного переиспользуемого host'а или коллекции), поэтому опасная точка (пункты 1, 2, 4, 5) осталась непроверенной.

Уже существующая инфраструктура, на которую опирается это решение: `IGV2UiPropertyHost::GetPropertyHostState()` хранит committed snapshot хоста. С `GBF-04` это не только `LastCommittedProperties` (`FGV2PreparedUiObject`), но и `LastCommittedSchema` с `LastCommittedSchemaId`: значение без схемы не задаёт форму, в которую его можно безопасно восстановить после schema switch. `FGV2KeyedCollection::ReconcilePrepared` уже применяет структурный swap-back для порядка детей контейнера (`PreviousChildren`, `GV2KeyedCollection.h:103-115`), но только для структуры ierarkhii, не для свойств уже замьютированных переиспользуемых элементов.

## Decision

1. **Единый принцип: захват перед мутацией, откат в обратном порядке той же машиной.** На каждой границе выше, прежде чем Commit применяет единицу N к переиспользуемому/live состоянию, committed snapshot, необходимый для отмены единиц `1..N-1`, уже доступен: `LastCommittedProperties` **вместе с** `LastCommittedSchema` и `LastCommittedSchemaId` хоста (для property/host/nested-screen уровня), тот же tuple каждого элемента коллекции и факт «был ли экран новым или переиспользуемым» для Shell attach. При отказе единицы N уже применённые `1..N-1` откатываются в обратном порядке — не bespoke restore-кодом на каждый вид данных, а **тем же** Prepare/Commit consumer pipeline, скормленным прежним значением и прежней схемой вместо candidate. Только после успешного physical inverse возвращается захваченный tuple; если inverse отказал, tuple запрещено менять, потому что он больше не соответствует физическому состоянию. Только после того, как откат завершён, Commit возвращает failure вызывающему; `ActiveScreens` и committed snapshots продвигаются к новой ревизии только если **вся** транзакция, включая вложенные, успешна целиком.
2. **Обратный plan обязателен и проверяем.** Prepare строит inverse для каждой прямой mutation от committed snapshot; отсутствие schema у непустого previous value или отказ построения дают typed diagnostic `core:diagnostic.ui_rollback.*` и не допускают Commit. `GetUiMutationKindsRequiringInverse()` — named enumerator применимых kinds; `ValidateUiRollbackPlan` сопоставляет forward/inverse 1:1 по actual mutation plan. Поэтому удаление inverse любого перечисленного вида красит test до physical Commit.
3. **Явное решение по каждой границе:**
   - **Свойство (1)**: `CommitUiHostProperties` получает заранее валидированный обратный plan, построенный из committed value и committed schema. При отказе на свойстве K он коммитит inverse для свойств `1..K-1`, восстанавливая физическое состояние до возврата failure.
   - **Host (2)**: `CommitScreenFields` откатывает уже закоммиченные в этом вызове хосты `1..K-1` механизмом (1), используя их собственный pre-call committed tuple; `RollbackFieldPlans` возвращает tuple только после успешного physical inverse. `OnScreenFieldsApplied` и tab callbacks (`OnTabModelApplied`, `OnTabSelectionUpdated`, `OnTabChanged`) удалены GBF-06 после полного Asset Registry audit. Произвольный Blueprint/UI-callback не исполняется внутри отменяемой транзакции.
   - **Экран/документ (3)**: `CommitReconcile` шаг 1 откатывает уже закоммиченные в ЭТОМ вызове экраны `1..K-1` механизмом (2) — это закрывает буквальный разрыв, который сегодняшний текст `UIDocumentAndReconciliation.md` признаёт только для «остальных слоёв», не для уже пройденных.
   - **Keyed collection item (4)**: перед циклом Commit по `PreparedItems` захватывается полный committed tuple каждого существующего (переиспользуемого) элемента, участвующего в этой ревизии, плюс текущее состояние `Panel`-детей/`ActiveWidgetsByKey`. При отказе на элементе K элементы `1..K-1` откатываются механизмом (1) и после удачного inverse возвращают свои tuple; swap-back детей контейнера остаётся структурным+property.
   - **Вложенный экран в табе (5)**: рекурсия механизма (2)/(3) без нового code path — вложенный экран сам является полноценным host'ом со своим committed tuple и возвращает его через `RollbackFieldPlans`.
   - **Shell attach (6)**: захват тривиален — новый экран либо уже был присоединён в этом же шаге, либо нет. При отказе присоединения экрана B, экраны, присоединённые **в этом же шаге** ранее (например A), отсоединяются обратно (`Shell->DetachScreen`) прежде, чем шаг 1 (уже применённые property-мутации A) тоже откатывается механизмом (3); `ActiveScreens` на этом шаге ещё не продвинут, поэтому по нему откатывать нечего. Это дополняет, а не заменяет `GBH-01`: тот убирает предсказуемые причины отказа из Commit, это ADR обеспечивает восстановление для оставшегося непредсказуемого случая.
4. **Переиспользуется существующий pipeline, а не вводится второй.** Physical recovery на любом уровне — это повторный проход **обычного** Prepare/Commit со старым snapshot, а не bespoke undo каждого вида данных. После его успеха accounting recovery присваивает ровно тот typed committed tuple, из которого был построен inverse; оно не выводится повторно из candidate и не изменяет виджет. Структурный откат (порядок детей `Panel`, Shell attach) переиспользует тот же swap-back идиом, которым `FGV2KeyedCollection::ReconcilePrepared` уже пользуется для собственного контейнера.
5. **Отклонено: shadow/staged дерево с атомарным свопом.** Несовместимо с моделью переиспользуемых виджетов, которая существует специально ради сохранения UI-local состояния (scroll position, анимация, фокус) между ревизиями (таблица реконсиляции: «Обновить данные виджета на месте; сохранить UI-local состояние»). Параллельное shadow-дерево обязано быть новым экземпляром виджета — это ломает in-place переиспользование для КАЖДОЙ успешной ревизии, а не только для отказавших.
6. **Отклонено как самостоятельная альтернатива (частично уже принято как дополнение): «Commit не может отказать после первой live-мутации».** Условие плана связывает это конъюнкцией с deterministic recovery для оставшегося непредсказуемого отказа — то есть даже полный вынос fallible-логики в Prepare не снимает потребность в механизме этого ADR, а только сокращает частоту его срабатывания. `GBH-01` уже выполнил такое сужение для Shell attach конкретно; общий механизм восстановления при этом остаётся обязательным и реализуется `GBH-10` для всех границ выше.
7. **Отклонено: сузить нормативный контракт до допустимого partial state.** Прямо запрещено планом; узаконило бы именно те разрывы, которые `UIDocumentAndReconciliation.md` сегодня документирует как известные (строка про экран A, оставшийся в дереве Shell), вместо их устранения.

## Consequences

- `GBH-10` реализует механизм на всех шести границах; Evidence: `GV2UiMutationPlan.cpp` (1), `GV2ScreenWidgetBase.cpp` (2, 3 частично), `GV2LayeredUiReconciler.cpp` (3, 6), `GV2PropertyConsumers.cpp` (4, 5).
- `Docs/UI/UIDocumentAndReconciliation.md` обновлён этим change set: секция «Границы транзакционности и отката» и строка про известный остаточный разрыв Shell attach ссылаются на это решение вместо описания разрыва как открытого без владельца.
- `GBH-11` обязан инъектировать отказ на **второй** мутации переиспользуемого live host/экрана/элемента коллекции (не на границе между разными экранами, которую уже проверял `PCC-07`) и сравнить состояние первой, уже закоммиченной мутации, `LastCommittedProperties`, порядок/identity детей коллекции, `ActiveScreens` и binding revision с baseline предыдущей ревизии.
- `GBF-04` добавляет schema-switch regression: candidate и previous одного field host используют разные schemas; отказ после первой mutation восстанавливает форму previous schema. Отдельный test перебирает `GetUiMutationKindsRequiringInverse()` и удаляет inverse каждой kind.
- `GBF-05` фиксирует границу accounting recovery: `GV2.UI.LayeredReconciliationContract` сравнивает physical state, committed tuple и следующую Prepare после rollback host/экрана и nested tab screen; `GV2.UI.StandardPropertyConsumers` делает то же для переиспользуемого keyed item.
- `GBF-07` делает множество sequence boundaries перечислимым: `validate_ui_rollback_boundaries.py` выводит definitions `Commit*`/`AttachScreenToLayer` из production source, требует `rollback_boundary` для roots и `rollback_leaf`/`rollback_delegate` для каждого bare `Commit`, сопоставляет IDs с `EGV2UiRollbackBoundary` и требует executable `ReplayInverse`/`RestoreStructure` classification. Это source-shape gate, а не доказательство тела recovery; новый mutation path вне этой grammar обязан расширить gate и получить runtime fault-injection test тем же change set.
- Контракт, видимый Lua/схеме, не меняется: откат — исключительно внутреннее поведение Commit-фазы.

## Rejected alternatives

- **Shadow/staged tree со свопом** — см. Decision 4.
- **Структурный вынос всех fallible operations без recovery для остатка** — см. Decision 5.
- **Партиал-стейт как допустимый нормальный контракт** — см. Decision 6.
- **Отдельный bespoke undo-код на каждую границу вместо переиспользования Prepare/Commit** — отклонён по той же причине, что и в Decision 3: удваивает поверхность, которую нужно доказывать корректной, вместо использования уже проверенного пути.
