# ADR-0024: Lua Spec Runner

## Context

ADR-0020 зафиксировал, что код принадлежит Lua, если не требует возможностей, недоступных ей по trust model. Рантайм этому следует: gameplay-правила уходят в `Scripts/`.

Проверки этих правил — нет. `HeadlessSimulationContract` требует, чтобы portable-проверка объявлялась entry point в `Testing/`-заголовке своего module, то есть была функцией C++. Правило, написанное на Lua, приходится проверять из C++, а тестовые модули и сценарии собирать строковыми литералами внутри `.cpp`.

Замер на 2026-08-15: conformance-обвязка занимает 8794 строки C++, из них 5326 — один `GV2LuaLifecycleConformance.cpp`. Две задачи, добавившие примерно 50 строк Lua-логики (`world.lua` и проверка `current_location_id` в `state_validator.lua`), потребовали 439 и 575 строк C++ соответственно.

Это та же болезнь, которую лечил CGS-M4, вынося валидатор состояния из C++ в `Scripts/`. Она переехала в тестовые файлы, где действующий гейт её не ловит по построению: `Tools/Content/validate_host_conformance_parity.py` запрещает host-локальные проверки, но Lua внутри conformance-файлов разрешает как тестовые фикстуры.

Побочное следствие текущей схемы: покрытие обоими host-ами обеспечивается ручной работой — для каждого entry point нужно не забыть добавить обёртку в Unreal automation, и это стережёт отдельный скрипт.

## Decision

- Вводится **Lua spec runner**: один generic portable entry point, который обнаруживает и исполняет Lua-спеки.
- Спеки живут в `Tests/Lua/` — отдельном дереве, не входящем в `Scripts/` и не попадающем в упакованную игру.
- Обнаружение детерминировано: файлы сортируются, порядок исполнения воспроизводим, спеки не зависят друг от друга и от порядка.
- Провал даёт стабильный идентификатор `<spec>.<case>` — тот же контракт, что у существующих entry points.
- Оба host-а вызывают один и тот же runner. Добавление спеки автоматически расширяет покрытие обоих; отдельная обёртка на правило больше не нужна.
- Граница сохраняется: правила, выраженные в Lua, проверяются спеками; C++ API (сериализация manifest/digest, replay, marshaller, JSON5, schemas) проверяется существующими C++ conformance entry points.
- Новое правило, выраженное в Lua, запрещено проверять новым C++ conformance entry point. Существующие наборы мигрируют по мере того, как их всё равно приходится изменять; массовая единовременная миграция не требуется.

## Consequences

- Добавление gameplay-правила перестаёт требовать C++ вообще: правило — файл в `Scripts/`, проверка — файл в `Tests/Lua/`.
- Автор контента, пишущий Lua, получает возможность писать и проверки к нему.
- Паритет усиливается: покрытие обоими host-ами следует из наличия спеки, а не из дисциплины разработчика.
- `HeadlessSimulationContract` и `BuildAndTooling` требуют правки: формулировка «проверка объявляется entry point в `Testing`-заголовке» перестаёт быть единственной допустимой формой.
- Гейт паритета расширяется: он обязан обнаруживать новый C++ conformance entry point, проверяющий Lua-правило.
- Спеки исполняются внутри VM, поэтому недоступны `gv2-content`, у которого VM нет по контракту. Это не ограничение: контентная валидация к Lua-правилам не относится.
- Существующие 8794 строки остаются валидными и не блокируют переход.

## Rejected alternatives

- Оставить C++ conformance единственной формой: сохраняет цену примерно 500 строк C++ за правило и делает написание проверок недоступным автору контента.
- Разместить спеки внутри `Scripts/`: делает их частью module tree и упакованной игры, смешивает production-код с тестовым.
- Сгенерировать C++-обвязку из Lua-спек: сохраняет промежуточный артефакт и его рассинхронизацию, не убирая ни одной из причин.
- Отказаться от требования исполнять проверки обоими host-ами: снимает боль ценой того самого расхождения, ради предотвращения которого parity gate и построен.
