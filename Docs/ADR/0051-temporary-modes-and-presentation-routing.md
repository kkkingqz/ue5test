# ADR-0051: Временные режимы как категория состояния и маршрутизация презентации

> **Решение:** состояние запуска временного режима (Mode Run) — отдельная категория рядом с canonical state: одно `core`-хранилище, не более одного активного режима, запись только внутри command handler, журнал из [ADR-0050](0050-transactional-mutation-window.md), вне state hash и save. Презентация выбирает между экраном активного режима и построителем по умолчанию: регистрация source остаётся единственной, `view` возвращает только route-экран, маршрутизация не является композицией.
> **Нормативный текст:** категория состояния и правило UI-local уточняются этим решением в [Overview](../Architecture/Overview.md#категории-состояния) и [UI Document](../UI/UIDocumentAndReconciliation.md#ui-local-state); правила объявления `modes`, маршрутизации и событий переносятся в [Authoring Surface](../Architecture/AuthoringSurfaceContract.md), [Commands and Events](../Architecture/CommandsAndEvents.md) и [Screen Templates](../UI/ScreenTemplates.md) задачей EGC-21 плана [Engine Gap Closure](../Plans/EngineGapClosure/README.md).
> **Основание:** [предложение о временных игровых режимах](../Proposals/TemporaryGameModesProposal.md).

## 1. Контекст и проблема

Текстовой RPG нужны механики, занимающие игрока целиком: торговля, диалог, бой, танец. Сегодня они выразимы только командами экрана локации и модальными окнами, и промежуточный прогресс приходится держать либо в canonical state, либо в `local`-таблицах модулей — без изоляции между spec case, без отката и без проверки формы.

**Противоречие contract, а не частный случай.** Правило [UI-local state](../UI/UIDocumentAndReconciliation.md#ui-local-state) требует: значение, влияющее на gameplay, становится canonical state. Состояние незавершённого боя влияет на gameplay и намеренно не сохраняется. Категория «Lua runtime state» ([Overview](../Architecture/Overview.md#категории-состояния)) этого не покрывает: она описывает то, что перестраивается при bootstrap и load, и не даёт ни изоляции, ни отката, ни валидации формы. Поэтому нужна категория, а не исключение.

**Состояние презентации на входе** (проверено по коду): `Scripts/runtime/presentation_source.lua` допускает ровно один источник (`PresentationSourceDuplicateRegistration`); единственный зарегистрированный источник — `textsystem:module.presentation.location_presenter`, и он **уже** является цепочкой выбора: четыре фикстурных ветки, затем экран текущей локации; `Scripts/runtime/command_dispatcher.lua` вызывает `game.presentation.resolve()` после каждой успешной команды. [ADR-0039](0039-presentation-source-singleton.md) отклонил композицию источников и назвал наблюдаемое условие пересмотра — см. раздел 3.

## 2. Решение

### D1 — Transient mode state как категория состояния

Одно `core`-хранилище активного режима: не более одного режима одновременно, вложенность не поддерживается. Содержимое run — только portable values, объявленные дескрипторами `field.*` того же вида, что prototype сущности; запись возможна только внутри command handler, как для canonical state ([INV-003](../Architecture/Invariants.md)); записи журналируются категорией `transient` единого журнала окна мутации ([ADR-0050](0050-transactional-mutation-window.md)) и откатываются вместе с командой. В state hash и в save run не входит. Хранилище является участником реестра изоляции тестов, поэтому активный режим не переходит между spec case.

Правило UI-local state уточняется: значение, влияющее на gameplay, хранится в canonical state **или** в transient mode state активного режима. Отсюда следствие, снимающее двусмысленность: значение, решающее, открыт ли слой, и влияющее на правила режима, — это run state, а не UI-local. Подтверждение покупки, от которого зависит применение итога, принадлежит run; оформление того же подтверждения — слой документа.

### D2 — Контракт режима и смена режима

Объявление `modes.<key> = { start, view }` даёт `<package>:mode.<key>`; повторное объявление, объявление после freeze и отсутствие `view` отвергаются тем же протоколом, что для services. Вызовы: `start`, `require_active`, `state`, `finish`, `cancel` и `modes.active()`. Отказы `mode.not_active`, `mode.already_active` и `mode.active` принадлежат `core`.

`start()` при активном режиме — typed refusal `mode.already_active`, а не неявное завершение текущего режима: неявное завершение сделало бы итог предыдущего режима следствием чужой команды.

`finish()` и `start()` в одной команде **разрешены**. Инвариант формулируется как «не более одного активного режима в любой наблюдаемой точке», а не «команда не может сменить режим»: переход диалог → бой и диалог → реакция иначе требует двух команд, между которыми публикуется интерактивная ревизия экрана локации — то есть кадр, в котором игрок может нажать то, что уже не относится к происходящему.

### D3 — Маршрутизация выбором, а не композицией

Регистрация источника остаётся единственной, но зарегистрированная функция меняет смысл: это **построитель route по умолчанию**. `resolve()` сначала спрашивает `modes.active()` и при активном режиме вызывает его `view`. Маршрутизатор живёт в `core` и не знает построитель `textsystem` по имени — направление зависимостей `core → textsystem → rh` сохраняется.

`view` — чистая проекция `(canonical state, run) → route-экран`: он возвращает **только route**, ничего не публикует и ничего не мутирует. Слои режима открывают его команды, и они помечаются owner = активный режим; при `finish()`/`cancel()` они удаляются той же ревизией, которой route возвращается к построителю по умолчанию.

Merge документов из нескольких источников по-прежнему отвергается, и проблема мержа не возникает: активен не более одного режима, поэтому у route ровно один владелец в каждый момент.

### D4 — Порядок: транзакция, факты, презентация

`event_bus.commit_command_context()` доставляет факты синхронно, и только после этого вызывается `game.presentation.resolve()` — обе операции исполняются в одном `pcall` команды. Поэтому решение транзакции из [ADR-0050](0050-transactional-mutation-window.md) принимается сразу после закрытия окна мутации: **до** публикации фактов и до презентации.

Следствие: ошибка маршрутизатора или `view` не откатывает каноническое состояние и не отзывает доставленные факты. Обработка такой ошибки остаётся прежней — ошибка команды. Превращение ошибки презентации в типизированную диагностику касается всех построителей, а не только режимов, и этим решением не вводится.

### D5 — Случайность: воспроизводимость сохраняется

Run-поток случайности **объявляется режимом**, а не выдаётся каждому. Для режима с объявленным потоком команда старта один раз тянет `game.random.next_u32("core:random_stream.mode_seed")` — обычную каноническую запись в обычной команде; значение становится зерном run-локального потока, выводимого с отдельным тегом домена (`gv2-prng-run-v1`), чтобы при том же зерне последовательность не совпадала с канонической. Состояние потока хранится в run дескриптором `field.random_stream`, принадлежащим `core`: тег алгоритма и четыре 32-битных слова проверяются тем же правилом, которым `state_validator` проверяет `meta.prng`, и не протекают в авторский слой. Броски внутри режима канонического хеша не меняют и журналируются как transient-записи, поэтому отказ внутри хода не съедает ролл.

Автоматический бросок на каждом `start()` отвергнут: он распространил бы оговорку из следующего абзаца на все режимы сразу, включая те, которым случайность не нужна.

**Воспроизводимость — принятое свойство, а не умолчание.** `meta.prng` входит в канонический хеш и в сейв, поэтому сейв, снятый до старта режима, после загрузки даёт то же зерно и ту же последовательность: повтор боя из одного сейва идентичен. Это цена детерминизма replay и golden-прогонов, и она выбрана осознанно.

Отсюда форма критерия отмены: `cancel()` режима **без** объявленного потока оставляет хеш состояния равным хешу до старта полностью; `cancel()` режима **с** объявленным потоком оставляет единственное расхождение — одно продвижение `core:random_stream.mode_seed`, сделанное успешной командой старта.

### D6 — Сохранение и загрузка

`core:command.session.save` при активном режиме даёт typed refusal `core:error.mode.active`. Альтернатива — не блокировать, а защиту свести к тому, что экран режима не показывает кнопку сохранения, — отвергнута: это утверждение без перечислителя, а цена ошибки — молча потерянный незавершённый режим. Отказ обратим: режим завершается или отменяется, после чего сохранение проходит.

`core:command.session.load` не отказывается. Замена сессии уничтожает VM вместе с run ([ADR-0044](0044-session-replacement-and-registry-sealing.md) D1), поэтому незавершённый режим отбрасывается по построению: после load `modes.active()` равен `nil` и открывается построитель по умолчанию. Зеркалить отказ сохранения на загрузку не нужно.

### D7 — Stable ID kind `mode`

`mode` вносится строкой в реестр kind [спецификации Stable ID](../Architecture/StableIDSpecification.md#kind-registry). Правила объявления, повторного и позднего объявления — правила freeze реестров на фазе `register` — живут рядом с правилами services в [Authoring Surface](../Architecture/AuthoringSurfaceContract.md) и переносятся туда задачей EGC-21. Раздел «Lifecycle and publication freeze» спецификации описывает публикацию контента ([ADR-0023](0023-stable-id-publication-freeze.md)), и смешивать его с freeze реестров нельзя: это две разные заморозки.

Публикационное правило для mode-id совпадает с правилом для `command`: сейв mode-id не несёт, потому что run не сохраняется, а внешняя поверхность — `mode_id` в payload `core:event.mode.*`, на который подписываются моды и квесты. Переименование режима после публикации пакета ломает подписчиков и подпадает под ту же публикационную заморозку, что остальные опубликованные идентификаторы пакета.

Реестр kind при этом объявляет себя неполным, а грамматика разрешает в позиции kind любой segment: проверка делается поштучно через `is_kind`/`IsOfKind`. Превращение реестра в перечислитель — отдельная задача (EGC-20A плана), а не часть этого решения.

### D8 — События режима

Механизм публикует post-commit факты `core:event.mode.started` и `core:event.mode.finished` с полями `mode_id` и `outcome`; `cancel()` даёт `outcome = "cancelled"`. Изменения run сами по себе событий не порождают. Публикация подчиняется [INV-004](../Architecture/Invariants.md): факты доставляются только после успешного commit команды.

## 3. Отношение к ADR-0039

[ADR-0039](0039-presentation-source-singleton.md) отклонил композицию источников и назвал наблюдаемое условие пересмотра. Условие израсходовано **частично**, и это зафиксировано датированной пометкой в самом ADR-0039.

- **Наступило:** второй владелец route появился — `view` активного режима, перестраиваемый после каждой команды.
- **Не наступило:** вторая регистрация источника. `register_source` принимает одну функцию, `PresentationSourceDuplicateRegistration` в силе, и проблема мержа из `Decision` п. 3 ADR-0039 не возникла, потому что активен не более одного режима.
- **Сохранено:** композиция и мерж документов из нескольких источников, вторая регистрация и молчаливая перезапись остаются запрещёнными. Статус ADR-0039 не меняется: отклонённое там решение остаётся отклонённым.
- **Переформулировано:** в прежнем виде условие пересмотра больше не опровержимо, поэтому композиция обсуждается заново при двух владельцах route, претендующих на один `ui_instance_id` (тогда сначала правило порядка и приоритета), а потребность в отдельном `ui_instance_id` композицией не является.

## 4. Последствия

- Режим пишется целиком на authoring surface: без `game.*`, без сырого `game.state` и без собственного presentation-модуля.
- У route ровно один владелец в каждый момент; нерешённая проблема мержа остаётся нерешённой и не блокирует режимы.
- Активный режим не протекает между spec case, потому что хранилище входит в реестр изоляции.
- Игрок не может сохраниться внутри режима — наблюдаемая смена поведения, выбранная вместо молчаливой потери прогресса.
- Повтор режима из одного сейва воспроизводим, в том числе для боя: сейв-скам возможен и является следствием детерминизма.
- Критерий «`cancel()` не меняет хеш» становится двухчастным: безусловным для режима без объявленного потока и с единственным расхождением для режима с потоком.
- `view` как чистая проекция делает UI режима выводимым из `(canonical, run)`; исключение — слои, которые живут в документе и опознаются по owner.

## 5. Отвергнутые альтернативы

**Несколько presentation sources с мержем route.** Отклонено в ADR-0039 и не пересматривается: правила порядка и конфликта шаблонов для одного `instance_key` не существует, а при одном активном режиме они и не нужны.

**`view`, возвращающий весь документ как чистую проекцию.** Сильнее по инварианту, но требует, чтобы каждый временный элемент UI режима стал объявленным полем run: модальное подтверждение, выделение, страница — всё это тянет вперёд поля-коллекции и делает `show_modal` внутри команды режима ошибкой. Слои с owner дают тот же результат на выходе дешевле.

**Transient state как частный случай «Lua runtime state».** Эта категория перестраивается при bootstrap и load и не несёт ни изоляции, ни отката, ни валидации формы; объявить run её частным случаем значило бы оставить правило UI-local нарушенным и лишить run трёх механизмов, для которых он и вводится.

**Вложенные режимы и несколько активных одновременно.** Вводит вопрос владельца route и порядок завершения; ни одна механика стартового пакета этого не требует.

**Неявное завершение текущего режима при `start()`.** Итог одного режима становился бы следствием команды другого.

**Запрет `finish()` и `start()` в одной команде.** Дал бы промежуточную интерактивную ревизию экрана локации между диалогом и боем.

**Сохранение незавершённого режима.** Потребовало бы версионировать форму run и миграции для него; run по построению временный.

**Зерно вне канонического состояния.** Сломало бы сейв-скам вместе с детерминизмом replay и golden-прогонов.

**Незаблокированное сохранение с дисциплиной экрана.** Защита «экран режима не показывает кнопку сохранения» не имеет перечислителя: первый же экран, забывший правило, теряет прогресс молча.

**Автоматический бросок зерна на каждом `start()`.** Сделал бы оговорку в критерии отмены всеобщей, в том числе для режимов без случайности.

**Правила объявления режима в разделе публикационной заморозки спецификации Stable ID.** Смешало бы freeze реестров на фазе `register` с публикацией контента; у этих заморозок разные владельцы и разные последствия.
