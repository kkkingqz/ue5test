# Тексты и переводы

> **Задача:** написать текст, который увидит игрок, и перевести его.
> **Нужно:** прочитанный [Setup](Setup.md).
> **Проверка:** `gv2-content coverage GameData/rh --locale=ru` показывает полноту перевода.

## Почему текст — отдельный объект

Ни в одном объекте нет названия прямо в поле. Вместо этого — ссылка на текст:

```json5
label_text_id: "rh:text.item.iron_sword.name",
```

Причина простая: текст переводится, а всё остальное — нет. Цена меча одинакова на всех языках, название — нет. Разделив их, мы получаем возможность отдать переводчику один файл вместо всего контента.

Побочная выгода: один и тот же текст можно переиспользовать в нескольких местах, и он останется согласованным.

## Исходный текст

Живёт в `GameData/rh/definitions/texts.json5`:

```json5
{
  id: "rh:text.item.iron_sword.name",
  data: { source_message: "Iron sword" },
},
```

`source_message` — исходная формулировка, с которой делаются все переводы. Пишется на английском и не должна быть пустой.

Она же работает запасным вариантом: если перевода на нужный язык нет, игрок увидит `source_message`. Не пустое место и не идентификатор — читаемый текст. Поэтому осмысленный `source_message` важен, даже если игра выйдет только на русском.

## Переводы

Переводы лежат отдельно от контента, в формате PO — том же, которым пользуются переводчики во всём мире. Один файл на язык: `GameData/rh/localization/ru.po`.

Начало файла — служебный заголовок, его не трогают:

```po
msgid ""
msgstr ""
"Language: ru\n"
"MIME-Version: 1.0\n"
"Content-Type: text/plain; charset=UTF-8\n"
```

Дальше идут записи, по три строки каждая:

```po
msgctxt "rh:text.item.iron_sword.name"
msgid "Iron sword"
msgstr "Железный меч"
```

| Строка | Что это |
|---|---|
| `msgctxt` | Идентификатор текста — по нему находится соответствие |
| `msgid` | Точная копия `source_message` |
| `msgstr` | Перевод |

`msgid` обязан совпадать с `source_message` дословно. Если вы поправили исходный текст, поправьте и `msgid` — иначе перевод не найдётся, и игрок увидит английский вариант.

Файлы PO открываются любым текстовым редактором, но переводчику удобнее в специальном — Poedit и подобных. Формат стандартный, никаких особенностей у нас нет.

## Сбор текстов из кода

Если в скриптах были добавлены новые вызовы `M.text("key")` или `M.fail("key")`, их можно автоматически собрать в `definitions/texts.json5` и каталоги перевода:

```bash
python3 Tools/Content/collect_texts.py GameData/rh
```

Утилита найдёт все использованные текстовые ключи и коды отказов, добавит недостающие определения со стандартным `source_message` и подготовит шаблоны в PO-файлах.

## Проверка полноты

```bash
gv2-content coverage GameData/rh --locale=ru
```

Команда показывает, сколько текстов переведено и какие остались. Непереведённый текст не является ошибкой — игра запустится и покажет `source_message`. Это осознанно: перевод не должен блокировать работу над контентом.

## Именование текстов

Строгого правила нет, но удобно повторять адрес объекта, которому текст принадлежит:

```text
rh:item.weapon.iron_sword   →  rh:text.item.iron_sword.name
rh:actor.npc.merchant       →  rh:text.npc.merchant.name
rh:location.city.market     →  rh:text.location.market.title
```

Так по идентификатору текста сразу видно, чей он, и при удалении объекта легко найти осиротевшие тексты.

## Частые ошибки

**`msgid` не совпадает с `source_message`.** Самая частая. Перевод молча не подхватывается, игрок видит английский. Проверяется командой `coverage`.

**Правка `source_message` без правки `msgid`.** Тот же результат. Меняете исходный текст — пройдитесь по переводам.

**Пустой `source_message`.** Ошибка проверки: текст обязан быть непустым.

**Кириллица в `source_message`.** Формально не запрещена, но тогда исходный язык становится русским, и английский придётся заводить переводом. Проще держать исходник английским.
