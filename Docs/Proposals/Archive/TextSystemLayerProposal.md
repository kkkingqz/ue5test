# Предложение по слою TextSystem

> **Предлагает:** промежуточный слой между движком и игрой — переиспользуемую основу текстовой игры.
> **Затрагивает:** [Modding](../../Architecture/Modding.md), [Stable ID Specification](../../Architecture/StableIDSpecification.md), [Build and Tooling](../../Architecture/BuildAndTooling.md).
> **Не является нормативным:** до реализации действует текущий contract.

## 1. Назначение

Разделения на `core` и игру оказалось недостаточно. Часть функциональности универсальна не для любой игры, а для класса текстовых игр: персонажи, локации, переходы, квесты, экранная презентация.

В ядре такие сущности превращают framework в движок одного жанра. В игре — заставляют каждую следующую текстовую игру писать их заново.

```text
core         универсальный runtime и интеграция с UE
  ↑
textsystem   переиспользуемая основа текстовой игры
  ↑
rh           правила и сущности конкретной игры
```

Зависимости строго снизу вверх. `core` не знает о `textsystem` и `rh`; `textsystem` не знает о `rh`.

## 2. Отношение к ADR-0026 — это осознанное исключение

[ADR-0026](../../ADR/0026-core-and-gameplay-ownership.md) отвергает вынесение подсистем в feature package «заранее»: «повторная применимость доказывается второй игрой, а не ожиданием».

**Второй текстовой игры нет.** Значит предложение нарушает собственное правило проекта, и это должно быть записано, а не пройти незамеченным.

Основание для исключения: цена разделения растёт с объёмом `rh`, а сейчас он минимален — четыре команды и три локации. Разделять систему из двухсот строк дешевле, чем из двух тысяч. Это довод о **стоимости момента**, а не о доказанной применимости, и ADR по этому предложению обязан сформулировать его именно так.

Практическое следствие: критерий ADR-0026 бинарен («нужна ли сущность более чем одной игре») и на три уровня не отвечает. Он расширяется до трёх вопросов:

| Вопрос | Ответ «да» означает |
|---|---|
| Нужна ли сущность любой игре на GV2, независимо от жанра? | `core` |
| Нужна ли она любой текстовой игре, но не любой игре вообще? | `textsystem` |
| Выражает ли она правила или содержание конкретной игры? | `rh` |

## 3. Состояние на входе

Проверено по коду; часть разделов исходной редакции опиралась на устаревшую картину.

### 3.1. Набор пакетов зашит в хостах

Это главное препятствие. Оба хоста перечисляют пакеты **по именам**:

```cpp
// Headless/Source/main.cpp
if (exists(GameDataDir / "core" / "package.json5")) Roots.push_back(…/"core");
if (exists(GameDataDir / "rh"   / "package.json5")) Roots.push_back(…/"rh");
```

`GV2RuntimeSubsystem.cpp` устроен так же. Пакет `sample`, заведённый ранее, в набор по умолчанию не попал.

То есть **добавление слоя сегодня требует правки C++ в двух местах**, что противоречит самой идее слоёв: если добавление пакета — изменение движка, слоёв не будет.

Механизм для исправления уже есть — `DiscoverPackagesFromDirectories`, проверка зависимостей и циклов, `mods.lock.json5`. Не хватает того, чтобы хост им пользовался вместо двух `if`.

Отдельно: `gv2-content` контейнерный режим не поддерживает — `validate GameData` даёт `package.json5 package root has no package.json5`. Три пакета придётся перечислять явно во всех вызовах CLI и CI.

### 3.2. Трёхзвенная цепочка сама по себе работает

Собрано во временном дереве: `core → textsystem → rh` с зависимостями через манифесты, корни перечислены явно — `validate` зелёный. Резолюция, порядок и проверка зависимостей на три уровня работают.

### 3.3. Автообнаружение модулей уже реализовано

Part J исходной редакции описывает то, что сделано планом [SimplifiedAuthoringSurface](../../Plans/Archive/SimplifiedAuthoringSurface/README.md): `generate_manifest.py`, вывод ID, скан литеральных `require`, гейт `rh_manifest_up_to_date_contract`.

Два уточнения к описанию: ручной манифест не удалён, а **стал генерируемым артефактом**, и ID выводится из пути **только для незамещаемых** модулей — замещаемые объявляют ID явно, потому что на них нацеливаются моды.

Отдельного этапа под это не нужно: новый пакет подхватывается генератором автоматически.

### 3.4. Источник презентации уже существует

`core:module.runtime.presentation_source` и `game.presentation.register_source` введены тем же планом; `location_screen.lua` уже регистрируется источником и не вызывается геймплеем. Переносить нужно **владение** презентером, а не строить механизм.

### 3.5. Квестов не существует вовсе

Секция `state.quests` объявлена и версионирована, kind `quest` есть в реестре — но ни одного definition, ни одной операции, ни одного потребителя.

Значит «перенести generic Quest foundation» — это **создать с нуля подсистему без единого потребителя**, что прямо противоречит и ADR-0026, и духу самого предложения. Вынесено из области.

### 3.6. Геттеры и дискриминаторные методы используются

`get_gold`, `get_stamina`, `is_player`, `is_npc` предлагалось удалить «если не используются». Проверка выполнена: они используются спекой `Tests/Lua/actors/actor_extension.lua`. Условие удаления не выполняется — либо меняется спека, либо методы остаются.

### 3.7. Разбиение спеков сегодня бинарно

Фикстурная сессия — только `Tests/Lua/commands` (литерал в `LuaSpecRunner.cpp`), остальное идёт на боевой сессии `core` + `rh`. Трёхуровневое тестирование требует не «ещё одной сессии», а **карты «подкаталог → конфигурация пакетов»** и разнесения существующих `world`, `economy`, `actions`, `presentation` по уровням.

Хорошая новость: жёсткий список подкаталогов в двух местах C++ заменён на общую `DiscoverProductionSessionSubtreeNames()`, поэтому расширять придётся одну функцию.

### 3.8. Схемы переезжают второй раз

`item_v1` и `location_v1` переехали из `core` в `rh` планом [CoreBoundaryMigration](../../Plans/Archive/CoreBoundaryMigration/README.md). Теперь `location` уезжает в `textsystem` — тот же файл, вторая миграция за неделю. Не ошибка, критерий изменился законно, но должно быть названо.

### 3.9. Замороженный корпус под правило не подпадает

`Tests/Fixtures/PortableContentCore/valid/core` содержит `core:actor.*`, `core:item.*`, `core:location.*`. Он изображает **пакет по имени core**, а не движок, и остаётся как есть. Требование «core tests без Actor/Location» к нему не относится — иначе придётся перестраивать корпус и золотой прогон ради переименования фикстур.

## 4. Границы

**Входят:** набор пакетов из данных, пакет `textsystem`, перенос владения локацией и переходом, презентер локации, декларативные экраны, трёхуровневое тестирование, чистка `rh/actors.lua`.

**Не входят:**

- **Quest foundation.** Подсистемы не существует, потребителей нет. Создаётся, когда появится первый квест в `rh`, и сразу в том слое, которого потребует второй квест.
- **Inventory как подсистема TextSystem.** `add_item` остаётся в `rh`, пока не появится вторая игра или вторая механика, которой он нужен.
- Наследование классов Lua: расширение идёт существующими механизмами — схемные расширения, декораторы экземпляров и определений, managed-операции.
- Изменение грамматики Stable ID, отказ от Lua, перенос авторитета геймплея в UE.

# Part A. Core

Ядро остаётся жанрово-нейтральным: Lua-рантайм, загрузка пакетов и модулей, репозиторий, Stable ID, каноническое состояние, сейв, команды, сервисы, EventBus, детерминизм, диагностика, локализация, авторская инфраструктура, примитивы презентации.

Ядро не знает понятий `Actor`, `Location`, `Quest`, `Travel`, `Inventory`, `Gold`, `Stamina`, `Dialog`.

**Следствие для существующего кода.** После переноса перехода из ядра исчезают `core:command.location.travel`, `core:service.location` и `Scripts/gameplay/location_service.lua`. У `Scripts/gameplay/root.lua` не остаётся ни одного обработчика — модуль удаляется, как ранее удалилась команда награды.

EventBus остаётся универсальным: для него одинаковы `textsystem:event.location.entered` и `rh:event.quest.rewarded`. Он обеспечивает жизненный цикл, порядок, проверку payload и подписки, но не знает смысла события.

# Part B. TextSystem

## Базовый актор

Минимум: определение, идентичность экземпляра, `current_location` типа `ref_definition<location>`. Параллельного `current_location_id` в designer-facing API не существует.

Операции: `require_location(location)` — ничего не мутирует, даёт типизированный отказ; `move_to(location)` — меняет каноническое состояние и публикует факты входа и выхода.

Дополнительные поля базового актора вводятся только если обязательны для любой текстовой игры. `gold` и `stamina` таковыми не являются и остаются в `rh`.

## Локация

База: связность (`connected_locations`) и экран. Операции `is_connected(target)` и `require_connected(target)`.

Стоимость и допустимость перехода принадлежат игре: `textsystem` знает, что переход возможен, `rh` — чего он стоит.

## Расширение из RH

Отдельной иерархии классов не вводится. `rh` добавляет поля схемным расширением, методы — декоратором, доменные инварианты — managed-операциями.

Дизайнер видит одну сущность и не знает, откуда пришёл каждый член:

```lua
player.current_location      -- textsystem
player.gold                  -- rh
player:require_location(t)   -- textsystem
player:require_gold(10)      -- rh
```

# Part C. RH

Только правила и сущности конкретной игры. Переход объявляется как команда игры:

```lua
commands.travel = function(target)
    player.current_location:require_connected(target)   -- textsystem
    player:require_stamina(5)                           -- rh

    player:spend_stamina(5)                             -- rh
    player:move_to(target)                              -- textsystem
end
```

Перекрытие `core:command.location.travel` удаляется: ядро не владеет геймплейным переходом, а `textsystem` не владеет его ценой.

## Чистка `rh/actors.lua`

Уходит в `textsystem`: `current_location`, `require_location`, `travel`/`move_to`, декоратор определения локации, `is_connected`, `require_connected`, регистрация ссылочного поля локации.

Остаётся в `rh`: золото, выносливость, `add_item` и регистрации игры.

Дополнительно: повторяющаяся проверка суммы сводится к одной функции, а описания ресурсов (поле, код ошибки, имена параметров) — к таблице, чтобы золото и выносливость не были двумя копиями одного кода.

# Part D. Презентация

Презентер локации принадлежит `textsystem`: он собирает экран из описания локации и списка связанных локаций. `rh/scripts/presentation/location_screen.lua` удаляется.

Механизм уже есть — источник презентации регистрируется и вызывается рантаймом после успешного commit. Переносится владение, а не машинерия.

Декларативные экраны становятся возможны: три предусловия закрыты планом [ContentEditorPrerequisites](../../Plans/Archive/ContentEditorPrerequisites/README.md). Схема экрана получает описание, семантические действия и признак «включить переходы в связанные локации».

**Семантическое действие — новый механизм, а не переименование.** Сегодня `action(commands.buy, sword)` возвращает пару `command_id` плюс аргументы. Именованное действие с поздним связыванием (`textsystem:action.location.travel` → `rh:command.travel`) вводит реестр действий, которого нет, и **kind `action`, которого нет в реестре kind**. Добавление kind требует schema binding по [Stable ID Specification](../../Architecture/StableIDSpecification.md). Это отдельная работа, и её нельзя описывать как деталь презентера.

# Part E. Структура пакетов

```text
textsystem/
├── definitions/     базовые схемы: actor, location, screen
├── schemas/
├── localization/
├── package.json5
└── scripts/
    ├── gameplay/    actors, locations
    └── presentation/location_presenter.lua
```

`textsystem` не содержит данных `rh`: ни рынка, ни таверны, ни меча, ни стоимости перехода.

Порядок загрузки: `core`, `textsystem`, `rh`. Цепочка замещения модулей идёт по тому же порядку, поэтому `require_base()` в `rh` даёт версию `textsystem`, а не ядра — это следствие, которое надо учитывать при переносе замещаемых модулей.

# Part F. Тестирование

| Уровень | На чём | Что проверяет |
|---|---|---|
| Core | Абстрактные фикстуры | Рантайм, команды, EventBus, состояние и сейв, репозиторий, Stable ID, примитивы презентации |
| TextSystem | Отдельный пакет-образец | Локация, переход, связность, презентер, сохранение и загрузка |
| RH | Игровой набор | Стоимость перехода, работа, ожидание, покупка, расширения актора |

Требует **карты «подкаталог спеков → конфигурация пакетов»**: сегодня разбиение бинарно. Существующие `world`, `economy`, `actions`, `presentation` разносятся по уровням — это отдельный этап, а не побочный эффект переноса.

Пакет-образец для TextSystem не заводится с нуля: расширяется существующий `sample`, чтобы не держать два демонстрационных пакета.

## Этапы

| Этап | Содержание | Обоснование порядка |
|---|---|---|
| **0** | Набор пакетов собирается из данных; хосты и CLI перестают знать имена пакетов | Без этого этап 1 упирается в правку C++ |
| 1 | Пакет `textsystem` с зависимостью от `core`; поведение `rh` не меняется | Пустой слой проверяет загрузку до переноса |
| 2 | Владение локацией актора: `current_location`, `require_location`, `move_to` | — |
| 3 | Топология локаций: связность, `is_connected`, `require_connected` | — |
| 4 | `rh:command.travel`; удаление `core:command.location.travel`, `core:service.location` и `Scripts/gameplay/root.lua` | После 2 и 3 |
| 5 | Презентер локации переезжает в `textsystem` | — |
| 6 | Декларативные экраны и реестр семантических действий | Предусловия закрыты |
| 7 | Трёхуровневое разбиение спеков | После 1–5 |
| 8 | Чистка `rh/actors.lua` | После 2–4 |

Этап 0 — единственный, без которого не начинается ничего. Этап 1 обязан завершиться зелёным при **пустом** `textsystem`: если трёхзвенный набор работает до переноса, любая поломка на этапах 2–4 однозначно относится к переносу.

Автообнаружение модулей отдельным этапом не идёт — оно реализовано.

## Критерии приёмки

**Core.** В публичном API нет понятий `Actor`, `Location`, `Quest`, `Travel`, `Inventory`, `Gold`, `Stamina`. `Scripts/gameplay/` в ядре отсутствует.

**Пакеты.** Добавление четвёртого пакета не требует ни строки C++. `gv2-content` принимает контейнерный каталог.

**TextSystem.** Локация, переход и презентер работают в пакете-образце без `rh`. Данных `rh` в нём нет.

**RH.** `travel` объявлен игрой; в `actors.lua` нет кода локации; золото и выносливость не являются двумя копиями одного кода; `location_screen.lua` удалён.

**Дизайнер.** В геймплейном коде не видно границы слоёв: `player:require_location(t)` и `player:require_gold(10)` выглядят одинаково.

**Тесты.** Спеки уровня Core проходят без `textsystem` и `rh`; спеки TextSystem — без `rh`.
