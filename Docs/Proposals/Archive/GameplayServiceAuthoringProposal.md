# Предложение по авторскому слою игровых сервисов

> **Предлагает:** авторский синтаксис `services.<name> = { … }` для stateless-процессов, координирующих несколько сущностей, вместе с первым настоящим потребителем — торговцем в пакете `rh`.
> **Затрагивает:** [Commands and Events](../../Architecture/CommandsAndEvents.md), [Lua Runtime Contract](../../Architecture/LuaRuntimeContract.md), [Stable ID Specification](../../Architecture/StableIDSpecification.md).
> **Не является нормативным:** реализовано планом [GameplayServices](../../Plans/Archive/GameplayServices/README.md), актуальное правило — в [Lua Runtime Contract](../../Architecture/LuaRuntimeContract.md).

## 1. Назначение

В рантайме есть реестр игровых сервисов: `register`, `get`, `require`, `exists`, `list`, `freeze`. Авторского API к нему нет, поэтому пакет вынужден знать устройство реестра — ровно то, от чего авторский слой избавил команды, события, действия и методы сущностей.

Предложение добавляет авторский синтаксис:

```lua
services.trade = {
    buy = function(buyer, seller, item) … end,
}
```

Игровой сервис — это **stateless-процесс, координирующий несколько сущностей, когда у операции нет естественного единственного владельца**.

## 2. Отношение к ADR-0026: механизм вводится вместе с потребителем

[ADR-0026](../../ADR/0026-core-and-gameplay-ownership.md) отвергает создание подсистем «заранее», а план TextSystemLayer по этому же правилу отказался вводить Quest foundation: «подсистемы не существует, потребителей нет».

**У реестра сервисов сегодня нет ни одного потребителя.** `game.services` используется только собственной спекой жизненного цикла. Единственный реальный сервис — `core:service.location` — был удалён планом TextSystemLayer, когда владение локацией переехало в `textsystem`, и заменён методами сущностей.

Поэтому авторский слой сервисов не принимается сам по себе. Он принимается **вместе с первым настоящим потребителем**, и потребитель определён конкретно: торговец в пакете `rh`.

Сегодня `rh:command.buy` списывает золото у игрока и создаёт предмет из воздуха. Продавца нет: золото не появляется ни у кого, товар не убывает. Это односущностная операция, и сервис ей не нужен. Потребитель делает её настоящей: у меча и брони появляется владелец — NPC-торговец, который получает золото и теряет товар. Только тогда операция координирует две равноправные сущности и попадает под критерий раздела 4.

Если торговец не появляется в том же плане, предложение не реализуется.

## 3. Не входит

- Второй реестр сервисов или собственный bus: используется существующий `game.services`.
- Сервис как альтернатива команде: сервис не является публичным игровым намерением.
- Состояние внутри сервиса.
- Наследование сервисов и расширение чужого сервиса модом.
- Отдельная транзакционная модель.
- Требование заводить сервис под каждый вспомогательный helper.
- `services.inventory`, `services.combat` и прочие сервисы без потребителя.

## 4. Граница: метод сущности или сервис

Критерий один — естественный владелец операции.

| Условие | Форма |
|---|---|
| У операции есть естественный единственный владелец | Метод сущности: `actor:add_gold(10)`, `actor:move_to(loc)` |
| Назначение операции одной сущности было бы искусственным | Сервис: `services.trade.buy(buyer, seller, item)` |

Критерий формулируется через владение, а не через фиксированный список операций. `actor:move_to(location)` корректно остаётся методом сущности, хотя «перемещение» интуитивно звучит как процесс.

## 5. Место в цепочке

```text
Semantic Input → Command → Validators → Command Handler
    → Gameplay Service → Entity Methods → Canonical State → Commit → Events
```

Сервис исполняется внутри уже открытой транзакции команды. Он не открывает окно мутации, не создаёт отдельный commit и не публикует события немедленно.

## 6. Синтаксис объявления

Объявление атомарно:

```lua
services.trade = {
    buy = function(buyer, seller, item) … end,
    sell = function(seller, buyer, item) … end,
}
```

Распределённая форма `services.trade.buy = …` не поддерживается: она размывает владельца, усложняет проверку дубликатов и заморозку и провоцирует восприятие сервиса как открытого пространства имён.

Вызов использует точку, а не двоеточие: сервис не является экземпляром сущности и не имеет осмысленного `self`.

```lua
services.trade.buy(player, merchant, sword)
```

Форма `service("trade", { … })` отвергнута: в проекте сложился декларативный стиль `commands.foo = …`, `actions.foo = …`, `Actor.foo = …`.

Вызываемый сервис (`services.combat(...)`) не вводится даже для сервиса с одной операцией: рантайм моделирует сервис таблицей, и сервис остаётся пространством операций.

## 7. Идентичность

Объявление `services.trade` в пакете `rh` создаёт `rh:service.trade`. Полный ID для локального сервиса автор не пишет.

Kind `service` **отсутствует** в реестре kinds [Stable ID Specification](../../Architecture/StableIDSpecification.md) и должен быть туда добавлен. Отдельно: `service_registry.register` сегодня проверяет только «непустая строка» — в отличие от `validator_registry`, требующего `stable_id.is_kind(id, "validator")`. Проверка формы ID добавляется в реестр вместе с kind.

Дубликат canonical ID — ошибка bootstrap, а не перекрытие.

## 8. Контракт таблицы сервиса

**Проверяемое гейтом.** Таблица содержит только функции. Поле-значение отклоняется:

```lua
services.trade = {
    tax = 0.1,              -- отклоняется
    buy = function(…) end,
}
```

Причина: сервис не должен становиться вторым, скрытым игровым состоянием.

**Конвенция без гейта.** Захваченные замыканием константы допустимы:

```lua
local BASE_FEE = 10
services.trade = { buy = function(…) … end }
```

Изменяемое захваченное состояние (`local cache = {}` над телом сервиса) нарушает детерминизм, но статически не обнаруживается: проверка «только функции» видит поля таблицы, а не upvalue. Это правило конвенции, и предложение фиксирует его как конвенцию, а не выдаёт за гарантию.

Данные, которые должны пережить операцию, принадлежат каноническому состоянию.

## 9. Неизменяемость после регистрации

```text
объявление → проверка таблицы → неизменяемая обёртка → регистрация → заморозка реестра
```

После регистрации подмена операции отклоняется — и для локального имени, и для канонического:

```lua
services.trade.buy = another_function              -- отклоняется
services["rh:service.trade"].sell = replacement    -- отклоняется
```

Заморозка реестра защищает состав; авторский слой обязан защитить и саму выставленную таблицу. Объявление после заморозки отклоняется типизированной ошибкой.

Обращение к неизвестному локальному имени возвращает не `nil`, а ошибку — по образцу `UnknownCommandKey` в проксе команд.

## 10. Владение и поведение модов

У сервиса один владелец. Мод не дописывает и не заменяет чужой сервис. Если моду нужно изменить поведение:

| Задача мода | Механизм |
|---|---|
| Ограничить команду | Validator |
| Отреагировать на результат | Event Subscriber |
| Добавить поведение сущности | Entity Extension |
| Другой процесс | Собственный сервис |

## 11. Межпакетное обращение и момент разрешения

```lua
local trade = services["rh:service.trade"]
```

**Ссылка на уровне модуля разрешается на заморозке**, когда зарегистрированы сервисы всех модулей. Отсутствующий сервис — ошибка bootstrap с указанием обращающегося пакета и запрошенного ID.

Разрешение в момент вызова отвергнуто: опечатка в ID давала бы отказ в середине команды вместо отказа на старте. Динамический поиск внутри тела функции не запрещён, но не рекомендуется и такой гарантии не даёт.

## 12. Аргументы

Сервис — внутренний вызов Lua→Lua, а не пересечение boundary. Он получает обычные авторские объекты: обёртки акторов, дескрипторы определений, экземпляры, скалярные значения. Приведение к portable-представлению и обратно ради внутреннего вызова не выполняется.

## 13. Мутация, `fail()` и события

Сервис меняет каноническое состояние только внутри активного окна мутации команды. Собственного окна он не открывает; вызов вне команды отклоняется существующими механизмами.

`fail()` и `emit()` доступны в теле сервиса и работают по обычным правилам команды: отказ до мутации, события — после успешного commit.

**Атрибуция следует пакету объявления, а не вызывающему.** Сервис — замыкание в `_ENV` своего пакета, поэтому `fail("trade.item_not_available")` внутри `rh:service.trade` даёт `rh:error.trade.item_not_available` независимо от того, какой пакет вызвал сервис. Это тот же механизм, что у методов сущностей ([ADR-0031](../../ADR/0031-entity-authoring-extensions.md)), и при межпакетных вызовах он становится наблюдаемым, поэтому фиксируется явно.

## 14. Execution scope наследуется от вызывающего

Сервис исполняется в scope вызывающего и не создаёт собственного. Практическое следствие: сервис, вызванный из валидатора, подчиняется ограничениям валидатора.

Формулировка «мутирующий сервис из валидатора завершится ошибкой мутации» недостаточна: она срабатывает, только если сервис действительно пишет в состояние. Сервис, вызывающий `emit(...)` или `commands.*:later(...)`, прошёл бы незамеченным. Поэтому охранники побочных эффектов, вводимые планом [CommandValidators](../../Plans/Archive/CommandValidators/README.md), применяются к телу сервиса так же, как к телу валидатора; «мутирующие точки входа Gameplay Service» из его перечня закрываются этим правилом.

Вложенный вызов сервиса из сервиса — обычный вызов Lua: он не создаёт ни команды, ни окна мутации, ни отдельного commit.

## 15. Первый потребитель: торговец в `rh`

Определение `rh:actor.npc.merchant` уже существует и не участвует ни в чём. План обязан сделать его участником:

- экземпляр торговца существует в состоянии и находится на рынке;
- меч и броня принадлежат торговцу как экземпляры предметов, а не появляются из воздуха;
- покупка проходит через `services.trade.buy(player, merchant, item)`;
- покупатель платит, **продавец получает золото**, товар меняет владельца;
- отсутствие товара у продавца — отказ `fail("trade.item_not_available")` до мутации.

Разделение ответственности при этом становится наглядным:

```text
commands.buy            публичное намерение
validate(...)           независимая политика
services.trade.buy      процесс двух сущностей
actor:spend_gold(...)   поведение одной сущности
emit(...)               зафиксированный факт
```

Операции инвентаря одной стороны (`has_item`, `take_item`, `receive_item`) остаются методами сущности — у них есть естественный владелец. Сервис владеет только координацией.

## 16. Целевой вид

```lua
services.trade = {
    buy = function(buyer, seller, item)
        local price = item.price

        buyer:require_gold(price)
        seller:require_item(item, "trade.item_not_available")

        buyer:spend_gold(price)
        seller:add_gold(price)

        local instance = seller:take_item(item)
        buyer:receive_item(instance)

        emit("trade.completed", {
            buyer = buyer,
            seller = seller,
            item = item,
            price = price,
        })
    end,
}

commands.buy = function(item)
    player:require_location(market)
    services.trade.buy(player, merchant, item)
end
```

## 17. Диагностика

| Ошибка | Условие |
|---|---|
| `InvalidServiceName` | локальное имя не является допустимым сегментом Stable ID |
| `InvalidServiceImplementation` | значение не таблица |
| `ServiceFieldNotFunction` | таблица содержит поле, не являющееся функцией |
| `ServiceDuplicateDeclaration` | повторное объявление сервиса с тем же caноническим ID |
| `ServiceDeclarationAfterFreeze` | объявление после закрытия авторской фазы |
| `ServiceImmutableAfterRegistration` | попытка подменить операцию после регистрации |
| `UnknownServiceKey` | обращение к необъявленному локальному имени |
| `ServiceTargetMissing` | ссылка на несуществующий сервис на заморозке |

## 18. Критерии приёмки

1. Авторское окружение предоставляет `services`; `services.foo = { … }` регистрирует сервис в существующем реестре.
2. Canonical ID локального сервиса генерируется автоматически; kind `service` внесён в реестр kinds, а `service_registry.register` проверяет форму ID.
3. Объявление атомарно; распределённая форма отклоняется.
4. Таблица принимает только функции.
5. Реализация неизменяема после регистрации; объявление после заморозки и обращение к неизвестному имени отклоняются типизированными ошибками.
6. Дубликат canonical ID отклоняется до старта сессии.
7. Межпакетная ссылка на уровне модуля разрешается на заморозке; отсутствующий сервис — ошибка bootstrap.
8. Сервис получает обычные авторские объекты без приведения к portable-представлению.
9. `fail()` и `emit()` из сервиса атрибутируются пакету объявления, а не вызывающему.
10. Сервис наследует execution scope вызывающего; из валидатора запрещённые операции отклоняются так же, как в теле валидатора.
11. Сервис не открывает окно мутации; мутация вне команды отклоняется.
12. Вложенный вызов сервиса не создаёт команды, окна мутации и отдельного commit.
13. Мод не может подменить или дополнить чужой сервис.
14. **Экземпляр торговца существует в состоянии, владеет мечом и бронёй и находится на рынке.**
15. **Покупка проходит через `services.trade.buy`: покупатель платит, продавец получает золото, товар меняет владельца.**
16. **Отсутствие товара у продавца даёт отказ до мутации.**
17. Поведение совпадает в UE и headless; спека одна и исполняется обоими хостами.
