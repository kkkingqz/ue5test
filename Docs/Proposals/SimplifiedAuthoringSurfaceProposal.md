# Предложение по упрощению авторской поверхности

> **Предлагает:** убрать инфраструктурную обвязку из designer-facing Lua и переработать `rh` под неё.
> **Затрагивает:** [Lua Runtime Contract](../Architecture/LuaRuntimeContract.md), [Commands and Events](../Architecture/CommandsAndEvents.md), [Build and Tooling](../Architecture/BuildAndTooling.md).
> **Не является нормативным:** до реализации действует текущий contract.

Продолжение [Designer Lua Authoring](DesignerLuaAuthoringProposal.md). Тот слой убрал из геймплея Stable ID, реестры и конверты; практическая переработка `rh` показала, что осталась вторая половина — обвязка самого слоя.

## 1. Назначение

> **Designer-facing Lua должен быть кодом игры, а не кодом интеграции игры с GV2.**

Contracts, Commands, Events, окно мутации, Stable ID, репозиторий, сейв и детерминизм сохраняются без изменений.

## 2. Состояние на входе

Lua-часть `rh` — 791 строка. По назначению она распределена так:

| Что | Строк | Оценка |
|---|---:|---|
| `gameplay/actors.lua` | 206 | Код программиста, сложность нормальная |
| `services/economy.lua` | 203 | Дублирует методы актора почти целиком |
| `presentation/location_screen.lua` | 106 | В основном статические данные |
| `scripts/manifest.lua` | 77 | Инфраструктура |
| `shop`, `work`, `travel`, `time` | 183 | Правила игры плюс обвязка |
| `gameplay/root.lua` | 16 | Только включение модулей в граф |

Сами правила текущего слайса умещаются в двадцать строк прозы: работать можно только в таверне при выносливости выше пяти; переход стоит пять выносливости и требует связности; покупка требует нужной локации и денег.

Цель не в сокращении строк, а в том, чтобы соотношение перестало быть таким.

Проверено дополнительно:

- `rh:service.economy` используется **только собственной спекой** — удаление стоит переписывания одного файла;
- маршрутизация презентации отсутствует: `UI document: routes, layers, overlays` не реализован, активен один экран за раз;
- загрузчик исполняет модуль через `luaL_loadbufferx` плюс `lua_pcall`, поэтому подмена `_ENV` технически тривиальна.

## 3. Граница предложения

**Part A** — чего не хватает авторской поверхности. **Part B** — переработка `rh` под неё.

Правило разделения: если проблема общая для будущего геймплея, она чинится в слое, а не локальным помощником внутри `rh`.

# Part A. Авторская поверхность

## 4. Окружение authoring-скрипта

Сейчас каждый файл начинается тремя строками обвязки, заканчивается `return M`, а между ними каждое обращение несёт префикс `M.`.

Предлагается класс файлов с собственным окружением:

```text
scripts/authoring/*.lua
```

Файлы этого каталога получают лексическое окружение с именами `commands`, `player`, `world`, `def`, `fail`, `emit`, `on`, `text`, `button`, `show_screen`. Окружение знает namespace пакета, поэтому `commands.work` — это `rh:command.work`, а `def.location("city.tavern")` — `rh:location.city.tavern`.

Дескриптор создаёт загрузчик до исполнения файла, поэтому `return M` не нужен.

### 4.1. Это пересмотр решения, а не новая идея

Два круга назад рассматривались ровно три варианта — runtime-owned globals, пролог из локальных, per-module `_ENV` — и был выбран пролог, **чтобы не менять нормативное правило**.

Расчёт оказался неверен: цена не в одной строке пролога, а в префиксе `M.` на каждой ссылке в каждой строке. Пересмотр законен, но оформляется ADR с указанием, что именно не сошлось.

Полезный нюанс: правило «module source не создаёт globals» остаётся истинным — authoring-скрипт не создаёт глобальных, он читает имена из своего `_ENV`. Править нужно только фразу «Per-module environments в v1 отсутствуют».

### 4.2. Это не sandbox

Окружение существует ради эргономики и не является границей безопасности или владения. Модули программиста продолжают использовать обычное окружение и `require`.

## 5. Автообнаружение модулей

Ручной `manifest.lua` перечисляет `module_id`, `source`, `dependencies` и `replaceable` для каждого файла. Создание геймплейного файла требует правки другого технического файла — для дизайнера это неприемлемо.

Скрипты обнаруживаются инструментом сборки; канонический манифест становится **генерируемым артефактом**. Удаляется ручной источник истины, а не детерминированный граф модулей.

Зависимости выводятся статическим сканом **литеральных** `require(...)`. Динамический `require(variable)` в автообнаруживаемом модуле запрещён.

### 5.1. ID из пути — только для незамещаемых модулей

Для обычного модуля `scripts/runtime/actors.lua` → `rh:module.runtime.actors` безобиден: его ID никто снаружи не называет.

Для `replaceable` — нет. Мод замещает `core:module.gameplay.root`, называя его явно, и цепочка провайдеров входит в `ScriptSetHash`. Переименование файла тихо переименовало бы то, на что нацелен мод.

Поэтому: **ID выводится из пути только для незамещаемых модулей; всё, что помечено `replaceable`, объявляет ID явно.** Дизайнер с этим не сталкивается — замещаемые модули пишет программист.

Тем же рассуждением закрывается вопрос зависимостей замещения: `require_base()` не является литеральным `require` и статическим сканом не находится, поэтому отношение замещения всё равно требует явных метаданных.

### 5.2. Редкие метаданные

`replaceable`, цель замещения и особые зависимости жизненного цикла живут в `package.json5` либо в компактном блоке для программиста. Обычный authoring-скрипт таких сведений не содержит.

## 6. Неявный успех команды

Дизайнер не пишет `{ ok = true, value = … }` для обычного успеха:

```text
return nil        → успех без значения
return value      → успех со значением
return fail(...)  → типизированный отказ
непойманная ошибка → fault команды
```

**Отказом является только объект, произведённый `fail()`.** Любое другое возвращённое значение — значение, даже если у него случайно есть поле `ok`. Без этого правила форма результата стала бы неявно значимой.

## 7. Доменные операции и предусловия

Дизайнер не разбирает результат каждой операции:

```lua
player:spend_gold(item.price)
player:add_item(item)
```

Повторяющиеся предусловия выражаются доменными методами:

```lua
player:require_location(tavern)
player:require_stamina(6)
player:require_gold(item.price)
```

### 7.1. Разделение отказа и ошибки

`require_*` и `spend_*` имеют **разную** семантику:

| Вызов | При невыполненном условии |
|---|---|
| `player:require_gold(10)` | Типизированный отказ команды |
| `player:spend_gold(10)` | **Fault**: предусловие не проверено |

Причина: если `require_*` — санкционированная проверка, то отказ от `spend_*` означает, что дизайнер её забыл. Это ошибка программиста, а не отказ игры, и сообщение должно указывать на пропущенную проверку, а не на нехватку золота.

### 7.2. Границы механизма

Автопродвижение отказа реализуется нелокальным выходом. Следствие, которое надо записать: обёртывание вызова в `pcall` внутри designer-кода перехватит сентинел и сломает механизм.

Правило `AuthoringFailAfterMutation` не меняется: отказ после первой мутации остаётся ошибкой независимо от того, откуда он пришёл. Rollback не вводится.

## 8. Обработчик получает объекты

Сегодня `travel.lua` вручную разбирает транспортный DTO. Такого кода в designer-facing слое быть не должно: канонизация и обратное превращение — обязанность границы слоя.

```lua
function commands.travel(target)   -- target уже DefinitionHandle<Location>
```

Из designer-facing API исчезают формы с `_id` там, где существует объект: остаётся `player.current_location`, возвращающая handle. Canonical ID — внутреннее представление.

Смена локации выполняется доменным методом `player:travel(target)`, который отвечает за изменение состояния и сопутствующие факты; проверка связности остаётся в команде.

## 9. Презентация без участия геймплея

Геймплей не должен знать, после какого изменения нужно перестроить интерфейс. Вызовов вида `build_and_publish_screen()` в командах не остаётся.

### 9.1. Целевая семантика

```text
Command commit → состояние обновлено → презентация инвалидирована
              → активный маршрут заново разрешает желаемое состояние экрана
```

### 9.2. Что делается сейчас, а что после маршрутизации

Маршрутизации не существует: `UI document: routes, layers, overlays` не реализован, активен один экран за раз. Поэтому целевая семантика закладывается **архитектурно**, а работает в упрощённом виде:

- вводится **источник презентации** — зарегистрированная функция, разрешающая желаемый экран из текущего состояния;
- рантайм вызывает её после каждой успешно закоммиченной команды;
- геймплей об этом не знает и ничего не вызывает.

Когда появится UI document, маршрутизатор заменит собой источник презентации, **не затрагивая ни одной строки геймплея** — в этом и состоит смысл закладки.

Оптимизация в v1 не входит: допускается повторное разрешение после каждой команды. Отслеживание зависимостей добавляется позже, семантика для дизайнера не меняется.

## 10. Общие команды вместо команды на товар

`shop.buy_sword` и `shop.buy_armor` вместе с таблицей цен в Lua — неверный уровень абстракции: цена уже лежит в definition предмета.

Остаётся одна `commands.buy(item)`. Добавление товара не создаёт команду и не меняет Lua.

Дублирование доменного API устраняется: `add_gold`/`spend_gold`/`add_stamina`/`spend_stamina`/`add_item` существуют в одном месте — на акторе. Если сложная экономика потребует сервиса, он живёт **под** этими методами, и дизайнер его не видит.

## 11. Декларативные экраны

Статический экран не должен собираться Lua-строителем. Screen definition получает описание, семантические действия и признак «включить переходы в связанные локации»; переходы строит переиспользуемый presenter, читающий `connected_location_ids`.

Связь «действие интерфейса → Action Registry → Command» сохраняется: декларативность экрана не отменяет реестр действий.

### 11.1. Этап заблокирован

Схемные изменения для экранов упираются в те же три предусловия, что и [Content Editor Plugin](ContentEditorPluginProposal.md), раздел 40: правило версионирования схем, правка поля в `Json5AstRewriter`, authoring-метаданные схем.

Раньше них декларативные экраны начинать нельзя.

# Part B. Переработка RH

## 12. Целевая структура

```text
scripts/
    authoring/
        gameplay.lua      -- правила игры
    runtime/
        actors.lua        -- доменные примитивы программиста
```

Отсутствуют: `manifest.lua`, `root.lua`, `economy.lua`, `location_screen.lua`, а также отдельные `shop`, `work`, `travel`, `time` — при нынешнем объёме дробить четыре крошечные команды на четыре модуля незачем. Разделить позже можно без изменения публичных Command ID.

## 13. Целевой gameplay

```lua
local market = def.location("city.market")
local tavern = def.location("city.tavern")

function commands.work()
    player:require_location(tavern)
    player:require_stamina(6)

    player:spend_stamina(2)
    player:add_gold(10)
end

function commands.wait_day()
    player:require_location(tavern)

    player:add_stamina(10)
end

function commands.buy(item)
    player:require_location(market)
    player:require_gold(item.price)

    player:spend_gold(item.price)
    player:add_item(item)
end

function commands.travel(target)
    player:require_stamina(5)
    player.current_location:require_connected(target)

    player:spend_stamina(5)
    player:travel(target)
end
```

Здесь нет: `M`, `return M`, `game.*`, Stable ID, `current_location_id`, разбора DTO, ручного Result, обновления интерфейса, поиска сервисов, регистрации.

## 14. Что остаётся сложным намеренно

`runtime/actors.lua` продолжает заниматься выделением экземпляров, валидацией, декораторами определений, преобразованием типизированных ссылок, реализацией managed-свойств и каноническими ошибками. Это нормальная сложность.

Критерий: **геймдизайнеру не нужно читать этот файл, чтобы добавить контент.**

Не упрощается и то, что является настоящей семантикой: различие `:run()` и `:later()` сохраняется, managed-поля продолжают требовать методов вместо свободного присваивания. Упрощается обвязка, а не смысл.

## 15. Спеки

Authoring-скрипт не возвращает дескриптор и живёт в особом окружении, поэтому спека не может его потребовать через `require`. Правила проверяются **через диспетчеризацию команд**: спека отправляет команду и проверяет результат, состояние и события.

Прямой доступ к телу authoring-функции не предоставляется: если правило нельзя проверить через команду, это признак того, что оно и не является правилом игры.

## 16. Раздел Docs/Authoring

Раздел описывает нынешний синтаксис целиком и после переработки устаревает весь. Он **удаляется** вместе с переработкой и создаётся заново, когда набор команд и доменных методов стабилизируется.

Оставлять его в устаревшем виде хуже, чем не иметь: инструкция, расходящаяся с кодом, дороже отсутствующей.

## 17. Этапы

| Этап | Содержание | Блокировки |
|---|---|---|
| 1 | Окружение authoring-скрипта, прямые имена, неявный успех | ADR по `_ENV` |
| 2 | Автообнаружение, генерируемый манифест, ID из пути для незамещаемых | — |
| 3 | `require_*` и `spend_*` с разделённой семантикой | — |
| 4 | Слияние четырёх модулей `rh` в один authoring-файл | 1–3 |
| 5 | Единый доменный API, удаление `economy.lua` | 3 |
| 6 | Источник презентации и автоматическая инвалидация | — |
| 7 | Декларативные экраны, удаление `location_screen.lua` | Три предусловия редактора |

Этапы 1–6 самодостаточны. Этап 7 ждёт чужой работы и выносится отдельно, чтобы план не висел незакрытым из-за него.

## 18. Не входит

Отдельный DSL; отказ от Lua; rollback состояния; отмена Commands и Validators; изменение грамматики Stable ID; хранение definitions в Lua; обход репозитория; автоматический выбор между `run` и `later`; перенос авторитета геймплея в UE.

## 19. Критерии приёмки

**Авторская поверхность.** Designer-facing команда не содержит `M.`, `game.*`, литералов Stable ID, `current_location_id`, конвертов результата, ручной регистрации, разбора транспортного DTO и вызовов обновления интерфейса.

**Модульная система.** Добавление designer-файла не требует правки манифеста, списка модулей, списка зависимостей и `root.lua`. Инструмент строит детерминированный канонический манифест сам.

**RH.** `manifest.lua`, `root.lua`, `economy.lua` удалены; `shop.buy_sword` и `shop.buy_armor` заменены общей `buy(item)`; цена берётся только из definition; команды не вызывают код презентации; `current_location_id` в designer-коде отсутствует; `travel` получает handle; добавление товара не требует Lua; сейв и `state_hash` сохраняют прежние гарантии.

**Читаемость.** Основной геймплей понятен человеку, знающему базовый Lua и правила игры, без знания внутреннего устройства GV2.
