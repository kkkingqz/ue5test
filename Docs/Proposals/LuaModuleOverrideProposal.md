# Предложение по замещению Lua-модулей

> **Предлагает:** замещение Lua-модуля пакетом с доступом к замещённой реализации.
> **Затрагивает:** [Lua Runtime Contract](../Architecture/LuaRuntimeContract.md), [Modding](../Architecture/Modding.md).
> **Не является нормативным:** до реализации действует текущий contract.

## Назначение и область

Предлагается дать пакету две возможности над Lua-кодом: полностью заместить модуль ядра и расширить его, не переписывая. Обе реализуются **одним механизмом** — замещением с доступом к базовой реализации: не вызвал базу — получилась замена, вызвал — расширение.

Это переносит на модули правило, уже действующее для definitions: побеждает последний провайдер, override заменяет запись целиком, deep merge отсутствует ([INV-010](../Architecture/Invariants.md)). Мутация чужих таблиц экспорта не вводится и закрывается.

Предложение не занимается обнаружением пакетов, порядком загрузки и lock-файлом — это [ModPackageLifecycleProposal](ModPackageLifecycleProposal.md), от которого настоящее предложение зависит.

## Исходное состояние

Проверено на рантайме экспериментом (временное дерево скриптов, `gv2-headless --check-scripts`):

- Таблица экспорта загруженного модуля **мутируема**: модуль может подменить чужую функцию и добавить своё поле, и это видят все последующие модули. Отказа нет. `__newindex` стоит только на `game.repository` и `game.save_slots`, `freeze` — только на реестрах `game`.
- Мутировать можно и модуль ядра: `core:module.runtime.mutation_window` патчится так же беспрепятственно, как геймплейный модуль.
- Единственный существующий заслон: `require` разрешён только для объявленной прямой зависимости. Патч без объявления отвергается на загрузке. Но объявленный патч неотличим в манифесте от обычного чтения.

То есть неконтролируемое расширение уже возможно; предложение заменяет его контролируемым и закрывает текущий путь.

## Владение и источники истины

- Манифест пакета владеет тем, какие `module_id` пакет предоставляет.
- Манифест ядра владеет тем, какие его модули разрешено замещать.
- Загрузчик владеет резолюцией `module_id` в цепочку провайдеров и порядком исполнения.
- Run manifest владеет идентичностью фактически исполненного набора скриптов.
- Пакет не владеет содержимым чужих таблиц экспорта — ни своим, ни ядра.

## Резолюция модуля

`module_id` резолвится по порядку загрузки пакетов; побеждает последний провайдер. Порядок — тот же, что для definitions: ядро, затем включённые моды в явном пользовательском порядке.

Правила заимствуются у definitions без изменений:

- Пакет объявляет `core:module.*` только как замещение. Если ни один ранний провайдер не дал такого `module_id`, кандидат получает диагностику класса `foreign_new_id` — то же правило, что запрещает создание нового `core:*` ID из мода.
- Два провайдера одного `module_id` внутри одного пакета остаются fatal duplicate.
- Невалидное замещение блокирует кандидат целиком; откат к замещённой реализации запрещён.
- Диагностика содержит package ID, package-relative source и `module_id`.

## Замещаемость

Дескриптор модуля в манифесте объявляет `replaceable`. **По умолчанию модуль запечатан.** Попытка заместить запечатанный модуль — типизированный отказ `LuaModuleSealed` с блокировкой кандидата.

Стартовая разметка ядра:

| Каталог | Замещаемость |
|---|---|
| `runtime/`, `boundary/`, `bootstrap/` | Запечатано |
| `gameplay/`, `debug/` | Замещаемо |
| `presentation/`, `resources/` | Запечатано до появления конкретной потребности |

Расширять список замещаемого дешевле, чем сужать: снятие пометки ломает уже написанные моды.

Это делает границу движка и игры свойством рантайма, а не соглашением: ядро, на котором стоят детерминизм, окно мутации и сейв, замещению не подлежит.

## Доступ к базе

Загрузчик публикует глобальную функцию `require_base()` рядом с уже существующей `require`. Она валидна только во время инициализации замещающего модуля и возвращает таблицу экспорта предыдущего победителя в цепочке. Вызов из любого другого места — `LuaModuleBaseNotAvailable`.

Идиома расширения:

```lua
local base = require_base()

local M = setmetatable({ id = "core:module.gameplay.root" }, { __index = base })

function M.handle_command(request)
    if request.command_id == "mymod:command.craft" then
        return craft(request)
    end
    return base.handle_command(request)
end

function M.register(ctx)
    base.register(ctx)
    -- собственные регистрации мода
end

return M
```

Идиома полной замены — тот же файл без `require_base()` и без `__index`.

`setmetatable(M, { __index = base })` обязателен для расширения: без него мод молча потеряет часть поверхности базового модуля. Это документируется в guide, а не проверяется рантаймом — предсказать нужную поверхность загрузчик не может.

## Семантика цепочки

- Базовый source исполняется ровно один раз и до замещающего.
- Модулем становится таблица победителя. Базовая таблица не регистрируется как модуль и доступна только через `require_base()`.
- `require(id)` из любого другого модуля всегда возвращает победителя, независимо от глубины цепочки.
- Хуки жизненного цикла (`register`, `migrate_state`, `restore_instances`) вызываются **только у победителя**. Делегирование базе — явный вызов, а не автоматика: иначе полная замена невозможна.
- Второй замещающий пакет получает базой таблицу первого. Цепочка детерминирована порядком пакетов.
- Регистрация в реестрах `game` разрешена только внутри хуков. Побочные эффекты на верхнем уровне модуля при замещении исполнятся и у базы, и у победителя — это правило фиксируется контрактом явно.

## Граф зависимостей

Эффективный набор зависимостей замещённого модуля — **объединение объявленных по всей цепочке**. Базовый source исполняется и вызывает свои `require`, поэтому его зависимости обязаны быть загружены, даже если замещающий пакет о них не знает.

Проверки missing/duplicate/cycle/reachability выполняются на объединении, до инициализации первого модуля. Замещающий модуль объявляет только свои прямые зависимости.

## Заморозка таблиц экспорта

После возврата таблицы модуля загрузчик ставит на неё метатаблицу с `__newindex`, дающим типизированную ошибку `LuaModuleExportFrozen`, и `__metatable = false` — тот же приём, что уже применён к `game.repository`. Базовая таблица замораживается так же.

Заморозка не мешает использовать базу целью `__index`: защищается сама таблица, а не её чтение.

Это закрывает патч экспортов, оставшийся единственным неконтролируемым путём расширения. Перед включением требуется убедиться, что ни один текущий модуль не пишет в таблицу экспорта после инициализации; этап выполняется отдельно и первым.

## Детерминизм

`FRunManifest` сегодня фиксирует `LuaReleaseNumber`, `RepositoryContentHash`, seed и принятые команды. Набор скриптов он не фиксирует: пока Lua лежит только в `Scripts/`, это терпимо, но как только модуль может приехать из пакета, замещение молча меняет прогон.

Предлагается добавить `ScriptSetHash` — канонический хэш по упорядоченному списку `(module_id, [(package_id, source_hash), …])` для всей цепочки каждого модуля. Расхождение при replay даёт отказ того же класса, что существующий `lua_release_mismatch`.

`--check-scripts` печатает цепочки замещений: без этого отладка мода, замещённого другим модом, сводится к угадыванию.

## Сейв

Save metadata уже обязана хранить enabled mods, order, versions и fingerprints ([Modding](../Architecture/Modding.md)). В fingerprint входит `ScriptSetHash`: сейв, снятый с замещённым `core:module.gameplay.root`, обязан быть отличим от сейва без мода.

Отсутствие замещающего пакета при загрузке обрабатывается общим правилом отсутствующего мода и не превращается в тихий откат на базовую реализацию.

## Обнаружение скриптов в пакете

Сейчас оба хоста рекурсивно собирают `Scripts/` из корня проекта: UE — `FPaths::ProjectDir()/Scripts`, headless — рабочий каталог. Скрипты внутри пакета не обнаруживаются вообще.

Требуется:

- обнаружение `scripts/` внутри пакета в `GV2ContentHostSupport` (filesystem-часть, вне portable core по [ADR-0019](../ADR/0019-content-host-support-module.md));
- атрибуция source пакетом: имя источника становится `@<package_id>/<relative>` вместо `@Scripts/<relative>`, чтобы стек и диагностика показывали владельца;
- отказ обоих хостов от жёстко зашитого корня в пользу набора пакетов.

## Типизированные отказы

| Код | Когда |
|---|---|
| `LuaModuleSealed` | Пакет замещает запечатанный модуль |
| `LuaModuleForeignNewId` | Пакет объявляет `core:module.*`, которого не дал ранний провайдер |
| `LuaModuleBaseNotAvailable` | `require_base()` вне инициализации замещающего модуля |
| `LuaModuleExportFrozen` | Запись в таблицу экспорта после инициализации |

## Требуется ADR

Реализация меняет семантику загрузчика модулей и уточняет [INV-006](../Architecture/Invariants.md): замораживаются не только реестры `game`, но и таблицы экспорта. До начала работ создаётся ADR, фиксирующий: замещение как единый механизм для замены и расширения, запрет мутации экспортов, запечатанность по умолчанию и правило «хуки только у победителя». Затронутые contracts — `LuaRuntimeContract` и `Modding` — обновляются синхронно.

## Этапы внедрения

**M1. Заморозка и разметка.** Заморозить таблицы экспорта, ввести `replaceable` в дескриптор манифеста и разметить ядро. Новой возможности не появляется — это защита. Выполняется первым и отдельно, потому что несёт единственный риск регресса.

**M2. Замещение и база.** Резолюция `module_id` по провайдерам, `require_base()`, семантика цепочки, объединение зависимостей, типизированные отказы. Проверяется Lua-спеками с синтетическим вторым провайдером, без реальных пакетов.

**M3. Скрипты в пакете.** Обнаружение `scripts/` внутри пакета, атрибуция source, отказ хостов от зашитого корня, фикстура реального мод-пакета, исполняемая обоими хостами.

**M4. Детерминизм и сейв.** `ScriptSetHash` в run manifest и в save fingerprint, вывод цепочек в `--check-scripts`, cross-host parity замещённого набора.

Каждый этап оставляет ровно один reference execution path: промежуточное состояние, где часть модулей резолвится по-старому, а часть по-новому, не допускается.

## Польза, риски и трудоёмкость

**Польза.** Геймплей выносится в отдельный пакет без C++; расширение и замена получают одну модель вместо двух; неконтролируемый патч закрывается; замещение попадает в run digest и сейв, а не остаётся невидимым.

**Трудоёмкость:** **L** — затрагивает загрузчик в `GV2RuntimeCore`, обнаружение в `GV2ContentHostSupport`, оба хоста и run manifest.

**Риск: мод ломается при переименовании в ядре.** Мод, вызывающий `base.handle_command`, зависит от имени, которое никто не версионирует. Мера: замещение — не первый выбор; для добавления команд, валидаторов, сервисов и подписок предпочтительны реестры, где мод не знает внутренних имён. Замещение остаётся для случаев, где реестра нет по форме задачи.

**Риск: заморозка экспортов ломает существующий код.** Мера: отдельный первый этап, полный прогон conformance и Lua-спеков до перехода к M2.

**Риск: двойное исполнение побочных эффектов.** Базовый и замещающий source исполняются оба. Мера: правило «регистрация только в хуках» фиксируется контрактом и покрывается негативной спекой.

**Риск: цепочка из нескольких модов неотлаживаема.** Мера: `--check-scripts` печатает цепочку по каждому замещённому `module_id` в M4.

**Риск: замещаемость расползётся.** Каждый новый `replaceable` — это публичное обязательство. Мера: пометка ставится по конкретной потребности, а не заранее.

## Не входит в предложение

- Патч таблиц экспорта в любом виде, включая объявленный в манифесте — закрывается на M1.
- Декораторы по именам функций (регистрация обёрток в рантайме). Механизм ортогонален замещению и добавляется поверх, если гранулярность модуля окажется крупна. Сейчас потребности нет.
- Замещение модулей ядра.
- Проверка того, что замещающий модуль сохранил поверхность базового.
- Hot reload и подмена модуля в активной сессии: изменение набора модулей по-прежнему требует полного restart сессии.
- Sandbox для враждебного кода; trust model из [Modding](../Architecture/Modding.md) не меняется.
- Обнаружение пакетов, порядок загрузки и lock-файл — [ModPackageLifecycleProposal](ModPackageLifecycleProposal.md).

## Критерии приёмки

- Пакет замещает `core:module.gameplay.root` и полностью заменяет поведение, не вызывая базу.
- Пакет замещает тот же модуль, вызывает `require_base()` и делегирует базе необработанные команды.
- Два пакета, замещающие один `module_id`, выстраиваются в цепочку по порядку пакетов; результат детерминирован и не зависит от порядка файлов.
- Замещение запечатанного модуля отвергается `LuaModuleSealed` с блокировкой кандидата.
- `core:module.*` без раннего провайдера отвергается как `foreign_new_id`.
- Запись в таблицу экспорта после инициализации отвергается `LuaModuleExportFrozen`.
- Хуки жизненного цикла вызываются только у победителя; негативная спека покрывает отсутствие автоматического вызова базовых хуков.
- Зависимости базы загружаются, даже если замещающий пакет их не объявил; цикл по объединению цепочки отвергается до инициализации.
- Одинаковый набор пакетов даёт одинаковый `ScriptSetHash` в UE и headless; замещение модуля меняет хэш и обнаруживается при replay.
- Правила, выразимые в Lua, проверяются Lua-спеками ([ADR-0024](../ADR/0024-lua-spec-runner.md)); C++ проверяет только резолюцию провайдеров, заморозку и хэш.
