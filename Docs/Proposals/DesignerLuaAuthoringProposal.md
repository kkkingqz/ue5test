# Предложение по designer-facing Lua

> **Предлагает:** слой поверх фасада `game`, на котором геймдизайнер пишет обычный Lua, не видя Stable ID, реестров, конвертов команд и presentation DTO.
> **Затрагивает:** [Lua Runtime Contract](../Architecture/LuaRuntimeContract.md), [Commands and Events](../Architecture/CommandsAndEvents.md), [Canonical State and Save](../Architecture/CanonicalStateAndSave.md).
> **Не является нормативным:** до реализации действует текущий contract.

Документ заменяет `Human-Friendly Gameplay Authoring Layer v2` и `Designer-Friendly Lua Gameplay Authoring` — обсуждение по ним сведено здесь в принятые решения. Визуальный frontend — в [Content Editor Plugin](ContentEditorPluginProposal.md).

## Граница слоёв

```text
UE Content Editor / JSON5          Designer Lua
─────────────────────────          ────────────────────────────
создать тип                        получить сущность
добавить поля                      читать и менять runtime state
создать static definition          писать Commands
                                   вызывать методы
                                   Events
                                   Screens
```

Определения не создаются из Lua. Дизайнер почти не видит JSON5, потому что заводит сущности через редактор; Lua получает уже существующие.

## Состояние на входе

Проверено по коду; часть предложений предыдущих редакций опиралась на неверную картину.

- Снимок репозитория строится **до создания Lua VM**; `gv2-content` не линкует VM вовсе. Объявление definitions из Lua несовместимо с этим порядком.
- `game.commands.execute` не существует. Есть `game.runtime.dispatch_command`, `game.commands.enqueue`, `.handlers`, `.validators`.
- Отката состояния нет. При типизированном отказе откатываются только факты (`event_bus.rollback_command_context`); мутации остаются.
- Валидаторы исполняются **до открытия окна мутации**, поэтому отказ валидатора и отказ из тела обработчика — разные вещи.
- Payload события отвергает любую таблицу с метатаблицей — обёртки передать нельзя.
- `mutation_window` знает только `window_open`; признака «была запись» нет.
- `unwrap_state` вызывается ровно из двух спеков и **ни из одного продакшн-модуля**; `is_guarded` не вызывается нигде. Продакшн-валидация состояния получает сырое дерево из C++.
- Канонические секции: `meta`, `player`, `actors`, `item_instances`, `world`, `quests`, `mods`. Секции для runtime-состояния, привязанного к definition, нет.
- Раздельные типы текста: `TextSpec` требует canonical `text_id` kind `text`; сырая строка им не станет.
- `debug` не открыт, поэтому имя Lua-функции получить нельзя.

## Принятые решения

### Идентичность и регистрация

- **Команда именуется ключом таблицы, а не именем функции.** `commands["shop.buy"] = function(item) … end` → `rh:command.shop.buy`. Переименование локальной helper-функции ничего не меняет; `debug` не нужен; опубликованный ID не зависит от рефакторинга.
- **Регистрация отложена до фазы `register`.** `commands` во время загрузки модуля — не реестр, а authoring-дескриптор. Адаптер обходит дескриптор на фазе `register` и выполняет настоящую регистрацию, после чего реестры замораживаются. Тем же способом объявляются подписки: `on(...)` тоже накапливается в дескрипторе, а не регистрируется на месте.
- **Definition-хэндлы можно захватывать при загрузке модуля, instance-хэндлы — нельзя.** Определения закреплены на сессию, обёртки одноразовы. `player` и подобные — аксессоры, разрешающие экземпляр на каждое обращение, а не значения, сохранённые при загрузке.

### Отказ команды

- **`fail()` до первой мутации** — обычный типизированный отказ обработчика. Это **не валидатор**: настоящие валидаторы остаются programmer API для модов, перехвата, приоритетов и межмодульных проверок.
- **`fail()` принимает ключ ошибки и параметры, а не текст.** `fail("travel.insufficient_stamina", { current = …, required = 5 })` даёт `rh:error.travel.insufficient_stamina`. Пользовательский текст живёт отдельно как `rh:text.error.travel.insufficient_stamina` и локализуется общим путём — иначе правило «в геймплейном коде нет пользовательских строк» нарушается первым же отказом.
- **`fail()` после первой мутации** — `AuthoringFailAfterMutation`, ошибка программиста, а не отказ. Сообщение называет команду и требует перенести проверки выше первой мутации.
- Признак даёт **сам runtime**: `mutation_window` ведёт монотонный `write_revision`, увеличиваемый в `__newindex` guarded-прокси. Обработчик запоминает значение на входе, `fail()` сравнивает. Счётчик считает любую запись в канонический state независимо от того, кто её сделал — дизайнер, доменный метод или сервис.

### Виды property

Схема объявляет для каждого поля **хранилище** и **политику записи**.

| Вид | Хранилище | Чтение | Запись |
|---|---|---|---|
| Definition | Снимок репозитория | да | нет — `Cannot modify definition field` |
| Plain state | Каноническое состояние | да | прямое присваивание; схема проверяет тип, nullable, kind ссылки, min/max, enum |
| Managed state | Каноническое состояние | да | только через зарегистрированную операцию |

```lua
print(aria.name)          -- definition, чтение
aria.morale = 40          -- plain state
aria.gold = 100           -- отказ: managed
aria:add_gold(10)         -- managed, штатный путь
```

Managed выбирается там, где у поля есть доменные инварианты. Политику можно ужесточить позже (`Plain` → `Managed` с регистрацией сеттера), не трогая место хранения.

### Динамические поля у definition-kind

`market.owner = aria` допустимо, если `owner` объявлен полем со `Storage: Runtime State`. Такое состояние живёт в **одной универсальной секции**, а не в секции на каждый kind: иначе добавление поля новому виду сущности потребует правки ядра, чего мы избегаем.

Секция ключуется по `definition_id` и валидируется динамически — по реестру полей, а не по литералу в `state_validator`. Реестр заполняется пакетом, как реестр ссылочных полей из CBM-10.

### Локация персонажа

Локация — свойство персонажа. Единственное хранимое поле — `player.current_location`; `world.current_location` остаётся **read-only аксессором** к нему.

Хранить оба нельзя: два представления одного факта войдут в канонический хэш и в сейв и рано или поздно разойдутся, дав два разных ответа на вопрос «где игрок».

### Исполнение команд

Различие времени исполнения видимо в коде, а не выводится из контекста:

```lua
commands.buy:run(sword)          -- синхронная диспетчеризация, собственное окно мутации
commands.reward:later(aria, 10)  -- отложенно, своё окно после текущей команды
action(commands.buy, sword)      -- ничего не исполняет, только связывает
```

`:run()` — синхронная канонная диспетчеризация: команда получает **собственное** окно мутации. Вызов `:run()` из активного обработчика запрещён как вложенная диспетчеризация (`CommandDispatchReentrant`) — это уже поведение рантайма, а не новое правило. Внутри команды композиция делается вспомогательными функциями, доменными методами и сервисами; другую команду планируют через `:later()`.

Автоматический выбор между `run` и `later` отклонён: команда, отложенная из подписчика, исполняется в другом окне мутации, и скрывать это значит делать поведение зависимым от невидимого контекста.

Обычные вспомогательные функции командами не становятся и вызываются как обычный Lua.

### События

`emit(name, payload)` разворачивает обёртки в canonical ID перед публикацией и сворачивает обратно при доставке — иначе конверт отвергнет payload. Следствие, которое фиксируется явно: **подписчик получает свежую обёртку, читающую текущее состояние**, а не снимок на момент публикации. Для post-commit фактов это верное поведение, но оно должно быть записано, а не обнаружено.

### Текст

Пользовательские строки не пишутся в геймплейном коде:

```lua
button(text("market.buy_sword"), action(commands.buy, sword))
```

Отдельный инструмент собирает литеральные вызовы `text(...)`, у которых нет записи в PO-каталоге, и дописывает их. Границы инструмента: он видит только литеральные аргументы (`text(prefix .. name)` не найдётся) и обязан создавать не только запись перевода, но и сам `text`-definition, иначе ссылка не разрешится.

### Изоляция сырого состояния

Ни один геймплейный модуль, доменный метод или сервис не получает сырое каноническое состояние: все пишут через guarded-представление, и потому все проходят проверку окна и увеличивают `write_revision`.

`unwrap_state` становится runtime-internal и возвращается отдельным `admin`-handle по образцу реестра подписчиков; `guard_state` остаётся в экспорте — его вызывает C++. После заморозки таблиц экспорта ([ADR-0025](../ADR/0025-lua-module-replacement-and-export-freezing.md)) заново опубликовать `unwrap` подменой чужого экспорта невозможно, поэтому изоляция структурная, а не декоративная.

Стоимость перехода мала: продакшн-Lua `unwrap_state` не использует, затронуты два спека.

### Доступ к именам

Designer-facing имена (`fail`, `emit`, `on`, `commands`, `player`, `world`) не становятся глобальными: правило «module source не создаёт globals» остаётся, per-module окружения в v1 отсутствуют. Имена берутся прологом из дескриптора модуля:

```lua
local M = rh.gameplay()
local fail, emit, on, commands = M.fail, M.emit, M.on, M.commands
local player, world = M.player, M.world
```

Одна строка против изменения нормативного правила.

### Совместимость

**До production-релиза обратная совместимость не поддерживается.** Сейв, снятый другой версией, может не грузиться; переименование чего угодно допустимо. Это снимает миграции с самых дорогих пунктов — универсальной секции состояния и переноса локации на актора.

Правило действует **только до релиза**. После него включается [ADR-0023](../ADR/0023-stable-id-publication-freeze.md) и версии секций начинают что-то значить.

## Целевой вид файла

```lua
local M = rh.gameplay()
local fail, emit, on, commands = M.fail, M.emit, M.on, M.commands
local player = M.player

local tavern = rh.def.location("city.tavern")

commands.travel = function(target)
    if player.stamina < 5 then
        return fail("travel.insufficient_stamina", {
            current = player.stamina,
            required = 5,
        })
    end
    if not player.current_location:is_connected(target) then
        return fail("travel.not_connected", { target = target })
    end

    player:spend_stamina(5)
    player.current_location = target

    emit("location.enter", { actor = player, location = target })
end

on("quest.reward_aria", function()
    commands.reward_actor:later(M.actor("aria"), 10)
end)

return M
```

`is_connected` — метод definition-обёртки. Это **вторая категория декораторов**: сегодня `register_type` даёт методы экземплярам актора, здесь нужны методы definition-kind. Реестр симметричен первому и должен вводиться вместе с ним, иначе разъедется по форме.

## Уточнения, обязательные до реализации

Семь мест, которые текст подразумевал, но допускал две разные реализации.

### Граница канонизации аргументов

Правило симметрично событиям и действует **рекурсивно по таблицам аргументов**: на границе слоя обёртка разворачивается в canonical ID, на входе в обработчик ID снова превращается в свежую обёртку.

```text
commands.buy:run(sword)          →  sword  → rh:item.weapon.iron_sword
commands.reward:later(aria, 10)  →  aria   → actor@42  → переносимый DTO в очереди
```

Для `:later()` это обязательно: положить одноразовую обёртку в очередь нельзя.

**Проверено: сегодня аргументы команды не проверяются на переносимость вовсе.** `validate_request` убеждается только, что `args` — таблица. Обёртка дошла бы до очереди и до run manifest, где аргументы сериализуются в канонический JSON. То есть дыра существует и без designer-слоя.

Проверка переносимого значения уже написана для конверта события (`event_envelope`, локальная `freeze_table`). Заводить вторую копию для аргументов и третью для очереди не следует: правило одно, реализация должна быть одна.

### Два типа ссылок в схеме

«Ссылка на сущность» неоднозначна, поэтому вводятся два типа:

| Тип | Хранится | Чтение возвращает |
|---|---|---|
| `ref_definition<actor>` | `rh:actor.aria` | definition-обёртку |
| `ref_instance<actor>` | `actor@42` | свежую runtime-обёртку |

Следствие, которое нужно заложить сразу: **instance-ссылки требуют проверки ссылочной целостности при удалении**. Сегодня `actor_registry.remove` вручную обходит `item_instances[*].owner_id` и поля квестов. С произвольными `ref_instance` в универсальной секции этот обход обязан стать реестро-ориентированным, иначе удаление актора оставит висячие ссылки, которых валидатор состояния не увидит.

### Проверка при записи plain-поля

Порядок строгий:

```text
кандидат → проверка схемы → запись → write_revision++
                  ↓
             отказ: записи нет, счётчик не растёт
```

`aria.morale = -500` при `min = 0` даёт типизированный authoring-отказ **до** изменения состояния.

**Где живёт эта проверка — не в окне мутации.** `mutation_window` guard-ит `game.state` целиком и о схемах не знает; чтобы проверять поле, ему нужна карта «путь → схема», а это заметно тяжелее. Ответственности делятся так:

| Слой | Отвечает за |
|---|---|
| Окно мутации | разрешение на запись и `write_revision` |
| Authoring-обёртка поля | тип, nullable, kind ссылки, min/max, enum |

Прямая запись программиста в `game.state` минует схемную проверку, но не минует разрешение и счётчик. Это осознанная граница, а не упущение.

Коллекции из этого следуют: `dog.accepted_food` обязан возвращать authoring-обёртку с `add`/`remove`, проверяющую элемент по схеме. `table.insert` на guarded-таблице пройдёт разрешение и увеличит счётчик, но схему не проверит — значит либо коллекция перехватывает вставку, либо это документированное неохраняемое место.

### Штатные операции managed-поля объявлены схемой

```text
gold:
    Storage: Runtime State
    WritePolicy: Managed
    Operations: [add_gold, spend_gold]
```

Тогда отказ имеет формальный источник:

```text
'gold' is managed. Use add_gold() or spend_gold().
```

Дополнение: на фазе freeze рантайм обязан проверить, что каждая объявленная операция действительно существует на обёртке соответствующего discriminator. Иначе сообщение будет советовать несуществующий метод — а это худший вид диагностики.

### Минимальная форма presentation

```lua
show_screen {
    template = core.screen("menu"),
    description = text("market.description"),
    buttons = {
        button(text("market.buy_sword"), action(commands.buy, sword)),
        button(text("market.go_tavern"), action(commands.travel, tavern)),
    },
}
```

`action()` принимает **дескриптор команды и переносимые аргументы**, а не произвольное замыкание. Иначе из него нельзя получить semantic input, который является парой `command_id` + canonical args. Аргументы канонизируются тем же правилом границы, поэтому `action` и `:later()` устроены одинаково.

### Отказ несёт ключ, а не текст

```lua
return fail("travel.insufficient_stamina", {
    current = player.stamina,
    required = 5,
})
```

→ `rh:error.travel.insufficient_stamina`, параметры уходят в конверт отказа.

Текст для игрока — отдельный `rh:text.error.travel.insufficient_stamina`. Соответствие «код ошибки → текст» задаётся соглашением об именовании и должно быть записано: presentation обязан знать правило, а инструмент сбора текстов — собирать и тексты ошибок наравне с текстами интерфейса.

### Таблица возвращаемых типов

Неоднозначность «`rh.location(...)` — definition, а `rh.actor(...)` в примере — экземпляр» устраняется тем, что кэшируемость видна в имени:

| Вызов | Возвращает | Можно кэшировать при загрузке модуля |
|---|---|---|
| `rh.def.location("city.tavern")` | `DefinitionHandle<Location>` | да |
| `rh.def.item("weapon.sword")` | `DefinitionHandle<Item>` | да |
| `rh.def.actor("aria")` | `DefinitionHandle<Actor>` | да |
| `M.actor("aria")` | свежая `RuntimeActor` | нет |
| `M.player` | динамический аксессор | нет |

Правило одной фразой: **всё под `rh.def.*` закреплено на сессию и кэшируемо; всё остальное разрешается на каждое обращение.** При появлении экземпляров предметов различие станет ежедневным, поэтому оно вводится сразу, а не когда заболит.

## Отклонено

Из предыдущих редакций отклонено всё, что меняло формат статических definitions.

| Предложение | Причина |
|---|---|
| Объявление definitions из Lua | Снимок строится до создания VM; `gv2-content` не линкует Lua; `repository_content_hash` стал бы зависеть от исполнения Lua |
| Вывод `namespace`/`kind`/`path` из пути файла | Противоречит «Kind не выводится из directory» и «`definition_type` не выводится из filename/path» |
| Упрощённый конверт без `schema_version`/`type`/`definitions` | Конверт закрыт |
| Ссылки вида `location:tavern` | Не сокращение Stable ID, а другая нотация: грамматика требует `namespace:kind.path` |
| `command(work)` с выводом имени из функции | `debug` не открыт; переименование функции меняло бы опубликованный ID |
| Автовыбор между `run` и `later` | Скрывает смену окна мутации |
| Присваивание в поле definition | Снимок неизменяем на сессию |
| Сырые строки в presentation | Обходит локализацию |

Формат ссылок остаётся единым: `rh:location.city.tavern` в файлах, диагностике и инструментах. Сокращения существуют только как аргументы функций слоя.

## Проверки

Всё выразимо в Lua, кроме `write_revision` и изоляции `unwrap_state` — они в модулях ядра, но тоже проверяются спеками ([ADR-0024](../ADR/0024-lua-spec-runner.md)).

Обязательные случаи:

- `fail()` до мутации — отказ; после — `AuthoringFailAfterMutation`;
- `write_revision` растёт при записи через доменный метод и через сервис, а не только через прямое присваивание;
- **`table.insert`/`table.remove` на guarded-таблице проходят через `__newindex`** — если нет, дыра и в разрешении на запись, и в счётчике;
- идемпотентная запись (`x = x`) считается мутацией — поведение фиксируется спекой, а не обнаруживается;
- запись в definition-поле отклоняется; в managed-поле отклоняется с указанием штатной операции;
- `emit` с обёрткой в payload проходит, подписчик получает обёртку;
- команда, зарегистрированная из дескриптора, доступна после freeze; попытка добавить её после — отказ;
- сокращённая форма ссылки в `GameData/` отвергается валидацией контента;
- обёртка в аргументах команды разворачивается в ID, а обработчик получает свежую обёртку — и для `:run()`, и для `:later()`, и рекурсивно по вложенным таблицам;
- непереносимое значение в аргументах отвергается тем же правилом, что и в payload события;
- отклонённая запись plain-поля не меняет ни состояние, ни `write_revision`;
- элемент, добавляемый в коллекцию, проверяется по схеме;
- удаление сущности с живой `ref_instance` на неё отклоняется;
- объявленная операция managed-поля существует на обёртке — проверяется на freeze.

Эксклюзивность `write_revision` внутри команды держится на трёх правилах: вложенный dispatch запрещён, подписчики исполняются при закрытом окне, отложенные команды получают своё окно. Обоснование записывается рядом со счётчиком — при ослаблении запрета вложенности правило `fail()` сломается тихо.

## Этапы

1. **Фундамент в ядре.** `write_revision` в окне мутации, `unwrap_state` в admin-handle, спеки на оба.
2. **Дескриптор и команды.** `rh.gameplay()`, `commands` как дескриптор, отложенная регистрация, `fail()` с правилом мутации, `run`/`later`.
3. **Property model.** `Storage` и `Write Policy` в схеме, definition-поля только на чтение, plain со схемной проверкой, managed через операции.
4. **Универсальная секция runtime-состояния** и реестр её полей; динамические поля у definition-kind.
5. **Events и presentation.** `emit`/`on` с разворачиванием обёрток, `action`/`button`/`show_screen` с обязательным `text()`.
6. **Инструмент сбора текстов.**

Этап 1 не меняет ничего наблюдаемого и может идти первым независимо. Этап 4 — самый дорогой и единственный, меняющий форму состояния.

## Не входит

- Объявление definitions и схем из Lua.
- Отдельный язык, визуальный скриптинг, отказ от Lua.
- Удаление programmer API: `game.repository`, `game.instances`, реестры, Stable ID, декораторы остаются.
- Отмена валидаторов: `fail()` покрывает типовой случай, валидаторы — моды, приоритеты, перехват.
- Хранение состояния в обёртках и обход командного пути.
- Per-module окружения и capability sandbox.

## Критерии приёмки

- Текущий слайс `rh` (`work`, `wait_day`, `buy`, `travel`) выражается без единого обращения к `game.*` в теле команд.
- `fail()` после мутации даёт ошибку с указанием команды, а не тихий частичный эффект.
- Запись в managed-поле отклоняется и называет штатную операцию.
- Добавление поля со `Storage: Runtime State` новому виду сущности не требует правок ядра.
- `unwrap_state` недостижим из геймплейного пакета.
- Ни одна пользовательская строка не встречается в геймплейном коде, включая отказы: `fail()` принимает ключ.
- Отказ managed-поля называет операцию, объявленную схемой, а не зашитую в сообщение.
- Слайс проходится целиком, `state_hash` до и после сохранения совпадает.
