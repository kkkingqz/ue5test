# Предложение по композиции и масштабированию UI

> **Предлагает:** правило идентичности повторяемых элементов, вложенный Screen Instance и вкладки, растягивание по режиму ресурса, целевое разрешение авторинга и принадлежность темы слою.
> **Затрагивает:** [UI Document and Reconciliation](../UI/UIDocumentAndReconciliation.md), [Screen Templates](../UI/ScreenTemplates.md), [Image Resources](../UI/ImageResources.md), [UI Index](../UI/README.md).
> **Не является нормативным:** до реализации действует текущий contract.

## 1. Назначение

Контентный трек закрыт: пакеты подключаются из данных, слои `core → textsystem → rh` разделены, геймплей пишется в авторском слое. Дальше — интерфейс.

Между текущим состоянием и играбельным интерфейсом лежат пять пробелов. Два из них — уже спроектированное, но не реализованное поведение; три не описаны нигде.

| Пробел | Природа |
|---|---|
| Слои, оверлеи, модалки, реконсиляция по `instance_key` | Описано в [UI Document](../UI/UIDocumentAndReconciliation.md), не реализовано |
| Перестроение только изменившегося | Политика принята («Full update policy»), механизма нет |
| Идентичность повторяемых элементов | Одна строка требования без правил, области действия и проверки |
| Вкладки | Отсутствуют во всех contracts |
| Масштабирование, целевое разрешение, поведение при разных пропорциях | Отсутствуют полностью |

Плюс один вопрос владения: `UGV2UiTheme` — единственная подсистема, не отнесённая ни к одному из трёх слоёв.

Предложение закрывает всё перечисленное одним набором решений, потому что решения связаны: вкладки невозможны без реконсиляции экземпляров, реконсиляция бессмысленна без правила ключей, а правило растягивания определяет, что вообще может лежать во вкладке.

## 2. Состояние на входе

Проверено по коду и contracts.

| Что | Сейчас |
|---|---|
| Активный экран | Один; `UGV2RuntimeSubsystem` при следующем accepted Screen request полностью строит замену |
| Слои Game Shell | Именованы в contract; `FGV2ScreenRegistryEntry.Layer` по умолчанию `location_content` |
| Оверлеи и модалки | В конверте документа объявлены как `overlays: []` / `modals: []`; кода нет |
| Реконсиляция | Восемь шагов описаны; сопоставление по `layer + instance_key` не реализовано |
| Ключи повторяемых элементов | Одна нормативная строка: «Repeated field items обязаны иметь deterministic `key` из durable identity». Фактически `key` использует только `core:schema.ui_field.button_list.v2` |
| Schemas Screen Field | Пять: `rich_text.v3`, `button_list.v2`, `checkbox.v1`, `input_field.v1`, `dropdown_select.v1` |
| Вкладки | Отсутствуют |
| Режимы изображения | `fixed_aspect`, `nine_slice`, `tile` реализованы как правила отрисовки ресурса, не как правило раскладки блока |
| Масштабирование и DPI | Не упоминаются ни в одном документе `Docs/UI/` |
| Тема | `UGV2UiTheme` (`UDataAsset`), `Content/UI/Styles/DA_UITheme_Default`; слой не определён |
| Фокус, геймпад, Back | Отдельное [предложение по CommonUI](CommonUIRuntimeIntegrationProposal.md), не реализовано |
| Дайджест презентации | `FRunResult` содержит `FinalScreenId` и `FinalScreenFields` — один экран |

## 3. Принятые решения

Решения приняты до написания предложения и здесь только фиксируются.

**3.1. Каноничен экран.** Канонично то, что Lua формирует как desired document: маршрут и его поля. Прокрутка, активная вкладка, раскрытый список, наведение, всплывающая подсказка — UI-local, живут в UE и в сейв не попадают. После загрузки интерфейс строится из канонического состояния заново.

**3.2. Дайджест не расширяется.** Прямое следствие 3.1: `FinalScreenId` и `FinalScreenFields` продолжают описывать всё каноническое. Оверлеи и модалки в дайджест не добавляются.

**3.3. Растягивание задаётся режимом фонового ресурса.** Бесшовная текстура (`tile`) — растягивается свободно. Конкретное изображение (`fixed_aspect`) — только с сохранением пропорций. Кнопка и рамка (`nine_slice`) — растягиваются с фиксированными углами. Отдельного свойства раскладки не вводится.

**3.4. Тема и шаблоны экранов принадлежат `textsystem`** и остаются ассетами UE.

**3.5. Клавиатура и геймпад закладываются архитектурно, но не реализуются** в рамках этого предложения.

## 4. Идентичность повторяемых элементов

Текущая формулировка «deterministic `key` из durable identity» задаёт намерение, но не задаёт ни области уникальности, ни источника значения, ни последствий нарушения. Ниже — полное правило.

**Базовое правило.** Каждый повторяемый элемент имеет `key`, уникальный в пределах непосредственного родительского контейнера и выведенный из смысла элемента, а не из его позиции.

### 4.1. Ключ обязателен

Отсутствие `key` у элемента повторяемого поля — ошибка документа, отклоняемая до apply, а не молчаливый откат к индексу.

Индекс как запасной вариант — механизм, который делает реконсиляцию тихо неправильной: вставка элемента в начало списка «изменяет» все последующие. Ошибка при этом не наблюдаема — интерфейс выглядит корректно и лишь пересоздаёт виджеты.

### 4.2. Область уникальности — контейнер

Полный путь складывается: `layer` → `instance_key` экрана → `field_id` → `key` элемента. Это уже форма `node_key_path` в binding registry, и правило её не меняет, а объявляет обязательной.

Следствие: дизайнер не обязан выдумывать глобально уникальные имена, а два одинаковых подсписка на одном экране остаются возможны.

### 4.3. Источник значения ключа

В порядке приоритета, все варианты детерминированы:

1. явный `key`, заданный автором;
2. Stable ID или instance ID сущности, которой соответствует элемент — `rh:item.weapon.iron_sword`, `actor@42`;
3. для элемента без сущности — `command_id` с каноникализованными аргументами.

Поскольку идентификаторы есть у каждой сущности, большинство списков получает ключи без участия автора. В авторском слое это означает, что перебор по сущностям ключей не требует: их выводит `mod.button` и построители полей. Явный `key` нужен только спискам, собранным вручную.

### 4.4. Ключ не выводится из отображаемого текста

Текст локализуется. Ключ, выведенный из `text_id` или из локализованной строки, меняется вместе с языком и обнуляет переиспользование при смене локали — то есть ровно в тот момент, когда пересборка всего интерфейса наиболее заметна.

### 4.5. Ключ не содержит изменяемого состояния

`rh:item.potion` — корректный ключ. `rh:item.potion#3`, где `3` — количество, — нет.

Смена ключа по contract означает «это другая сущность»: элемент уничтожается и создаётся заново. Ключ с вшитым количеством, ценой или доступностью гарантирует пересоздание при каждом изменении и отключает переиспользование именно там, где оно нужно.

### 4.6. Реконсиляция контейнера

Внутри поля выполняются те же шаги, что для Screen Instances, на уровень ниже. Сопоставление по паре «тип элемента + `key`»:

| Ситуация | Действие |
|---|---|
| Ключ совпал, тип совпал | Обновить значения на месте; UI-local состояние элемента сохраняется |
| Ключ совпал, тип изменился | Заменить элемент |
| Ключа нет в предыдущей ревизии | Создать |
| Ключа нет в desired | Логически отключить, затем удалить |
| Порядок изменился, набор ключей тот же | Переупорядочить без пересоздания |

Последняя строка — причина существования ключей.

### 4.7. Дубликат ключа — ошибка

Два элемента с одинаковым `key` в одном контейнере отклоняют документ целиком, того же класса, что `CommandAlreadyDefined`. Если элементы действительно являются разными сущностями — это instance ID, уникальные по построению.

### 4.8. Что проверяется

Статически проверяемо: наличие ключа, уникальность в контейнере, соответствие грамматике, отсутствие вывода из `text_id`.

Стабильность ключа между ревизиями статически не проверяется. Её ловит диагностика dev-сборки: контейнер, который за несколько ревизий не переиспользовал ни одного дочернего элемента, сообщает об этом. Диагностика ловит и опечатки в ключах, и случайно вшитое в ключ состояние, и стоит один счётчик на контейнер.

## 5. Вложенный Screen Instance и вкладки

### 5.1. Почему вкладка не может быть обычным полем

Активная вкладка — UI-local (решение 3.1). Значит переключение вкладки не проходит через Semantic Input, не порождает команду и не создаёт новую ревизию документа. Значит **содержимое всех вкладок обязано присутствовать в документе одновременно**, иначе UE нечего показать при переключении.

Содержимое вкладки — это произвольный набор Screen Fields. Поле, внутри которого лежат поля, вводит новое понятие вложенности полей и требует второго механизма apply.

### 5.2. Предлагаемое решение: Screen Instance становится рекурсивным

Вкладка — это Screen Instance, вложенный в поле-контейнер. Route, оверлей и модалка — экземпляры верхнего уровня; набор вкладок — хост экземпляров внутри экрана.

```json5
{
  field_id: "panels",
  schema_id: "core:schema.ui_field.tab_set.v1",
  value: {
    default_tab_key: "inventory",
    tabs: [
      {
        key: "inventory",
        title: { text_id: "textsystem:text.tab.inventory", args: {} },
        screen_id: "rh:screen.panel.inventory",
        fields: { /* полный набор полей вложенного экрана */ },
      },
      {
        key: "journal",
        title: { text_id: "textsystem:text.tab.journal", args: {} },
        screen_id: "rh:screen.panel.journal",
        fields: { },
      },
    ],
  },
}
```

Что это даёт:

- новых механизмов apply нет: вложенный экземпляр разрешается через тот же Screen Registry и применяет поля тем же `ApplyScreenFields`;
- реконсиляция вкладок — это правило раздела 4, где `key` вкладки является её `instance_key`;
- вкладка получает собственный шаблон, то есть верстается в UMG Designer наравне с экраном;
- `node_key_path` естественно удлиняется, а binding registry не меняется.

### 5.3. Ограничение размещения

Запись Screen Registry получает `layer: "embedded"`. Экран с этим layer может быть только вложенным содержимым и не может быть маршрутом, оверлеем или модалкой; обратно — экран маршрута не может быть содержимым вкладки. Нарушение — ошибка валидации реестра, а не рантайма.

Вложенность ограничена одним уровнем: набор вкладок не может содержать набор вкладок. Ограничение снять дешевле, чем ввести, а потребителя у произвольной вложенности сейчас нет.

### 5.4. Активная вкладка

Хранится в UE по паре «путь экземпляра экрана + `field_id` набора вкладок». Правила:

- начальное значение — `default_tab_key`, при его отсутствии первая вкладка;
- при реконсиляции, сохраняющей экземпляр экрана, активная вкладка сохраняется;
- если активная вкладка исчезла из набора — активной становится `default_tab_key`, затем первая;
- при уничтожении экземпляра экрана состояние теряется вместе с ним;
- в сейв не попадает.

### 5.5. Интерактивность неактивных вкладок

Ключевой инвариант, без которого вложенность становится дырой в input path.

Binding records создаются для **всех** вкладок, потому что документ содержит их целиком. Но интерактивна только активная вкладка: handle неактивной вкладки существует, однако Semantic Input отклоняет его так же, как stale handle.

Переключение вкладки меняет множество интерактивных handles, не меняя ревизию документа. Это единственное UE-local изменение, влияющее на интерактивность, и оно обязано быть записано явно.

## 6. Растягивание и масштабирование

### 6.1. Растягивание блока определяется режимом его фонового ресурса

| Режим ресурса | Поведение блока |
|---|---|
| `tile` | Растягивается по обеим осям свободно |
| `fixed_aspect` | Растягивается только с сохранением пропорций |
| `nine_slice` | Растягивается по обеим осям; углы неизменны |
| Блок без фонового ресурса | Определяется шаблоном: текст и контейнеры по содержимому |

Механизм уже существует: `UGV2ImageWidgetBase` объявляет `AcceptedRenderMode`, а для `fixed_aspect` — `FixedAspectRatio`. Меняется статус этих данных: сегодня они говорят, как рисовать, и станут говорить, как блок ведёт себя в раскладке.

Практическое следствие — проверяемое противоречие. Блок, объявивший `AcceptedRenderMode = fixed_aspect`, но помещённый в слот со свободным растягиванием по обеим осям, является ошибкой шаблона. Проверка добавляется в существующую automation по полному инвентарю `/Game/UI`, которая уже обходит все `WBP_*`.

**Правило фонового слоя.** Слой `background` обязан заполнять видимую область при любых пропорциях. `fixed_aspect` этого не гарантирует и, по [Image Resource Contract](../UI/ImageResources.md), не допускает ни crop, ни неравномерного растягивания. Поэтому фон строится как `tile`-подложка, поверх которой опционально вписывается `fixed_aspect`-иллюстрация. Полноэкранная иллюстрация без подложки — ошибка композиции.

### 6.2. Целевое разрешение авторинга

**1920 × 1080.** Все 2D-ресурсы и все размеры в шаблонах задаются в авторских единицах этого разрешения.

Основание: совпадает с наиболее распространённым разрешением, даёт целое отношение к 4K, и в нём же удобно принимать иллюстрации от художника.

Значение хранится в одном месте как константа проекта и не повторяется в шаблонах.

### 6.3. Правило масштабирования

Два числа: целевая высота 1080 и минимальная расчётная ширина 1440 авторских единиц (то же 1080 при пропорции 4:3).

```text
scale = min(viewport_height / 1080, viewport_width / 1440)
```

Смысл: до пропорции 4:3 масштаб задаётся высотой, и раскладка одинакова на любом широком экране. Уже 4:3 масштаб задаётся шириной, чтобы минимальная расчётная ширина всегда помещалась.

| Разрешение | Пропорция | `scale` | Авторская область |
|---|---|---|---|
| 1280 × 720 | 16:9 | 0.667 | 1920 × 1080 |
| 1920 × 1080 | 16:9 | 1.000 | 1920 × 1080 |
| 3840 × 2160 | 16:9 | 2.000 | 1920 × 1080 |
| 2560 × 1600 | 16:10 | 1.481 | 1728 × 1080 |
| 3440 × 1440 | 21:9 | 1.333 | 2580 × 1080 |
| 1024 × 768 | 4:3 | 0.711 | 1440 × 1080 |
| 1280 × 1024 | 5:4 | 0.889 | 1440 × 1152 |

Колонка контента ограничена по ширине 1920 авторскими единицами и центрируется; избыточную ширину получает фоновый слой. Это удерживает длину строки в читаемых пределах на сверхшироких экранах и не требует отдельной раскладки.

Раскладок по контрольным точкам (breakpoints) не вводится: одна раскладка, один масштаб, два числа.

### 6.4. Масштаб текста

Размеры типографики в теме задаются в авторских единицах и масштабируются вместе с раскладкой. Отдельный пользовательский множитель размера текста в это предложение не входит, но тема обязана выражать размеры так, чтобы он мог быть добавлен без пересмотра токенов.

### 6.5. Безопасная область

Границы безопасной области применяются оболочкой как отступы Game Shell и boundary не пересекают. Значения для ТВ и мобильных платформ в это предложение не входят; резервируется только место их применения.

## 7. Длина текста в локалях

Русская строка обычно на 20–30 % длиннее английской. Тема с фиксированными размерами кнопок начинает обрезать текст на переводе, причём в основной локали, а не в тестовой — исходные сообщения английские.

Правило: минимальный размер интерактивного элемента выводится из содержимого, а не задаётся константой темы. Токены темы задают отступы, типографику и минимальные размеры касания, но не ширину кнопки.

Проверка: генерируемая псевдолокаль удлиняет каждое сообщение на фиксированную долю; automation обходит зарегистрированные экраны и требует, чтобы ни один текстовый блок не оказался усечён. Гейт дешёвый и ловит ровно тот дефект, который иначе обнаруживается после перевода.

## 8. Тема и шаблоны экранов: принадлежность слою

### 8.1. Владение

Тема и шаблоны экранов принадлежат `textsystem`: они выражают внешний вид текстовой игры, а не механизм движка и не правила конкретной игры. Это применение критерия трёх вопросов из [ADR-0030](../ADR/0030-textsystem-layer-and-data-driven-package-set.md) к ассетам UE.

Хранилищем остаётся UE. Тема — набор ссылок на классы стилей, кривые и брашы; переносить это в JSON5 значило бы пересобрать в контенте типизацию, которую редактор уже даёт.

### 8.2. Как владение становится видимым

Сегодня принадлежность ассета слою не наблюдаема: всё лежит в `Content/UI/`. Предлагается конвенция каталогов:

```text
Content/UI/                  инфраструктура core: Game Shell, leaf-адаптеры, WBP_ScreenBase, реестр
Content/TextSystem/UI/       тема, стили, шаблоны экранов текстовой игры
Content/RH/UI/               шаблоны и стили конкретной игры
```

Проверка выполняется валидацией Screen Registry: класс, привязанный к `screen_id` с namespace `X`, обязан лежать в каталоге слоя `X` или ниже по цепочке зависимостей. Это тот же по смыслу гейт, что `validate_core_boundary.py` для идентификаторов, только на стороне UE.

### 8.3. Минимальная тема ядра

Из владения `textsystem` следует, что конфигурация без `textsystem` остаётся без темы. Но `core` сохраняет собственные экраны — `core:screen.error`, `core:screen.loading`, `core:screen.recovery`, — которые обязаны отрисоваться в том числе при отказе загрузки контента.

Поэтому `core` содержит минимальную тему, достаточную только для этих трёх экранов, а тема `textsystem` её замещает. Аварийный экран, зависящий от игрового пакета, — это отказ, который невозможно показать.

## 9. Заготовка под фокус и ввод

Реализация не входит; входит то, что дороже добавить позже:

- порядок обхода объявляется данными шаблона, а не порядком создания виджетов;
- набор вкладок объявляет владельца фокуса по умолчанию;
- смена активной вкладки и открытие модалки — точки, в которых фокус будет назначаться и восстанавливаться;
- Back остаётся неназначенным, но слои перечислены в порядке, в котором он будет их разбирать: модалка, оверлей, маршрут.

Полное решение — [предложение по интеграции CommonUI](CommonUIRuntimeIntegrationProposal.md).

## 10. Не входит в предложение

- Фокус, навигация геймпадом и Back — отдельное предложение.
- Расширение дайджеста презентации: решение 3.2.
- Раскладки по контрольным точкам и портретная ориентация.
- Значения безопасной области для ТВ и мобильных платформ.
- Переопределение темы из контентного пакета.
- Вложенность наборов вкладок глубже одного уровня.
- Пользовательский множитель размера текста.

## 11. Этапы

1. **Идентичность.** ADR, правило ключей, гейт документа, диагностика переиспользования.
2. **Реконсиляция.** Слои Game Shell, оверлеи, модалки, сопоставление по `layer + instance_key`, переиспользование виджетов.
3. **Вкладки.** Рекурсивный Screen Instance, `core:schema.ui_field.tab_set.v1`, UI-local активная вкладка, интерактивность только активной вкладки.
4. **Масштабирование.** Разрешение авторинга, правило масштаба, растягивание по режиму ресурса, проверка шаблонов.
5. **Тема.** Принадлежность слою, каталоги, гейт реестра, минимальная тема ядра, псевдолокаль.

Этапы 1→2→3 строго последовательны. Этапы 4 и 5 независимы от них и друг от друга, но выполняются в указанном порядке, чтобы переезд ассетов не пересекался с правкой раскладки в тех же шаблонах.

## 12. Критерии приёмки

- Документ без `key` у повторяемого элемента и документ с дубликатом ключа отклоняются до apply.
- Изменение порядка элементов при неизменном наборе ключей не пересоздаёт ни одного виджета.
- Одновременно существуют маршрут, оверлей и модалка; модалка блокирует нижние слои, удаление владельца каскадно удаляет его модалки.
- Ревизия, меняющая одно поле одного экрана, не пересоздаёт остальные экземпляры.
- Переключение вкладки не порождает команду, не меняет ревизию документа и не попадает в сейв.
- Handle неактивной вкладки отклоняется Semantic Input.
- Сохранение и загрузка возвращают маршрут; активная вкладка, прокрутка и стек оверлеев — начальные.
- На 1280×720, 1920×1080, 3840×2160, 3440×1440 и 1024×768 раскладка отличается только масштабом и шириной фона.
- Блок с `fixed_aspect` в свободно растягивающемся слоте — ошибка валидации шаблона.
- Псевдолокаль не даёт усечённого текста ни на одном зарегистрированном экране.
- Класс экрана из namespace пакета вне каталога своего слоя — ошибка валидации реестра.
- Конфигурация без `textsystem` отрисовывает `core:screen.error`, `core:screen.loading` и `core:screen.recovery`.
