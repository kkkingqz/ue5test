# CommandPanel: WrapSize=1200 не масштабируется под viewport

> **Показывает:** известное расхождение между `ADR-0035` (Responsive Layout and Scaling Model, см. [ScreenTemplates.md](../UI/ScreenTemplates.md)) и фактическим поведением `ButtonRepeater` в `WBP_CommandPanel`. Обнаружено при работе над `DCA-02` (`DeclaredCompositeAdoption`), 2026-09-03.
> **Не является нормативным:** целевое поведение задаёт `ADR-0035`; этот файл фиксирует наблюдаемый дефект, а не предписывает решение.

## Проблема

[ScreenTemplates.md:65](../UI/ScreenTemplates.md) формулирует правило: *«Равномерное масштабирование кадра (uniform frame scale) запрещено: раскладка отзывчивая (responsive) и распределяет фактический viewport»*.

`ButtonRepeater` внутри `WBP_CommandPanel` использует Widget Blueprint `WBP_ListView_WrapButtons` с корневым `WrapBox`, у которого:

```
bExplicitWrapSize = true
WrapSize = 1200
```

Это фиксированное число в Slate-юнитах, не зависящее от фактически выделенной ширины панели. Оно нарушает принцип «распределяет фактический viewport» дословно: на широких разрешениях (4K, QHD, ultrawide) кнопки перенесутся на новую строку заметно раньше, чем позволяет реально доступное место, недоиспользуя ширину `CommandPanel`. Значение не привязано ни к `FGV2LayoutConstants::VirtualLayoutWidth` (1920×1080 базис из `Dual Resolution Basis`, ADR-0035), ни к какой-либо DPI/scale-кривой.

Остальные четыре `CollectionHost` в тех же трёх composite-экранах (`MeterRepeater`, `ItemRepeater`, `EffectRepeater`, `CharacterRepeater`) используют `WBP_ListView_Wrap` с `bExplicitWrapSize = false` — динамический режим, при котором `SWrapBox` в реальном (тикающем) окне действительно пересчитывает точку переноса на каждый кадр под фактическую ширину. Только `ButtonRepeater` — исключение.

## Где это в коде/контенте

- `Content/UI/Widgets/WBP_ListView_WrapButtons.uasset` — `WrapBox.bExplicitWrapSize=true`, `WrapSize=1200`.
- `Content/TextSystem/UI/Widgets/WBP_CommandPanel.uasset` — `ButtonRepeater` использует именно этот класс, а не общий `WBP_ListView_Wrap`.
- Движковый код: `Engine/Source/Runtime/Slate/Private/Widgets/Layout/SWrapBox.cpp` — `PreferredSize` (порог переноса при `bUseAllottedSize == !bExplicitWrapSize == true`) обновляется только внутри `SWrapBox::Tick()`, который регистрируется через `SetCanTick(bUseAllottedSize)`.
- Тест: `Source/GV2/Private/Tests/GV2RuntimeSubsystemTests.cpp`, `FGV2LocationScreenViewportMatrixTest` (`GV2.Runtime.UI.LocationScreenViewportMatrix`, метка `BAI-10`).

## Почему тест не ловит это на всех 6 разрешениях

`BAI-10` — единственная строгая per-button geometry-проверка (левый/верхний/правый/нижний край каждой из 6 кнопок строго внутри `CommandPanel`) — выполняется **только** при `Res.Size.X == 1280 && Res.Size.Y == 720`. На остальных пяти разрешениях матрицы (4K, QHD, FHD, UW-QHD, UW-FHD) для `CommandPanel` проверяется только `CommandAllocated.X > 0 && CommandAllocated.Y > 0` — то есть что панель вообще что-то заняла, без проверки корректности переноса кнопок.

Дополнительная методологическая проблема: тест использует голый `SVirtualWindow`, который никогда не регистрируется в `FSlateApplication` и поэтому никогда не тикает вложенные виджеты. Из-за этого `PreferredSize` у любого `WrapBox` в динамическом режиме (`bExplicitWrapSize=false`) в этом тесте вообще не обновляется между итерациями цикла по разрешениям и застревает на значении первого прохода (4K, самое широкое). Иными словами, сам тестовый harness сегодня не способен честно проверить responsive-перенос ни для одного `WrapBox` на разрешениях, отличных от первого — независимо от того, `1200` там зашито или нет. Именно поэтому исходный автор перешёл на `bExplicitWrapSize=true` только для `ButtonRepeater`: это единственный способ получить детерминированный, не зависящий от Tick результат в этом типе теста — ценой того, что значение перестаёт быть отзывчивым по-настоящему.

## Почему это не регрессия DCA-02

Значение `WrapSize=1200` существовало на исходном `ButtonContainer` (`WrapBox`, до появления `UGV2ListViewWidgetBase`-обёртки) до начала работы над `DCA-02` — восстановлено побайтовой сверкой со старым `.uasset` через `unreal-mcp` (`git show HEAD:.../WBP_CommandPanel.uasset` → временная загрузка в `/Game/_TempInspect` → `ObjectTools.get_properties` → удалено после сверки). `DCA-02` по своему скоупу («на этом шаге меняется форма ассета, а не поведение», см. [Prerequisites.md](../Plans/DeclaredCompositeAdoption/Prerequisites.md)) обязан был сохранить существующее поведение геометрии без изменений, поэтому значение было перенесено как есть в отдельный `WBP_ListView_WrapButtons`, а не пересмотрено.

## Происхождение значения

Значение введено коммитом `c2526ae` «Измерить выделенную геометрию в матрице разрешений (SVC-05)», 2026-08-23. Change set состоит из трёх файлов: тест `FGV2LocationScreenViewportMatrixTest`, doc и `WBP_CommandPanel.uasset`. Последний пункт сообщения коммита:

> Настроить явный размер переноса `WrapSize` в `WBP_CommandPanel` для предотвращения переполнения по вертикали.

То есть `bExplicitWrapSize=true` появился **в том же change set, что и проверка, которую он заставляет пройти**. Переполнения по вертикали до этого коммита не наблюдал никто, кроме добавленного им же утверждения `BAI-10` на 720p.

Само число подтверждает это независимо от сообщения: `1200` — ширина `CommandPanel` на 1280×720 за вычетом отступов, то есть замер, снятый на единственном разрешении, где новая проверка работает строго. На 4K панель шире примерно втрое, а порог переноса остаётся тем же.

Реконструкция мотива, записанная в разделе выше как предположение («исходный автор перешёл на `bExplicitWrapSize=true`… это единственный способ получить детерминированный результат»), тем самым подтверждена историей, а не только правдоподобием. Уточнение: выбор был не про детерминизм вообще, а про конкретное утверждение — harness не тикает, честно измерить отзывчивый перенос было нельзя, и продукт подстроили под возможности инструмента.

## Почему это не нашёл ни один гейт

Три независимых пробела, все проверены:

1. **У требования `ADR-0035` нет перечислителя.** Строка `ADR-0035` не встречается ни в одном тесте. Требование существует только как текст контракта.
2. **`Content/` вне досягаемости гейтов целиком.** `WrapSize` и `bExplicitWrapSize` не встречаются ни в `Source/`, ни в `Tools/`, ни в `Docs/`. Все гейты проекта — текстовые сканы по `Source/` и `Docs/`; ни один не читает ассеты. Параметр раскладки, живущий в `.uasset`, невидим для них по построению. Это отсутствующий класс гейтов, а не пробел конкретного.
3. **Отрицательная проверка `BAI-10` охраняет не то утверждение.** Оба `TestFalse` («Artificial … overflow … is rejected») испытывают лямбду `TestFitsInBounds`, объявленную на `GV2RuntimeSubsystemTests.cpp:5416`. Положительные утверждения (`:5390`–`:5414`) её не используют — там развёрнутые `TestTrue` с inline-сравнениями. Лямбда дублирует логику, а не является ею: удаление всех двенадцати реальных проверок оставит оба отрицательных теста зелёными.

## Решение

Пути исправления, перечисленные в версии 1.0 этого файла как возможные, приняты все три и разложены на задачи `M4` плана [DeclaredCompositeAdoption](../Plans/DeclaredCompositeAdoption/LayoutInvariant.md):

| Задача | Что закрывает |
|---|---|
| `DCA-13` | Тик в harness; строгая geometry-проверка на всех шести разрешениях; фактическое покрытие видно в выводе теста |
| `DCA-14` | Отрицательная проверка испытывает тот же предикат, что выносит положительный вердикт |
| `DCA-15` | Перечислитель по дереву виджетов для `ADR-0035`; `WrapSize` перестаёт быть константой; первый гейт, читающий `Content/` |
| `DCA-16` | Правило: артефакт, изменённый вместе с проверкой, обоснован независимо от неё |

## Статус

`known_nonconformance`, не закрыт. Зарегистрирован как `STATUS-009` в [ImplementationStatus.md](ImplementationStatus.md). Способ исправления выбран и разложен на `DCA-13…16`; удаление строки `STATUS-009` — часть `Done` задачи `DCA-15`.
