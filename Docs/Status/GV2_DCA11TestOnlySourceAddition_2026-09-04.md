# DCA-11: `Source/GV2/Private/Tests/GV2Dca11InventoryTabsTests.cpp` — разбор правки под `Source/`

> **Показывает:** почему `DCA-11`'s единственная правка под `Source/` — новый тестовый файл, а не производственный код — не нарушает M3's инвариант «три новых композита без единой строки C++», и почему без него нельзя было обойтись. Записано по требованию `DCA-12` («если хотя бы один из трёх композитов потребовал C++, причина разобрана и записана строкой `STATUS-NNN` либо отдельной задачей»; растворение правки в отчёте вместо отдельной записи closure не даёт).
> **Не является нормативным:** это разбор одного change set, а не правило на будущее. Это отдельная запись, не строка `ImplementationStatus.md`, потому что ниже не открытое несоответствие с условием закрытия, а уже закрытое, сознательно допущенное исключение — добавлять и тут же не иметь что закрывать было бы фиктивной записью.

## Что добавлено

Один новый файл, `Source/GV2/Private/Tests/GV2Dca11InventoryTabsTests.cpp` (284 строки, коммит `f5c1f5f`), реализующий `IMPLEMENT_SIMPLE_AUTOMATION_TEST(FGV2Dca11InventoryTabsFixtureTest, "GV2.Runtime.UI.Dca11InventoryTabs", ...)`. Ни одна существующая строка `Source/` не изменена — независимо проверено `git diff --stat f5c1f5f~1 f5c1f5f -- Source/`, показывающим только этот файл со знаком `+`.

## Почему это не нарушает инвариант M3

Инвариант M3 («три полностью новых композита без единой строки C++») — про то, что **сама модель композита** (`WBP_InventoryTabs`, `WBP_InventoryCategoryBlock`, три Screen Template) не требует новых `IGV2UiPropertyHost`-классов, новых `EGV2DeclaredUiCapabilityKind`, новых Property Consumer'ов или любой другой продакшен-возможности. Это и проверено: все capability, задействованные `inventory_tabs` (`Text`, `ResourceRef`, `Key`, `NestedScreen`, `CollectionHost`, необязательность через `bOptional`, `FallbackNameHint`-резолюция `ChildCapabilityName`, гейт композиционных циклов `DUC-11`), уже существовали до `DCA-09` и использовались другими ассетами. Change set самого композита — исключительно `Content/`, `GameData/`, `Tests/Lua/`.

Добавленный файл — **тест**, не производственный код: он не меняет поведение рантайма ни для одного существующего или будущего ассета, только НАБЛЮДАЕТ его на реальных `Content/`/`GameData/`-ассетах через уже существующие `FGV2SessionCoordinator`/`FGV2LayeredUiReconciler`. Инвариант "ни одной строки C++" относится к тому, что **делает** модель, а не к тому, чем это **доказывается** — иначе ни один из трёх композитов не прошёл бы верификацию вообще, поскольку даже red→green демонстрации через `unreal-mcp` (временная порча `DeclaredCapabilities` + прогон существующего `GV2.UI.CapabilityObservabilityCompositeSweep`) уже полагаются на существующий C++-тест, просто не добавляя новый.

## Почему нельзя было обойтись без нового файла

Единственный уже существующий тест, доказывающий тот же класс поведения («глубокий Prepare-отказ не оставляет следов на предках, вложенные экраны реконсилируются по-настоящему») — `GV2Duc10NestedChainTests.cpp` (`GV2.Runtime.UI.Duc10NestedChain`), написанный в задаче `DUC-10`, **до** начала плана `DeclaredCompositeAdoption`. Это не общий, параметризуемый по контенту тест — он жёстко ссылается на конкретные имена виджетов и `screen_id` фикстуры `duc10_nested_chain` (`RootScreen->GetWidgetFromName(TEXT("TabsHost"))`, `Tabs->GetScreenWidgetForTab(TEXT("info"))` и т.д.). Такой же бесшовный сквозной прогон для `inventory_tabs` физически не мог использовать существующий тест — потребовался бы новый файл при **любом** новом ассете, для которого нужна эта конкретная проверка (глубина > 2 уровней, реальный rollback между уровнями), независимо от того, какая задача плана его создаёт. Это структурное ограничение существующего инструментария (нет обобщённого «прогони произвольную цепочку Screen Template и проверь rollback» теста), а не пробел, специфичный для `inventory_tabs`, и не регрессия этой задачи.

`GV2.UI.CapabilityObservabilityCompositeSweep` (используемый DCA-09/10 без нового C++) сюда не подходит: он рефлективно проверяет только «каждая объявленная capability по отдельности готовится/коммитится с синтетическим значением» — он не строит реальный многоуровневый `FGV2UiDocumentViewModel`, не вызывает `Reconciler.PrepareReconcile`/`CommitReconcile`, и не умеет утверждать «состояние экрана A не изменилось после отказа в композите B пятью уровнями глубже» — категория проверки, которую `inventory_tabs`'s Done требует явно, а `location_description`/`npc_portrait` — нет.

## Статус

Закрыто, условия для повторного открытия нет: это не дефект и не незавершённая работа, а сознательно допущенное, ограниченное по объёму исключение (один тестовый файл, ноль production-строк), заранее разрешённое собственной Evidence-строкой задачи `DCA-11` в [Authoring.md](../Plans/DeclaredCompositeAdoption/Authoring.md). Не зарегистрировано как `STATUS-NNN` в [ImplementationStatus.md](ImplementationStatus.md), поскольку эта таблица — открытые несоответствия контракту, ожидающие исправления, а здесь закрывать нечего.

Если в будущем понадобится **обобщённый** (не привязанный к конкретной фикстуре) тест «прогони реальный многоуровневый Screen Template и проверь rollback на любом уровне», это самостоятельная задача инструментария — не блокирует и не блокируется `DeclaredCompositeAdoption`.
