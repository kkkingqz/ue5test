## GenericUiTransactionFollowUp

Проверка 2026-09-03 на tip `c909fc0`. План заявлен выполненным, все задачи и milestones отмечены `[x]`.

Проверено по коду и подтверждено: `GBF-01` (`AddChild() == nullptr` даёт `false`, гейт `validate_shell_attach_failure_consumption.py` с отрицательным самотестом), `GBF-02` (`FieldSpec.KeyedBy` проецируется в `KeyPropertyName`, сравнение исполнимо), `GBF-03` (`static_assert` по `sizeof` отсутствует, инвентарь членов в CTest), `GBF-04` (`GetUiMutationKindsRequiringInverse()` как перечислитель видов, `PreviousSchema`/`PreviousSchemaId` в снимке, `ui_rollback.inverse_missing` как отказ Prepare), `GBF-06` (`OnScreenFieldsApplied` физически отсутствует в `Source/`, ноль вхождений в `.uasset`), `GBF-07` (`validate_ui_rollback_boundaries.py` выводит `Commit*`/`AttachScreenToLayer` из исходника, шесть маркеров в коде, enum и recovery-mapping как независимая ожидаемая сторона).

Портативные проверки зелёные: `ctest` 74/74, `gv2-headless --check-scripts`, `validate_docs.py`.

- **`GBF-AF-01` — Полный прогон UE automation красный; сценарий `GBF-05` для вложенного экрана не работает.**

  `GV2.Runtime.UI.NestedInstancesAndTabsContract` падает семью утверждениями с меткой `GBF-05`. Воспроизводится детерминированно, два независимых прогона. Полный прогон: 107 успехов из 108.

  Утверждения добавлены коммитом `87ca89e` «Восстанови committed state при UI rollback» — то есть самой задачей `GBF-05`, и с момента написания они не проходили ни разу.

  Наблюдаемая последовательность:

  1. `FGV2TabContainerTabsPropertyConsumer::Prepare` отклоняет кандидата из двух вкладок (`info`, `failure`) — ожидалось принятие.
  2. Последующий `CommitWithFailureInjector` возвращает **успех** — ожидался отказ.
  3. `DayText` остаётся `"Wednesday"` вместо отката к `"Tuesday"`; `ValueBar` — `0.2` вместо `0.7`.
  4. `LastCommittedProperties` вложенного ребёнка также содержит `"Wednesday"`.

  Механизм пункта 2 читается в коде: `Prepare` (`GV2PropertyConsumers.cpp:1661`) делает `PreparedTabs.Reset()` на входе и добавляет по одной вкладке; при отказе на второй вкладке (`GV2PropertyConsumers.cpp:1884`) он возвращает `false`, **не очистив `PreparedTabs`**. В контейнере остаётся готовый к применению план первой вкладки, и следующий `Commit` его применяет. Это частично применённое состояние, запрещённое [ADR-0041](../ADR/0041-ui-commit-rollback-model.md), и нарушение инварианта самой `GBF-04`: транзакция, чья подготовка провалилась, исполняться не должна.

  Причина пункта 1 не установлена: диагностика `core:diagnostic.ui_mutation.prepare_failed` не выведена в лог теста, поскольку сообщение об ошибке форматируется в аргументе `TestTrue` рядом с самим вызовом.

  Затрагивает `Done` задачи `GBF-05` («это выполняется для хоста, экрана, переиспользуемых элементов keyed-коллекции и **вложенного экрана**») — три из четырёх путей зелёные, четвёртый нет.

- **`GBF-AF-02` — Закрытие `GBF-08` подтверждено прогоном 16 тестов из 108.**

  `Done` задачи требовал «полный прогон — UE automation, портативный CTest, `gv2-headless --check-scripts`, `validate_docs.py` — зелёный». Запись в [архиве ревью](Archive/GenericBoundaryHardeningFollowupReview.md) фиксирует `Automation RunTests GV2.UI`: 16/16 success.

  Фильтр `GV2.UI` покрывает ровно 16 тестов. Падающий тест принадлежит группе `GV2.Runtime.UI.*` — 11 тестов, ни один из которых под этот фильтр не попадает. Всего в наборе 108.

  То есть множество «все тесты» было подменено множеством «тесты, чьё имя начинается с `GV2.UI.`», и подмена не видна из записи: строка отчёта выглядит как полный прогон. Это тот самый класс, ради устранения которого написан план (`GBF-07`, «универсальное утверждение требует перечислителя»), в его собственной задаче закрытия.

  Отдельно: обе предыдущие такие сверки (`PCC-12`, приёмка `GBH`) находили непокрытую часть работы собственного плана, и `GBF-08` прямо это цитирует как основание не считать сверку формальной.

- **`GBF-AF-03` — Таблица «Состояние на входе» содержит исход выполнения.**

  Строка `OnScreenFieldsApplied` в [README плана](../Plans/GenericUiTransactionFollowUp/README.md) описывает не состояние на входе, а результат `GBF-06` («Удалены GBF-06: Asset Registry audit … не нашёл Blueprint implementation»). Таблица входа перестаёт быть записью о том, с чего начинали.

  Там же: в итоговом Definition of Done отмечены `[x]` только пункты `GBF-07` и `GBF-08`, тогда как все три milestone отмечены выполненными. Расхождение внутри одного документа.
