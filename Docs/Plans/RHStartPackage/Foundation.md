# Пакет с нуля

> **Материализует:** этап M0 [плана](README.md): каркас пакета и старт новой игры, модель персонажа, словари условий и эффектов, конвейер взаимодействия, десять локаций и переходы.

## RSP-01 — Каркас пакета и старт новой игры

- [ ] RSP-01 — Каркас пакета и старт новой игры

**Файлы:** удалить заглушку: `GameData/rh/scripts/authoring/gameplay.lua`, `scripts/gameplay/actors.lua`, `scripts/runtime/session_start.lua`, её Definitions, schemas и строки `localization/ru.po`. Создать раскладку `scripts/authoring/{model,rules,modes,content}/`, `scripts/runtime/start_bridge.lua`, новый `scripts/manifest.lua` и `package.json5`; schemas kinds `scenario` и `config`; Definitions `rh:scenario.default`, `rh:config.rules`, стартовой локации, её экрана и игрока; `rules/start.lua` с `rh:command.game.start`. Документы: новый `Docs/RH/ContentData.md` (форматы данных собственных kinds), новый `Docs/Status/ResourceRequests.md`, индексы `Docs/RH/README.md` и `Docs/README.md`.

**Зависит от:** GAP-017, GAP-016.

**Вход:** стартовая локация, Definition игрока.

**Решение:** `rh:command.game.start` читает Definition `scenario` и создаёт игрока в стартовой локации. Мост вызывает эту команду только при новой игре и не содержит другой логики. Следующие задачи добавляют в `scenario` NPC, предметы и флаги вместе с их первым потребителем.

**Инвариант:** [RH Gameplay Architecture § 1](../../RH/GameplayArchitecture.md#1-назначение-и-границы): код — только в `scripts/authoring/`, кроме моста, а мост ничего не решает о содержимом мира. Нарушение — мост, который создаёт экземпляры или читает сценарий.

**Не считается закрытием:**
- перенос заглушки под новыми именами;
- мост, создающий игрока сам;
- стартовое состояние, заданное в Lua, а не в Definition `scenario`;
- тексты и ресурсы заглушки, оставленные «на потом».

**Done:**
- В пакете нет файлов и Stable ID заглушки; перечислитель — `git ls-files GameData/rh` и repository Definitions namespace `rh` до и после.
- Раскладка соответствует [§ 2.1](../../RH/GameplayArchitecture.md#21-раскладка); каждый authoring-файл объявлен в `scripts/manifest.lua`.
- Мост — единственный файл вне `scripts/authoring/`; он только вызывает `rh:command.game.start`.
- Новая игра создаёт игрока в стартовой локации из `rh:scenario.default`.
- После load мост команду старта не вызывает.
- Профиль `core + textsystem + rh` открывает `textsystem:screen.location` стартовой локации.
- `Docs/RH/ContentData.md` описывает форматы `scenario` и `config`; `Docs/Status/ResourceRequests.md` содержит заявки на ресурсы стартовой локации; оба документа добавлены в индексы.

**Evidence:** specs пакета: новая игра, load без повторного старта; `gv2-headless --check-scripts`; `validate_docs.py`; `ctest`.

## RSP-02 — Модель персонажа

- [ ] RSP-02 — Модель персонажа: характеристики, выносливость, деньги, формулы

**Файлы:** `scripts/authoring/model/actor.lua`, `scripts/authoring/model/formulas.lua`; schema расширения `actor` (`rh`): имя, портрет, теги, значения характеристик; параметры формул в `rh:config.rules`; `Docs/RH/ContentData.md`; `Docs/RH/GameplayArchitecture.md` § 4.3 и § 5.1 при уточнении правил.

**Зависит от:** RSP-01; GAP-012.

**Вход:** набор характеристик; формулы максимума и восстановления выносливости.

**Решение:** одна таблица имён характеристик порождает поля `Actor`. `actor:base(stat)` возвращает значение экземпляра, а если его нет — значение Definition. Модификаторов в стартовом пакете нет, поэтому итог равен базе; модификаторы добавляются вместе с первым источником. Выносливость и деньги — поля с операциями модели.

**Инвариант:** [§ 3](../../RH/GameplayArchitecture.md#3-инварианты): набор характеристик одинаков у игрока и NPC; итоговые значения не сохраняются. Нарушение — отдельный набор у игрока или поле итогового значения в state.

**Не считается закрытием:**
- характеристики, объявленные по одной в разных местах;
- значения уникального NPC, скопированные в экземпляр при создании;
- числа баланса в коде формул вместо параметров `config`.

**Done:**
- Набор характеристик объявлен одной таблицей в `model/actor.lua`, поля `Actor` порождаются из неё.
- `actor:base(stat)` читает значение экземпляра, иначе Definition.
- У уникального NPC в state нет копии значений его Definition.
- Выносливость и деньги меняются только операциями модели; результат меньше нуля отклоняется.
- Формулы читают параметры из `config`.
- Обход: каждая Definition `actor` пакета задаёт значение или диапазон каждой характеристики набора; перечислитель — repository (kind `actor`, namespace `rh`) и таблица набора.

**Evidence:** specs модели с отрицательным случаем на каждую операцию; обход; `check-scripts`.

## RSP-03 — Словари условий и эффектов

- [ ] RSP-03 — Словари условий и эффектов

**Файлы:** `scripts/authoring/rules/conditions.lua`, `scripts/authoring/rules/effects.lua`; варианты `union` условий и эффектов в schemas kinds `rh`; `Docs/RH/ContentData.md`.

**Зависит от:** RSP-02.

**Решение:** тип условия — Service `rh:service.condition_<type>` с `check` и `reason`; тип эффекта — `rh:service.effect_<type>` с `apply` и необязательным `check`. Общие функции проверяют список условий до первой причины и исполняют список эффектов по порядку. Начальный набор — типы, которые использует контент RSP-04 и RSP-05; следующие типы добавляет задача их первого потребителя.

**Инвариант:** [§ 5.2](../../RH/GameplayArchitecture.md#52-словари-условий-и-эффектов): условие только читает; причину формирует тип условия. Нарушение — условие, которое пишет state, или причина, записанная в данных взаимодействия.

**Не считается закрытием:**
- ветвление по типу условия внутри конвейера;
- тип без `reason`;
- параметры, проверяемые только в Lua, а не schema.

**Done:**
- Каждый тип условия — Service с `check` и `reason`, каждый тип эффекта — Service с `apply`.
- Параметры каждого типа описаны вариантом `union` по полю `type`; Definition с неизвестным типом не проходит сборку repository.
- Проверка списка условий не меняет `write_revision`.
- Обход: каждый `type` в `requires` и `effects` Definitions `rh` имеет Service; перечислитель — repository Definitions namespace `rh`.
- Обход: каждый Service семейств `condition_*` и `effect_*` имеет методы своего контракта; перечислитель — registry Services по префиксу.
- Каждый тип используется контентом плана.

**Evidence:** specs словаря: `check` и `reason`, отказ, отсутствие записи; отрицательная сборка с неизвестным типом; оба обхода.

## RSP-04 — Конвейер взаимодействия

- [ ] RSP-04 — Конвейер взаимодействия

**Файлы:** `scripts/authoring/rules/interactions.lua`; schema kind `interaction`; связка `rh:action.interact` → `rh:command.perform`; взаимодействия стартовой локации; `Docs/RH/ContentData.md`.

**Зависит от:** RSP-03.

**Вход:** взаимодействия стартовой локации.

**Решение:** `rh:service.interactions` с `context`, `check` и `apply` по [§ 2.4](../../RH/GameplayArchitecture.md#24-проверка-отдельно-от-записи) и [§ 5.3](../../RH/GameplayArchitecture.md#53-конвейер-взаимодействия). Исполнитель — игрок. До RSP-06 кнопки взаимодействий перечисляются в данных экрана локации; недоступное взаимодействие отказывает при нажатии.

**Инвариант:** [§ 2.4](../../RH/GameplayArchitecture.md#24-проверка-отдельно-от-записи): все проверки до первой записи. Нарушение — `fail()` после списания выносливости (`AuthoringFailAfterMutation`).

**Не считается закрытием:**
- Command или Semantic Action на каждое взаимодействие;
- проверка выносливости внутри эффекта;
- `check`, который пишет state.

**Done:**
- Взаимодействие — Definition `interaction`: текст, стоимость, условия, эффекты; новое взаимодействие не требует Lua.
- Кнопки взаимодействий связаны с `rh:action.interact` → `rh:command.perform`.
- `check` возвращает первую причину в порядке: условия → выносливость → предусловия эффектов.
- `apply` списывает выносливость, исполняет эффекты по порядку и публикует `rh:event.interaction_completed`.
- Отказ любого шага оставляет state hash неизменным.
- Причина отказа даёт error `rh:error.<key>` и существующий текст `rh:text.error.<key>`; проверяется spec каждого типа условия и конвейера — это напоминание, а не гейт.

**Evidence:** specs конвейера: успех, отказ по условию, по выносливости, по предусловию эффекта, state hash до и после отказа.

## RSP-05 — Десять локаций и переходы

- [ ] RSP-05 — Десять локаций и переходы

**Файлы:** Definitions `location` и экранов (`definitions/locations_<группа>.json5`); schema расширения `location` (`rh`): стоимость входа, взаимодействия локации; `scripts/authoring/rules/travel.lua`; связка `textsystem:action.location.travel` → `rh:command.travel`; тексты-заглушки; `Docs/Status/ResourceRequests.md`; `Docs/RH/ContentData.md`.

**Зависит от:** RSP-04; GAP-012.

**Вход:** десять локаций — названия, связи, стоимость входа, взаимодействия.

**Решение:** переход проходит конвейер: `check` — связь, условия перехода, выносливость не меньше стоимости входа целевой локации; `apply` — списание, перемещение, `rh:event.travel_completed`.

**Инвариант:** [§ 4.2](../../RH/GameplayArchitecture.md#42-что-где-хранится): стоимость перехода — одна на локацию, стоимость её входа. Нарушение — стоимость на связи или в коде.

**Не считается закрытием:**
- `move_to` без конвейера;
- стоимость в Lua;
- переход, недоступный из меню локации.

**Done:**
- Десять локаций со связями по входу дизайнера; у каждой — Definition `location` и экран.
- Переход списывает стоимость входа целевой локации.
- При нехватке выносливости переход отклоняется с причиной, state hash не меняется.
- Переход в несвязанную локацию отклоняется.
- После перехода публикуется `rh:event.travel_completed` с исходной и целевой локацией.
- Обход: каждая связь ведёт в существующую локацию, стоимость входа неотрицательна, каждая локация достижима из стартовой; перечислитель — repository kind `location` namespace `rh`.
- Заявки на картинки и тексты локаций записаны в `Docs/Status/ResourceRequests.md`.

**Evidence:** specs перехода: успех, нехватка выносливости, несвязанная локация, событие; обход.
