# Режимы стартового пакета

> **Материализует:** этап M2 [плана](README.md): отчёт о конце хода, магазин, флаги, диалог, продажа, реакции на переход, танец.

Каждый режим делится на чистое ядро в `rules/` и оболочку в `modes/` ([RH Gameplay Architecture § 5.12](../../RH/GameplayArchitecture.md#512-временные-режимы)). Состав Mode Run и политика записи каждого режима — [Temporary Game Modes § 3.1](../../Proposals/TemporaryGameModesProposal.md#31-режимы-стартового-пакета-rh). Запуск режима из взаимодействия проверяет `modes.active()` в `check`, до первой записи.

## RSP-10 — Отчёт о конце хода

- [ ] RSP-10 — Отчёт о конце хода

**Файлы:** `scripts/authoring/modes/turn_report.lua`; запуск из `rules/turn.lua`.

**Зависит от:** RSP-08; механизм режимов; SR-002.

**Решение:** `rh:command.turn.end` при непустом списке записей запускает `rh:mode.turn_report`. Записи показываются по одной; листание — UE-local. Кнопка «Продолжить» на последней записи завершает режим.

**Инвариант:** [§ 5.6](../../RH/GameplayArchitecture.md#56-ход): результаты фаз уже применены командой конца хода; отчёт — только показ. Нарушение — запись в state при закрытии отчёта.

**Не считается закрытием:**
- номер текущей записи в Mode Run;
- открытие отчёта при пустом списке;
- модальное окно вместо экрана в основном слое.

**Done:**
- При непустом списке записей конец хода открывает экран отчёта со всеми записями в порядке фаз.
- При пустом списке режим не запускается, открыт экран локации.
- Закрытие отчёта возвращает экран локации и не меняет state hash.

**Evidence:** specs: пустой и непустой отчёт, закрытие; поля экрана соответствуют SR-002.

## RSP-11 — Магазин

- [ ] RSP-11 — Магазин

**Файлы:** schemas kinds `item` (новая версия) и `shop`; `scripts/authoring/rules/shop.lua`, `scripts/authoring/modes/shop.lua`; эффект `open_shop`; Definitions предметов и магазинов; взаимодействия «магазин» на локациях; `Docs/RH/ContentData.md`.

**Зависит от:** RSP-04; механизм режимов; SR-003.

**Вход:** предметы (название, описание, цена, иконка), магазины, их локации и ассортимент.

**Решение:** запуск — взаимодействие с эффектом `open_shop`. `rh:service.shop` проверяет и исполняет покупку: деньги, наличие товара в ассортименте; списание; создание экземпляра предмета у игрока. Запас бесконечный, цена — из Definition предмета.

**Инвариант:** [§ 2.4](../../RH/GameplayArchitecture.md#24-проверка-отдельно-от-записи): покупка проверяет всё до списания. Нарушение — отказ после списания денег.

**Не считается закрытием:**
- модальное подтверждение покупки;
- цены или ассортимент в Lua;
- уменьшение запаса;
- ID конкретного магазина в коде режима.

**Done:**
- Кнопка магазина на локации — взаимодействие с эффектом `open_shop`.
- Запуск при активном режиме отклоняется до записи.
- Экран показывает ассортимент, цены и описания из данных.
- Покупка списывает цену и создаёт предмет у игрока; после покупки меняются деньги и доступность, `key` товаров остаются прежними.
- Товар, на который не хватает денег, неактивен; причина — из проверки покупки.
- «Уйти» завершает режим и возвращает экран локации.
- Обход: каждый товар каждого магазина — существующая Definition `item` с ценой не меньше нуля; перечислитель — repository kind `shop`.

**Evidence:** specs: покупка, нехватка денег (state hash не меняется), неактивный товар, выход; обход.

## RSP-12 — Флаги

- [ ] RSP-12 — Флаги

**Файлы:** schema kind `flag`; поле флагов `Actor` в `scripts/authoring/model/actor.lua`; условие и эффект флага в `rules/conditions.lua` и `rules/effects.lua`; Definitions флагов; `Docs/RH/ContentData.md`.

**Зависит от:** RSP-03; GAP-008.

**Вход:** флаги, используемые диалогами.

**Решение:** флаг — Definition `flag`; флаги игрока и NPC хранятся полем-словарём с ключом — ID флага. Производитель — эффекты вариантов диалога, потребитель — условия вариантов (RSP-13).

**Инвариант:** [§ 3](../../RH/GameplayArchitecture.md#3-инварианты): ветка диалога описывается данными. Нарушение — отдельное поле Lua на каждый флаг.

**Не считается закрытием:**
- имя флага строкой без Definition;
- флаг, объявленный полем Lua.

**Done:**
- Флаг — Definition `flag`; флаги игрока и NPC хранятся по ID флага.
- Условие и эффект флага ссылаются на флаг по ID; ссылка на несуществующий флаг не проходит сборку repository.
- Флаг, который не ставит ни эффект, ни сценарий, обход отмечает как ошибку; перечислитель — repository Definitions `flag`, эффекты флагов в данных и `scenario`.

**Evidence:** specs: установка и проверка флага у игрока и у NPC; отрицательная сборка; обход.

## RSP-13 — Диалог

- [ ] RSP-13 — Диалог

**Файлы:** schema kind `dialogue`; `scripts/authoring/rules/dialogue.lua` (чистое ядро навигации), `scripts/authoring/modes/dialogue.lua`; эффект `start_dialogue`; Definitions диалогов; `Docs/RH/ContentData.md`.

**Зависит от:** RSP-12; механизм режимов; SR-004; имя NPC в реплике — GAP-011.

**Вход:** диалоги: шаги, реплики, картинки, варианты ответа, их условия и эффекты.

**Решение:** ядро получает шаг, флаги участников и выбор, возвращает видимые варианты и эффекты выбора. Оболочка хранит в Mode Run ID диалога, текущий шаг и участников; эффекты выбора применяются сразу. «Далее» — вариант без условий.

**Инвариант:** [§ 5.12](../../RH/GameplayArchitecture.md#512-временные-режимы): ядро не читает и не пишет state. Нарушение — обращение ядра к `player` или `world`.

**Не считается закрытием:**
- ветвление в Lua по ID диалога;
- текущий шаг в canonical state;
- отдельная кнопка «Далее» вне списка вариантов.

**Done:**
- Диалог запускается для игрока и NPC; условия вариантов проверяются по флагам обоих.
- Вариант, чьи условия не выполнены, показывается по правилу данных варианта: скрыт или неактивен с причиной.
- Выбор применяет эффекты варианта сразу и переходит к следующему шагу; конечный шаг завершает режим.
- Ядро навигации проверено specs без механизма режимов.
- Обход: каждый `next` ведёт в существующий шаг, каждый шаг достижим из начального, у каждого шага есть вариант или он конечный; перечислитель — repository kind `dialogue`.

**Evidence:** specs ядра и оболочки: ветвление по флагам игрока и NPC, эффекты выбора, завершение; обход.

## RSP-14 — Продажа с оценкой

- [ ] RSP-14 — Продажа с оценкой

**Файлы:** schema kind `appraisal`; `scripts/authoring/rules/appraisal.lua` (чистое ядро оценки), `scripts/authoring/rules/sale.lua`; эффект продажи для вариантов диалога; взаимодействия продажи на локациях; Definitions оценок; `Docs/RH/ContentData.md`.

**Зависит от:** RSP-13; GAP-004.

**Вход:** какие предметы принимаются, формула оценки, исходы, их условия и диалоги, итог сделки.

**Решение:** кнопка продажи — отдельное от магазина взаимодействие. Команда находит у игрока предметы из Definition `appraisal`, ядро оценивает их по свойствам и параметрам, исход выбирает диалог. Сделка применяется эффектом варианта этого диалога.

**Инвариант:** [§ 5.12](../../RH/GameplayArchitecture.md#512-временные-режимы): оценка — чистая функция. Нарушение — ID конкретных предметов в коде оценки.

**Не считается закрытием:**
- текст исхода в коде;
- оценка внутри режима магазина;
- удаление предмета до выбора игрока.

**Done:**
- Продажа находит у игрока предметы, заданные Definition `appraisal`; если их нет, запускается диалог исхода «нечего продать» из данных.
- Оценка — чистая функция от свойств предметов и параметров; specs ядра — без механизма режимов.
- Исход определяется условиями исходов и запускает свой диалог.
- Предмет удаляется и деньги начисляются только эффектом варианта; отказ игрока не меняет state hash.
- Обход: каждый исход ссылается на существующий диалог; перечислитель — repository kind `appraisal`.

**Evidence:** specs ядра на граничных значениях формулы; specs продажи: согласие, отказ, нет предметов; обход.

## RSP-15 — Реакции на переход

- [ ] RSP-15 — Реакции на переход

**Файлы:** schema kind `reaction`; `scripts/authoring/rules/reactions.lua`; Definitions реакций; `Docs/RH/ContentData.md`.

**Зависит от:** RSP-05, RSP-13; GAP-010; построение экрана после очереди отложенных команд.

**Вход:** реакции на переход: условия, шанс, порядок, запускаемое взаимодействие.

**Решение:** по [§ 5.13](../../RH/GameplayArchitecture.md#513-events-и-реакции). Подписчик на `rh:event.travel_completed` ставит в очередь `rh:command.reaction.run`; команда перебирает реакции события по порядку, проверяет условия, бросает шанс из потока `rh:random_stream.reactions` и исполняет эффекты первой сработавшей.

**Инвариант:** подписчик работает при закрытом mutation window ([Commands and Events](../../Architecture/CommandsAndEvents.md)). Нарушение — бросок или запись в подписчике.

**Не считается закрытием:**
- условия реакции в подписчике;
- список реакций в Lua;
- реакция, перезапускающая уже активный режим.

**Done:**
- Реакция — Definition `reaction`: событие, условия, шанс, порядок, эффекты; новая реакция не требует Lua.
- Подписчик только ставит команду в очередь.
- Реакции проверяются по порядку; срабатывает первая; при активном режиме команда ничего не меняет.
- Одинаковый seed даёт одинаковые исходы.
- Экран режима, запущенного реакцией, открывается без промежуточного интерактивного экрана локации.
- Обход: событие каждой реакции имеет подписчика `rh`; перечислитель — repository kind `reaction`.

**Evidence:** specs: срабатывание, несрабатывание по условию и по шансу, порядок, активный режим, seed; обход.

## RSP-16 — Танец

- [ ] RSP-16 — Танец

**Файлы:** schema kind `dance`; `scripts/authoring/rules/dance.lua` (чистое ядро), `scripts/authoring/modes/dance.lua`; эффект `start_dance`; Definitions танцев; `Docs/RH/ContentData.md`.

**Зависит от:** RSP-09; механизм режимов; SR-005; RNG режимов; выбор участников из присутствующих — GAP-005.

**Вход:** правила танца: временные характеристики сцены и их расчёт из базовых, движения, условия, завершение, итог для участников.

**Решение:** ядро: из базовых характеристик участников — сцена; из сцены, движения и потока случайности — новая сцена; из конечной сцены — изменения участников. Оболочка хранит сцену и зерно в Mode Run и записывает итог одной командой.

**Инвариант:** [§ 5.12](../../RH/GameplayArchitecture.md#512-временные-режимы): временные характеристики существуют только в режиме. Нарушение — запись временной характеристики в state.

**Не считается закрытием:**
- изменение характеристик участников после каждого движения;
- `game.random` внутри ядра вместо потока из Mode Run;
- два участника, заданные в коде.

**Done:**
- Танец запускается для двух и более NPC.
- Временные характеристики рассчитываются из базовых и хранятся только в Mode Run.
- Кнопки — движения из Definition `dance`; недоступное движение неактивно с причиной.
- Итог записывается участникам одной командой при завершении; отмена не меняет state hash, кроме `meta.prng`.
- Ядро — чистая функция; одинаковое зерно даёт одинаковую последовательность сцен.
- Обход: каждая характеристика, на которую ссылается Definition `dance`, есть в наборе; перечислитель — repository kind `dance` и таблица набора.

**Evidence:** specs ядра: расчёт сцены, движения, итог, повторяемость по зерну; specs оболочки: запуск, движение, завершение, отмена; обход.
