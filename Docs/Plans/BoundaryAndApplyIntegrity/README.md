# План целостности границы и применения

> **Материализует:** подтверждённые находки внешнего ревью от 2026-08-23 и расхождения `STATUS-005…007`.
> **Задачи:** BAI-01…11.
> **Результат:** данные не теряются на границе молча, успешным считается только фактически выполненное применение, а утверждение о транзакционности либо истинно, либо снято.

## Цель

Закрыть один корневой дефект и его следствия.

Корень: **схема поля не замкнута**. Адаптер читает ключи, которые знает, и игнорирует остальные. Поэтому автор контента, отправивший `item_icon_resource_ids`, `character_resource_ids` или ключ с опечаткой, не получает ни ошибки, ни данных на экране. Этот механизм уже дважды произвёл живой дефект: персонажи сцены (LOC-AF-04, устранён точечно) и иконки предметов/эффектов (NEW-03, открыт). Точечная починка второго случая оставит механизм на месте и произведёт третий.

Смежная группа — применение, сообщающее успех, которого не было: пропуск reconcile при неразрешённом классе виджета (`STATUS-007`) и немутирующий откат, который мутирует (`STATUS-006`).

## Состояние на входе

| Что | Сейчас |
|---|---|
| Неизвестный ключ внутри значения поля | Игнорируется; проверка `unknown field` работает только по `field_id` |
| `item_icon_resource_ids`, `effect_icon_resource_ids` | Презентер их вычисляет и отправляет, `BuildLocationPlayerStatus` не читает |
| Контракт `location_player_status.v1` | Описывает `name` и портрет; коллекций предметов и эффектов не упоминает |
| Неразрешённый класс дочернего виджета | Четыре пути композитов пропускают reconcile и возвращают `true` |
| То же условие в `ButtonList` / `DropdownSelect` | Возвращает `false` с логом — эталон уже есть |
| `ReconcileEntries` при отказе `ApplyItem` | Оставляет переиспользованные виджеты в новом состоянии; doc-комментарий утверждает обратное |
| `CompositeRollbackContract` | После `false` проверяет только число детей |
| Грамматика ключа повторяемого элемента | Контракт требует `[a-z0-9_.-]+`, реализация принимает ещё `@` и `:`, собственные примеры контракта требуют их |
| Типографский conformance | Ни один виджет не создаётся; сравнивается helper сам с собой |
| Границы кнопок на 1280×720 | Проверены только `size > 0` и нижний край; горизонтальное переполнение зелёное |
| `GetItemRepeater` и ещё четыре геттера | `BlueprintPure`, при этом делают `NewObject` и `SetContainerPanel` |
| `StaminaMeter`, `Character`, `ResourceIcon` | Объявлены и привязываемы; первые два — устаревшая поверхность, третий только сворачивается и никогда не показывается |

## Принятые решения

- **Сначала замыкание схемы, потом ключи.** Обратный порядок даёт зелёный экран и оставленный механизм: добавить два ключа в адаптер дешевле, но именно это и было сделано для персонажей, после чего дефект воспроизвёлся.
- **Замыкание вводится с миграцией, а не одним переключателем.** Отклонение неизвестного ключа немедленно ломает любое поле, где такой ключ уже есть. BAI-01 сначала делает нарушение наблюдаемым, BAI-02 чинит найденное, и только BAI-03 переводит его в отказ.
- **Ложное утверждение снимается, если не становится истинным в этом же change set.** Doc-комментарий `UGV2ListViewWidgetBase` о транзакционности либо подкрепляется откатом, либо переписывается по факту. Оставить как есть нельзя.
- **Эталон не изобретается.** Поведение при неразрешённом классе приводится к уже существующему в `CanApplyButtonModels`, а не проектируется заново.

## Границы

Не входят: `STATUS-001` (lifecycle сессии), `STATUS-002` (effects), `STATUS-003` (sentinel политики масштабирования — требует ADR и меняет поведение существующих ассетов), `STATUS-004` (предиктивный глубокий preflight). Пять схем без Lua-производителя (`image`, `portrait`, `progress_bar`, `modal`, `tab_container`) — незадействованная поверхность, а не дефект; в план не входят.

## Общие правила выполнения

1. Порядок задач M1 не меняется: наблюдаемость, миграция, отказ, документация.
2. Каждое исправленное утверждение получает проверку на **отрицательный** случай: тест обязан краснеть, если поведение вернётся.
3. Тест, доказывающий более слабое свойство, чем заявляет его имя, переписывается или снимается; дополнение его новым assert поверх старого не считается закрытием.
4. Ассеты меняются только через `unreal-mcp`, с последующими compile, save и прогоном automation.
5. Закрытая строка `STATUS-005…007` удаляется из [Implementation Status](../../Status/ImplementationStatus.md) тем же change set, который её закрывает.
6. Правки нормативных контрактов (`Docs/UI/`) выполняются в той же задаче, что и код, который делает утверждение истинным.

## Итоговый Definition of Done

- [ ] Неизвестный ключ внутри значения Screen Field отклоняется типизированной ошибкой, а не игнорируется. (BAI-01…03)
- [ ] Иконки предметов, вычисленные презентером, видны на экране локации. (BAI-02)
- [ ] Контракт `location_player_status.v1` описывает форму поля целиком, включая обе коллекции. (BAI-04)
- [ ] Неразрешённый класс дочернего виджета даёт отказ применения, а не успех с пустой коллекцией. (BAI-05)
- [ ] Отказ `ApplyItem` не оставляет переиспользованные виджеты в новом состоянии, либо утверждение о транзакционности снято и заменено фактическим. (BAI-06)
- [ ] `CompositeRollbackContract` проверяет значения переиспользованных виджетов, а не только их число. (BAI-07)
- [ ] Единая грамматика ключа действует одновременно в контракте, C++, Lua и conformance. (BAI-08)
- [ ] Типографский conformance создаёт виджеты и читает фактический размер шрифта их renderer-ов. (BAI-09)
- [ ] На 1280×720 проверяется вхождение кнопки в обе оси и в границы своей панели, на длинном тексте. (BAI-10)
- [ ] Ни один `BlueprintPure` не создаёт объектов; мёртвая привязка снята. (BAI-11)
