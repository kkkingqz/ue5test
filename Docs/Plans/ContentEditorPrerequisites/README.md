# План предусловий редактора контента

> **Материализует:** раздел 40 [Content Editor Plugin](../../Proposals/ContentEditorPluginProposal.md).
> **Задачи:** CEP-01…12.
> **Результат:** три блокирующих пункта закрыты; редактор контента и декларативные экраны разблокированы.

## Цель

Закрыть три возможности, без которых визуальный редактор будет порождать изменения, которые нечем проверить: правило версионирования схем, точечную правку поля в файле и метаданные представления для схем.

Работа разблокирует сразу два направления — [Content Editor Plugin](../../Proposals/ContentEditorPluginProposal.md) целиком и декларативные экраны из [Simplified Authoring Surface](../../Proposals/SimplifiedAuthoringSurfaceProposal.md), которые не вошли в свой план по той же причине.

Первые два пункта не требуют Unreal Editor вовсе и проверяются существующими средствами.

## Состояние на входе

Проверено экспериментом на копии `GameData/rh`.

**Репозиторий уже является арбитром схемных изменений.** Сужение `min: 0` → `min: 50` даёт при сборке диагностику с файлом, строкой, definition и JSON-указателем:

```text
error core:diagnostic.schema.value.constraint_failed definitions/items.json5:9:16
  int64 value violates min/max constraint (definition=rh:item.weapon.iron_sword)
  (pointer=/definitions/0/data/price)
```

**Две версии схемы одного типа сосуществуют.** `item.v1` и `item.v2` рядом, файлы definitions на разных версиях — `validate` зелёный. Поэтапная миграция контента возможна без новой машинерии; это меняет оценку строгого правила с дорогой на дешёвую.

**Схема влияет на `content_hash`.** Комментарий не меняет хэш (он считается по нормализованным значениям), значимое изменение — меняет. Поэтому метаданные представления обязаны быть изолированы от хэша.

**Позиций достаточно, смещений нет.** Диагностики несут `StartLine`/`StartColumn`/`EndLine`/`EndColumn`; байтовых смещений в спане нет, и перевод позиции в смещение — отдельная работа.

**Переписыватель умеет четыре операции:** создать файл, отформатировать запись, вставить запись, заменить строковые токены. Изменить значение поля и удалить запись он не умеет.

## Принятые решения

- **Строгая классификация схемных изменений.** Аддитивно-необязательное — на месте; сужение, удаление, переименование и новое обязательное поле — только с новой `schema_version`. Старая версия живёт, пока контент переезжает. Раньше вариант оценивался дороже: предполагалось, что сосуществование версий надо строить, — оно уже работает.
- **Точечная правка по спану, а не перезапись файла.** Перезапись из разобранной модели дешевле на порядок, но уничтожает комментарии и форматирование: первый же автор, открывший diff после смены `hp: 100` на `120`, увидит переписанный файл целиком и перестанет доверять редактору.
- **Метаданные представления — в отдельном файле рядом со схемой.** Изоляция от `content_hash` получается структурно, а не отдельной избирательностью в нормализации, и повторяет уже принятое решение по PO-каталогам. Риск устаревания снимается гейтом.

## Границы

Входят: правило версионирования и его фиксация фикстурой, точечная правка значения поля и удаление записи, поверхность CLI для обеих операций, формат и выдача метаданных представления, гейт на устаревшие метаданные.

Не входят:

- сам плагин редактора — [Content Editor Plugin](../../Proposals/ContentEditorPluginProposal.md);
- декларативные экраны и удаление `location_screen.lua`;
- автоматическая миграция контента между версиями схемы: инструмент переноса появится, когда появится вторая версия реальной схемы;
- обнаружение разрушающего изменения сравнением с предыдущей версией схемы: правило держится следствием — несовместимость ломает сборку.

```text
CEP-01 (ADR) ─┬─► M1
              ├─► M2
              └─► M3
```

После ADR три этапа независимы и могут идти в любом порядке или параллельно: они закрывают разные возможности и не пересекаются по коду.

## Общие правила выполнения

1. Точечная правка обязана сохранять комментарии и форматирование всего файла, кроме изменённого узла. Round-trip проверяется на файле с комментариями.
2. Метаданные представления не влияют на `content_hash` и на сборку репозитория; их отсутствие не является ошибкой.
3. Изменение схемы меняет `content_hash` — задачи, трогающие схемы фикстур, осознанно обновляют pinned-значения.
4. Каждая задача, меняющая failure semantics, добавляет negative case.
5. Новое observable behavior синхронно отражается в contract.
