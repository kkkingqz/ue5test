# План экрана локации

> **Материализует:** [Gameplay Location Screen](../../Proposals/GameplayLocationScreenProposal.md).
> **Задачи:** GLS-01…16.
> **Результат:** первый настоящий игровой экран — один шаблон `textsystem` с четырьмя композитами, наполняемый определением локации и текущим состоянием, работающий от 4K до 720p.

## Цель

Собрать экран, который одновременно является рабочим экраном локации и интеграционной проверкой всего базового набора UI: он трогает почти каждый примитив, оба конвейера, три политики масштабирования и семантический ввод.

Ключевое решение лежит не в раскладке, а под ней: **экран является одним Screen Instance с устойчивой идентичностью**. Постоянство верхней панели и панели персонажа обеспечивается переиспользованием экземпляра при реконсиляции, а не отдельными слоями оболочки.

## Состояние на входе

Проверено по коду.

| Что | Сейчас |
|---|---|
| Многослойная реконсиляция | Реализована: `FGV2LayeredUiReconciler`, `UGV2GameShellWidgetBase`, шесть слоёв |
| Примитивы `core` | `Text`, `Image`, `Button`, `Icon`, `ProgressBar`, `Separator`, `Panel`, `ScrollArea`, `ListView`, `TabContainer` |
| Композиты `textsystem` | `RichText`, `RichTextPopover`, `ButtonList`, `Modal`, `Portrait` |
| Шаблон `LocationScreen` | Назван в [UI Index](../../UI/README.md) как принадлежащий `textsystem`; не существует |
| Презентер локации | `textsystem:module.presentation.location_presenter` строит экран из определения локации и определения экрана |
| Идентификатор шаблона | `M.show_screen({ template = screen_id })` — **идентификатор определения экрана используется как ключ реестра шаблонов** |
| Схема определения экрана | `core:schema.definition.screen.v1`: заголовок, описание, соседние локации, действия. Ни фона, ни персонажа |
| Экраны `rh` | Три определения: таверна, рынок, ворота |
| Ресурсы-заглушки | Отсутствуют; политика подстановки в contract описана |

## Принятые решения

- **Модель экрана и набор значений разделены.** Модель — один шаблон с фиксированными полями; значения — определение локации плюс текущее состояние.
- **Экран является одним Screen Instance маршрута**; переход между локациями не меняет ни `screen_id`, ни `instance_key`.
- **Все четыре композита принадлежат `textsystem`.** Экран не создаёт ни одного ассета в `Content/RH/UI/`: игра участвует только данными.
- **Фон — подложка `tile` плюс вписанная иллюстрация `fixed_aspect`.** Обрезка не вводится, контракт изображений не меняется.
- **Персонаж один**, вписывается по правилу `contain` с привязкой к нижнему краю; множитель масштаба через границу не передаётся.
- **`screen_ids` сохраняется** и определяет, чем наполняется экран для данной локации.
- **Подсказки в этот план не входят.**
- **Отсутствующий ресурс заменяется заглушкой** соответствующего режима отрисовки.
- **Размеры задаются preferred с ограничениями min/max**; доли экрана в процентах остаются ориентиром на опорном разрешении.

## Границы

Входят: контракт экрана, четыре композита, презентер, расширение схемы определения экрана, ресурсы и заглушки, проверка на матрице разрешений.

Не входят:

- **Подсказки для иконок** — отложенный набор элементов, вводится со своим потребителем.
- Несколько персонажей, слой переднего плана, иконки команд, значки уведомлений — второй срез.
- Диалоги, инвентарь, лист персонажа, журнал заданий.
- Произвольный граф сцены, анимация персонажей, трёхмерная область просмотра.
- Система контрольных точек раскладки.

## Критический путь

```text
M1 ─┬─► M2 ─┬─► M4
    └─► M3 ─┘
```

**M1 обязателен для обоих.** Пока идентификатор определения экрана используется как ключ шаблона, `screen_id` маршрута меняется при каждом переходе, экземпляр пересоздаётся целиком, и никакое постоянство панелей невозможно.

M2 и M3 независимы: композиты собираются под известные схемы полей, презентер наполняет те же схемы.

## Общие правила выполнения

1. Ассеты редактора создаются и меняются только через `unreal-mcp`, с compile, save и проверкой контракта automation-тестом.
2. Ни один композит не создаёт собственного пути для текста, изображения или повторяемых детей; проверяется automation по полному инвентарю `/Game/UI`.
3. Ни один ассет этого плана не попадает в `Content/UI/` или `Content/RH/UI/`: все четыре композита и шаблон принадлежат `textsystem`.
4. Ни одно физическое значение отрисовки не пересекает границу Lua.
5. Повторяемые элементы подчиняются общему правилу ключей.
6. Правила проверяются на **отрицательный** случай.
7. Новое observable behavior синхронно отражается в contract того же change set.

Отдельного ADR план не требует: все решения являются уточнением уже принятых правил — трёхуровневого владения, модели документа, контракта изображений. Если по ходу выяснится, что меняется инвариант, ADR создаётся до отметки первой задачи.

## Итоговый Definition of Done

- [ ] Идентификатор шаблона и идентификатор определения экрана разделены; `route.screen_id` не меняется при переходе между локациями.
- [ ] Переход между локациями переиспользует экземпляр экрана: верхняя панель и панель персонажа не пересоздаются, а обновляются.
- [ ] Экран собран из примитивов `core` и композитов `textsystem`; в `Content/RH/UI/` нет ни одного ассета.
- [ ] Четыре поля экрана имеют схемы и адаптеры наравне с существующими.
- [ ] Значения собираются из определения экрана и текущего состояния; игра не пишет полей документа напрямую.
- [ ] Фон сохраняет пропорции без обрезки при любых пропорциях экрана.
- [ ] Персонаж вписан и привязан к нижнему краю; множитель масштаба через границу не передаётся.
- [ ] Отсутствующий ресурс заменяется заглушкой; экран остаётся пригодным.
- [ ] Команды строятся списком, подчиняются правилу ключей и отправляют семантические действия.
- [ ] Экран пригоден к использованию на 1280×720 и проходит матрицу из шести разрешений.
- [ ] Экран практически проверяет базовый набор: примитивы, оба конвейера, три политики масштабирования, семантический ввод.
