# M5 — Package Boundary

> **Материализует:** `STATUS-010` и две части `STATUS-008`, дописанные проверкой границы пакетов 2026-09-03.
> **Задачи:** DCA-18…21.
> **Результат:** принадлежность к пакету и порядок слоёв выводятся из пиннингованного замыкания, а не из литералов в C++.

## Результат этапа

Проверка на зашитые значения дошла до границы пакетов и нашла там ту же форму, что в раскладке, но с более острым следствием: **перечислитель существует в проекте и не читается**. `GameData/mods.lock.json5` перечисляет ровно `core`, `textsystem`, `rh` с полем `load_index`, задающим порядок слоёв. Три места в `Source/` кодируют это же знание литералами и расходятся с ним и друг с другом.

Хорошее состояние тоже стоит записать: `rh:` и `sample:` в `Source/` не встречаются ни разу — из 1378 идентификаторов с пакетом 1269 это `core:`, 109 `textsystem:`. Правило развязки держится там, где его записали; этап распространяет его на то, что записано не было.

Что найдено:

| Место | Что закодировано литералами | Задача |
|---|---|---|
| `GV2ScreenRegistry.cpp:24-51` | Порядок слоёв как лесенка из двух ветвей с безусловным `return true` в конце | DCA-18 |
| `GV2ScreenFieldMaterializer.cpp:21-25` | Четыре корня схем, включая `sample`, которого нет в замыкании | DCA-19 |
| `GV2UiCapability.cpp:12` | Владелец схемы как закрытая тройка; результат не читает ни один production-путь | DCA-20 |
| `GV2UiCapabilityObservability.cpp:40-44` | Четыре `textsystem:` id в модуле уровня `core` | DCA-21 |

DCA-18, DCA-19 и DCA-20 независимы: они лежат в разных файлах и решают разные вопросы. DCA-21 закрывается последней — гейт зеленеет только после того, как места исправлены.

## Задачи

- [x] **DCA-18 — Порядок слоёв выводится из замыкания, а не из лесенки имён**
  - `UGV2ScreenRegistry::IsAssetAllowedForScreenNamespace` реализует `ADR-0035 §5` двумя ветвями — `core` не ссылается на `/game/textsystem/` и `/game/rh/`, `textsystem` не ссылается на `/game/rh/` — и завершается безусловным `return true`. Для любого другого namespace проверки нет вовсе: мод может ссылаться на ассеты `rh`, два мода — друг на друга. Порядок, который лесенка кодирует руками, лежит в `mods.lock.json5` как `load_index`.
  - Инвариант: правило слоёв формулируется через порядок пакетов, а не через их имена. Лесенка задаёт N−1 правило для N известных пакетов и молчит ровно про тот случай, ради которого правило существует, — про пакет, которого не было при её написании.
  - Не считается закрытием: добавление ветки для `rh` и для `sample` — это удлиняет лесенку, не меняя её природы; сохранение `return true` как поведения по умолчанию для неизвестного namespace.
  - Done:
    - решение принимается сравнением позиций пакета-владельца экрана и пакета-владельца ассета в порядке замыкания;
    - namespace, отсутствующий в замыкании, отклоняется, а не разрешается по умолчанию;
    - соответствие каталога ассета пакету перестаёт быть сравнением строкового префикса с зашитым списком;
    - существует случай с пакетом, которого нет в лесенке сегодня, и он отрицательный;
    - тест не берёт ожидаемую сторону из реализации: ожидание выводится из `load_index`, а не из перечисления тех же ветвей.
  - Evidence: `Source/GV2/Private/UI/GV2ScreenRegistry.cpp`, `Source/GV2/Private/Tests/GV2RuntimeSubsystemTests.cpp:4352`, `GameData/mods.lock.json5`, `Docs/Status/ImplementationStatus.md` (`STATUS-010`).
  - **Реализация (2026-09-06):** `IsAssetAllowedForScreenNamespace` получила третий параметр `PackageLoadOrder` (`TArray<FString>`, индекс = `load_index`) и теперь принимает решение сравнением позиций `IndexOfByPredicate` — своей и владельца ассета — вместо двух `if`-веток по имени; namespace, отсутствующий в массиве, возвращает `false` до какого-либо дальнейшего сравнения (замена безусловного хвостового `return true`). Сопоставление каталога ассета пакету вынесено в отдельную `FindOwningPackageForAssetPath` — единственная таблица `{префикс контента → package_id}` на все namespace вместо копии префиксов в каждой ветке; она называет только *владение* (какого пакета этот каталог), а не *порядок* — сама по себе таблица не решает allow/deny.

    Порядок берётся не заново изобретённым парсером, а тем же путём, которым его уже читает `UGV2RuntimeSubsystem::ResolveRepositoryPackageRoots()` — `GV2ContentHostSupport::DiscoverPackagesFromContainer` по `GameData/mods.lock.json5`, до этой задачи возвращавшим `FPackageDescriptor` (`package_id` + `load_index`) с сохранением только путей и отбрасыванием самого списка. Новая `UGV2ScreenRegistry::GetPackageLoadOrderFromGameData()` — независимый второй вызов того же обнаружения (Subsystem его не хранит доступным для `GV2ScreenRegistry.cpp` способом); дублирования знания при этом нет — источник один, `mods.lock.json5`, читается дважды одним и тем же кодом. `Validate()` теперь получает пустое покрытие (пакеты не разрешились) как явную ошибку, а не молчаливое разрешение всего.

    Тест (`GV2.Runtime.UI.ThemeOwnershipAndTextLengthContract`) переписан: вместо десяти утверждений с зашитым `true`/`false` — цикл по десяти парам (namespace, путь), где ожидание вычисляется в самом тесте отдельной `ExpectedAllowed` (сравнение позиций в РЕАЛЬНОМ `GetPackageLoadOrderFromGameData()`, не копия production-веток), с покрытым счётчиком (`CasesCovered` против `UE_ARRAY_COUNT(Cases)`). Дополнительно: (1) `"sample"` — namespace, отсутствующий в реальном `mods.lock.json5`, — отклоняется явным `TestFalse`, ровно тот случай, которого не было и который называет `STATUS-010`; (2) синтетический порядок из четырёх пакетов показывает, что появление нового пакета работает без единой новой ветки в реализации; (3) синтетический **развёрнутый** порядок (`rh, textsystem, core`) переворачивает допустимое направление ссылок — доказательство, что решение читается из позиций массива, а не подставлено по имени namespace.

    Верификация: headless `Automation RunTests GV2;Quit` — 108/108 passed, 0 ошибок; portable `ctest` — 76/76. `STATUS-010` удалён из `ImplementationStatus.md` целиком (версия 2.12 → 2.13) — условие закрытия выполнено дословно.

- [x] **DCA-19 — Корни схем берутся из пиннингованного замыкания**
  - `GV2ScreenFieldMaterializer.cpp:21-25` сканирует `GameData/core`, `textsystem`, `rh`, `sample`. `sample` отсутствует в `mods.lock.json5`, то есть сканируется пакет, которого в замыкании сессии нет. Это тот же фиксированный список, что и в `FGV2UiSchemaCache` (`STATUS-008`), но в другом файле — и `STATUS-008` его не называл.
  - Инвариант: сессия видит ровно те пакеты, которые приняло её замыкание. Список корней, живущий отдельно от замыкания, делает состав контента зависящим от того, что физически лежит в каталогах, а не от того, что принято.
  - Не считается закрытием: удаление одного `sample` из списка — список останется списком; вынесение того же списка в общую константу, чтобы «не дублировался» — это устраняет расхождение двух копий, но не их отрыв от замыкания.
  - Done:
    - корни схем выводятся из того же замыкания, которым пользуется загрузка контента;
    - обе копии списка (`GV2ScreenFieldMaterializer`, `FGV2UiSchemaCache`) перестают существовать как списки;
    - пакет, отсутствующий в замыкании, не сканируется, и это проверено;
    - схема, чей namespace не совпадает с пакетом-источником, отклоняется, а не регистрируется по собственному полю `id`;
    - соответствующая часть `STATUS-008` закрыта или сужена до того, что действительно осталось.
  - Evidence: `Source/GV2/Private/Application/GV2ScreenFieldMaterializer.cpp`, `Source/GV2/Private/UI/GV2UiSchemaCache.cpp`, `GameData/mods.lock.json5`.
  - **Реализация (2026-09-06):** обе копии списка (`GV2ScreenFieldMaterializer.cpp`'s `DiscoverDefaultSchemaPackageRoots`, четыре зашитых пути включая несуществующий в замыкании `sample`) заменены на новый общий `GV2PackageClosure::DiscoverFromGameData()` (`Source/GV2/Private/Application/GV2PackageClosure.h/.cpp`) — единственное место, читающее `GameData/mods.lock.json5` через `GV2ContentHostSupport::DiscoverPackagesFromContainer` и возвращающее пары `{package_id, каталог}`, упорядоченные по `load_index`. Тот же вызов уже существовал дважды по факту (`UGV2RuntimeSubsystem::ResolveRepositoryPackageRoots` — со своей веткой для тестового фикстура `sample`, не общей; и `UGV2ScreenRegistry::GetPackageLoadOrderFromGameData` из `DCA-18`) — `GV2ScreenRegistry.cpp` переведён на общий хелпер тем же изменением, вместо третьей отдельной копии дискавери-вызова.

    `FGV2UiSchemaCache::PackageRoots` сменил тип с `TArray<FString>` на `TArray<FGV2SchemaPackageRoot>` (`{PackageId, RootDirectory}`) — конструктор и оба тестовых прямых вызова (`GV2UiPropertyHostTests.cpp:342`, `GV2DeclaredCompositeTests.cpp:227`) обновлены. `EnsureDiscovered()` теперь парсит собственное поле `id` каждой найденной схемы через `GV2ContentCore::FStableId::Parse` и сравнивает его namespace с `Root.PackageId`: несовпадение — тот же путь, что для битого JSON5 (схема просто не регистрируется, а не выбрасывает ошибку), поэтому подложенная в чужой каталог схема с namespace `core:` внутри `GameData/rh` больше не проходит по одному только `id`. `RegisterUiSchemaDocument`'s `PackageId` аргумент заодно исправлен с полного пути (`TCHAR_TO_UTF8(*Root)`, использовалось только для диагностик, но было неверного типа) на чистый `package_id`.

    Новый тест `GV2.Runtime.ContentAuthoring.SchemaRootsFromClosure` (`GV2UiPropertyHostTests.cpp`) проверяет оба Done-пункта напрямую: (1) `GV2PackageClosure::DiscoverFromGameData()` возвращает ровно три пакета `mods.lock.json5` и не включает физически существующий, но не пиннингованный `GameData/sample`; (2) реальная схема `textsystem:schema.ui_field.location_commands.v1`, поданная в `FGV2UiSchemaCache` с намеренно неверным тегом `core`, не регистрируется (`GetCompiledSchema` возвращает `nullptr`), а с верным тегом `textsystem` резолвится как раньше — без изменения содержимого `GameData/`, только тегом корня.

    `STATUS-008` сужен до части Decision 7 (`DCA-20`); часть про фиксированные списки и Decision 6 закрыта текстом в самой строке.

  - **Реализация (2026-09-06):** `GResourceProbeCandidates` (пять зашитых id, четыре `textsystem:resource.ui.missing_*` и один `core:resource.ui.old_paper_tile_256`) и отдельный дублирующий зашитый default-пара `textsystem:resource.ui.missing_icon`/`missing_portrait` в `MakeDistinctValuePair` заменены одной `GetResourceProbeCandidates()`, читающей `UGV2ImageResourceCatalogSettings::GetConfiguredCatalog()->GetEntries()` — кандидаты пробы наблюдаемости приходят из данных (фактически загруженного каталога ресурсов), а не названы в коде `GV2`. Проверка показала, что простой перенос тех же id в `core:`-эквивалент был невозможен без создания нового контента: у `core` сегодня есть ровно один image-ресурс (`old_paper_tile_256`, tile-режим), а все `FixedAspect`-кандидаты существуют только в `textsystem` — обоснование, почему выбран путь «из данных», а не «заменить строки на другие строки».

    Новый гейт `GV2.Runtime.UIKit.PackageNameLiteralGate` (`Source/GV2/Private/Tests/GV2PackageBoundarySourceTests.cpp`) сканирует каждый production `.cpp` под `Source/GV2` (тесты — вне области, по тексту задачи) и для каждого пакета из пиннингованного замыкания (`GV2PackageClosure::DiscoverFromGameData()`), кроме `core`, ищет его как целое слово внутри строкового литерала — это ловит и `<pkg>:`-префиксованный id, и голый литерал имени пакета (например, каталоговый компонент `/game/<pkg>/`). Множество пакетов берётся сканированием того же замыкания, которым уже пользуются `DCA-18`/`DCA-19`, а не зашито тут же второй раз. Строки комментариев вырезаются перед проверкой (иначе документирующий пример вроде `// e.g. "textsystem:foo"` ложно бы сработал).

    Три обоснованных исключения — `GetPackageBoundaryExceptions()`, растёт только осознанно: (1) `GV2ScreenRegistry.cpp` — `FindOwningPackageForAssetPath`'s таблица `{content-root → package_id}` (`DCA-18`), не выводимая из `mods.lock.json5` (там нет понятия `/Game/`-путей); (2) `GV2RuntimeSubsystem.cpp` и (3) `GV2SessionCoordinator.cpp` — парные тестовые fixture-ветки под `WITH_DEV_AUTOMATION_TESTS`, форсирующие пакет `sample` вместо `rh` для тестов, которым нужен пакет без конфликта travel-действия `textsystem`. Гейт проверяет, что каждое из трёх исключений действительно сработало на скане (`ExceptionsHit.Num() == GetPackageBoundaryExceptions().Num()`) — устаревшее исключение, переставшее что-либо покрывать, тоже стало бы видимой ошибкой.

    Существующий `CORE_DECOUPLING_RULE` (`Tools/Content/validate_core_decoupling.py`, ctest `core_decoupling_gate_contract`) не тронут: он покрывает другую площадь (`Scripts/`, `GameData/core/`, весь `Source/` включая тесты, только `rh`/`sample`, зашитые в его собственном regex) и по тексту задачи остаётся отдельным правилом. Побочный эффект первой версии нового файла: собственные объясняющие комментарии нового теста содержали строки `` `rh:` ``/`` `sample:` `` для описания старого гейта и сами провалили `core_decoupling_gate_contract` — переформулировка без буквальных префиксованных id устранила это, не меняя смысла.

    Продемонстрировано: временный синтетический литерал `TEXT("rh:diagnostic.synthetic_probe")`, добавленный в `GV2UiCapability.cpp` (файл вне списка исключений), уронил `PackageNameLiteralGate` с указанием точного файла и строки; после отката — снова зелёный.
