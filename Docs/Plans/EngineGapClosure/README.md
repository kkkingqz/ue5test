# Engine Gap Closure: план реализации

> **Материализует:** закрытие [пробелов движка](../../Status/EngineGaps.md) и [заявок на экраны](../../Status/ScreenRequests.md) в порядке, при котором каждый этап закрывается полностью до начала следующего; основание — [Temporary Game Modes](../../Proposals/TemporaryGameModesProposal.md), [Mutation Window Transactionality](../../Proposals/MutationWindowTransactionalityProposal.md) и [архитектура геймплея rh](../../RH/GameplayArchitecture.md).
> **Не является нормативным:** проектирование ниже описывает рекомендуемую реализацию. Новые правила и failure semantics фиксируются ADR на этапе M0 и переносятся в contracts задачей EGC-21; план не подменяет ADR.
> **Исполнение:** последовательно по задачам. Checkbox задачи — единственный источник её завершения.

**Цель:** довести движок до состояния, в котором геймплей `rh` пишется целиком на authoring surface без обходов через `game.*` и сырое `game.state`, а экраны собираются из уже существующих элементов.

## Почему порядок водопадный

Этапы выполняют разные команды, и команда авторского слоя начинает работу только после полного закрытия этапа по движку: вариант параллельной работы с зависимостями между отдельными задачами отвергнут. Из этого следуют два правила, которых нет в других планах.

**Правило 1. У каждого гэпа критерий закрытия, который можно опровергнуть.** Реестр пробелов писался как справка о состоянии: его поле «Требуется» задаёт направление, а не границу. В водопаде реестр становится договором между этапами, поэтому поле `Done` каждой задачи формулирует проверяемое утверждение, а не намерение.

**Правило 2. У каждого механизма фикстурный потребитель** (таблица «задача → потребитель» — в [Д1](StateAndAuthoring.md))**.** Авторский слой — предпоследний этап, поэтому в момент закрытия движка ни один его механизм не имеет реального потребителя. Единственная защита от «движок угадал неправильно» — фикстура, которая делает то, что потом будет делать `rh` ([ADR-0046](../../ADR/0046-test-content-coupling-boundary.md) это прямо разрешает). Механизм без фикстурного вызова не закрывает задачу, даже если он покрыт unit-spec.

## Этапы

| Этап | Содержание | Закрывает |
|---|---|---|
| M0 — Решения до кода | Транзакционное окно мутации: один журнал, живущий командой, с перечисленными триггерами отката; временные режимы как категория состояния и маршрутизация презентации | — |
| Д1 — Состояние и авторская поверхность | Журнал и откат, выводимая изоляция, режимы, экземпляры, коллекции, перебор Definitions, поля расширений, аргументы текста, priority | GAP-003…GAP-005, GAP-008…GAP-013 |
| Д2 — Презентация и возможности UI | Маршрутизатор, полная публикация документа, источники меню, панели статуса, подсказка вне текста, реестр kind как перечислитель | GAP-001, GAP-002, GAP-006, GAP-007 |
| Э3 — Экраны | Пять Screen Template по заявкам | SR-001…SR-005 |
| Э4 — Контент `rh` | Отвязка регрессии движка от игрового контента, снятие заглушки геймплея, механики и шесть пунктов стартового пакета | [стартовый пакет](../../Status/EngineGaps.md#стартовый-пакет-rh-что-блокирует) |

Д1 и Д2 — два полностью закрываемых подэтапа одного этапа по движку: обе команды, экранная и авторская, начинают после Д2. Разделение существует ради двух точек приёмки вместо одной, а не ради параллельной работы.

## Что каждый этап передаёт следующему

Правило ведения планов требует перед отметкой `[x]` назвать, что следующая задача считает существующим. На уровне этапов это:

| Граница | Следующий этап считает существующим |
|---|---|
| M0 → Д1 | категорию transient mode state, правило единого журнала с перечнем триггеров отката и признаком мутации для `fail()` на журнале, порядок «транзакция → факты → презентация», kind `mode` в [Stable ID](../../Architecture/StableIDSpecification.md), пометку об израсходованном условии в [ADR-0039](../../ADR/0039-presentation-source-singleton.md) |
| Д1 → Д2 | `modes.active()` и run активного режима, читаемые из построителя экрана; выводимую изоляцию, в которую Д2 добавляет своё состояние; фикстурный пакет `Tests/Fixtures/SyntheticMechanicalFixture/synthetic/` и общий для обоих хостов перечислитель корней пакетов тира, которым он загружается (EGC-07) |
| Д2 → Э3 | объявленные `enabled`/`disabled_reason` у элемента меню, механизм подсказки с одним работающим потребителем, маршрут экрана режима, источники меню и значения панелей статуса |
| Э3 → Э4 | пять зарегистрированных Screen Template с их schema, у каждого фикстурный документ, проходящий Prepare/Commit; заглушку геймплея `rh` ещё на месте — она остаётся живым корпусом регрессии до начала Э4 |

## Срезанный состав возможностей UI

Из двух возможностей, которых не хватало заявкам и которые не были записаны ни одним гэпом, в план входит одна.

**Входит: подсказка вне текстовых фрагментов** (EGC-20). Общая половина механизма наведения уже существует и задокументирована как переиспользуемая: содержимое подсказки — вложенный подготовленный экран (`FPreparedRichTextHover`), позиционирование — `IGV2ScreenAnchorHost`, присоединение — host-local участник `overlay_stack`, длительность объявляется контентом. Жизненный цикл при этом принадлежит `UGV2RichTextWidgetBase`. Задача — извлечь его во владельца, у которого может быть второй потребитель.

**Не входит: UI-local выбор, управляющий содержимым.** Механизм «N подготовленных альтернатив, одна активная, переключение без новой ревизии» существует как `tab_container`, но его переключатель — заголовок с единственным текстовым значением, и внешнего объявленного триггера у `SelectTabByKey`/`SelectTabByIndex` нет. Вместо расширения механизма приняты два решения по содержанию заявок:

- [SR-002](../../Status/ScreenRequests.md#sr-002-отчёт-о-конце-хода) теряет требование UE-local листания: номер текущей записи — transient mode state, «Далее» — обычная команда режима. Это делает отчёт структурно идентичным [SR-004](../../Status/ScreenRequests.md#sr-004-экран-диалога), где шаг и так является новой ревизией того же Screen Instance.
- [SR-003](../../Status/ScreenRequests.md#sr-003-экран-магазина) теряет отдельную область описания: описание товара показывается в его строке, выбора нет.

Обе правки вносятся в заявки задачей EGC-21 как часть переноса правил, а не задним числом при реализации экранов.

## Заглушка геймплея снимается, а не дописывается

Пакет `rh` сегодня содержит заглушку: `authoring/gameplay.lua` на 148 строк со всеми командами разом (`travel`, `time.wait_day`, `work.do_work`, `request_buy`, `buy`, `confirm_buy`, `cancel_buy`, `start_game`), `services.trade`, семь action bindings, модуль `gameplay/actors.lua` на 153 строки, объявленный `authoring = true`, но читающий `game.state` напрямую, и `runtime/session_start.lua`. Всего 353 строки Lua и семь файлов definitions.

Эта же заглушка — единственный живой игровой корпус, против которого Д1, Д2 и Э3 проверяют регрессию: `rh_layered_presentation_spec` входит в пять specs, которые EGC-16 обязан пройти без правок. Поэтому порядок такой:

1. заглушка живёт без изменений до конца Э3, кроме двух вынужденных правок — EGC-08 снимает три прямых обращения к `game.state`, EGC-32 снимает дублирование цены;
2. Э4 начинается с EGC-27 — регрессия движка отвязывается от игрового контента: двадцать Lua-spec ссылаются на `rh:`, и до переноса каждый шаг снятия заглушки красил бы проверки движка;
3. EGC-28 снимает заглушку целиком и раскладывает пакет по слоям `mechanics/` и `content/`, которых сегодня нет;
4. EGC-29…EGC-35 наполняют пакет заново.

Дописывать механики рядом с заглушкой нельзя: это дало бы два конвейера действия в одном пакете и команды, различающиеся только именем.

## Риски

**Этап по движку нельзя проверить своими потребителями.** Снимается правилом 2 выше. Остаточный риск: фикстура выражает то, что автор плана считает нужным геймплею, а не то, что окажется нужным. Поэтому фикстуры Д1 выводятся из механик [архитектуры геймплея](../../RH/GameplayArchitecture.md#5-механики), а не придумываются по месту.

**Режимы вводят новое расхождение, если откат canonical state опаздывает.** Команда режима, упавшая после первой канонической записи, оставила бы run восстановленным, а состояние — частично изменённым. Поэтому EGC-03 стоит перед EGC-05, а не рядом с ним, и журнал один (EGC-01). Отдельная половина того же риска — отказ, а не ошибка: `fail()` перехватывается внутри окна, поэтому журнал, живущий окном, к моменту отказа уже отброшен, и триггеры отката перечисляются решением M0, а не выводятся из слова «ошибка».

**Изоляция тестов сегодня — рукописный список из четырёх переменных.** Пятая, добавленная где угодно, протекает между spec case молча. EGC-04 делает множество выводимым до того, как режимы добавят в него пятый элемент; иначе тот же дефект будет заработан заново на следующем куске временного состояния.

**Объём.** Этап по движку — 22 задачи (M0 — две, Д1 — тринадцать, Д2 — семь), включая два ADR, и ещё две задачи Э4 уходят на снятие заглушки, а не на геймплей. Это программа, а не один change set. Декомпозиция Э4 держится на уровне пунктов стартового пакета и принадлежит [Docs/RH](../../RH/README.md): она уточняется, когда закрывается Э3, и не является источником задач до этого момента.
