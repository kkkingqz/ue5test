# Д1 — состояние и авторская поверхность

> **Материализует:** подэтап Д1 [Engine Gap Closure](README.md): транзакционность, временные режимы и те возможности authoring surface, без которых механики [архитектуры геймплея rh](../../RH/GameplayArchitecture.md#5-механики) невыразимы. Ни одна задача этапа не требует работы в редакторе.

**Фикстурный потребитель на каждую задачу (правило 2 плана).** EGC-21 проверяет, что у каждого механизма Д1 и Д2 он есть, поэтому он назван в самой задаче, а не выводится при закрытии этапа:

|---|---|
| EGC-03, EGC-06 | команды фикстурного пакета, пишущие и в canonical state, и в run |
| EGC-04 | синтетическая переменная уровня модуля в spec протечки |
| EGC-05, EGC-07 | демонстрационный режим в `SyntheticMechanicalFixture` |
| EGC-08 | предметы с владельцем в фикстурном пакете — будущий инвентарь |

## EGC-03 — Реализовать журнал окна мутации и откат канонического состояния

- [x] EGC-03 — Реализовать журнал окна мутации и откат канонического состояния

**Зависимость:** EGC-01. **Файлы:** `Scripts/runtime/mutation_window.lua`, `Scripts/runtime/command_dispatcher.lua`, `Scripts/authoring/context.lua`, `Tests/Lua/lifecycle/mutation_window.lua`, `Tests/Lua/authoring/commands.lua`. Docs: `CanonicalStateAndSave.md`, `CommandsAndEvents.md`, `AuthoringSurfaceContract.md` (scope больше не хранит `initial_write_revision`).

**Инвариант:** [ADR-0050](../../ADR/0050-transactional-mutation-window.md). Окно мутации уже перехватывает каждую запись охраняемым прокси с `__newindex` и ведёт монотонный `write_revision`; точка встраивания существует и используется. Нарушение — состояние, доверенное после пойманной ошибки или после отказа.

**Решение:** журнал в окне мутации: однократная запись прежнего значения на пару «таблица, ключ», категория — поле записи: `canonical` и `transient`, счётчик растёт только на первой. Здесь используется только `canonical`: первым пишет в `transient` EGC-05, в откат эту категорию вводит EGC-06. Ключ, отсутствовавший до команды, восстанавливается отсутствующим, а не присутствующим со значением `nil`. Журнал не является частью канонического состояния, не попадает в сейв и не пересекает boundary. `write_revision` остаётся монотонным и не откатывается.

Решение «применить или отбросить» принимает `command_dispatcher`, когда исход команды известен: откат на вылетевшей ошибке, на отказе, возвращённом обработчиком таблицей, и на `fail()`. Поэтому журнал живёт командой, а не окном, и окно получает второй вход: `execute_in_window` остаётся самоопределяющимся — commit на нормальном возврате, откат на ошибке, — потому что его вызывают 96 раз в 18 spec-файлах и ещё раз внутри Lua-строки C++-теста сейвов, а отложенную форму использует только dispatcher. Транзакция, не решённая к моменту следующего открытия окна, — ошибка, а не отбрасывание по умолчанию. Решение принимается сразу после закрытия окна — **до** `event_bus.commit_command_context()` и до `game.presentation.resolve()`: оба исполняются в том же `pcall`, поэтому решение в нижней ветке ошибки откатывало бы состояние после доставленных фактов. Отказ валидатора в перечень триггеров не входит: `run_validators` исполняется до открытия окна, поэтому фикстура на этот случай зелена при любой реализации.

Признак мутации для `fail()` переводится со счётчика на журнал: `AuthoringFailAfterMutation` срабатывает по непустому каноническому срезу журнала, а `initial_write_revision` уходит из scope. Правило сохраняется, меняется сигнал, и проверкой этого служит `Tests/Lua/authoring/commands.lua`, который обязан пройти без правок.

**Не считается закрытием:** откатить только верхний уровень `game.state`, оставив вложенные таблицы; сравнить хеши вместо восстановления значений; держать журнал и восстановление в `command_dispatcher` поверх окна вместо вызова отката, принадлежащего окну; откатывать только вылетевшую ошибку, оставив отказ без отката; переложить решение «применить или отбросить» на каждого вызывающего `execute_in_window`; оставить `initial_write_revision` в scope вторым признаком мутации рядом с журналом.

**Шаги:**
1. Записать независимые фикстуры: разрежённый ключ, вложенная таблица, повторная запись того же ключа, ошибка в середине обработчика, отказ таблицей после мутации, `fail()` после мутации (остаётся `AuthoringFailAfterMutation`), `fail()` до мутации, успешная команда, нерешённая транзакция к следующему открытию окна.
2. Реализовать журнал и откат в `mutation_window.lua`; добавить отложенную форму входа и оставить `execute_in_window` самоопределяющимся; `command_dispatcher` вызывает `commit` или `rollback` до отбрасывания контекста событий.
3. Перевести `AuthoringFailAfterMutation` на канонический срез журнала и убрать `initial_write_revision` из scope; `Tests/Lua/authoring/commands.lua` проходит без правок.
4. Доказать, что хеш состояния после пойманной ошибки и после каждого вида отказа равен хешу до команды, через `state_hasher`, а не через чтение отдельных полей.
5. Мутационная проба: отключить применение журнала — краснеет ровно проверка равенства хешей; сузить триггер до вылетевшей ошибки — краснеют ровно фикстуры отказа.
6. Прогнать specs на обоих host-ах, `ctest`, `validate_docs`.

**Done:**
- Ошибка в середине обработчика оставляет каноническое состояние равным состоянию до команды, проверено хешем.
- Каждый из двух достижимых видов отказа — таблицей и `fail()` — оставляет каноническое состояние равным состоянию до команды, проверено хешем; отказ валидатора в перечень не входит, потому что окно к этому моменту не открыто.
- Отсутствовавший до команды ключ после отката отсутствует; присутствие со значением `nil` отвергается фикстурой.
- Успешная команда платит однократную запись прежнего значения на изменённый ключ и ничего больше.
- `fail()` до мутации не создаёт записей в журнале.
- `AuthoringFailAfterMutation` срабатывает по журналу, `initial_write_revision` в scope отсутствует, `Tests/Lua/authoring/commands.lua` проходит без правок.
- Нерешённая к следующему открытию окна транзакция даёт ошибку, проверено фикстурой.
- Решение транзакции принято до публикации фактов и до `resolve()`: ошибка, брошенная после commit контекста событий, состояние не откатывает; проверено фикстурой с падающим построителем презентации.
- Ни один из 18 spec-файлов и ни один C++-тест, вызывающие `execute_in_window`, не правятся.
- Отключение откатa краснит проверку равенства хешей и только её; сужение триггера до вылетевшей ошибки краснит ровно фикстуры отказа.

**Evidence:** `ctest --test-dir build` — 137/137, включая `gv2_headless_self_test` (headless Lua specs) и `gv2_headless_golden_replay_matches_digest` (state_hash golden run не изменился: `2b063c31c91de84ca867cf8f2980e6c67aa7d2a6116f1efc62f410ad34c6acad`, только `script_set_hash`/`digest_hash` — ожидаемо при правке `Scripts/`, обновлены в golden fixture по `Guides/RegenerateGolden.md`). `UnrealEditor-Cmd ... -ExecCmds="Automation RunTests GV2;Quit"` — 211/211, включая `GV2.Runtime.Lua.SpecRunnerHost` и `CommandValidatorSpecRunnerHost` (UE host). `validate_docs.py` — 209 файлов чисто. Мутационная проба 1 (отключено применение журнала в `rollback_transaction`): красными становятся ровно семь фикстур, сравнивающих хеш через `state_hasher` (sparse key, nested, repeated-write, boolean-false, error-mid-write, table-refusal, unresolved-left-open) — остальные specs зелёные. Мутационная проба 2 (в `command_dispatcher` триггер отката сужен до вылетевшей ошибки, `commit_transaction` вызывается и на отказе): красной становится ровно `dispatcher_rolls_back_canonical_state_on_table_refusal_after_mutation` — остальные specs зелёные, включая `fail()`-based фикстуры (у них откат идёт через тот же путь, что и ошибка). Обе пробы зафиксированы и возвращены к правильной реализации, финальный прогон после возврата — снова 137/137.

Побочно найдено и исправлено в рамках той же задачи (не входило в исходный список файлов): `Tests/Lua/authoring/command_validators.lua:67` проверял `observed_command_scope.initial_write_revision ~= nil` — после удаления поля из scope (ADR-0050 §2.3) assertion обязана проверять обратное; изменена на `== nil` с пометкой на ADR. Отдельно: `game.presentation.resolve()`, вызванный диспетчером после `event_bus.commit_command_context()`, оставляет `game.runtime.phase == "pumping_events"` при ошибке построителя презентации (диспетчер на ветке ошибки сбрасывает фазу только из `"executing_command"`) — это предсуществующий пробел, а не следствие журнала, и ADR-0051 прямо говорит, что обработка ошибки презентации «остаётся сегодняшней» и не входит в это решение; фикстура `dispatcher_commits_before_resolve_so_a_failing_presentation_builder_does_not_roll_back` восстанавливает фазу сама, не трогая `command_dispatcher.lua`.

## EGC-04 — Сделать изоляцию временного состояния между spec case выводимой

- [x] EGC-04 — Сделать изоляцию временного состояния между spec case выводимой

**Зависимость:** EGC-03. **Файлы:** `Scripts/authoring/context.lua` (`snapshot_test_state`/`restore_test_state`/`reset_test_state`), `Scripts/runtime/test_isolation.lua`, `Tests/Lua/lifecycle/registry_sealing.lua`, `Tests/Lua/authoring/runtime_state.lua`. Docs: `Guides/AddLuaSpec.md`, `HeadlessSimulationContract.md`.

**Инвариант:** [GAP-003](../../Status/EngineGaps.md#gap-003-сброс-временного-состояния-authoring-modules-между-lua-specs) и `AGENTS.md`, «Универсальное утверждение требует перечислителя». `snapshot_test_state` сегодня возвращает четыре переменные (`all_declared_validators`, `current_scope`, `all_referenced_services`, `is_frozen`); утверждение «изоляция покрывает временное состояние» опирается на рукописный список. Пятая переменная уровня модуля, добавленная где угодно, протекает между case молча и не учитывается хешем состояния.

**Решение:** ввести объявленную секцию изолируемого временного состояния: модуль инфраструктуры регистрирует своё временное состояние с функцией сброса, а `snapshot`/`restore`/`reset` обходят реестр, а не перечисляют переменные. Первые участники — существующие четыре; пятый приходит в EGC-05. Дополнительно — проверка, обнаруживающая изолируемое состояние, не попавшее в реестр: перечислитель выводится из upvalue модулей инфраструктуры, а не из списка имён.

**Не считается закрытием:** добавить пятую переменную в тот же рукописный список; оставить `reset_test_state` отдельной копией перечисления; проверить только то, что реестр непуст.

**Шаги:**
1. Воспроизвести протечку: синтетическая переменная уровня модуля, изменённая в одном case и прочитанная в следующем, — красный spec до правки.
2. Ввести реестр изолируемого состояния и перевести четыре существующие переменные в него; `snapshot`/`restore`/`reset` читают только реестр.
3. Подключить перечислитель, сопоставляющий фактическое изолируемое состояние модулей инфраструктуры с реестром; незарегистрированное состояние делает прогон красным.
4. Мутационная проба: снять регистрацию одного из четырёх — краснеет spec протечки, а не только сообщение перечислителя.
5. Описать правило в `AddLuaSpec.md`: новое временное состояние регистрируется в момент появления.

**Done:**
- `snapshot`/`restore`/`reset` не содержат имён конкретных переменных.
- Spec протечки красный до правки и зелёный после; мутация регистрации возвращает его в красное.
- Незарегистрированное изолируемое состояние обнаруживается перечислителем, выведенным из модулей, а не из списка.
- Правило регистрации записано в руководстве по spec.
- GAP-003 закрыт в своей механической половине; его тестовая половина (активный режим не переходит между case) закрывается EGC-07, и это названо здесь, чтобы гэп не остался без владельца.
- Задача не закрывает `STATUS-026` (`test_isolation` в графе production-сессии): его условие закрытия — понятие профиля модулей и отдельный ADR.

**Evidence:** `Scripts/runtime/test_state_registry.lua` — новый реестр участников (`register_participant`/`snapshot_all`/`restore_all`/`reset_all`/`registered_names`); `Scripts/authoring/context.lua` регистрирует свои четыре переменные как первых участников, `snapshot_test_state`/`restore_test_state`/`reset_test_state` теперь делегируют реестру и не называют переменных. Перечислитель — не runtime-рефлексия (в песочнице `OpenEnvironment`, `Source/GV2RuntimeCore/Private/GV2RuntimeSession.cpp`, открыты только `base`/`table`/`string`/`math`/`utf8`: `debug`, `io`, `load` недоступны, поэтому ни один модуль не может обойти чужие upvalue во время исполнения), а статический: `Tools/Content/validate_test_state_registry.py` выводит фактические mutable module-level `local` каждого проверяемого файла (переприсваиваемые, то есть не `require(...)` и не write-once константы) и сверяет их с `test_state_registry.register_participant(...)`-вызовами того же файла; подключён в `ctest` как `test_state_registry_gate_contract` (позитив) и `test_state_registry_gate_negative_contract` (`--self-test`: флагает незарегистрированный синтетический `local`, снимает флаг после регистрации, не флагает `require()`/константу). `ctest --test-dir build` — 139/139 (было 137 в EGC-03; +2 — новый gate contract и его негативный self-test), включая `gv2_headless_golden_replay_matches_digest` (`state_hash` не изменился: `2b063c31c91de84ca867cf8f2980e6c67aa7d2a6116f1efc62f410ad34c6acad`; обновлены `script_set_hash`/`digest_hash` по `Guides/RegenerateGolden.md`, ожидаемо при правке `Scripts/`). `UnrealEditor-Cmd ... -ExecCmds="Automation RunTests GV2;Quit"` — 211/211 (без изменений: новые Lua-кейсы учтены внутри существующего `GV2.Runtime.Lua.SpecRunnerHost`, а не отдельными Automation-тестами). `validate_docs.py` — 209 файлов чисто.

Spec протечки (`Tests/Lua/authoring/runtime_state.lua`): синтетическая `synthetic_leak_probe` зарегистрирована в `test_state_registry` ровно как это сделал бы пятый участник (EGC-05); `egc04_leak_probe_case_a_mutates_inside_isolated_context` мутирует её внутри `test_isolation.with_isolated_context`, `egc04_leak_probe_case_b_reads_default_if_isolated` (следующий по алфавиту, порядок прогона детерминирован сортировкой имён кейсов раннером) читает и требует значение по умолчанию.

Мутационные пробы (две, обе зафиксированы и возвращены, финальный прогон после возврата снова 139/139):
1. Снята регистрация `authoring.is_frozen` в `context.lua` → `validate_test_state_registry.py` краснеет на `is_frozen` и только на нём; `ctest` целиком тоже красный (`test_state_registry_gate_contract`).
2. Снята регистрация `test.synthetic_leak_probe` в `runtime_state.lua` → краснеет ровно `runtime_state.egc04_leak_probe_case_b_reads_default_if_isolated` (а не "только сообщение перечислителя" — перечислитель тут не применим, он проверяет только `context.lua`, поэтому именно spec протечки несёт сигнал для любого участника за пределами исходных четырёх), остальные specs зелёные.

Побочно: `Scripts/runtime/test_isolation.lua` не потребовал функциональных изменений (его вызовы `authoring_context.snapshot_test_state`/`reset_test_state`/`restore_test_state` остаются по тем же именам, теперь делегирующим реестру) — добавлен только пояснительный комментарий. При первой попытке участник был назван `test_state_registry.register`, что столкнулось с универсальным bootstrap lifecycle hook'ом `M.register(ctx)`, который `registry_lifecycle` вызывает на фазе `"register"` для каждого загруженного модуля (`Source/GV2RuntimeCore/Private/GV2RuntimeSession.cpp`, `RunLifecyclePhase("register", ...)`); переименовано в `register_participant` во всех вызывающих местах.

Механизм принадлежит `core`, семантика каждого режима — пакету. Нарушение — `core`, знающий про торговлю, или режим, живущий в `local`-таблице пакета и невидимый для изоляции, хеша и откатa.

**Решение:** одно `core`-хранилище активного режима (не более одного) с portable-значениями run. Authoring-поверхность получает имя `modes` рядом с существующими 32 именами `_ENV`: объявление `modes.<key> = { start, view }`, вызовы `start`, `require_active`, `state`, `finish`, `cancel` и `modes.active()`. Короткий key даёт `<package>:mode.<key>`; повторное объявление, late declaration и отсутствие `view` отвергаются на freeze тем же протоколом, что `services`. Отказы `mode.not_active`, `mode.already_active` и `mode.active` (сохранение при активном режиме, [ADR-0051](../../ADR/0051-temporary-modes-and-presentation-routing.md)) принадлежат `core`. `finish()` и `start()` в одной команде разрешены: инвариант — не более одного активного режима в любой наблюдаемой точке. Хранилище регистрируется участником реестра изоляции из EGC-04. Содержимое run объявляется дескрипторами `field.*` того же вида, что prototype сущности: правило «только portable values» получает перечислитель вместо дисциплины автора. Режим может объявить run-локальный поток случайности; тогда `start()` один раз тянет зерно каноническим `game.random`, а состояние потока хранится дескриптором `field.random_stream`, принадлежащим `core`, который проверяет форму тем же правилом, что `state_validator` для `meta.prng`: тег алгоритма и четыре слова по 8 hex не протекают в авторский слой. Режим без объявления потока броска не делает. Записи в run идут через тот же охраняемый прокси, что каноническое состояние, с категорией `transient` ([ADR-0050](../../ADR/0050-transactional-mutation-window.md)): один `__newindex`, категория — параметр обёртки, счётчик растёт только на канонической категории.

**Не считается закрытием:** хранить run в `local`-таблице модуля; принять run как сырую таблицу без дескрипторов; завести для run второй охраняемый прокси рядом с каноническим; разрешить `start()` при активном режиме с неявным завершением текущего; запретить `finish()` и `start()` в одной команде; описать форму потока случайности скалярными полями, вынеся алгоритм в авторский слой; оставить сохранение при активном режиме без отказа; вызывать `view` из команды.

**Шаги:**
1. Записать фикстуры: объявление без `view`, повторное объявление, объявление после freeze, `start` при активном режиме, `finish()` и `start()` другого режима в одной команде, `require_active` без режима, запись в run необъявленного поля, `view` как чистая проекция (попытка мутации в нём — отказ), `core:command.session.save` при активном режиме.
2. Реализовать хранилище и authoring-поверхность; зарегистрировать хранилище в реестре изоляции.
3. Подключить дескрипторы полей run к той же проверке записи, что действует для prototype сущностей.
4. Проверить, что `view` вызывается только построителем экрана, а не командой: guard по аналогии с `guard_validator_side_effect`.
5. Обновить `LuaGameplayReference.md` справочником `modes`; правила — в `AuthoringSurfaceContract.md` задачей EGC-21.

**Done:**
- `modes` доступен в authoring `_ENV`; перечень именованных вызовов совпадает с принятым в ADR-0051.
- `finish()` с последующим `start()` в одной команде проходит; две одновременно активные записи в хранилище невозможны, проверено фикстурой.
- `core:command.session.save` при активном режиме даёт `core:error.mode.active`, а не сохраняет состояние без run.
- Форму run-потока проверяет `core`: фикстура с испорченным словом отвергается дескриптором, а не доходит до броска.
- Каждая фикстура отказа даёт названный typed refusal, а не ошибку Lua.
- Запись необъявленного поля в run отвергается тем же механизмом, что для prototype сущности.
- Хранилище является участником реестра изоляции из EGC-04, и это проверено spec протечки между case.
- `view` невозможно вызвать из команды.

**Evidence:** новый `Scripts/runtime/mode_store.lua` — один `core`-store (`declare`/`freeze`/`is_frozen`/`get_declaration`/`active`/`begin`/`end_mode`/`run_proxy`/`seed_random_stream_field`/`draw_u32`), два raw table (`active_raw`, `run_raw`), каждый обёрнут один раз `mutation_window.guard_state(_, "transient")` с устойчивой identity; зарегистрирован участником `test_state_registry` (EGC-04) с restore/reset, пишущими в raw table напрямую (не через proxy — вне команды окно закрыто). ## EGC-06 — Сделать run транзакционным вместе с командой и публиковать факты режима

- [ ] EGC-06 — Сделать run транзакционным вместе с командой и публиковать факты режима

**Зависимость:** EGC-05. **Файлы:** `Scripts/runtime/mode_store.lua`, `Scripts/runtime/mutation_window.lua`, `Scripts/runtime/command_dispatcher.lua`, `Scripts/runtime/event_bus.lua`, `Tests/Lua/authoring/modes.lua`, `Tests/Lua/lifecycle/mutation_window.lua`.

**Инвариант:** [ADR-0050](../../ADR/0050-transactional-mutation-window.md), правило единого журнала. Нарушение — второй журнал или вторая точка решения: ошибка откатывает одну категорию состояния и, возможно, не откатывает другую, и порядок применения начинает значить.

**Решение:** записи в run идут через тот же журнал окна мутации, что канонические, с теми же правилами однократного запоминания прежнего значения и обратного применения; различает их категория записи. `fail()` после изменения run, но до первой канонической записи, остаётся корректным отказом, и выполнимо это двумя решениями EGC-01: признак мутации для `fail()` — канонический срез журнала, а не счётчик, и откат срабатывает на отказе, а не только на вылетевшей ошибке. Механизм публикует post-commit факты `core:event.mode.started` и `core:event.mode.finished` (`mode_id`, `outcome`; `cancelled` при `cancel()`). Изменения run сами по себе событий не порождают. Команда, изменившая только run, не меняет хеш состояния.

**Не считается закрытием:** отдельный снимок run рядом с журналом; восстановление run в обработчике ошибки `command_dispatcher`; публикация событий из `start`/`finish` напрямую, минуя post-commit; запись в run с категорией `canonical`, из-за чего `fail()` после неё даст `AuthoringFailAfterMutation` и увеличит `write_revision`.

**Шаги:**
1. Фикстуры: `fail()` после записи в run; ошибка после записи в run и в canonical state; `cancel()` после серии записей; команда, изменившая только run.
2. Провести записи run через журнал; удалить любой отдельный путь восстановления.
3. Публиковать два факта post-commit; проверить, что откат команды не публикует ни одного.
4. Мутационная проба: вернуть отдельный снимок run — фикстура смешанной ошибки обязана покраснеть; снять фильтр категории в признаке мутации — краснеет ровно фикстура `fail()` после записи в run.
5. Проверить `cancel()` двумя случаями: режим без объявленного потока даёт полное равенство хеша, режим с потоком — единственное расхождение в `meta.prng["core:random_stream.mode_seed"]`; сравнение по срезам состояния, а не по одному полному хешу.
6. Проверить журналирование бросков: отказ после серии бросков в run возвращает состояние run-потока, и повторная команда даёт ту же последовательность.

**Done:**
- `fail()` или ошибка в команде режима оставляют run равным состоянию до команды.
- Смешанная ошибка (run + canonical) откатывает обе категории одним журналом; отдельный снимок краснит фикстуру.
- Команда, изменившая только run, не меняет хеш состояния.
- `cancel()` режима **без** объявленного run-потока оставляет хеш равным хешу до старта полностью.
- `cancel()` режима **с** объявленным потоком оставляет единственное расхождение — одно продвижение `core:random_stream.mode_seed`, сделанное успешной командой старта; исключение названо этим пунктом, а не оговоркой в прозе.
- Броски внутри режима идут по run-локальному потоку: команда, сделавшая только броски, канонического хеша не меняет, а её отказ возвращает состояние потока журналом.
- Отменённая команда не публикует ни одного факта режима.
- Запись в run не попадает в канонический срез журнала и не увеличивает `write_revision`, поэтому `fail()` после неё не даёт `AuthoringFailAfterMutation`; проверено фикстурой `fail()` после записи в run, а снятие фильтра категории её краснит.
- `fail()` после записи в run откатывает run, а не только возвращает отказ; проверено сравнением `modes.state()` до команды и после, потому что run вне хеша состояния.

**Evidence:** specs обоих host-ов, значения хешей, вывод мутационной пробы.
