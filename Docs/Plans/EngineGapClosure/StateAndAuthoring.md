# Д1 — состояние и авторская поверхность

> **Материализует:** подэтап Д1 [Engine Gap Closure](README.md): транзакционность, временные режимы и те возможности authoring surface, без которых механики [архитектуры геймплея rh](../../RH/GameplayArchitecture.md#5-механики) невыразимы. Ни одна задача этапа не требует работы в редакторе.

**Фикстурный потребитель на каждую задачу (правило 2 плана).** EGC-21 проверяет, что у каждого механизма Д1 и Д2 он есть, поэтому он назван в самой задаче, а не выводится при закрытии этапа:

| Задача | Фикстурный потребитель |
|---|---|
| EGC-03, EGC-06 | команды фикстурного пакета, пишущие и в canonical state, и в run |
| EGC-04 | синтетическая переменная уровня модуля в spec протечки |
| EGC-05, EGC-07 | демонстрационный режим в `SyntheticMechanicalFixture` |
| EGC-08 | предметы с владельцем в фикстурном пакете — будущий инвентарь |
| EGC-09 | персонажи фикстурного пакета в двух локациях и с тегом |
| EGC-10 | поле-список и словарь флагов на prototype фикстурного пакета |
| EGC-11 | две Definitions одного kind в фикстурном пакете, одна добавлена новым файлом |
| EGC-12 | блок расширения фикстурного пакета с полем характеристики |
| EGC-13 | объявленные поля `world` фикстурного пакета |
| EGC-14 | текст фикстурного пакета с вложенным текстовым аргументом |
| EGC-15 | два подписчика фикстурного пакета с разным priority |
| EGC-16, EGC-17 | режим фикстурного пакета со своим `view` и своими слоями |
| EGC-18, EGC-19 | источники меню и значения панелей фикстурного пакета |
| EGC-20 | элемент списка кнопок с объявленной подсказкой во фикстурном экране |

Отсутствие потребителя в этой таблице — незакрытая задача, а не упущение приёмки.

Порядок задач — порядок исполнения. EGC-03 стоит перед режимами намеренно: режим, чья команда упала после первой канонической записи, без отката оставил бы run восстановленным, а состояние частично изменённым.

## EGC-03 — Реализовать журнал окна мутации и откат канонического состояния

- [ ] EGC-03 — Реализовать журнал окна мутации и откат канонического состояния

**Зависимость:** EGC-01. **Файлы:** `Scripts/runtime/mutation_window.lua`, `Scripts/runtime/command_dispatcher.lua`, `Tests/Lua/lifecycle/mutation_window.lua`. Docs: `CanonicalStateAndSave.md`, `CommandsAndEvents.md`.

**Инвариант:** [ADR-0050](README.md). Окно мутации уже перехватывает каждую запись охраняемым прокси с `__newindex` и ведёт монотонный `write_revision`; точка встраивания существует и используется. Нарушение — состояние, доверенное после пойманной ошибки.

**Решение:** журнал внутри открытого окна: однократная запись прежнего значения на пару «таблица, ключ». Успешное закрытие окна отбрасывает журнал; ошибка применяет его в обратном порядке и затем поднимает ошибку как сейчас. Ключ, отсутствовавший до команды, восстанавливается отсутствующим, а не присутствующим со значением `nil`. Журнал не является частью канонического состояния, не попадает в сейв и не пересекает boundary. `write_revision` не откатывается.

**Не считается закрытием:** откатить только верхний уровень `game.state`, оставив вложенные таблицы; сравнить хеши вместо восстановления значений; реализовать откат в `command_dispatcher` поверх окна, а не внутри него.

**Шаги:**
1. Записать независимые фикстуры: разрежённый ключ, вложенная таблица, повторная запись того же ключа, ошибка в середине обработчика, `fail()` до мутации, успешная команда.
2. Реализовать журнал в `mutation_window.lua`; на ветке ошибки `command_dispatcher` вызывает откат до отбрасывания контекста событий.
3. Доказать, что хеш состояния после пойманной ошибки равен хешу до команды, через `state_hasher`, а не через чтение отдельных полей.
4. Мутационная проба: отключить применение журнала — краснеет ровно проверка равенства хешей.
5. Прогнать specs на обоих host-ах, `ctest`, `validate_docs`.

**Done:**
- Ошибка в середине обработчика оставляет каноническое состояние равным состоянию до команды, проверено хешем.
- Отсутствовавший до команды ключ после отката отсутствует; присутствие со значением `nil` отвергается фикстурой.
- Успешная команда платит однократную запись прежнего значения на изменённый ключ и ничего больше.
- `fail()` до мутации не создаёт записей в журнале.
- Отключение откатa краснит проверку равенства хешей и только её.

**Evidence:** specs на обоих host-ах, вывод мутационной пробы, значения хешей до и после, `ctest`.

## EGC-04 — Сделать изоляцию временного состояния между spec case выводимой

- [ ] EGC-04 — Сделать изоляцию временного состояния между spec case выводимой

**Зависимость:** EGC-03. **Файлы:** `Scripts/authoring/context.lua` (`snapshot_test_state`/`restore_test_state`/`reset_test_state`), `Scripts/runtime/test_isolation.lua`, `Tests/Lua/lifecycle/registry_sealing.lua`, `Tests/Lua/authoring/runtime_state.lua`. Docs: `Guides/AddLuaSpec.md`, `HeadlessSimulationContract.md`.

**Инвариант:** [GAP-003](../../Status/EngineGaps.md#gap-003-сброс-временного-состояния-authoring-modules-между-lua-specs) и `AGENTS.md`, «Универсальное утверждение требует перечислителя». `snapshot_test_state` сегодня возвращает четыре переменные (`all_declared_validators`, `current_scope`, `all_referenced_services`, `is_frozen`); утверждение «изоляция покрывает временное состояние» опирается на рукописный список. Пятая переменная уровня модуля, добавленная где угодно, протекает между case молча и не учитывается хешем состояния.

**Решение:** ввести объявленную секцию изолируемого временного состояния: модуль инфраструктуры регистрирует своё временное состояние с функцией сброса, а `snapshot`/`restore`/`reset` обходят реестр, а не перечисляют переменные. Первые участники — существующие четыре; пятый приходит в EGC-05. Дополнительно — проверка, обнаруживающая изолируемое состояние, не попавшее в реестр: перечислитель выводится из upvalue модулей инфраструктуры, а не из списка имён.

**Не считается закрытием:** добавить пятую переменную в тот же рукописный список; оставить `reset_test_state` отдельной копией перечисления; проверить только то, что реестр непуст.

**Шаги:**
1. Воспроизвести протечку: синтетическая переменная уровня модуля, изменённая в одном case и прочитанная в следующем, — красный spec до правки.
2. Ввести реестр изолируемого состояния и перевести четыре существующие переменные в него; `snapshot`/`restore`/`reset` читают только реестр.
3. Подключить перечислитель, сопоставляющий фактическое изолируемое состояние модулей инфраструктуры с реестром; незарегистрированное состояние делает прогон красным.
4. Мутационная проба: снять регистрацию одного из четырёх — краснеет spec протечки, а не только сообщение перечислителя.
5. Описать правило в `AddLuaSpec.md`: новое временное состояние регистрируется в момент появления.

**Done:**
- `snapshot`/`restore`/`reset` не содержат имён конкретных переменных.
- Spec протечки красный до правки и зелёный после; мутация регистрации возвращает его в красное.
- Незарегистрированное изолируемое состояние обнаруживается перечислителем, выведенным из модулей, а не из списка.
- Правило регистрации записано в руководстве по spec.
- GAP-003 закрыт в своей механической половине; его тестовая половина (активный режим не переходит между case) закрывается EGC-07, и это названо здесь, чтобы гэп не остался без владельца.
- Задача не закрывает `STATUS-026` (`test_isolation` в графе production-сессии): его условие закрытия — понятие профиля модулей и отдельный ADR.

**Evidence:** красный и зелёный прогон spec протечки, вывод перечислителя, мутационная проба, оба host-а.

## EGC-05 — Ввести хранилище режимов и `modes` в authoring surface

- [ ] EGC-05 — Ввести хранилище режимов и `modes` в authoring surface

**Зависимость:** EGC-02, EGC-04. **Файлы:** создать `Scripts/runtime/mode_store.lua`, `Scripts/authoring/modes.lua`, `Tests/Lua/authoring/modes.lua`; изменить `Scripts/authoring/context.lua` (`create_authoring_environment`, freeze, `verify_service_targets`), `Scripts/bootstrap/manifest.lua`. Docs: `AuthoringSurfaceContract.md`, `RuntimeFacadeAndRegistries.md`, `Authoring/LuaGameplayReference.md`.

**Инвариант:** [ADR-0051](README.md), [ADR-0026](../../ADR/0026-core-and-gameplay-ownership.md). Механизм принадлежит `core`, семантика каждого режима — пакету. Нарушение — `core`, знающий про торговлю, или режим, живущий в `local`-таблице пакета и невидимый для изоляции, хеша и откатa.

**Решение:** одно `core`-хранилище активного режима (не более одного) с portable-значениями run. Authoring-поверхность получает имя `modes` рядом с существующими 32 именами `_ENV`: объявление `modes.<key> = { start, view }`, вызовы `start`, `require_active`, `state`, `finish`, `cancel` и `modes.active()`. Короткий key даёт `<package>:mode.<key>`; повторное объявление, late declaration и отсутствие `view` отвергаются на freeze тем же протоколом, что `services`. Отказы `mode.not_active` и `mode.already_active` принадлежат `core`. Хранилище регистрируется участником реестра изоляции из EGC-04. Содержимое run объявляется дескрипторами `field.*` того же вида, что prototype сущности: правило «только portable values» получает перечислитель вместо дисциплины автора.

**Не считается закрытием:** хранить run в `local`-таблице модуля; принять run как сырую таблицу без дескрипторов; разрешить `start()` при активном режиме с неявным завершением текущего; вызывать `view` из команды.

**Шаги:**
1. Записать фикстуры: объявление без `view`, повторное объявление, объявление после freeze, `start` при активном режиме, `require_active` без режима, запись в run необъявленного поля, `view` как чистая проекция (попытка мутации в нём — отказ).
2. Реализовать хранилище и authoring-поверхность; зарегистрировать хранилище в реестре изоляции.
3. Подключить дескрипторы полей run к той же проверке записи, что действует для prototype сущностей.
4. Проверить, что `view` вызывается только построителем экрана, а не командой: guard по аналогии с `guard_validator_side_effect`.
5. Обновить `LuaGameplayReference.md` справочником `modes`; правила — в `AuthoringSurfaceContract.md` задачей EGC-21.

**Done:**
- `modes` доступен в authoring `_ENV`; перечень именованных вызовов совпадает с принятым в ADR-0051.
- Каждая фикстура отказа даёт названный typed refusal, а не ошибку Lua.
- Запись необъявленного поля в run отвергается тем же механизмом, что для prototype сущности.
- Хранилище является участником реестра изоляции из EGC-04, и это проверено spec протечки между case.
- `view` невозможно вызвать из команды.

**Evidence:** specs на обоих host-ах, перечень отказов, прогон spec протечки с активным режимом, `ctest`.

## EGC-06 — Сделать run транзакционным вместе с командой и публиковать факты режима

- [ ] EGC-06 — Сделать run транзакционным вместе с командой и публиковать факты режима

**Зависимость:** EGC-05. **Файлы:** `Scripts/runtime/mode_store.lua`, `Scripts/runtime/mutation_window.lua`, `Scripts/runtime/command_dispatcher.lua`, `Scripts/runtime/event_bus.lua`, `Tests/Lua/authoring/modes.lua`, `Tests/Lua/lifecycle/mutation_window.lua`.

**Инвариант:** [ADR-0050](README.md), правило единого журнала. Нарушение — второй журнал: ошибка откатывает одну категорию состояния и, возможно, не откатывает другую, и порядок применения начинает значить.

**Решение:** записи в run идут через тот же журнал окна мутации, что канонические, с теми же правилами однократного запоминания прежнего значения и обратного применения. `fail()` после изменения run, но до первой канонической записи, остаётся корректным отказом — это выполнимо потому, что EGC-01 решил не увеличивать канонический `write_revision` на записи в run; иначе сработал бы `AuthoringFailAfterMutation`. Механизм публикует post-commit факты `core:event.mode.started` и `core:event.mode.finished` (`mode_id`, `outcome`; `cancelled` при `cancel()`). Изменения run сами по себе событий не порождают. Команда, изменившая только run, не меняет хеш состояния.

**Не считается закрытием:** отдельный снимок run рядом с журналом; восстановление run в обработчике ошибки `command_dispatcher`; публикация событий из `start`/`finish` напрямую, минуя post-commit; проведение записей run через канонический прокси, из-за чего они увеличат `write_revision`.

**Шаги:**
1. Фикстуры: `fail()` после записи в run; ошибка после записи в run и в canonical state; `cancel()` после серии записей; команда, изменившая только run.
2. Провести записи run через журнал; удалить любой отдельный путь восстановления.
3. Публиковать два факта post-commit; проверить, что откат команды не публикует ни одного.
4. Мутационная проба: вернуть отдельный снимок run — фикстура смешанной ошибки обязана покраснеть.
5. Проверить `cancel()` на равенство хеша состояния хешу до старта режима.

**Done:**
- `fail()` или ошибка в команде режима оставляют run равным состоянию до команды.
- Смешанная ошибка (run + canonical) откатывает обе категории одним журналом; отдельный снимок краснит фикстуру.
- Команда, изменившая только run, не меняет хеш состояния.
- `cancel()` оставляет хеш равным хешу до старта режима.
- Отменённая команда не публикует ни одного факта режима.
- Запись в run не увеличивает канонический `write_revision`, поэтому `fail()` после неё не даёт `AuthoringFailAfterMutation`; проверено фикстурой `fail()` после записи в run.

**Evidence:** specs обоих host-ов, значения хешей, вывод мутационной пробы.

## EGC-07 — Завести демонстрационный режим в тестовой фикстуре

- [ ] EGC-07 — Завести демонстрационный режим в тестовой фикстуре

**Зависимость:** EGC-06. Закрывает тестовую половину [GAP-003](../../Status/EngineGaps.md#gap-003-сброс-временного-состояния-authoring-modules-между-lua-specs). **Файлы:** `Tests/Fixtures/SyntheticMechanicalFixture/` (definitions, authoring-модуль режима), `Tests/Lua/authoring/modes.lua`, `Tests/Lua/save/` (save во время режима). Docs: `AddLuaSpec.md`.

**Инвариант:** [ADR-0046](../../ADR/0046-test-content-coupling-boundary.md). Демонстрационный режим живёт в фикстуре, а не в production-пакете; `Source/GV2` и общие specs не называют игровых идентификаторов.

**Решение:** режим фикстуры проходит полный жизненный цикл: старт из команды, команды изменения run, отказ после изменения run, `cancel`, `finish` с применением итога одной командой, save во время режима и load после него. Это первый потребитель механизма — правило 2 плана.

**Не считается закрытием:** spec, вызывающий `modes` напрямую без команд; режим, объявленный внутри spec-файла, а не в фикстуре как обычный пакет; отсутствие проверки save/load.

**Шаги:**
1. Объявить режим в фикстуре по тем же правилам, по которым его объявит `rh`: authoring-модуль, definitions, action bindings.
2. Пройти жизненный цикл командами, а не прямыми вызовами хранилища.
3. Выполнить `SaveToSlot` во время активного режима и `StartFromSave`: run отсутствует в сейве, `modes.active()` равен `nil`, открыт экран по умолчанию.
4. Проверить, что активный режим не переходит между spec case.
5. Подписать фикстурный модуль на `core:event.mode.started` и `core:event.mode.finished` и проверить оба факта: продюсер появляется в EGC-06, и без потребителя события остались бы механизмом, который ни на что не влияет и потому не проверяется.
5. Повторная команда режима после `finish()` отвергается `mode.not_active`.

**Done:**
- Жизненный цикл пройден только командами; прямых вызовов хранилища в spec нет.
- Сейв, снятый во время режима, не содержит run; после load активного режима нет.
- Активный режим не переходит между case, проверено прогоном двух case подряд.
- Команда после `finish()` отвергается названным отказом.
- Оба факта режима имеют потребителя: фикстурный подписчик получает `started` и `finished` с ожидаемым `outcome`, включая `cancelled`.
- Фикстура не содержит идентификаторов игровых пакетов.

**Evidence:** specs обоих host-ов, содержимое сейва, прогон двух case, `validate_test_content_coupling`.

## EGC-08 — Операции с экземплярами любого kind

- [ ] EGC-08 — Операции с экземплярами любого kind

**Зависимость:** EGC-03. **Файлы:** `Scripts/runtime/instance_registry.lua`, `Scripts/authoring/context.lua` (`instances`), `Scripts/authoring/properties.lua`, `Scripts/runtime/state_validator.lua`, `Tests/Lua/lifecycle/instance_identity.lua`, `Tests/Lua/authoring/properties.lua`. Docs: `AuthoringSurfaceContract.md`, `CanonicalStateAndSave.md`, `Authoring/LuaGameplayReference.md`.

**Инвариант:** [GAP-004](../../Status/EngineGaps.md#gap-004-операции-с-runtime-instance-не-actor-kind), [ADR-0027](../../ADR/0027-designer-lua-authoring-layer.md). Это единственный гэп, снимающий **действующее** нарушение: `GameData/rh/scripts/gameplay/actors.lua` читает и пишет `game.state.item_instances` напрямую в трёх местах, что архитектура `rh` запрещает своим же текстом.

**Решение:** `instance_registry` получает `get`, перечисление по kind, по владельцу и по Definition в детерминированном порядке, смену владельца и удаление с политикой по ссылкам. Authoring `instances` получает соответствующие вызовы, возвращающие wrapper. Поля экземпляра объявляются через prototype (`Item.condition = field.integer(...)`), методы prototype доступны на wrapper, из wrapper доступна его Definition. `ref_instance` разрешается для любого kind, а не только через `game.instances.actors.get`.
