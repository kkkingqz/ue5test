# Test Suite Restructuring: план реализации

> **Материализует:** границу между contract-тестом движка и smoke-тестом игрового контента в физической организации `Source/GV2/Private/Tests`. Основание — измеренное состояние suite (ниже) и уже принятый критерий [core decoupling](../../Architecture/BuildAndTooling.md).
> **Не является нормативным:** решение о том, что automation-тест механики не вправе ссылаться на id и asset пакета конкретной игры, фиксируется ADR задачей TSR-02 до реализации. План не расширяет и не сужает покрытие suite.
> **Исполнение:** последовательно по задачам. Checkbox задачи — единственный источник её завершения.

**Цель:** получить тестовый suite, в котором место теста определяется проверяемой границей движка, а не историей файла; в котором contract-тест переживает переименование локации, кнопки или виджета в игровом пакете; и в котором отдельный тест читается целиком.

**Технологии:** существующие UE Automation, Python-гейты в `Tools/Testing`, CTest, паттерн синтетических `core:`-fixtures, уже применяемый в suite. Нового runtime module и нового тестового framework план не требует.

## Измеренное состояние

`GV2RuntimeSubsystemTests.cpp` — 12 341 строка и 69 automation-тестов, **45% всего тестового кода модуля** (27 667 строк в 52 файлах). Внутри — семь несвязанных доменов: UI-кит и тема, image catalog, layered reconciliation, локации и rendering, screen field, session lifecycle, save/load.

Привязка к конкретному игровому контенту, измеренная по `Source/GV2/Private/Tests`:

| Что | Сколько | Источник, который тест дублирует константой |
|---|---|---|
| Литералы `textsystem:`-namespace | 131 вхождение, из них 69 в главном файле | `GameData/textsystem/` — id экранов, схем полей, ресурсов |
| Упоминания `market` | 43 вхождения, из них 41 в главном файле | `GameData/rh/definitions/locations.json5` — три локации пакета `rh` |
| Упоминания `tavern` | 36 вхождений, все в главном файле | там же |
| Имена компонентов экрана (`topbar`, `playerstatus`, `commandpanel`, `sceneview`) | 368 | Widget Blueprints в `/Game/TextSystem/UI/` |
| Asset paths к экранам игровых пакетов | `WBP_LocationScreen`, `WBP_RHScreen`, `WBP_SceneView`, `WBP_CommandPanel` | content layout, который автор игры вправе менять |

Привязка к локациям концентрированная, а не размазанная: 67 строк главного файла упоминают `market` или `tavern`, и во всём каталоге `Tests` их касаются ровно два файла. Это делает M2 выполнимым пофайлово, но не делает привязку безобидной.

Конкретный вид привязки: тест ищет кнопку по entry id `travel_city_market`, требует `tavern_keeper` в repeater персонажей и утверждает «на рынке 0 персонажей». Каждое из трёх утверждений ломается при штатном изменении игры, не задевающем ни одной границы движка.

Существующий gate `Tools/Content/validate_core_decoupling.py` запрещает литералы двух game-пакетов и **не знает про третий**, через который прошли все 131 вхождение. Существующий `Tools/Testing/validate_no_hardcoded_asset_paths.py` намеренно исключает каталог `Tests` (`EXCLUDED_DIR_NAME = "Tests"`) с обоснованием, верным для smoke-теста и не верным для 69 тестов.

## Почему дешёвые пути не дают результата

| Подход | Результат и цена | Выбор |
|---|---|---|
| Разрезать файл по доменам и остановиться | Снимает боль ревью, оставляет 131 привязку и растаскивает их по шести файлам, где они дальше от глаз | Недостаточен |
| Добавить третий пакет в regex существующего gate | Немедленно красный билд на 131 существующем вхождении; без ratchet превращается в массовое переписывание одним change set | Не исполним как есть |
| Заменить контентные id на синтетические поиском-заменой | Тест продолжает проверять содержимое фикстуры вместо границы движка; «0 персонажей» остаётся утверждением о данных | Недостаточен |
| Разделить границы, зафиксировать ratchet, затем переносить и отвязывать | Даёт перечислитель вместо рукописного списка, запрещает новый регресс до начала работ, делает каждый последующий change set локальным | Основа плана |

## Рекомендуемое устройство

### Две категории теста с разными правами

**Contract-тест механики** проверяет границу движка: repeater строит N entry по декларации, keyed collection сохраняет порядок при swap, travel-переход меняет активный экран слоя, save публикует новое поколение слота. Он не вправе называть id, asset path или имя виджета пакета конкретной игры. Его фикстура синтетическая и объявлена в самом тесте.

**Content smoke** проверяет, что реальная игра стартует и по ней можно пройти. Он вправе загружать реальные asset и ходить по реальным локациям, но его утверждения структурные: «экран слоя присутствует», «переход принят», «после возврата состояние восстановлено» — не «0 персонажей» и не «кнопка называется travel_city_market». Ожидаемые значения он берёт из того же контента, что и runtime, а не из константы в C++.

Категория теста — не комментарий, а проверяемое свойство: contract-тест живёт в файле, который gate сканирует строго, content smoke — в явно названном перечне файлов с обоснованием на каждый.

### Синтетическая фикстура вместо игрового пакета

Паттерн уже существует в suite: `core:command.test.*`, `core:actor.character.hero` и синтетические каталоги темы, регистрируемые прямо в тесте. `core:` — зарезервированный движковый namespace, он exempt в gate by design. Задача TSR-06 не вводит механизм, а доводит существующий до покрытия локаций, сцен и команд, чтобы у теста механики не оставалось причин брать игровой пакет.

### Ratchet вместо разового запрета

Gate получает baseline фактических привязок и проверяет одно: множество привязок не выросло. Каждая задача M2 сокращает baseline; TSR-10 обнуляет его и превращает ratchet в обычный запрет. Baseline порождается перечислителем из TSR-01, не ведётся руками и не хранится как список файлов, который придётся синхронизировать.

## Объём фиксации

План включает 10 задач: TSR-01…10. Он не меняет покрытие: множество automation test id после каждого этапа равно множеству до него, кроме TSR-08 и TSR-09, где изменения перечислены поимённо и обоснованы. Первая фиксируемая поверхность — `Source/GV2/Private/Tests` и гейты в `Tools/`; тесты portable-слоя (`Source/GV2RuntimeCore`, CTest targets) планом не затрагиваются. Lua-спеки `Tests/Lua/**` — третья категория и тоже вне плана: они проверяют содержательные правила игры на реальном контенте, поэтому ссылка на его id для них штатна, а не дефект. Следствие прямое: после TSR-10 переименование локации по-прежнему делает красным `Tests/Lua/presentation/location_transition_spec.lua`, и это ожидаемо.

Это реорганизация и отвязка существующих проверок, не обещание найти новые дефекты и не запрет добавлять тесты впоследствии.

## Этапы и зависимости

| Milestone | Задачи | Проверяемый результат |
|---|---|---|
| M0 — Барьер против регресса | TSR-01…02 | Перечислитель привязок, ADR о двух категориях, ratchet-gate с зафиксированным baseline |
| M1 — Перенос по файлам | TSR-03…05 | Шесть доменных файлов, идентичное множество test id, общие хелперы в одном заголовке |
| M2 — Отвязка от контента | TSR-06…08 | Синтетическая фикстура покрывает механику, baseline сокращён до перечня smoke-файлов |
| M3 — Оптимизация тестов | TSR-09…10 | Дробление тестов свыше порога, baseline обнулён, правило перенесено в contracts |

Зависимости: `01 → 02 → 03 → 04 → 05 → 06 → 07 → 08 → 09 → 10`.

Порядок не переставляется. Ratchet ставится **до** переноса, иначе перенос легализует 131 привязку в шести новых файлах. Перенос идёт **до** отвязки, потому что после него каждый change set M2 локален в файле на 1–2 тысячи строк, а не в 12-тысячном монстре. Дробление идёт **последним**, потому что отвязка схлопывает часть кода жирных тестов и дробить до неё — работа впустую.

## M0 — Барьер против регресса

### TSR-01 — Вывести фактические привязки тестов к контенту

- [x] TSR-01 — Вывести фактические привязки тестов к контенту

**Зависимость:** нет. **Файлы:** создать `Tools/Testing/inventory_test_content_coupling.py` с negative self-tests; источник списка game-пакетов — `GameData/*/package.json5` (поля `namespace`, `ue_content_roots`), не константа в скрипте.

**Инвариант:** [достоверная приёмка](../../Architecture/BuildAndTooling.md). Утверждение «тесты не зависят от контента» проверяется перечислителем, а не просмотром кода. Перечислитель множества привязок — сам скрипт: он читает актуальный состав пакетов из манифестов и сканирует `Source/**/Tests`, поэтому появление четвёртого пакета не требует правки скрипта.

**Решение:** скрипт выводит три класса привязки и печатает их как стабильно отсортированный отчёт: namespaced id любого пакета, кроме `core:`; строковый литерал, начинающийся с любого `ue_content_roots` игрового пакета (поле необязательно — у `sample` его нет, и его отсутствие означает «у пакета нет префиксов путей», а не пропуск пакета и не отказ скрипта); entry id и имя виджета, встречающиеся одновременно в тесте и в `GameData/*/definitions/**`. Третий класс — эвристика и помечается отдельно: он предлагает кандидатов для ревью, не формирует запрет.

**Не считается закрытием:** захардкодить список пакетов или путей в скрипте; пропустить пакет, у которого нет `ue_content_roots`; выводить только первый класс, потому что он ловится regex проще всего; отчёт, порядок строк которого зависит от обхода файловой системы.

**Шаги:**
1. Прочитать состав пакетов и их content roots из манифестов; убедиться, что `core` распознан как exempt, а остальные — как game-пакеты. Пакет без `ue_content_roots` остаётся в перечне и участвует в первом классе.
2. Реализовать три класса сканирования по `Source/**/Tests` с исключением комментариев (прецедент: line-level regex существующего gate ловит упоминание в комментарии — см. `strip_comments` в `validate_no_hardcoded_asset_paths.py`).
3. Negative self-tests: синтетический тестовый файл с известной привязкой каждого класса обнаруживается; файл только с `core:` id — нет.
4. Получить и зафиксировать отчёт на текущей ревизии; сверить итог первого класса с независимым `grep`-счётом как контрольной суммой.

**Done:**
- Скрипт выводит состав game-пакетов из манифестов; добавление пакета в `GameData/` меняет отчёт без правки скрипта.
- Пакет без `ue_content_roots` обработан как определённый случай: он присутствует в первом классе и не даёт ни исключения, ни молчаливого пропуска; случай покрыт self-test.
- Каждый из трёх классов имеет проходящий negative self-test.
- Отчёт детерминирован: два запуска на одной ревизии дают побайтово равный вывод.
- Итог первого класса совпадает с независимым подсчётом по репозиторию; расхождение объяснено, а не списано.

**Evidence:** отчёт на текущей ревизии, negative self-test выводы, контрольная сумма первого класса.

### TSR-02 — Зафиксировать две категории теста и поставить ratchet

- [x] TSR-02 — Зафиксировать две категории теста и поставить ratchet

**Зависимость:** TSR-01. **Файлы:** `Docs/ADR/0046-test-content-coupling-boundary.md` (следующий свободный номер); `Tools/Testing/validate_test_content_coupling.py` + CTest target; `Docs/Architecture/BuildAndTooling.md`.

**Инвариант:** [core decoupling](../../Architecture/BuildAndTooling.md). Существующее исключение `EXCLUDED_DIR_NAME = "Tests"` в `validate_no_hardcoded_asset_paths.py` и отсутствие третьего пакета в `validate_core_decoupling.py` — два места, через которые движковый код получает обратную зависимость от контента. ADR меняет не строгость gate, а гранулярность: исключение остаётся для явно названных smoke-файлов и снимается для остальных.

**Решение:** ADR фиксирует две категории, их права и способ различения. Gate поверх перечислителя TSR-01 сравнивает текущие привязки с baseline и падает, если появилась привязка, которой в baseline нет. Baseline хранится как данные рядом с gate, содержит привязку с её файлом и классом, и уменьшается только вместе с change set, который реально убрал привязку. Список smoke-файлов — часть baseline с обязательным полем обоснования на каждый файл. Тем же change set в baseline попадает предварительный потолок размера файла suite: он вычисляется из actual размеров на этой ревизии как наибольший файл, кроме растворяемого `GV2RuntimeSubsystemTests.cpp` (3306 строк `GV2RuntimeCoreTests.cpp`), и хранится как данные, а не как число в скрипте. Потолок нужен здесь по той же причине, по которой ratchet ставится до переноса: без него M1 вправе породить новый пятитысячный файл, и возразить этому будет нечем до самого M3. TSR-09 заменяет его обоснованным порогом по распределению, снятому после M2.

**Не считается закрытием:** добавить третий пакет в regex существующего gate и объявить дыру закрытой — asset paths и entry id останутся; baseline, который растёт вместе с новыми тестами; ADR, переписывающий мотивацию исключения `Tests` вместо того, чтобы назвать, чем оно было неправо до появления проверки.

**Шаги:**
1. Написать ADR: границы двух категорий, почему smoke-тест вправе ходить по реальному контенту, почему contract-тест не вправе, как категория проверяется машинно.
2. Сгенерировать baseline из отчёта TSR-01; пометить файлы, которые остаются smoke, с обоснованием на каждый.
3. Gate: сравнение с baseline, negative self-tests на новую привязку в contract-файле и на рост baseline без соответствующего удаления.
4. Записать в baseline предварительный потолок размера файла, вычисленный из actual размеров; negative self-test на файл свыше потолка.
5. Включить в CTest рядом с существующими decoupling targets; проверить, что полный прогон зелёный на текущей ревизии.
6. Обновить `BuildAndTooling.md` и ссылку на ADR в существующих gate-скриптах, чьё обоснование уточняется.

**Done:**
- ADR принят и назван в contracts; он отвечает, чем исключение `Tests` было неправо, а не только чем новая схема лучше.
- Baseline порождён перечислителем TSR-01, не набран вручную; его пересборка на той же ревизии даёт тот же файл.
- Gate падает на синтетически добавленной привязке в contract-файле и на baseline, выросшем без удаления — оба случая имеют negative self-test.
- Baseline содержит предварительный потолок размера файла, выведенный из actual размеров, а не назначенный числом; gate краснеет на файле свыше потолка, случай покрыт negative self-test.
- Полный CTest зелёный на текущей ревизии без изменения самих тестов; растворяемый `GV2RuntimeSubsystemTests.cpp` назван в baseline как единственное исключение из потолка, действующее до конца M1.

**Evidence:** ADR, baseline, negative self-test выводы, зелёный CTest до начала переноса.

## M1 — Перенос по файлам

### TSR-03 — Вынести общие хелперы в один заголовок

- [x] TSR-03 — Вынести общие хелперы в один заголовок

**Зависимость:** TSR-02. **Файлы:** `Source/GV2/Private/Tests/GV2PresentationTestFixtures.h` (существующий, 334 строки, включён 10 файлами) либо новый заголовок рядом, если предметная область не совпадает; источник переносимого — анонимный namespace в начале `GV2RuntimeSubsystemTests.cpp`.

**Инвариант:** [достоверная приёмка](../../Architecture/BuildAndTooling.md), test isolation по CFC-02A. Хелпер в анонимном namespace виден только своей translation unit: при копировании в новые файлы компилятор промолчит, и suite получит расходящиеся копии `GV2SimulateResponsiveFrame` и scoped-овверайдов, каждая со своим поведением teardown.

**Решение:** перенести общие хелперы один раз, до первого переноса тестов. Scoped-овверайды, меняющие глобальное состояние, переносятся с сохранением RAII-семантики, установленной CFC-02A: сохранение прежнего значения и восстановление на любом выходе.

**Не считается закрытием:** скопировать хелперы в каждый новый файл; оставить в анонимном namespace то, что после переноса нужно двум файлам; вынести хелпер, потеряв восстановление прежнего значения.

**Шаги:**
1. Определить фактическое множество хелперов, которые понадобятся более чем одному файлу после разбиения, по кластерам из TSR-04/05 — не по предположению, а по вызовам в переносимых блоках.
2. Перенести их в заголовок; в исходном файле оставить только те, что используются одним кластером.
3. Собрать модуль; убедиться, что ни один хелпер не продублирован (перечислитель — повторяющиеся определения в `Tests/**`).
4. Прогнать полный UE automation: множество test id и их исход не изменились.

**Done:**
- Каждый хелпер, нужный более чем одному будущему файлу, имеет ровно одно определение.
- Scoped-овверайды сохраняют и восстанавливают прежнее значение; проверено вложенным scope и ранним выходом.
- Множество automation test id и их исход совпадают с прогоном до change set.

**Evidence:** отчёты UE до и после, список перенесённых хелперов с их callers.

### TSR-04 — Перенести save/load как пилот

- [x] TSR-04 — Перенести save/load как пилот

**Зависимость:** TSR-03. **Файлы:** создать `Source/GV2/Private/Tests/GV2SaveAndLoadTests.cpp`; источник — строки 10518–12341 исходного файла, 15 тестов с общим префиксом `FGV2SaveAndLoad*`.

## M2 — Отвязка от контента

### TSR-06 — Довести синтетическую фикстуру до покрытия механики

- [ ] TSR-06 — Довести синтетическую фикстуру до покрытия механики

**Зависимость:** TSR-05. **Файлы:** `Source/GV2/Private/Tests/GV2PresentationTestFixtures.h` и, при необходимости, синтетические schema/definition данные под `core:`; источник существующего паттерна — `core:command.test.*` и `core:actor.character.hero`, уже используемые в suite.

**Инвариант:** [core decoupling](../../Architecture/BuildAndTooling.md). `core:` — зарезервированный движковый namespace, exempt by design; фикстура в нём не создаёт обратной зависимости движка на игру. Фикстура остаётся тестовыми данными и не становится игровым контентом: она не попадает в `mods.lock.json5` и не грузится production-хостом. Ровно этот класс расхождения уже открыт: [`STATUS-026`](../../Status/ImplementationStatus.md) фиксирует, что `core:module.runtime.test_isolation` объявлен зависимостью `core:module.bootstrap.main` и потому грузится в каждой игровой сессии, хотя сама capability одноразовая. Фикстура не вправе повторить этот маршрут и тем расширить уже открытый gap.

**Решение:** расширить существующий паттерн до сцены с персонажами, панели команд с переходами и экрана с несколькими слотами полей — то есть до формы, которую сейчас берут из игрового пакета тесты локаций и repeater. Фикстура объявляется в тесте и описывает ровно ту структуру, которую тест проверяет: две «локации» с переходом между ними, одна с одним персонажем, другая без.

**Не считается закрытием:** скопировать игровые определения локаций под другим namespace — это та же привязка с переименованным префиксом; фикстура, воспроизводящая три локации `rh` вместо минимальной пары; добавление фикстуры в состав пакетов; объявление фикстуры зависимостью `core:module.bootstrap.main` — это тот самый маршрут, которым `test_isolation` попал в граф production-сессии.

**Шаги:**
1. Вывести фактическую форму данных, которую требуют механические тесты локаций и repeater, из их текущих утверждений.
2. Реализовать минимальную фикстуру этой формы в `core:`; проверить, что она компилируется schema cache и разрешается теми же production-путями, что игровой контент.
3. Доказать, что фикстура отличается по структуре от игровой: число локаций, id и связи не совпадают с `GameData/rh/definitions/locations.json5`.
4. Убедиться, что фикстура не видна production-хосту: её отсутствие в `mods.lock.json5`, в package discovery и в графе модулей `core:module.bootstrap.main` проверено, а не заявлено.

**Done:**
- Фикстура покрывает форму, требуемую механическими тестами; перечислитель требований — их текущие утверждения, снятые на шаге 1.
- Разрешение фикстуры идёт теми же production-путями, что и игрового контента.
- Состав фикстуры не совпадает с игровым по id и связям; совпадение формы допустимо, совпадение содержимого — нет.
- Фикстура не участвует в package discovery production-хоста; проверено запуском, а не чтением.
- `STATUS-026` не расширен: фикстура не объявлена зависимостью `core:module.bootstrap.main` и не появляется в графе модулей production-сессии. Граф снят с запуска и приложен к evidence.

**Evidence:** требования, снятые с текущих утверждений; результат compile/resolve фикстуры; вывод package discovery.

### TSR-07 — Перевести contract-тесты на синтетическую фикстуру

- [ ] TSR-07 — Перевести contract-тесты на синтетическую фикстуру

**Зависимость:** TSR-06. **Файлы:** файлы кластеров из TSR-05, содержащие привязки по отчёту TSR-01; перечень — из baseline TSR-02, не из этого плана.

**Инвариант:** [core decoupling](../../Architecture/BuildAndTooling.md) и ADR-0046. Contract-тест проверяет границу движка, а не состояние игры: после этой задачи переименование локации, кнопки или виджета в игровом пакете не делает красным ни один тест, кроме smoke.

**Решение:** каждая привязка обрабатывается одним из трёх исходов, и исход записывается: переведена на синтетическую фикстуру; признана smoke и перенесена в smoke-файл; признана избыточной и удалена вместе с дублирующим утверждением. Утверждения вида «0 персонажей» переформулируются в утверждения о механике: repeater построил столько entry, сколько объявлено фикстурой.

**Не считается закрытием:** заменить префикс пакета и оставить остальное; перевести тест на фикстуру, сохранив утверждение о конкретном содержимом; объявить привязку smoke без обоснования в baseline; удалить утверждение вместо перевода, не показав, что его проверяет другой тест.

**Шаги:**
1. Разбить baseline на порции по файлам кластеров; работать change set на файл.
2. Для каждой привязки выбрать и записать исход из трёх; для «избыточна» назвать тест, который сохраняет проверку.
3. Переформулировать утверждения о содержимом в утверждения о механике; ожидаемые числа брать из объявления фикстуры, а не из константы.
4. После каждого change set сокращать baseline ровно на обработанные привязки и прогонять gate.
5. Проверить устойчивость: временно переименовать локацию и entry id **только в `GameData/*/definitions/*.json5`** — имя виджета в проверку не входит, оно живёт в `.uasset` и требует сессии с `unreal-mcp` и отдельного обоснования. Прогнать suite, откатить правку и, если изменился fingerprint, перегенерировать `mods.lock.json5` и golden по [RegenerateGolden](../../Guides/RegenerateGolden.md). Ни один contract-тест не краснеет; smoke — краснеет или берёт новое имя из контента; красные Lua-спеки ожидаемы и в счёт не идут.

**Done:**
- Каждая привязка из baseline имеет записанный исход; отсутствие исхода блокирует закрытие задачи.
- Ожидаемые значения в переведённых тестах выводятся из объявления фикстуры; ни одно не задано константой, дублирующей контент.
- Проверка переименованием: множество красных automation-тестов при переименовании локации и entry id не содержит contract-тестов. Перечислитель — прогон suite на изменённом контенте, не рассуждение. Правка контента откачена, fingerprint и golden восстановлены.
- Baseline содержит только привязки smoke-файлов; каждая с обоснованием.

**Evidence:** таблица исходов по привязкам, прогоны после каждого change set, результат проверки переименованием, сокращающийся baseline.

### TSR-08 — Свести content smoke к проверяемой поверхности

- [ ] TSR-08 — Свести content smoke к проверяемой поверхности

**Решение:** оставить проверяемую поверхность: игра стартует, стартовый экран слоя присутствует, переход между локациями принят, возврат восстанавливает состояние. Тесты, ставшие после TSR-07 дубликатами contract-проверок, удаляются с указанием заменяющего теста.

**Не считается закрытием:** оставить smoke в прежнем виде, переложив его в отдельный файл; сохранить утверждение о конкретном числе персонажей как «проверку контента»; удалить smoke целиком — тогда разрыв движка и контента перестаёт ловиться.

**Шаги:**
1. Перечислить кандидатов в smoke из baseline; для каждого назвать, какой разрыв он ловит и не ловит ли его уже contract-тест.
2. Переписать оставшиеся на структурные утверждения с ожиданиями из контента.
3. Удалить дубликаты, назвав заменяющий тест поимённо.
4. Проверить, что smoke ловит настоящий разрыв: временно сломать связь между локациями в `GameData/*/definitions/*.json5` — smoke краснеет. Правка откатывается тем же шагом, fingerprint и golden восстанавливаются по [RegenerateGolden](../../Guides/RegenerateGolden.md).
5. Зафиксировать перечень smoke-файлов в baseline как окончательный.

**Done:**
- Каждый оставшийся smoke-тест ловит названный разрыв, не покрытый contract-тестом.
- Ожидаемые значения читаются из контента теми же путями, что и runtime.
- Удалённые тесты имеют названный заменяющий тест; изменение множества test id перечислено поимённо и обосновано.
- Проверка сломанной связью: smoke краснеет, contract-тесты — нет.

**Evidence:** таблица кандидатов с их разрывами, diff множества test id с обоснованием, результат проверки сломанной связью.

1. Проверить, что baseline содержит только smoke-файлы; остаток, если он есть, вынести строкой `STATUS-NNN` — следующий свободный номер на момент записи, а не зарезервированный заранее — со ссылкой на конкретное правило и evidence.

- Baseline содержит только smoke-файлы; любой остаток имеет строку `STATUS-NNN`, заведённую в момент записи.
- Существующий gate выводит запрещённые namespace из манифестов; добавление пакета в `GameData/` расширяет запрет без правки скрипта.
- Правило двух категорий перенесено в contracts и на него ссылаются оба gate.
- Изменения множества test id за весь план перечислены поимённо, каждое с обоснованием из TSR-08 или TSR-09.

**Evidence:** финальный baseline, negative self-test на новый пакет, diff contracts, итоговая сверка множества test id.

---

## Правила выполнения и остановки

- Change set не объединяет перенос и правку теста: перенос доказывается равенством множеств id, правка — изменением утверждений. Вместе они недоказуемы.
- Evidence переноса требует прогона UE automation, который конфликтует с живым редактором; задачи M1 выполняются в сессии, где это учтено.
- Красный gate TSR-02 останавливает работу: сначала объясняется появившаяся привязка, потом продолжается перенос.
- Задача, потребовавшая изменить архитектурный инвариант, останавливается до ADR.

## Критерий выхода

Ни один файл suite не превышает порога TSR-09. Переименование локации, кнопки или виджета в игровом пакете делает красными в `Source/**/Tests` только smoke-тесты, названные в baseline; содержательные Lua-спеки `Tests/Lua/**` краснеют штатно и в это утверждение не входят. Множество automation test id отличается от исходного ровно на изменения, перечисленные в TSR-08 и TSR-09. Правило двух категорий живёт в contracts и проверяется gate, выводящим состав пакетов из манифестов.
