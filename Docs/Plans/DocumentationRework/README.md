# План переработки документации

> **Материализует:** разбор состояния документации по итогам ревизии корпуса.
> **Задачи:** DOC-00…16.
> **Результат:** правила проекта записаны и заметны, инструкции перестают учить удалённому API, у авторского слоя появляется собственный контракт и собственная документация для дизайнера.

## Цель

Сократить документацию без потери правил, решений, диагностики и проверяемых примеров. Для будущего `Docs/Authoring/` приоритет обратный: ясность для человека важнее минимального объёма.

Проблемы точечные, но каждая работает против пользователя документации:

- инструкции в `Guides/` учат API, которого больше нет;
- у авторского слоя нет ни контракта, ни документации для дизайнера, хотя это главная поверхность проекта;
- `LuaRuntimeContract.md` собрал семнадцать разделов и стал общим складом;
- ключевые правила проекта — «до 1.0 совместимости нет» и «минимум C++» — либо не записаны вовсе, либо спрятаны;
- архив планов занимает треть корпуса.

## Execution baseline

`baseline_commit: a43c7d0de12802faf0ad78364b200487392ccb54`. Ожидание закрытия [UiFoundation](../UiFoundation/README.md) снято прямым решением владельца проекта: его документация уже стабилизирована, а незавершённая code-часть не блокирует M1.

## Принятые решения

- **Правила получают владельца и заметность.** Совместимость — новый контракт `CompatibilityPolicy.md` и новый инвариант; «минимум C++» остаётся у существующего владельца, меняется только видимость.
- **Authority отражается в front matter.** Документы вне `Architecture/`, `UI/` и accepted ADR не используют `status: normative`; active plan получает отдельный lifecycle-статус, а informative status применяется только в явно инструктирующих/информационных документах и routers.
- **Гейт на удалённые идентификаторы работает по инструктирующим тирам и scoped rules.** В планах и предложениях историческое упоминание удалённого API законно; в `Guides/`, `Concepts/` и будущем `Authoring/` prescriptive usage отклоняется, а явно классифицированный нормативный запрет или Editor-only пример допускается.
- **`LuaRuntimeContract` делится на три документа** по владению: VM и загрузка, фасад и реестры, авторский слой.
- **Авторский слой получает нормативный контракт и отдельный инструктирующий тир:** `Docs/Authoring/` открывается router-ом и минимум двумя самостоятельными reference-документами, а не одной растущей страницей.
- **`Guides/` — только для программиста.** Задачи дизайнера уезжают в `Authoring/`.
- **`ImplementationStatus` инвертируется:** перечисляет только подтверждённые незакрытые расхождения с контрактами, а не реализованное, roadmap или backlog.
- **Архив планов становится плоским каталогом summary-файлов.** Для выполненного `<PlanName>` создаётся `Docs/Plans/Archive/<PlanName>.md` с итогами всех этапов, полным перечнем task IDs и ссылкой на `source_commit`, содержащий полные файлы плана. После проверки ссылки исходный каталог плана удаляется. `Docs/Plans/README.md` не дублирует перечень выполненных планов и содержит только ссылку на `Archive/README.md`.
- **Номер ADR занимается созданием файла.** До этого план ссылается на решение по названию — правило применяется в этом плане с первой задачи.

## Границы

Входят: правила и их видимость, гейт и чистка legacy, разделение контракта, документация авторского слоя, переработка `Guides/`, инверсия `Status/`, сжатие архива.

Не входят:

- Переписывание архивных планов и предложений: это исторические записи.
- Перевод документации на английский или второй язык.
- Генерация справочника авторского слоя из кода: справочник пишется руками, потому что примеры важнее полноты.
- Изменение схемы front matter и правил валидатора сверх необходимой нормализации authority/lifecycle и перечисленных гейтов.

## Критический путь

```text
M1 ──► M2

M3 ──► M4 ──► M5
```

M1 предшествует M2: гейт материализует правило, а не наоборот. M3 предшествует M4: документация дизайнера ссылается на новый контракт авторского слоя. M4 предшествует M5: `Guides/` делится по аудитории только после того, как вторая аудитория получила свой каталог.

Ветви независимы и могут выполняться в любом порядке относительно друг друга.

## Общие правила выполнения

1. Ни одна задача не вводит второго источника истины: у правила ровно один владелец, остальные места на него ссылаются.
2. Каждое изменение правил валидатора сопровождается положительным и **отрицательным** cases.
3. Перенос или переименование документа обновляет все относительные ссылки в том же change set.
4. Задачи ссылаются на ADR по названию решения; номер занимается созданием файла (DOC-03).
5. `python3 Tools/Documentation/validate_docs.py` зелёный после каждой задачи.
6. Архивные proposals не переписываются по существу. DOC-15 заменяет каталоги выполненных plans плоскими summary-файлами: summary сохраняет результат каждого этапа и все task IDs, а полный исторический текст остаётся доступен по проверенной ссылке на `source_commit`.
7. Текст сокращается без удаления правил, решений, diagnostics и проверяемых примеров; в `Docs/Authoring/` ясность для человека важнее краткости.
