# DataDrivenUiComposition: итог выполнения

> **Материализует:** исторический итог выполненного плана; документ не является источником правил или задач.

## Цель и результат

**Цель:** сделать так, чтобы новый UI-блок из существующих базовых элементов собирался ассетом, схемой и Lua — без единой строки C++. На входе ответ был «нужен C++» по трём причинам: базовые элементы не были адресуемы как поля, объявление capability было чистым виртуальным C++-методом, а `key` был привязан к перечислению пятнадцати конкретных классов. Вдобавок средний уровень вложенности `экран → вкладки → блок` не работал: `EUiFieldKind::ScreenFields` проваливался в материализаторе (`UPP-R4`).

**Результат:** введено одно свойство идентичности со смыслом «идентичность внутри объемлющего хоста», доступное в Designer на каждом размещении и объявленное на общей поверхности хостов, а не по классам; любой базовый элемент может быть полем; `UGV2DeclaredCompositeWidgetBase` строит своё дерево capability из `UPROPERTY(EditAnywhere)` списка троек *(имя свойства, имя дочернего виджета, вид)*; `key` сведён к одной ветке через общее состояние хоста; `screen_fields` работает через тот же envelope, что и обычное поле экрана; цепочка из трёх уровней собрана из данных и выдерживает отказ на третьем; композиционный цикл отклоняется до `Ready`.

Доказательство не синтетическое: `UGV2LocationTopBarWidgetBase` переписан на объявляемый композит, а его C++-класс **удалён**. Производственный экран локации проходит через объявляемый путь.

## Этапы и задачи

### M1 — Addressable Elements

- `DUC-01` — Одно свойство идентичности внутри объемлющего хоста
- `DUC-02` — Базовые элементы становятся адресуемыми
- `DUC-03` — `key` перестаёт быть перечислением классов
- `DUC-04` — Охват sweep следует за адресуемостью

### M2 — Declared Composite

- `DUC-05` — Generic-композит и объявляемый список capability
- `DUC-06` — Схема объявляемого композита плоская
- `DUC-07` — Объявление проверяется против умений детей
- `DUC-08` — Один композит локации переписан на объявление

### M3 — Nested Screens

- `DUC-09` — `screen_fields` через обычный envelope
- `DUC-10` — Цепочка из трёх уровней собрана из данных и покрыта отказом
- `DUC-11` — Композиционный цикл виджетов отклоняется

## Ключевое место плана: DUC-07

Это была единственная задача, способная воспроизвести `UPP-R1` внутри нового механизма. Если строить дерево capability композита из того, что умеют дети, сверка `Schema ⊆ Capabilities` снова станет истинной по построению — обе стороны придут из одного источника.

Реализация этого избегает: дерево строится **только из объявления**, а независимой второй сверкой служит `DoesCapabilityTreeSupportKind` — именованный `RendererControl`-target, если он сам является хостом свойств, обязан самостоятельно объявлять хотя бы одну capability того же вида, что объявил композит. Источники независимы: объявление приходит из Designer-свойства, умения ребёнка — из его собственного `DescribeUiCapabilities`.

Проверка сознательно ограничена `RendererControl`: без этого сужения краснели четыре существующих теста через `CollectionHost`-репитеры, которые являются хостами свойств ради общего состояния, но не обязаны самообъявлять capability того смысла, которым их адресует родитель. Ограничение записано с обоснованием, а не выбрано умолчанием.

## Принятые по ходу решения

- **Роль одна, а не две.** Экран и блок различаются только тем, что экран проверяется на матрице разрешений. Поэтому введено одно свойство идентичности, а не отдельные field_id и property_name: два свойства дали бы автору ассета два способа выразить одно и то же.
- **Плоский объявляемый список вместо автоматического делегирования.** Разворачивание дерева ребёнка дало бы схему вида `{ label: { text, key }, value: { percent, label, key } }` с протечкой служебных свойств на каждый уровень. Плоский список даёт `{ day: TextSpec }`.
- **Ребёнку не нужен собственный идентификатор.** Дочерний виджет адресуется своим именем в `WidgetTree`, которое UMG даёт бесплатно.
- **Вложенность не ограничена.** Рассматривалось ограничение в два уровня и отклонено: рекурсия уже была реализована и неограниченна, обнаружение циклов схем работало, а ограничение стало бы **новым** правилом поверх работающего механизма — строго больше работы. Вместо него закрыты два реальных риска: композиционный цикл виджетов (`DUC-11`, прямой и косвенный, плюс проверка, что незарегистрированный экран не выдаётся за цикл) и фикстура на глубине не меньше двух (`DUC-10`).

## Что осталось за границами

Три оставшихся композита локации к объявлению не сводятся, и причины записаны в отчёте `DUC-08`: `UGV2LocationCommandPanelWidgetBase` дополнительно экспонирует `OnBindingInvoked` как `BlueprintAssignable` multicast, `PlayerStatus` и `Scene` несут собственные коллекции. Это не пропуск, а граница механизма: объявляемый композит покрывает случай «несколько существующих элементов под одним полем», а не произвольное поведение.

`UPP-R5` — принадлежность UI-схем closure репозитория и политика отказа для схем мода — осознанно отложена. Условие повторного открытия: становится обязательной, когда UI-блоки начнут поставляться модами; все текущие блоки проектные, и Designer-свойство как источник объявления это предположение закрепляет.

## Проверка

Полный регрессионный прогон на итоговом коммите: **102/102** UE automation, **68/68** портативных CTest, `gv2-headless --self-test`, `validate_docs.py` (165 файлов) — без ошибок.

Дополнительно сверено независимо при закрытии плана: `UGV2LocationTopBarWidgetBase` отсутствует в исходниках; `WBP_LocationTopBar` содержит `DeclaredCapabilities` с записями `EGV2DeclaredUiCapabilityKind::Text` и `::Key`, то есть производственный экран действительно идёт через объявляемый путь; цепочка `Cast<UGV2…>` в consumer ключа сократилась с пятнадцати ветвей до двух, и обе — именованные capability иного смысла (`selected_key`, `default_tab_key`), маршрутизируемые по имени, а не по типу; `EUiFieldKind::ScreenFields` обрабатывается материализатором; отрицательные тесты существуют для `target_kind_mismatch` и для прямого и косвенного композиционного цикла.
