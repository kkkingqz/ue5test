# M1 — Lua Spec Runner

## Результат этапа

Один generic portable entry point находит и исполняет Lua-спеки из `Tests/Lua/`. Оба host-а вызывают его; добавление спеки расширяет покрытие обоих без единой строки C++.

## Задачи

- [x] **TAS-01 — Определить формат спеки**
  - Спека — Lua-файл, возвращающий именованные кейсы; каждый кейс независим и не зависит от порядка.
  - Done: формат допускает подготовку окружения внутри кейса и не требует глобального состояния между кейсами; провал кейса не прекращает исполнение остальных, но фиксируется; формат описан в `BuildAndTooling`.
  - Evidence: `Docs/Architecture/BuildAndTooling.md` получил раздел «Формат Lua-спеки (`Tests/Lua/`)»: спека — `.lua`-файл под `Tests/Lua/`, вне module tree `Scripts/` и вне упакованной игры; возвращает таблицу `{ case_name = function() ... end, ... }`, ключ — segment grammar `^[a-z][a-z0-9_]*$` (тот же, что у `module_id`/`instance_id`), значение — функция без аргументов. Кейс сигнализирует провал ошибкой Lua (`error`/неудавшийся `assert`), успех — обычным возвратом. Кейс самодостаточен: строит нужную фикстуру (repository/session/state) внутри своего тела, не читает и не оставляет состояние для соседних кейсов; top-level код файла может декларировать только `local` requires/константы — контракт не гарантирует, исполняется ли тело файла один раз на все кейсы или заново на каждый (это стратегия runner-а, TAS-02), поэтому спека обязана работать корректно при любой из стратегий. Пустая таблица — невалидная спека (ошибка конфигурации, не ноль кейсов). Полная деривация идентификатора провала `<spec>.<case>` из пути файла явно оставлена TAS-03. Runner (обнаружение, исполнение, оба host-а) не реализован — предмет TAS-02/TAS-04.

- [x] **TAS-02 — Реализовать обнаружение и исполнение**
  - Runner рекурсивно собирает `Tests/Lua/**/*.lua`, сортирует и исполняет.
  - Done: порядок детерминирован и не зависит от файловой системы; отсутствие каталога не является ошибкой; спека, не возвращающая кейсов, отклоняется как ошибка конфигурации; спеки не попадают в module tree `Scripts/` и не грузятся загрузчиком модулей.
  - Evidence: Задача разложена на два независимо проверенных примитива, как и предполагает разделение TAS-02 (обнаружение+исполнение) / TAS-04 (подключение обоих host-ов к одному вызову).
    - **Обнаружение** — `GV2ContentHostSupport::DiscoverLuaSpecFiles()` (`Source/GV2ContentHostSupport/Public/GV2ContentHostSupport/LuaSpecDiscovery.h`, `.../Private/LuaSpecDiscovery.cpp`), тот же слой, что и `PackageDiscovery` (ADR-0019): рекурсивный обход `*.lua` под корнем, сортировка по forward-slash-нормализованному относительному пути (детерминирована независимо от порядка обхода файловой системы), отсутствующий корень возвращает пустой результат, а не ошибку. Проверено UE Automation `GV2.Runtime.ContentHostSupport.LuaSpecDiscovery` (`Source/GV2/Private/Tests/GV2LuaSpecDiscoveryTests.cpp`) на реальных временных файлах (не conformance entry point — это host-side filesystem-код по тому же прецеденту, что `PackageDiscovery`, не имеющий portable conformance-обвязки).
    - **Исполнение** — новый метод `FRuntimeSession::RunLuaSpec()` (`Source/GV2RuntimeCore/Public/GV2RuntimeCore/GV2RuntimeSession.h`, реализация в `.../Private/GV2RuntimeSession.cpp`): грузит текст спеки через `luaL_loadbufferx` (в обход module loader-а — спека никогда не попадает в `LoadedModulesRegistryKey`/`Scripts/` module tree), проверяет что возврат — таблица, что каждое значение — функция, что таблица не пуста (иначе `OutFault.Code = "LuaSpecEmpty"` / `"LuaSpecFormatInvalid"`), собирает имена кейсов в `std::vector`, сортирует (`std::sort`, детерминированный порядок независимо от внутреннего порядка обхода Lua-таблицы) и вызывает каждый кейс через `lua_pcall`; провал кейса пишется в `OutCaseResults[i].Success = false` и не прерывает остальные, `OutFault` используется только для нарушений формата самой спеки. На время исполнения (chunk + все кейсы) временно разрешён `require()` любого уже загруженного production-модуля (`AllowedDependenciesRegistryKey` пересобирается из `LoadedModulesRegistryKey`), очищается RAII-гвардом (`FRequireContextGuard`) на любом пути выхода. Портируемый конформанс-тест `GV2RuntimeCore::Testing::RunLuaSpecRunnerConformance()` (`Source/GV2RuntimeCore/Public/GV2RuntimeCore/Testing/GV2LuaSpecRunnerConformance.h`, `.../Private/GV2LuaSpecRunnerConformance.cpp`) — легитимная C++-проверка механизма, а не gameplay-правила (ADR-0024) — проверяет: провал одного кейса фиксируется и не прерывает остальные; порядок кейсов в результате детерминирован (`a_case`, `m_case`, `z_case` независимо от порядка объявления `z_case, a_case, m_case`); `require()` уже загруженного модуля работает внутри кейса; пустая таблица, не-таблица и не-функция в таблице отклоняются как `OutFault`. Исполняется на обоих хостах: `gv2-headless --self-test` (exit code 15 при провале) и UE Automation `GV2.Runtime.Lua.SpecRunnerConformanceCrossHost` — оба зелёные.
    - `ctest` 58/58, UE `GV2.Runtime` 52/52 (`TEST COMPLETE. EXIT CODE: 0`), `validate_host_conformance_parity.py` — 28 entry points.
    - Не входит в эту задачу (явно оставлено TAS-04): единая функция, вызывающая обнаружение+исполнение подряд по всем найденным файлам и подключённая к `gv2-headless --self-test`/UE automation — оба примитива готовы к этому, но сама привязка ещё не сделана.

- [x] **TAS-03 — Зафиксировать идентичность провала**
  - Провал возвращает стабильный `<spec>.<case>` по контракту существующих conformance entry points.
  - Done: идентификатор не содержит абсолютных путей, адресов и таймингов; при провале оба host-а сообщают одинаковую строку; ошибка Lua внутри кейса отличается от логического провала кейса по коду.
  - Evidence: `GV2ContentHostSupport::DeriveLuaSpecId()`/`MakeLuaSpecCaseFailure()`/`MakeLuaSpecFault()` (`Source/GV2ContentHostSupport/Public/GV2ContentHostSupport/LuaSpecIdentity.h`, `.../Private/LuaSpecIdentity.cpp`) — чистая, filesystem- и VM-независимая функция деривации, живёт рядом с `DiscoverLuaSpecFiles`, чей `RelativePath` она потребляет. `DeriveLuaSpecId("world/current_location.lua")` → `"world.current_location"` (`/` → `.`, расширение `.lua` отброшено); не содержит абсолютных путей (принимает только уже-относительный путь), адресов или таймингов по построению — чистая строковая функция. Две различимые формы `FLuaSpecFailure { Identifier, Code, Message }`: `MakeLuaSpecCaseFailure(spec, case, msg)` → `Identifier = "<spec>.<case>"`, `Code = "LuaSpecCaseFailed"` — логический провал кейса (кейс отработал как код, его assertion не совпал); `MakeLuaSpecFault(spec, fault_code, msg)` → `Identifier = "<spec>"` (без суффикса кейса — кейсы не были даже перечислены), `Code` — один из кодов `OutFault` от `RunLuaSpec` (`LuaSpecSyntaxError`/`LuaSpecLoadError`/`LuaSpecFormatInvalid`/`LuaSpecEmpty`). Различение достигается по `Code`, а не парсингом `Identifier`. Проверено UE Automation `GV2.Runtime.ContentHostSupport.LuaSpecIdentity` (`Source/GV2/Private/Tests/GV2LuaSpecIdentityTests.cpp`): деривация id для вложенного и top-level пути, состав обеих форм `FLuaSpecFailure`, `Code` двух форм различны. Оба host-а получат одинаковую строку по построению — деривация чистая и детерминированная, никакого host-специфичного состояния не читает; сквозная проверка на реальном прогоне на обоих host-ах — предмет TAS-04 (когда эта функция будет вызвана из orchestration-цикла). `ctest` 58/58, UE `GV2.Runtime` 53/53 (`TEST COMPLETE. EXIT CODE: 0`), `validate_host_conformance_parity.py` — 28 entry points (без изменений: эта функция не добавляет `Run*Conformance` entry point, gate её не видит и не должен).

- [x] **TAS-04 — Подключить оба host-а**
  - `gv2-headless --self-test` и Unreal automation вызывают один и тот же runner.
  - Done: новая спека исполняется обоими без изменения C++ и без новой обёртки; UE-сторона представлена одним тестом на весь runner, а не тестом на спеку; расхождение результата между host-ами останавливает сборку.
  - Evidence: Обнаружение (TAS-02, `GV2ContentHostSupport`), исполнение (TAS-02, `GV2RuntimeCore::FRuntimeSession::RunLuaSpec`) и идентичность провала (TAS-03, `GV2ContentHostSupport::LuaSpecIdentity`) нуждаются в общей точке связки, которую ни один из существующих таргетов не мог предоставить: `gv2_runtime_core` и `gv2_content_host_support` — сиблинги, оба зависят только от `gv2_content_core`, ни один не зависит от другого. Добавлен новый portable-модуль `GV2TestSupport` (CMake target `gv2_test_support`, UBT module `GV2TestSupport`, зависит от обоих) — `GV2TestSupport::RunLuaSpecs(SpecRoot, Session, OutResult)` (`Source/GV2TestSupport/Public/GV2TestSupport/LuaSpecRunner.h`, `.../Private/LuaSpecRunner.cpp`): обнаруживает `*.lua` под `SpecRoot`, для каждого файла зовёт `Session.RunLuaSpec` на уже запущенной сессии, агрегирует провалы через `MakeLuaSpecCaseFailure`/`MakeLuaSpecFault` в `OutResult.Failures`. Test-only библиотека — ни один gameplay-хост её не линкует.
    - `gv2-headless` (`Headless/Source/main.cpp`, `Headless/CMakeLists.txt` линкует `gv2_test_support`): внутри `if (bSelfTest)`, после всех C++ conformance-проверок и после запуска реальной production-сессии (настоящий `GameData/core` + настоящий `Scripts/bootstrap/manifest.lua`, до диспетчеризации команд, влияющих на digest) вызывает `GV2TestSupport::RunLuaSpecs("Tests/Lua", Runtime, Result)`; при провале печатает `lua_spec_failed id=... code=... message=...` на каждый провал и возвращает exit code 16.
    - UE: `GV2.Runtime.Lua.SpecRunnerHost` (`Source/GV2/Private/Tests/GV2LuaSpecRunnerHostTests.cpp`, добавлена зависимость `GV2TestSupport` в `Source/GV2/GV2.Build.cs`) — **один** тест на весь runner (не на спеку): строит репозиторий из реального `GameData/core`, грузит реальный `Scripts/`, стартует сессию, вызывает тот же `GV2TestSupport::RunLuaSpecs` над `Tests/Lua`, на провале — `AddError` на каждый `FLuaSpecFailure`.
    - Сквозная проверка вживую: временно создан `Tests/Lua/smoke/example.lua` с провальным кейсом → `gv2-headless --self-test` вернул `lua_spec_failed id=smoke.example.fails code=LuaSpecCaseFailed message=Tests/Lua/smoke/example.lua:6: deliberate smoke failure`, exit code 16; после исправления кейса — exit 0. Фикстура удалена (миграция реальных спек — TAS-12/13, не эта задача).
    - Расхождение между host-ами не требует отдельного механизма сравнения: оба host-а вызывают буквально одну и ту же скомпилированную функцию `GV2TestSupport::RunLuaSpecs` над одним и тем же деревом `Tests/Lua/`, поэтому любое расхождение результата — это отказ ОДНОГО из двух CI job-ов (та же гарантия, что и у остальных `Run*Conformance` entry points, которые тоже не имеют отдельного cross-host diff-шага).
    - `Tests/Lua` не стейджится в упакованную игру: `Source/GV2/GV2.Build.cs` стейджит только `Scripts/*.lua`, `Resources/*`, `GameData/*`; `Tests/` не тронут.
    - `ctest` 58/58, UE `GV2.Runtime` 54/54 (`TEST COMPLETE. EXIT CODE: 0`), `validate_host_conformance_parity.py` — 28 entry points (без изменений: `RunLuaSpecs`/UE-обёртка не названы `Run*Conformance`, gate их не видит — ожидаемо, это host wiring, а не conformance entry point).

- [x] **TAS-05 — Обновить контракты**
  - Зависимости: TAS-01–TAS-04.
  - Done: `HeadlessSimulationContract` описывает две допустимые формы проверки и границу между ними; `BuildAndTooling` описывает `Tests/Lua/`, формат спеки и участие в CI; `ImplementationStatus` обновлён.
  - Evidence: `Docs/Architecture/HeadlessSimulationContract.md` получил раздел «Две формы проверки и граница между ними» (после `## Conformance`): C++ conformance entry point для C++ API/механизмов vs Lua-спека для Lua-правил; граница — новый C++ entry point на Lua-правило запрещён; унаследованные C++-наборы (module lifecycle, repository access, world domain object, command validators — написаны до ADR-0024) остаются валидными без обязательной единовременной миграции; описано, что вызывают оба host-а. `Docs/Architecture/BuildAndTooling.md` — раздел «Формат Lua-спеки» (TAS-01) дополнен фактическим состоянием реализации: `GV2TestSupport` (новый CMake target/UBT module, таблица Portable targets), кто его вызывает и как (self-test exit code 16, UE `SpecRunnerHost`), отсутствующий `Tests/Lua/` не ошибка ни для одного host-а. `Docs/ImplementationStatus.md` получил строку «Lua Spec Runner (`Tests/Lua/`)» = Реализовано (формат/обнаружение/исполнение/идентичность/host-wiring — TAS-01–04), с явной пометкой, что в `Tests/Lua/` пока нет ни одной реальной спеки (миграция — M4, ещё не начата); заодно исправлено устаревшее число conformance entry points (22 → 28). `python3 Tools/Documentation/validate_docs.py` — 98 файлов, чисто.
