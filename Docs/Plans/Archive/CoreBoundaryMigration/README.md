# План приведения ядра к границе владения

> **Материализует:** [ADR-0026](../../../ADR/0026-core-and-gameplay-ownership.md) в коде и контенте.
> **Задачи:** CBM-01…16.
> **Результат:** в `core` не остаётся ни одной сущности, выражающей правила текущей игры.

## Цель

Привести код и контент в соответствие с [ADR-0026](../../../ADR/0026-core-and-gameplay-ownership.md): убрать из ядра демо-контент и игровую экономику, дать пакету точку расширения обёртки инстанса и перенести схемы `item`, `location` и большую часть `actor` в игровой пакет.

## Состояние на входе

Правило принято и перенесено в contracts; код ему пока не соответствует в четырёх местах.

| Что | Где | Почему нарушает |
|---|---|---|
| `get_gold`, `add_gold` | `Scripts/runtime/actor_registry.lua` | Экономика игры внутри ядра. Убрать некуда — точки расширения обёртки нет |
| `current_location_id = "location"` | `Scripts/runtime/state_validator.lua` | Поле состояния игры в общем реестре ссылочных полей |
| `core:screen.test`, `debug/start.lua` | `GameData/core`, `Scripts/debug/` | Демо-контент как часть ядра |
| `actor_v1`, `item_v1`, `location_v1` | `GameData/core/schemas/` | Схемы выражают модель одной игры: `base_hp`, `price`, `screen_ids` |

Инфраструктура для переноса готова: пакет несёт собственный Lua и definitions, замещение модулей работает, обратные ссылки блокируются гейтом `core_decoupling_gate_contract`, разрешение схем в `gv2-content` идёт по набору пакетов.

## Принятые решения

Все приняты [ADR-0026](../../../ADR/0026-core-and-gameplay-ownership.md), здесь — только следствия для порядка работ.

- **Точка расширения — фабрика-декоратор.** Ядро строит базовую обёртку и держит инварианты идентичности; пакет надстраивает поведение через `__index = base`. Реестр методов не вводится: он выражается через декоратор без остатка.
- **`discriminator` остаётся в схеме ядра.** Это единственное поле актора, которое требуется runtime: по нему выбирается обёртка. Остальные поля актора уезжают в пакет.
- **Незарегистрированный discriminator на время переноса не роняет сессию.** Базовая обёртка плюс список известных нерегистраций, который может только сокращаться; устаревшая запись — ошибка проверки. Приём тот же, что в плане PackageSupport.
- **Замороженный корпус не трогаем.** `Tests/Fixtures/PortableContentCore/valid/core` изображает пакет по имени `core`, а не движок. Его схемы и ID остаются как есть; golden-прогон от плана не меняется, кроме `script_set_hash`.
- **Порядок — от дешёвого к дорогому.** Демо и экономика бесспорны и не зависят ни от чего; схемы дороги и требуют готовой точки расширения.

## Границы

Входят: вынос демо в отдельный пакет, точка расширения обёртки инстанса, перенос экономики в `rh`, реестр ссылочных полей состояния, перенос схем `item`/`location` и урезание `actor_v1` до `discriminator`, гейт на новые игровые сущности в ядре.

Не входят:

- Feature packages (`gv2.inventory` и подобные): применимость доказывается второй игрой, а не ожиданием.
- Перенос схем `screen`, `text`, `resource` — они framework-протокол по [ADR-0026](../../../ADR/0026-core-and-gameplay-ownership.md).
- Пересмотр kind-реестра: список категорий остаётся прежним, меняется только его толкование.
- Переработка `core:command.location.travel` и `core:service.location`: команда уже перекрывается пакетом, отдельная работа.

## Milestones

- [x] M1 — [Demo Out](DemoOut.md): демо-контент покидает ядро.
- [x] M2 — [Instance Extension](InstanceExtension.md): точка расширения обёртки и перенос экономики.
- [x] M3 — [Schema Migration](SchemaMigration.md): схемы `item`, `location` и урезание `actor_v1`.
- [x] M4 — [Boundary Gate](BoundaryGate.md): проверка, закрепляющая границу.

## Критический путь

```text
Demo Out
Instance Extension → Schema Migration → Boundary Gate
```

M1 не зависит ни от чего и может идти параллельно. M3 без M2 невозможна: как только поля актора уезжают в пакет, ядро перестаёт знать их структуру, и обёртка обязана собираться пакетом.

## Общие правила выполнения

1. Каждый этап оставляет рабочую игру: слайс из плана TestGameplaySlice проходится целиком после любого из них.
2. Ни одна задача не меняет замороженный корпус `Tests/Fixtures/PortableContentCore/`. Изменение `repository_content_hash` golden-прогона — признак ошибки; изменение `script_set_hash` ожидаемо и обновляется воспроизведением манифеста.
3. Перенос definitions выполняется `gv2-content rename`, а не текстовой заменой.
4. Каждая задача, меняющая failure semantics, добавляет negative case.
5. Правила, выразимые в Lua, проверяются спеками ([ADR-0024](../../../ADR/0024-lua-spec-runner.md)).
6. Новое observable behavior синхронно отражается в contract.

- [x] Схема актора в ядре содержит только `discriminator`; `item` и `location` описаны пакетом.
- [x] Пакет регистрирует обёртку по discriminator и добавляет свои методы, не трогая ядро.
- [x] Незарегистрированный discriminator даёт типизированный отказ, список известных нерегистраций пуст.
- [x] Новая игровая сущность в `core` ломает CI.
- [x] Слайс TestGameplaySlice проходится целиком.

Первый пункт закрыт отдельным change set уже после архивации плана. На момент архивации в `GameData/core/definitions/screens.json5` оставались `core:screen.main` и `core:screen.inventory` — последний прямо предполагает наличие инвентаря, что [ADR-0026](../../../ADR/0026-core-and-gameplay-ownership.md) запрещает. Ссылок в контенте на них не было, но их удерживали `gv2-content`-кейсы CTest, направленные на живое `GameData/core`: негативные кейсы `new … screen core:screen.main` проверяли отказ по дубликату и при отсутствии определения записывали его обратно в дерево репозитория.

Снято так: все `gv2-content`-кейсы, кроме smoke-валидации живого контента, переведены на замороженный корпус — он для того и существует, а запись в него ловит `pcc_shared_fixture_contract` по неиндексированному файлу. Корпус дополнен PO-каталогом, чтобы быть полной фикстурой. После этого экраны и их тексты удалены, а гейт `core_boundary_gate_contract` дополнен правилом для экранов: они не различаются по kind, поэтому framework-экраны заданы явным списком.
