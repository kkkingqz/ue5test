# План реализации designer-facing слоя

> **Материализует:** [Designer Lua Authoring](../../../Proposals/Archive/DesignerLuaAuthoringProposal.md).
> **Задачи:** DLA-01…23.
> **Результат:** геймплей `rh` написан на designer-facing Lua; фасад в теле команд не встречается.

## Цель

Дать геймдизайнеру Lua, на котором игровое правило выражается без Stable ID, реестров, конвертов команд и presentation DTO — и перевести на него текущий геймплей `rh`.

Слой ничего не заменяет: он вызывает фасад, не владеет состоянием и не вводит второго пути мутации. Programmer API остаётся для модов, сложных валидаторов, сервисов и расширений.

## Состояние на входе

Проверено по коду.

| Что | Сейчас |
|---|---|
| Признак «была запись в состояние» | Отсутствует: `mutation_window` знает только `window_open` |
| Проверка переносимости аргументов команды | Отсутствует: `validate_request` проверяет только, что `args` — таблица |
| Проверка переносимого значения | Есть, но локальная внутри `event_envelope` |
| `unwrap_state` | В экспорте; вызывается двумя спеками, ни одним продакшн-модулем |
| Хранилище и политика записи в схеме | Отсутствуют |
| Секция состояния, привязанная к definition | Отсутствует; секции фиксированы литералом |
| Локация персонажа | `state.world.current_location_id` |
| Откат состояния | Отсутствует; при отказе откатываются только факты |

Из этого следует порядок: сначала признак записи и общий примитив переносимости, потому что на них стоят и правило `fail()`, и канонизация аргументов.

## Принятые решения

Все зафиксированы в [предложении](../../../Proposals/Archive/DesignerLuaAuthoringProposal.md) и выносятся в ADR первой задачей. Кратко:

- команда именуется ключом дескриптора, регистрация отложена до фазы `register`;
- `fail()` до первой мутации — отказ, после — `AuthoringFailAfterMutation`; признак даёт `write_revision` в самом окне мутации;
- три вида property: definition (чтение), plain state (запись со схемной проверкой), managed state (только штатные операции);
- обратное превращение ID в обёртку — помеченная ссылка, а не дескрипторы аргументов;
- runtime-поля хранятся sparse: чтение отсутствующего даёт schema default, любая запись материализует, снятие — `reset()`;
- локация — свойство персонажа, `world.current_location` остаётся read-only аксессором;
- до production-релиза обратная совместимость не поддерживается.

## Границы

Входят: `write_revision` и изоляция сырого состояния, дескриптор модуля и прокси команд, модель property в схеме, универсальная секция runtime-состояния, события и presentation через слой, инструмент сбора текстов, перевод геймплея `rh`.

Не входят:

- объявление definitions и схем из Lua;
- удаление programmer API — фасад, реестры и декораторы остаются;
- отмена валидаторов: `fail()` покрывает типовой случай, валидаторы остаются для модов, приоритетов и перехвата;
- per-module окружения и capability sandbox;
- визуальный редактор — [Content Editor Plugin](../../../Proposals/ContentEditorPluginProposal.md).

## Milestones

- [x] M1 — [Foundation](Foundation.md): признак записи, изоляция сырого состояния, общий примитив переносимости.
- [x] M2 — [Commands](Commands.md): дескриптор модуля, прокси команд, отложенная регистрация, `fail()`, `run`/`later`.
- [x] M3 — [Properties](Properties.md): хранилище и политика записи в схеме, три вида property, два типа ссылок.
- [x] M4 — [Runtime State](RuntimeState.md): универсальная секция, sparse-материализация, переезд локации на актора.
- [x] M5 — [Events and Presentation](EventsAndPresentation.md): `emit`/`on`, `action`/`button`/`show_screen`, тексты.
- [x] M6 — [RH Migration](RhMigration.md): геймплей `rh` переписан на новый синтаксис, старый путь удалён.

## Критический путь

```text
Foundation ─┬─► Commands ──────────┬─► Events and Presentation ─► RH Migration
            └─► Properties ─► Runtime State ──────────────────────┘
```

M1 не меняет ничего наблюдаемого и идёт первым. Ветки Commands и Properties независимы и могут идти параллельно; сходятся на M5 и M6.

M4 — единственный этап, меняющий форму состояния, и самый дорогой. M6 не начинается, пока не закрыты обе ветки: переписывать геймплей на половину слоя значит переписывать дважды.

## Общие правила выполнения

1. Слой вызывает фасад и никогда не пишет в состояние в обход окна мутации. Появление второго пути мутации — дефект, а не оптимизация.
2. Правила, выразимые в Lua, проверяются спеками ([ADR-0024](../../../ADR/0024-lua-spec-runner.md)). C++ трогается только там, где иначе нельзя: `write_revision` и изоляция `unwrap_state`.
3. Проверка переносимого значения существует в одном экземпляре: события, аргументы команд и параметры отказа используют её, а не свои копии.
4. Каждая задача, меняющая failure semantics, добавляет negative case.
5. Изменение `script_set_hash` в golden ожидаемо и обновляется воспроизведением манифеста; изменение `repository_content_hash` — признак ошибки, кроме задач, сознательно меняющих контент `rh`.
6. Новое observable behavior синхронно отражается в contract.

## Итоговый Definition of Done

- [x] В теле команд `rh` не встречается ни одного обращения к `game.*`.
- [x] Ни одной пользовательской строки в геймплейном коде, включая отказы.
- [x] `fail()` после мутации даёт ошибку с указанием команды, а не частичный эффект.
- [x] Запись в managed-поле отклоняется и называет операцию, объявленную схемой.
- [x] Добавление runtime-поля новому виду сущности не требует правок ядра.
- [x] `unwrap_state` недостижим из геймплейного пакета.
- [x] Слайс проходится целиком; `state_hash` до и после сохранения совпадает.
- [x] Старый путь регистрации геймплея `rh` удалён, а не оставлен запасным.

Два наблюдения, зафиксированных при приёмке.

Механизм managed-полей реализован и покрыт спеками, но `gold` и `stamina` актора в `rh` **не объявлены managed**: они остаются обычными полями обёртки, защищёнными только тем, что команды пользуются `add_gold`/`spend_stamina` по договорённости. Прямое присваивание `player.gold = 100` проходит, и на нём стоят фикстуры существующих спеков. Объявить их managed — отдельное решение с последствиями для подготовки состояния в тестах.

Текст отказа в поле `message` в декораторе `rh/scripts/gameplay/actors.lua` устранён отдельным change set после архивации: отказ приведён к форме соседей — `rh:error.economy.invalid_amount` с `params`. Тем же разбором обнаружено, что `Scripts/gameplay/root.lua` в ядре содержал команду `core:command.actor.reward` с золотом и четыре текста отказа в `message`; команда удалена следующим change set — потребителей у неё не было, а её механизм принадлежал игре, а не движку.
