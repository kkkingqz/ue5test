# GenericUiTransactionFollowUp: итог выполнения

> **Материализует:** исторический итог выполненного плана; документ не является источником правил или задач.

## Цель и результат

**Цель:** закрыть семь находок внешнего follow-up review от 2026-09-02 и привести механизмы транзакционной модели UI к правилу перечислителя. Раунд нашёл дефекты не на новой территории, а внутри ремонтной машинерии, построенной предыдущим планом: план отката строился по текущей схеме и потому неверно восстанавливал смену схемы; откат чинил физическое состояние и не чинил учётное; гейт полноты выводился из раскладки памяти вместо списка полей.

**Результат:** отказ `AddChild` доходит до восстановления по [ADR-0041](../../ADR/0041-ui-commit-rollback-model.md) вместо мнимого успеха; `keyed_by` схемы проецируется в capability, и сверка из `GBH-08` получила вторую сопоставимую сторону; полнота полей доказывается инвентарём членов по исходнику, а не `sizeof`; каждая прямая мутация имеет обратную, построенную от зафиксированной схемы, и невозможность её подготовить — отказ Prepare; откат возвращает `LastCommittedProperties` и метаданные схемы вместе с физическим состоянием; ни один Blueprint-callback не исполняется внутри отменяемой транзакции; множество границ отката перечисляет сканер по исходнику, а не рукописный список из шести.

## Этапы и задачи

### M1 — Deterministic Bugs

- `GBF-01` — Shell-attach сообщает о фактическом отказе
- `GBF-02` — `keyed_by` схемы проецируется в capability
- `GBF-03` — Инвентаризация членов вместо `sizeof`

### M2 — Structural Rollback

- `GBF-04` — Снимок зафиксированного состояния и обязательная обратная мутация
- `GBF-05` — Учётное состояние восстанавливается вместе с физическим

### M3 — Lifecycle and Closure

- `GBF-06` — Callback вне отменяемой транзакции
- `GBF-07` — Границы отката перечисляет механизм
- `GBF-08` — Сверка закрытий и архивация раунда

## Введённые перечислители

Главный результат плана лежит не в семи починках, а в том, что четыре универсальных утверждения перестали опираться на рукописные списки. Каждый перечислитель выводит фактическую сторону из исходника и сверяет её с независимо объявленной ожидаемой.

| Утверждение | Перечислитель |
|---|---|
| Все отказоспособные вызовы движка в attach-пути потребляют результат | `Tools/Testing/validate_shell_attach_failure_consumption.py` — выводит каждый `->AddChild(...)` внутри `AttachScreenToLayer` |
| Все поля capability классифицированы | `Tools/Testing/validate_ui_capability_member_inventory.py` — выводит члены структуры из объявления, сверяет с явной таблицей |
| Все границы отката покрыты контрактом восстановления | `Tools/Testing/validate_ui_rollback_boundaries.py` — выводит определения `Commit*`/`AttachScreenToLayer`, сверяет с `EGV2UiRollbackBoundary` и его recovery-mapping |
| Все виды мутаций, требующие обратной | `GetUiMutationKindsRequiringInverse()` — обход видов, по которому тест удаляет обратную мутацию для каждого |

Каждый из четырёх имеет исполняемый отрицательный самотест: синтетический неизвестный член, стёртое распространение отказа, новая граница без покрытия, удалённая обратная мутация.

## Что показала приёмка

План был заявлен выполненным. Независимая проверка не подтвердила закрытие и вернула в работу две задачи; обе доведены, находки записаны как `GBF-AF-01`…`GBF-AF-03` и устранены.

**Сценарий `GBF-05` для вложенного экрана не работал ни разу.** `GV2.Runtime.UI.NestedInstancesAndTabsContract` падал семью утверждениями, добавленными коммитом самой задачи `GBF-05`. Разбор дал две независимые причины. Фикстура публиковала в базовой ревизии одну вкладку из двух засеянных, а `ApplyTabEntries` очищает карту вкладок и заполняет её из принятой ревизии — верное поведение продукта, но неопубликованная вкладка вытеснялась и во второй ревизии пересоздавалась из Screen Registry с чужим набором хостов. Вторая причина — производственная: `Prepare` контейнера вкладок возвращал отказ, не сбросив уже подготовленные записи, и `Commit` применял префикс непринятой транзакции, то есть частично применённое состояние, запрещённое `ADR-0041`.

Починка закрывала класс, а не экземпляр: тот же дефект накопления жил в consumer'е keyed-коллекции. Обе функции получили сброс подготовленного на любом пути отказа, включая добавленные позже. Защита вскрыла продолжение — `Commit` вкладок с пустым планом публиковал пустой список вкладок, то есть применял состояние вместо его отсутствия.

**Закрытие `GBF-08` опиралось на 16 тестов из 108.** `Done` требовал полного прогона; запись фиксировала `Automation RunTests GV2.UI` — 16/16. Фильтр `GV2.UI` покрывает ровно 16 тестов, а падающий лежал в группе `GV2.Runtime.UI.*`, под фильтр не попадающей ни одним тестом. Множество «все тесты» было подменено множеством «тесты, чьё имя начинается с `GV2.UI.`», и подмена не читалась из отчёта.

Это тот же класс, ради устранения которого написан план, — в его собственной задаче закрытия. Наблюдение повторилось и при самой проверке: подсчёт результатов по строкам лога давал 107 из 108, потому что лог обрывается на последнем тесте при завершении сессии; достоверный счёт даёт `index.json`, который пишет `-ReportExportPath`.
