# План реализации реестра обработчиков команд

> **Материализует:** [Commands and Events](../../Architecture/CommandsAndEvents.md) и [Lua Runtime Contract § `game.commands`](../../Architecture/LuaRuntimeContract.md).
> **Задачи:** CHR-01…10.
> **Результат:** обработчик команды регистрируется по `command_id`, и пакет добавляет команду, не трогая ядро.

## Цель

Заменить упорядоченную цепочку обработчиков реестром с ключом `command_id`. Это последнее место, где добавление геймплейной команды требует правки файлов ядра, и последнее, где оно требует C++.

После этого в `rh` может поехать не только сущность, но и механика.

## Состояние на входе

`dispatcher.new(handlers)` принимает упорядоченный массив модулей с методом `handle_command(request)` и берёт первый, вернувший truthy; `false`/`nil` означает «не моя команда». Массив собирается литералом в `Scripts/boundary/ingress.lua`, а внутри `gameplay/root.lua` идёт вторая ступень разбора через `if request.command_id == …`.

Следствия:

- Добавить команду можно только правкой `ingress.lua` и `root.lua` — оба в слоях, которые пакет трогать не должен.
- `ingress.lua` требует `core:module.gameplay.root` и `core:module.debug.start`, то есть точка входа хоста знает обработчики конкретной игры.
- Список замораживаемых реестров захардкожен в C++ (`FreezeGameRegistry`), поэтому новый реестр требует правки C++ ровно один раз — и после этого команды больше её не требуют.

**Найденный дефект.** Цепочка не различает «никто не обработал» и «выполнено без результата»: при `command_result == nil` переменная `is_success` остаётся `true`, окно мутации коммитится, события доставляются, счётчик команд растёт. Проверено на живом хосте replay-манифестом с командой `core:command.does.not.exist` — прогон вернул `"success": true`, `"executed_commands_count": 1`, пустой `fault_code`. Это не отдельная ошибка, а прямое следствие того, что «не моя» и «выполнено» кодируются одинаково.

Рядом уже трижды реализован нужный паттерн: `validator_registry`, `service_registry`, `subscriber_registry` — регистрация по ID, проверка дубликата, freeze после фазы `register`, канонический порядок перечисления.

## Принятые решения

- **Ключ — `command_id`.** Не упорядоченная цепочка. Сквозных обработчиков, которым нужно видеть чужие команды, в архитектуре нет: «до» — валидаторы, «после» — события, у обоих свои реестры. Точный ключ даёт lookup вместо обхода, ошибку вместо тихого перекрытия по порядку и независимость регистрации от места в массиве.
- **Неизвестная команда — отказ.** `{ ok = false, error = { code = "core:error.command.unknown", params = { command_id } } }`. Именно отказ, а не fault: это плохой запрос, а не сломанная сессия. Окно мутации не открывается, события не доставляются — как при отказе валидатора.
- **Обработчик — функция, а не таблица.** При ключевании по команде обёртка с методом `handle_command` не нужна.
- **Приоритет не вводится.** При точном ключе порядок обработчиков ненаблюдаем. `sequence` сохраняется только для канонического перечисления в диагностике.
- **Перекрытие требует явного намерения.** Дубликат — всегда ошибка; замена существующей записи возможна только с `options.override = true`. Правило «поздний пакет побеждает» как у definitions вводить рано: пока ни один пакет не перекрывает команду ядра, это лишняя механика.
- **ADR не требуется.** `game.commands` уже объявлено зарезервированным полем фасада, а `validators` — его первым заполненным подполем. `handlers` — сосед по тому же правилу, что `game.instances.actors`. Достаточно обновления contract.

## Границы

Входят: реестр `game.commands.handlers`, диспетчеризация по ключу, типизированный отказ на неизвестную команду, конверсия обработчиков ядра, развязка `ingress` от игровых модулей, одна строка freeze в C++, регистрация команды из пакета, синхронизация contract и guide.

Не входят:

- Реестр доменных методов сущностей (`get_gold`/`add_gold` в `actor_registry.lua`) и реестр ссылочных полей (`current_location_id` в `state_validator.lua`) — отдельные работы того же рода.
- Перенос механик в `rh`: план даёт возможность, наполнение — следующий шаг.
- Правило «поздний пакет побеждает» для команд.
- Изменение модели валидаторов, событий и окна мутации.

## Milestones

- [ ] M1 — [Registry](Registry.md): реестр существует, заморожен и покрыт спеками.
- [ ] M2 — [Dispatch by Key](DispatchByKey.md): диспетчер ходит в реестр, неизвестная команда отклоняется, `ingress` развязан.
- [ ] M3 — [Package Commands](PackageCommands.md): пакет регистрирует команду; contract и guide синхронизированы.

## Критический путь

```text
Registry → Dispatch by Key → Package Commands
```

M1 оставляет реестр незадействованным — это нормальное состояние, а не второй путь исполнения: пока в него никто не регистрируется, поведение не меняется вовсе. Весь риск сосредоточен в M2, где переключение происходит атомарно: цепочка удаляется, а не остаётся запасным путём.

## Общие правила выполнения

1. `dispatcher.new(handlers)` удаляется, а не сохраняется как совместимая перегрузка: два пути диспетчеризации не допускаются.
2. Реестр повторяет форму `validator_registry` (регистрация на фазе `register`, freeze, дубликат, канонический порядок) — расхождение формы без причины считается дефектом.
3. Правила, выразимые в Lua, проверяются спеками `Tests/Lua/commands/` ([ADR-0024](../../ADR/0024-lua-spec-runner.md)); C++ меняется ровно одной строкой freeze.
4. Каждая задача, меняющая failure semantics, добавляет negative case.
5. Изменение `script_set_hash` в golden-прогоне ожидаемо и обновляется тем же change set; изменение `repository_content_hash` — признак ошибки.
6. Новое observable behavior синхронно отражается в contract.

## Итоговый Definition of Done

- [ ] Обработчик регистрируется по `command_id` и находится за один lookup.
- [ ] Неизвестная команда даёт типизированный отказ; окно мутации не открывается, события не доставляются.
- [ ] `ingress.lua` не требует ни одного игрового модуля.
- [ ] `gameplay/root.lua` не содержит разбора `if request.command_id == …`.
- [ ] Пакет регистрирует свою команду и она исполняется в обоих хостах без правки ядра.
- [ ] Дубликат отклоняется; перекрытие возможно только с явным `override`.
- [ ] Добавление команды не требует изменений в C++.
