# Индекс планов реализации

`Plans` содержит исполняемые декомпозиции уже принятых направлений. План не меняет архитектурный контракт и не заменяет Proposal или ADR: он связывает ограниченные задачи, зависимости и evidence завершения.

## Правила ведения

- Checkbox задачи является единственным источником её статуса завершения.
- `[ ]` означает, что Definition of Done ещё не подтверждён; `[x]` — подтверждён полностью.
- Для текущей работы после названия можно временно добавить `— in progress`; для блокировки — `— blocked: <причина>`.
- Нельзя отмечать задачу выполненной только по наличию кода: должны пройти перечисленные tests и быть добавлены ссылки в поле `Evidence` либо в итоговый отчёт change set.
- При завершении всех задач этапа синхронно отмечается milestone в его локальном `README.md`.
- Изменение архитектурного инварианта по ходу задачи требует ADR и обновления contracts до отметки `[x]`.
- Задача несёт четыре поля помимо описания: `Инвариант` — какой архитектурный инвариант она задевает и как выглядит его нарушение (ссылка на contract плюс следствие для этой задачи, но не пересказ contract); `Не считается закрытием` — дешёвые пути, которые выглядят решением; `Done` — список требований по одному в строке, а не предложение с точками с запятой; `Evidence`. Причина формы: требование, спрятанное в середине длинной фразы, пропускается молча — так был потерян пункт про `KeyPropertyName` в `GBH-08`, названный в задаче явно.
- Для каждого универсального утверждения в Definition of Done назван перечислитель множества, по которому оно проверяется (`AGENTS.md`, «Универсальное утверждение требует перечислителя»). Утверждение без перечислителя формулируется суженно либо переносится в `STATUS-NNN`.
- Прежде чем вносить в задачу рукописный список (файлов, классов, путей, полей), назвать источник, который его заменяет: перечислитель, который уже существует в проекте и не читается, а не список, который придётся поддерживать вручную. Во всех шести случаях, найденных сплошной проверкой `DeclaredCompositeAdoption` (таблица в [архивной сводке](Archive/DeclaredCompositeAdoption.md#общий-инвариант-плана)), источник уже был в проекте. Если источника действительно нет — это и есть содержание задачи, а не повод писать список (`AGENTS.md`, «Универсальное утверждение требует перечислителя»).
- У каждого множества, вводимого планом (ярус, реестр, перечисление, набор причин отказа), назван производитель: кто кладёт в него первый элемент и в какой задаче это происходит. Множество, которому ни одна задача плана не даёт ни одного участника, — не заготовка на будущее, а мёртвый механизм: он не проверяется, расходится с фактом молча и обходится дороже, чем повторное решение вопроса. Если решение о его устройстве уже принято и терять его жаль, оно записывается в ADR, а не остаётся невыполнимой задачей.
- Закрытие задачи включает проверку её границы со следующей: до отметки `[x]` назвать, что следующая по зависимости задача теперь считает существующим — множество, поле, маршрут, класс, — и убедиться, что оно существует именно в том виде, в каком она на него рассчитывает. Сплошная проверка плана [PresentationEffectPipeline](Archive/PresentationEffectPipeline.md) нашла пять дефектов, из них четыре на стыках: задача наделила ролью класс, который следующая обещала удалить; задача снимала маршрут, который восстанавливает только следующая за ней; задача требовала поля в данных, которого не заводил никто. Внутри каждой задачи всё было согласовано — расходились границы, и чтение одной задачи их не показывало.
- Не считается закрытием задачи change set, который одновременно добавляет или ужесточает проверку и меняет проверяемый ею артефакт, если сообщение коммита не отвечает, чем артефакт был неправ **до** появления проверки (`AGENTS.md`, раздел «Commits» — правило и разобранный прецедент `WrapSize=1200`). Это не запрет менять артефакт и проверку одним change set, а требование к направлению обоснования в сообщении.
- Полностью выполненный план перестаёт быть источником задач; его нормативный результат к этому моменту обязан быть перенесён в contracts.
- Сначала полный план со всеми отмеченными tasks/milestones фиксируется отдельным commit. Затем создаётся плоский `Archive/<PlanName>.md` с итогом каждого этапа, каждым task ID и исходным названием ровно один раз, owner contracts и полным `source_commit`.
- До удаления исходного каталога каждый path проверяется через `git cat-file -e <source_commit>:<path>`, representative файл — через `git show`. Summary и [archive index](Archive/README.md) публикуются вторым commit; zip и подкаталоги в `Archive/` запрещены.
