# Presentation Effect Pipeline: план реализации

> **Материализует:** раздел `Effect` контракта [Presentation Snapshot and Effects](../../UI/PresentationSnapshotAndEffects.md), который объявлен нормативным и не реализован ни одной строкой кода. Первым потребителем механизма становится всплывающее окно по наведению на размеченный текст.
> **Не является нормативным:** единый pipeline эффектов с двумя источниками и жизненный цикл виджета за пределами коммита фиксируются ADR (`ADR-0047`, `ADR-0048`) задачами `PEP-01` и `PEP-02` до реализации.
> **Исполнение:** последовательно по задачам. Checkbox задачи — единственный источник её завершения.

**Цель:** получить один механизм одноразовых эффектов презентации, которым пользуются все будущие эффекты независимо от источника; сделать всплывающее окно обычным ui-блоком, а не особым C++-классом; и довести первый эффект — плавное появление и затухание окна — до состояния, в котором окно остаётся полноценным интерактивным виджетом всё время своего ухода.

**Технологии:** существующий universal UI property pipeline и declared composites ([ADR-0040](../../ADR/0040-universal-ui-property-pipeline.md)), маршрут `NestedScreen` (доказан DUC-09/10/11), слой `overlay_stack` `UGV2GameShellWidgetBase`, `FGV2LayeredUiReconciler`, `FGV2PreparedPresentationTransaction`. Нового runtime-модуля и внешней tween-библиотеки план не требует.

## Измеренное состояние

**Эффектов нет вовсе.** Ни `publish_effect`, ни очереди, ни apply path, ни отбрасывания по stale target в `Scripts/`, `Source/`, `Tests/` не существует. `Scripts/authoring/presentation.lua` публикует только desired UI document. Раздел `Effect` контракта описывает DTO (`effect_id`, `sequence`, `target`, `args`), правила порядка и обязательные тесты — всё это открыто как [`STATUS-002`](../../Status/ImplementationStatus.md).

**Всплывающее окно существует, но устроено как Slate-тултип.** `UGV2RichTextPopoverWidgetBase` (`Source/GV2PresentationApply/Public/UI/GV2RichTextPopoverWidgetBase.h`) создаётся декоратором в `OnOpening()` (`GV2RichTextWidgetBase.cpp:62`) и уничтожается в `OnClosed()` через `SlateToolTip->ResetContentWidget()`. Декоратор объявляет `IsInteractive() == true`, поэтому курсор в окно увести можно, но закрытие безусловно и мгновенно: состояния «окно уходит, но ещё живо» в модели нет.

**Содержимое окна зафиксировано в C++.** `FGV2RichTextHoverViewModel` (`GV2WidgetTypes.h:167`) — ровно `Title`, `Description`, `ImageResourceId` плюс transient `ResolvedImageBrush`. Схема `core:schema.ui_field.rich_text.v3` повторяет эту тройку в поле `hover`. Добавить в окно ещё один элемент сегодня нельзя без правки структуры, виджета, `GV2CentralStylePreparer` и схемы одновременно.

**Окно намеренно вне транзакции.** `PSC-10B`: popover создаётся после commit экрана, поэтому не может быть целью собственной подготовленной операции, ничего не разрешает сам и получает все значения от `UGV2RichTextWidgetBase`, который получил их из Prepare. Он сознательно не реализует `IGV2UiStyleConsumer`, чтобы не попасть в перечислитель стилизуемого поддерева экрана.

**Слой для окна уже есть.** `UGV2GameShellWidgetBase` объявляет `background`, `location_content`, `character_presentation`, `core_interface`, `overlay_stack`, `modal_stack`. Блокировка нижних слоёв — свойство `modal_stack`, а не `overlay_stack`.

**Hover не пересекает границу Lua и не должен.** `SemanticInput.md:110`: открытие, позиционирование, задержка и закрытие popover не вызывают Lua; `WidgetRegistry.md:278`: hover/unhover не пересекают Lua boundary. План это правило сохраняет.

## Почему дешёвые пути не дают результата

| Подход | Результат и цена | Выбор |
|---|---|---|
| Добавить UMG-анимацию в Blueprint окна и остановиться | Затухание появится, но окно останется тултипом: Slate уничтожит его в `OnClosed()` на середине анимации. Интерактивность во время ухода недостижима в принципе | Не исполним как есть |
| Сделать затухание локальным таймером внутри `UGV2RichTextPopoverWidgetBase` | Работает для одного окна и создаёт второй механизм презентации мимо очереди и `sequence`. `STATUS-002` не закрывается, а к нему добавляется расхождение | Недостаточен |
| Реализовать effect pipeline только для Lua-источника | Первый же потребитель — hover — оказывается вне pipeline, потому что hover не пересекает границу Lua. «Единый pipeline» опровергается собственным первым примером | Недостаточен |
| Оставить окно особым C++-классом, добавив ему полей | Каждое следующее окно снова требует C++: структура, виджет, style preparer и схема правятся вместе | Недостаточен |
| Один pipeline с двумя источниками; окно — nested screen в `overlay_stack`; затухание — первый эффект этого pipeline | Закрывает `STATUS-002` механизмом, `STATUS-003` — правилом и реализацией, и снимает C++ с пути добавления нового окна | Основа плана |

## Рекомендуемое устройство

### Один pipeline, два источника

Эффект остаётся тем, чем его описывает контракт: `effect_id`, монотонный `sequence`, optional `target` и `args`. Различаются только точки входа. **Lua-источник** публикует эффект фиксированным биндингом рядом с `publish_snapshot`; DTO schema-валидируется и глубоко копируется в исходящую очередь, reconciler внутри Lua-вызова не запускается. **Host-local источник** — презентационное событие, не имеющее gameplay-смысла и потому не пересекающее границу Lua: наведение курсора на размеченный span. Оба источника кладут эффект в одну очередь, получают `sequence` из одного счётчика и проходят один apply path с одинаковым отбрасыванием по stale target и чужому поколению сессии.

Это расширение контракта, а не его обход: сегодня раздел `Effect` сформулирован как часть «Lua → UE сообщений». `PEP-01` фиксирует, что источник эффекта не входит в его identity, и что host-local эффект не вправе нести gameplay-значимое состояние — иначе он стал бы скрытым каналом авторитета мимо `INV-014`.

### Два вида ухода виджета

Уход виджета со сцены бывает двух разных природ, и до сих пор существовала только первая:

**Stale-удаление.** Реконсиляция убрала экран или элемент, потому что состояние, которое он показывал, исчезло. Ввод гасится немедленно, в момент логического удаления, а не физического: принимать клик по тому, чего уже нет, нельзя ни кадра. Handle удалённого span инвалидируется тогда же.

**Self-dismissal.** Элемент уводит себя сам по собственному таймеру, а состояние, которое он показывает, никуда не делось. Он остаётся полноценным интерактивным виджетом до конца ухода, и взаимодействие с ним уход отменяет. Всплывающее окно — ровно этот случай.

Различение обязано быть выражено в типе, а не в комментарии: `PEP-02` вводит его как состояние жизненного цикла с явным владельцем, `PEP-09` делает невыразимым интерактивный stale-виджет.

### Окно как обычный ui-блок

Всплывающее окно перестаёт быть `UGV2RichTextPopoverWidgetBase` и становится экземпляром экрана в `overlay_stack`, собранным из declared composites — теми же средствами, что и всё остальное. Поле `hover` схемы `rich_text` перестаёт быть фиксированной тройкой и несёт nested screen: маршрут `NestedScreen` уже доказан DUC-09/10/11 и уже selectable в Designer.

Следствие, ради которого это делается: добавление нового вида окна становится авторской работой в данных и Blueprint. Проверяется это не рассуждением, а вторым видом окна, собранным в фикстурах без единой строки C++ (`PEP-06C`).

### Ярусы участников слоя

Хосты слоёв — `UOverlay`, и `ApplyScreenSlotLayout` ставит каждому экрану `HAlign_Fill`/`VAlign_Fill`: все экраны слоя занимают его целиком и различаются только глубиной. Позиции в слое не существует, поэтому «где стоит участник» — всегда вопрос Z, а не раскладки.

Содержимое панели слоя перестаёт быть равным документу и становится **множеством участников** из двух ярусов, снизу вверх:

| Ярус | Источник | Порядок внутри яруса |
|---|---|---|
| Документный | инстансы desired-документа | порядок документа |
| Host-local | реестр участников, порождённых не из документа | монотонный счётчик создания |

**Ярус определяется наличием ранга документа, а не фактом ухода.** Host-local участник ранга документа не имел никогда, поэтому уход его яруса не меняет — он продолжает жить наверху и гаснуть. Это существенно для всплывающего окна: оно уходит по self-dismissal и обязано оставаться интерактивным до конца.

Ярус и вид ухода — независимые оси. Участник любого яруса может уходить как stale или как self-dismissal; вид ухода задаёт правило приёма ввода ([ADR-0048](../../ADR/0048-widget-exit-lifecycle-and-input-gating.md)), а не место в порядке. Окно, чей span или экран убран реконсиляцией, становится stale, оставаясь в host-local ярусе.

Третий ярус — для документных участников, переживающих потерю ранга документа, — этому плану не нужен: анимации переходов между экранами вне его области, поэтому физическое снятие документного участника остаётся синхронным и производителя у такого яруса нет. Его Z-место решено заранее и записано в [ADR-0048](../../ADR/0048-widget-exit-lifecycle-and-input-gating.md), чтобы план, вводящий переходы экранов, не переигрывал вопрос; строить механизм удержания с нулём потребителей этот план не берётся.

Fail-closed свойство сохраняется целиком. Сегодня `ReconcilePrepared` делает `ClearChildren` и заново добавляет только то, что пришло в `Models`, а `CreateItem` возвращает `nullptr`; ребёнок выживает, только если его назвал перечислитель. После изменения перечислителей два — документ и реестр недокументных участников, — и оба механические. Инвариант «содержимое панели = документ» заменяется на «содержимое панели = документ ∪ реестр» и остаётся сплошным.

Цена названа прямо: проход реконсиляции перестаёт быть чистой функцией от документа и начинает зависеть от переходного состояния слоя.

### Правка C++ как классифицируемое событие

План действует под отдельным правилом владельца проекта: **всякая правка C++ виджетов по ходу плана классифицируется в change set до отметки `[x]`.** Два допустимых исхода:

- **Механизм.** Правка добавляет или меняет сам движковый механизм — вид эффекта, состояние жизненного цикла, потребитель свойства. Такая правка законна, и её признак — что она одна обслуживает неограниченное число будущих авторских случаев.
- **Отсутствующий маршрут данных.** Правка понадобилась, потому что конкретный авторский случай не выражается данными. Такая правка не принимается как есть: задача обязана добавить маршрут, после которого этот класс случаев данными выражается, и показать это вторым случаем.

Третьего исхода нет. Правка, которую не удалось отнести ни к одному, останавливает задачу.

## Объём фиксации

План включает 10 задач: `PEP-01…10`. Первая фиксируемая поверхность — раздел `Effect` контракта презентации, схема `core:schema.ui_field.rich_text`, слой `overlay_stack` и widget-поверхность rich text. План закрывает [`STATUS-002`](../../Status/ImplementationStatus.md) целиком и [`STATUS-003`](../../Status/ImplementationStatus.md) обеими половинами — правилом и реализацией.

Вне плана: анимации переходов между экранами, звук, тосты и прочие виды эффектов. План строит механизм и доводит до конца ровно один его вид; остальные виды — авторская и содержательная работа поверх готового pipeline. Gameplay-семантика окна (что именно в нём показано) планом не задаётся.

Множество automation test id план расширяет; удалений не предполагается, кроме тестов `UGV2RichTextPopoverWidgetBase`, чья судьба перечисляется поимённо в `PEP-06B`.

`PEP-06` и `PEP-06A` между собой независимы — реестр участников и детектор наведения не пересекаются; оба обязаны предшествовать `PEP-06B`, который их первым потребляет. Порядок между ними выбран для линейности исполнения, а не по зависимости.

Порядок не переставляется. Оба ADR идут **до** кода, потому что обе задачи меняют архитектурный инвариант: первая — состав канала Lua → UE, вторая — модель владения виджетами и правило ввода [ADR-0041](../../ADR/0041-ui-commit-rollback-model.md). Механизм эффектов идёт **до** переезда окна, иначе переезд не на чем проверять и окно временно получает собственный таймер — ровно тот второй механизм, который план запрещает. Переезд окна идёт **до** затухания, потому что затухание требует виджета, переживающего собственное логическое удаление, а тултип им быть не может.

## M0 — Решения до кода

### PEP-01 — Зафиксировать единый pipeline эффектов с двумя источниками

- [x] PEP-01 — Зафиксировать единый pipeline эффектов с двумя источниками

**Зависимость:** нет. **Файлы:** [`ADR-0047`](../../ADR/0047-one-shot-effect-pipeline-and-origins.md); `Docs/UI/PresentationSnapshotAndEffects.md`.

**Инвариант:** [INV-014](../../Architecture/Invariants.md) — presentation восстановима и не является источником gameplay-истины. Host-local источник эффекта — новый путь, по которому в презентацию попадает сообщение, не пришедшее из Lua. Если такому эффекту разрешить нести gameplay-значимое состояние, он станет каналом авторитета мимо canonical state, и нарушение будет наблюдаемым: значение, пережившее reload, которого нет в сохранении.

**Решение:** ADR фиксирует, что identity эффекта не включает его источник: `effect_id`, `sequence`, `target`, `args` одинаковы для обоих. Lua-источник публикует фиксированным биндингом рядом с `publish_snapshot` со schema-валидацией и глубоким копированием. Host-local источник порождается презентационным событием, не имеющим gameplay-смысла, и обязан быть выводим заново из snapshot плюс состояния устройства ввода. Оба идут в одну очередь с одним счётчиком `sequence`. ADR отвечает, почему host-local источник не нарушает `INV-014`, а не только чем он удобен.

**Не считается закрытием:** ADR, разрешающий host-local эффекты общей формулировкой без критерия, по которому эффект признаётся не несущим gameplay-состояния; два счётчика `sequence`; описание источника как поля DTO — это вернуло бы источник в identity эффекта; ADR, откладывающий правило non-persistence «до реализации».

**Шаги:**
1. Написать ADR: состав DTO, два источника и их равноправие, единый `sequence`, правило отбрасывания по stale target и чужому поколению сессии, non-persistence при save/load.
2. Сформулировать критерий допустимости host-local эффекта проверяемо: эффект допустим, если его отсутствие не меняет ни одного значения canonical state и он восстановим из snapshot и состояния ввода.
3. Обновить `PresentationSnapshotAndEffects.md`: раздел `Effect` перестаёт быть частью «Lua → UE сообщений» и получает оба источника.
4. Назвать ADR в contracts и в `Docs/ADR/README.md`.

**Done:**
- ADR принят и назван в contracts; номер проверен по каталогу в момент записи.
- Критерий допустимости host-local эффекта сформулирован так, что его нарушение наблюдаемо, а не оценочно.
- Раздел `Effect` контракта описывает оба источника и единый `sequence`.
- ADR отвечает, чем прежняя формулировка «Lua → UE сообщения» была неправа, а не только чем новая полнее.

**Evidence:** ADR, diff контракта, `validate_docs`.

### PEP-02 — Зафиксировать жизненный цикл уходящего виджета и правило ввода

- [x] PEP-02 — Зафиксировать жизненный цикл уходящего виджета и правило ввода

**Зависимость:** PEP-01. **Файлы:** [`ADR-0048`](../../ADR/0048-widget-exit-lifecycle-and-input-gating.md); `Docs/UI/UIDocumentAndReconciliation.md`, `Docs/UI/README.md`.

**Инвариант:** [ADR-0041](../../ADR/0041-ui-commit-rollback-model.md) — модель commit/rollback реконсиляции, и владение виджетами, которое перечисляет `validate_session_snapshot_ownership.py`. Виджет, живущий после логического удаления, сегодня не принадлежит ни дереву слоя, ни кандидату; без явного владельца он становится untraced owning-указателем, и гейт с 13 негативными мутациями это обнаружит. Второе следствие: при откате коммита ([ADR-0041](../../ADR/0041-ui-commit-rollback-model.md)) и при замене сессии ([ADR-0044](../../ADR/0044-session-replacement-and-registry-sealing.md)) уходящий виджет обязан иметь определённую судьбу, иначе она окажется разной в разных ветках.

**Решение:** ADR вводит уход как состояние жизненного цикла с двумя различимыми видами. **Stale-удаление**: реконсиляция убрала элемент, показанное им состояние исчезло; ввод гасится в момент логического удаления, handles инвалидируются тогда же, физическое снятие может отстать. **Self-dismissal**: элемент уводит себя по своему таймеру при живом показанном состоянии; остаётся интерактивным до конца, взаимодействие отменяет уход. ADR называет владельца уходящего виджета, его судьбу при rollback и при замене сессии, и фиксирует, что `STATUS-003` закрывается обоими случаями, а не одним.

**Не считается закрытием:** записать различие как соглашение в комментарии; оставить владельца уходящего виджета неназванным «потому что он всё равно скоро исчезнет»; свести правило к «stale не интерактивен», не сказав, в какой момент гаснет ввод; ADR, не отвечающий на rollback и replacement.

**Шаги:**
1. Перечислить фактические места, где сегодня виджет снимается со сцены, — перечислителем, а не списком: обход `CommitReconcile` и его вызывающих.
2. Описать оба вида ухода, момент гашения ввода и владельца на каждом шаге.
3. Определить судьбу уходящего виджета при откате коммита и при замене сессии; обе ветки назвать явно.
4. Обновить `UIDocumentAndReconciliation.md` и `UI/README.md`: правило про «до завершения exit animation» переписывается через два вида ухода.
5. Назвать ADR в contracts.

**Done:**
- Оба вида ухода описаны с моментом гашения ввода, а не только с конечным состоянием.
- Владелец уходящего виджета назван для каждого шага его жизни; правило совместимо с перечислителем `validate_session_snapshot_ownership.py`.
- Судьба уходящего виджета при rollback и при replacement определена явно в обеих ветках.
- `UI/README.md` и `UIDocumentAndReconciliation.md` больше не формулируют инвариант через несуществующий механизм.
- ADR отвечает, чем прежняя формулировка была неправа: она выражала правило ввода через анимацию, которой не было, и потому выполнялась пусто.

**Evidence:** ADR, перечень мест снятия виджета со сцены, diff contracts.

### PEP-03 — Реализовать DTO, очередь и порядок эффектов

- [x] PEP-03 — Реализовать DTO, очередь и порядок эффектов

**Зависимость:** PEP-02. **Файлы:** `Source/GV2RuntimeCore/Public/GV2RuntimeCore/GV2RuntimeSession.h` и `.cpp` (`FPresentationEffect`, `EPresentationEffectRejectReason`, `ResolveEffectTarget`, `PublishHostLocalEffect`/`TakePendingEffects`); `Scripts/boundary/outbound.lua` (`publish_effect`/`take_pending_effects`, staged/committed lifecycle); `Source/GV2RuntimeCore/Private/GV2PresentationEffectConformance.cpp` и `Testing/GV2PresentationEffectConformance.h`; `Source/GV2/Private/Tests/GV2PresentationEffectConformanceTests.cpp`; `Tests/Lua/presentation/effect_queue_spec.lua`.

**Инвариант:** [достоверная приёмка](../../Architecture/BuildAndTooling.md) и раздел `Snapshot/effect ordering` контракта. Очередь без монотонного `sequence` и без отбрасывания чужого поколения — это тихая доставка эффекта в сессию, которая его не заказывала: наблюдаемо как всплывающее окно предыдущей сессии поверх новой.

**Решение:** DTO эффекта и очередь в переносимом слое, оба источника публикуют через одну функцию постановки, `sequence` выдаётся одним счётчиком. Отбрасывание по трём причинам — stale target, чужое поколение сессии, устаревшая ревизия — каждая со своей типизированной причиной, а не общим `false`. Lua-биндинг schema-валидирует и глубоко копирует DTO; reconciler внутри Lua-вызова не запускается.

**Не считается закрытием:** очередь без `sequence`; общий булев отказ вместо типизированных причин отбрасывания; постановка эффекта прямо из Lua-вызова; DTO, принимающий произвольный payload без схемы.

**Шаги:**
1. Определить DTO по контракту; реализовать очередь и единый счётчик `sequence`.
2. Реализовать три причины отбрасывания; на каждую — негативный тест.
3. Добавить Lua-биндинг публикации со schema-валидацией и глубоким копированием; проверить, что reconciler не вызывается изнутри Lua.
4. Проверить монотонность `sequence` при чередовании источников: эффекты из Lua и host-local в одной очереди не получают совпадающих номеров.

**Done:**
- `sequence` монотонен при любом чередовании источников; перечислитель — тест с обоими источниками вперемешку, а не по одному.
- Каждая из трёх причин отбрасывания имеет собственную типизированную причину и негативный тест.
- Lua-биндинг schema-валидирует DTO и глубоко копирует его; эффект с лишним или неизвестным полем отвергается до постановки.
- Reconciler не запускается внутри Lua-вызова; проверено, а не заявлено.

**Evidence:** прогоны негативных тестов, тест чередования источников, вывод schema-валидации.

**Приёмочная коррекция.** Первоначальная реализация оставляла committed Lua batch во внутренней Lua-очереди до произвольного будущего вызова `TakePendingEffects`; в production единственный вызов происходил только при hover. Это сохраняло уникальность `sequence`, но не порядок между Lua-публикацией и последующим host-local событием. Исправлено одной точкой `FGV2SessionCoordinator::DrainPresentationEffects`: coordinator вызывает её после каждого protected runtime entry до несвязанной host-работы, а host-local producer запрашивает тот же drain после публикации. `GV2.Runtime.Presentation.EffectsDrainAfterRuntimeEntry` доказывает путь без hover; перечислитель production-вызовов `TakePendingEffects` по-прежнему даёт ровно один call site.

### PEP-04 — Реализовать исполнение эффектов и non-persistence

- [x] PEP-04 — Реализовать исполнение эффектов и non-persistence

**Зависимость:** PEP-03. **Файлы:** `Source/GV2PresentationApply/Public/GV2PresentationApply/PresentationEffectApply.h` и `Private/PresentationEffectApply.cpp` (`EPresentationEffectKind`, `FGV2PresentationEffectApply`); `Source/GV2/Private/Tests/GV2PresentationEffectApplyTests.cpp`; non-persistence case 5 добавлен в `Source/GV2RuntimeCore/Private/GV2PresentationEffectConformance.cpp` (сохранение/загрузка через существующую портативную сессию, рядом с `GV2.Runtime.SaveAndLoad.*`, без правки самого файла).

**Реализация (закрытая с 0 видами эффекта):** перечисление `EPresentationEffectKind` заведено пустым (`Count = 0`) — единственный содержательный вид, прозрачность, явно вынесен в `PEP-08`, чтобы не объединять механизм с первым потребителем в одном change set. Экземплярность гейта полноты доказана мутацией по ходу разработки: временно добавленное значение перечисления (`TestOnlyMutationProbe`) поймано гейтом (`GV2.Runtime.Presentation.PresentationEffectApply` красный: «Zero unhandled effect kind diagnostics» — 1 вместо 0), после чего откачено. Компилятор эту мутацию НЕ ловит (пустой `switch` без `default` не выдаёт предупреждения в текущей сборочной конфигурации) — единственная измеренная гарантия здесь рантайм-гейт, симметричный `FGV2PropertyConsumerFactory::ValidateAllKindsHandled`, с независимой перепроверкой через `IsInapplicableKind` (без неё функция-заглушка `GetKindHandlingStatus` тихо провалила бы найденную мутацию через собственный fallback). `Apply` принимает только `Kind` — ни виджета, ни snapshot, ни gameplay-state в сигнатуре нет в принципе (граф сборки `GV2PresentationApply.Build.cs` не даёт этому модулю знать такие типы), поэтому отказ эффекта структурно не может задеть ни то, ни другое — гарантия ADR-0043 D2, а не тест поведения. Non-persistence проверен реальным `SaveToSlot`/`StartFromSave` над портативной сессией: canonical state hash не меняется при постановке недренированного эффекта, после реального перезапуска сессии из сохранённого слота хэш совпадает с состоянием до эффекта, а очередь эффектов пуста — поведением, а не отсутствием поля в контейнере.

**Инвариант:** [ADR-0043](../../ADR/0043-presentation-apply-boundary.md) — граница применения презентации: физическое применение получает только подготовленные значения и исполняется на Game Thread. Эффект, применяемый вне Game Thread, воспроизводит ровно тот класс отказа, который уже закрыт guard-ом в `FGV2PresentationApply::Apply`.

**Решение:** исполнитель эффектов на Game Thread, принимающий подготовленные значения. Вид эффекта — закрытое перечисление механизма с exhaustive dispatch: новое значение без явной ветки проваливает гейт полноты, симметрично `FGV2PropertyConsumerFactory::ValidateAllKindsHandled`. На компилятор здесь опираться нельзя — измерено при исполнении: пустой `switch` без `default` предупреждения не даёт, поэтому единственная гарантия — рантайм-гейт. Параметры и цель вида — данные. Отказ эффекта не трогает snapshot и gameplay state. Save/load эффекты не реплеит: незавершённый эффект не сохраняется и после загрузки не возобновляется.

**Не считается закрытием:** диспетчеризация по строковому `effect_id` через if-цепочку — при добавлении вида молчит компилятор; применение эффекта вне Game Thread «потому что он косметический»; тест non-persistence, проверяющий отсутствие поля в файле вместо поведения после загрузки.

**Шаги:**
1. Реализовать исполнитель на Game Thread; отклонить off-thread вызов типизированным отказом.
2. Ввести закрытое перечисление видов эффекта и exhaustive dispatch; добавить гейт полноты.
3. Проверить, что отказ эффекта не инвалидирует snapshot и gameplay state.
4. Проверить non-persistence поведением: эффект в процессе → сохранение → загрузка → эффект не возобновлён, состояние презентации восстановлено из snapshot.

**Done:**
- Новый вид эффекта без явной ветки не проходит: гейт полноты либо компилятор; случай покрыт негативным self-test.
- Off-thread применение отклоняется типизированным отказом; случай покрыт тестом.
- Отказ эффекта оставляет snapshot и gameplay state неизменными; проверено внесённым отказом, а не рассуждением.
- Non-persistence проверен поведением после реальной загрузки.

**Evidence:** вывод гейта полноты, негативные прогоны, save/load-прогон с эффектом в процессе.

### PEP-06 — Принять в слой участника, не пришедшего из документа

- [x] PEP-06 — Принять в слой участника, не пришедшего из документа

**Зависимость:** PEP-05. **Файлы:** `FGV2LayeredUiReconciler` (`CommitReconcile`, шаг 2), `FGV2KeyedCollection::ReconcilePrepared` (`PreparedKeyedCollection.h`), `UGV2GameShellWidgetBase` (`GetScreensInLayer`, `SetTopModalInteractive`).

**Инвариант:** [ADR-0042](../../ADR/0042-presentation-authority-and-publication.md) и владение виджетами. Сегодня недокументный ребёнок был бы молча выброшен: `ReconcilePrepared` делает `Container->ClearChildren()` и заново добавляет только пришедшее в `Models`, а `Models` строятся исключительно из `Plan.ScreensToUpdateOrAttach`. ### PEP-06C — Довести окно наведения до авторской полноты

- [x] PEP-06C — Довести окно наведения до авторской полноты

**Зависимость:** PEP-06B. **Файлы:** `GameData/core/schemas/ui_field_rich_text_v4.schema.json5` (длительность в `hover`); `GV2WidgetTypes.h`/`PreparedPresentationTransaction.h` (`Duration` на `FGV2RichTextHoverViewModel`/`FPreparedRichTextHover`); `GV2PropertyConsumers.cpp` (чтение `duration`, перенос через `FlattenRichTextSpan`); `Source/GV2PresentationApply/Private/UI/GV2RichTextWidgetBase.cpp` (перенос `Duration` в `ApplyPreparedRichTextSpans`); `Source/GV2/Public/UI/GV2ScreenWidgetBase.h`/`.cpp` (удержание в границах вьюпорта); `GV2RichTextSpanDecorator.cpp` (закрепляющий комментарий канала `SpanId`); `GV2LayeredReconciliationTests.cpp` (`ScreenAnchorHostViewportClamp`, `HoverWindowSelectableFromData`); `GV2LayoutInvariantSourceTests.cpp` (исключения `DCA-15` для тестовых WBP-фикстур); `Content/UI/Widgets/WBP_HoverFixtureAlpha.uasset`/`WBP_HoverFixtureBeta.uasset` (второй вид окна, созданы через `unreal-mcp`).

**Задача переписана после `PEP-06B`.** Прежняя формулировка требовала превратить общий попаповый стиль темы в ключевой набор и выбирать его токеном. Такого стиля больше нет: `PEP-06B` удалил `UGV2RichTextPopoverWidgetBase` вместе со всей его Theme-инфраструктурой (`RichTextPopover*`, `FPreparedRichTextPopoverStyle`, `IGV2PreparedRichTextPopoverStyleTarget`), и вид окна теперь задаётся тем, какой `screen_id` назван в `hover` конкретного спана. Это сильнее токена: токен выбирал стиль из фиксированного набора, `screen_id` выбирает целый экран. Задача сохраняет из прежней редакции то, что к новому механизму применимо, и добавляет свойства, которые при уходе от Slate были потеряны молча.

**Инвариант:** требование владельца проекта — новый вид окна не требует правки C++ — и [достоверная приёмка](../../Architecture/BuildAndTooling.md). Уход от Slate-тултипа отдал нам не только показ окна, но и его обязанности: удержание в границах экрана и ограничение размера выполнял слой окон Slate, и ни то ни другое не было заменено. Свойство, существовавшее до change set и исчезнувшее без решения, — регресс, а не упрощение.

**Решение:**

**Вид окна доказывается вторым экраном.** Механизм уже на месте после `PEP-06B`; непроверенным осталось само требование. Второй вид окна собирается целиком в данных и Blueprint-фикстуре — другой `screen_id`, другая рамка, другие габариты, ни строки C++.

**Удержание в границах вьюпорта возвращается как наше.** `SetAnchoredContentPosition` кладёт точку в слот канваса как есть, и ни вызывающий (`GV2RichTextWidgetBase.cpp`), ни реализация не ограничивают её вьюпортом: спан у правого или нижнего края даёт окно, частично уехавшее за экран. Slate-тултип делал это бесплатно, и потеря не была решением.

**Потолок размера решается явно.** `RichTextPopoverMaxWidth`/`MaxHeight` ограничивали любое окно игры и удалены вместе с темой попапа. Сегодня авторский WBP вправе закрыть слой целиком. Задача обязана записать выбор: принять как дисциплину авторинга либо вернуть потолок в форме, не воскрешающей общий стиль. Умолчание не допускается — свойство было и пропало побочным эффектом.

**Длительность получает дом в схеме.** `hover` в v4 получает поле длительности рядом со `screen_id`. Прежняя редакция отправляла её в попаповый стиль; стиля нет, и `PEP-08` остался бы без места в данных. Правка схемы на месте не требует ни новой версии, ни миграции: v4 введена `PEP-05`, и `hover` не заполнен ни в одном реальном пакете.

**Канал переноса `SpanId` закрепляется.** `FGV2RichTextSpanToolTip` оставлен `PEP-06B` как способ восстановить `SpanId` по найденному `SRichTextHyperlink`, но выглядит мёртвым кодом: все методы no-op, `IsEmpty()` всегда `true`, `IsInteractive()` — `false`. Первая же чистка неиспользуемого тултипа тихо сломает наведение, и компилятор промолчит. Помещено в эту задачу как названный остаток `PEP-06A`/`PEP-06B`: она последняя в этой области перед переходом к эффектам.

**Не считается закрытием:** собрать второй вид окна тем же `screen_id` — требование останется недоказанным; вернуть потолок общим стилем для всех окон — это воскрешение ровно того, что `PEP-06B` удалил как мёртвое; ограничить окно вьюпортом только по правому краю, потому что так проявилось в ручной проверке; положить длительность в C++, отложив место в данных «до появления второго значения»; оставить перенос `SpanId` как есть, ограничившись комментарием, — прецедент `CFC-AF-24` показал, что комментарий не механизм.

**Шаги:**
1. Добавить поле длительности в `hover` схемы v4; довести его до подготовленного hover спана тем же путём, которым туда приходит `screen_id`.
2. Реализовать удержание окна в границах вьюпорта; проверить на спанах у правого, левого, верхнего и нижнего краёв.
3. Принять решение по потолку размера и записать его; при возврате потолка — в форме, не создающей общего стиля.
4. Закрепить перенос `SpanId`: явный носитель либо тест, краснеющий при снятии привязки тултипа.
5. Собрать второй вид окна целиком в данных и Blueprint-фикстуре: другой `screen_id`, другая рамка, другие габариты.

**Done:**
- Второй вид окна собран без правки C++ — другой `screen_id`, отличающиеся рамка и габариты; проверено снятыми размерами двух окон, а не фактом зелёного прогона.
- Окно целиком помещается во вьюпорт при наведении на спан у каждого из четырёх краёв; перечислитель — прогон по четырём позициям, не одна проверка.
- Решение по потолку размера записано; если потолок возвращён, он не восстанавливает общий стиль для всех окон.
- У длительности есть место в данных: поле в `hover` схемы v4, заполняемое содержимым пакета; два вида окна вправе иметь разную длительность.
- Снятие привязки тултипа краснит тест либо невозможно, потому что `SpanId` носит явный носитель; проверено мутацией, а не чтением.

**Evidence:** снятые габариты двух видов окна, прогон по четырём краям вьюпорта, запись решения по потолку, мутационная проба на снятие привязки тултипа, схема v4 с полем длительности.

**Реализация.** Длительность получила поле `duration` (`kind: "number", min: 0.0, required: false`) в `hover` схемы `ui_field_rich_text_v4` — правка на месте, без новой версии схемы (v4 введена `PEP-05`, `hover` не заполнен ни в одном реальном пакете, миграция не нужна). Путь тот же, каким уже идёт `screen_id`: `FGV2RichTextSpansPropertyConsumer::Prepare` читает поле (типизированный отказ на не-число), кладёт в `FGV2RichTextHoverViewModel.Duration`, `FlattenRichTextSpan` переносит в `FPreparedRichTextHover.Duration`, `UGV2RichTextWidgetBase::ApplyPreparedRichTextSpans` — обратно в view model. Потребителя пока нет (появится в `PEP-08`), место в данных — есть.

Удержание в границах вьюпорта возвращено в `UGV2ScreenWidgetBase::SetAnchoredContentPosition`: позиция ограничивается собственным живым размером экрана (он всегда равен вьюпорту — слой Fill/Fill) минус живым размером контента, по каждой оси независимо, при нулевом размере (кадр ещё не отрисован) — без ограничения на этой оси, тем же принципом самолечения, что и переприменение позиции каждый тик из `PEP-06B`. Проверено прогоном по всем четырём краям (`GV2.UI.LayeredReconciliation.ScreenAnchorHostViewportClamp`, реальная геометрия через `SVirtualWindow`) плюс отдельно проверено, что точка внутри границ не меняется.

Потолок размера решён как дисциплина авторинга, без кода: положение, вправо/вниз ограничивающее содержимое вьюпортом, уже не даёт окну уехать за экран — а второе, более узкое ограничение («не даёт закрыть весь слой целиком») требует ЛИБО общего на все окна значения (то самое, что `PEP-06B` удалил как мёртвый код и что явно запрещено «не считается закрытием»), ЛИБО per-screen значения — а оно уже полностью в руках автора: `USizeBox.MaxDesiredWidth/Height` в собственном WBP экрана, без единой строки C++. Второй путь уже доступен и не требует отдельного механизма.

Перенос `SpanId` закреплён как ЕДИНСТВЕННО возможный (движок не даёт иного способа привязать данные к конкретному `SRichTextHyperlink` в момент, когда `SpanId` известен — `SetTag()` есть на `SWidget`, но виджет, которому его ставить, в момент разрешения `OnGenerateTooltip` не передаётся, только `Metadata`). Явного носителя не существует в принципе — задача сохраняет `FGV2RichTextSpanToolTip` и вместо этого закрепляет тест: мутацией (заменой `OnTooltip` на несвязанный `FSlateHyperlinkRun::FOnGenerateTooltip()`, пересборкой, прогоном и последующим откатом) подтверждено, что `GV2.Runtime.Presentation.RichTextSpanHoverDetector` краснеет («Exactly one anchor is captured» становится 0) — не читкой, а прогоном. Комментарий на месте вызова `OnTooltip` фиксирует и причину, и сам факт мутационной проверки.

Второй вид окна собран целиком в данных и Blueprint-фикстуре: `WBP_HoverFixtureAlpha` (граница `RootCanvas → SizeBox 120×80 → Border` красного тона) и `WBP_HoverFixtureBeta` (`220×140`, синего тона), обе — обычные `UGV2ScreenWidgetBase` Blueprint'ы без единой C++ правки, созданные через `unreal-mcp` (`UMGToolSet.CreateWidgetBlueprint`/`AddWidget`/`ObjectTools.set_properties`). Новый тест `GV2.UI.LayeredReconciliation.HoverWindowSelectableFromData` инстанцирует оба класса, реально рендерит их (`SVirtualWindow`) и снимает габариты именованного `ContentSize`-виджета через `GetWidgetFromName` — подтверждено: `120×80` и `220×140` соответственно, различны. `DCA-15`'s Half B (сканирование контента на абсолютные размеры) получил именованное исключение для `WBP_HoverFixture*` с объяснением, почему это не производственный контент.

### PEP-07 — Сделать hover host-local источником эффекта

- [x] PEP-07 — Сделать hover host-local источником эффекта

**Зависимость:** PEP-06C. **Файлы:** `OpenHoverOverlay`/`CloseHoverOverlay` на `UGV2PresentationInteractionSink` и их реализация в `UGV2RuntimeSubsystem`; `FRuntimeSession::PublishHostLocalEffect`/`TakePendingEffects` из `PEP-03`; `FGV2LayeredUiReconciler` (резолв ключа участника); `FGV2PresentationEffectApply` из `PEP-04`.

**Инвариант:** `SemanticInput.md:110` и `WidgetRegistry.md:278` — hover и unhover не пересекают границу Lua и не создают Semantic Input. Постановка эффекта не вправе это изменить: если наведение начнёт доходить до Lua, оно станет gameplay-событием, и `INV-014` будет нарушен тем, что презентация начнёт порождать истину.

**Решение:** наведение на span и уход курсора ставят host-local эффект в общую очередь, заменяя прямой вызов открытия, оставленный `PEP-06B`. Критерий допустимости из `PEP-01` проверяется на этом первом потребителе: эффект не меняет ни одного значения canonical state и восстановим из snapshot и состояния ввода. Ни один путь наведения не доходит до Lua-биндингов.

**`ui_instance_id` — адрес поколения документа, а не виджета.** `FUiDocument` несёт один `UiInstanceId` и одну `Revision` на весь документ; `FGV2UiBindingRegistry` держит их в единственном экземпляре (`CurrentUiInstanceId`, `CurrentRevision`). Поэтому `ResolveEffectTarget` отвечает на вопрос «актуален ли ещё эффект», а не «к чему он относится», и раздавать виджетам собственный `ui_instance_id` нельзя: это дало бы каждому копию документного факта и столько же мест, где она разойдётся с единственным настоящим.

**Адрес виджета уже существует и уже является данными.** `AttachHostLocalScreen` возвращает синтетический instance key, который вызывающий обязан сохранить и передать в `DetachHostLocalScreen`; `IsHostLocalInstanceKey` отличает его от документного по зарезервированному префиксу, недостижимому для authored instance_key. Это `FName` — он кладётся в `Args`, переживает портативную очередь и на стороне UE разрешается в виджет через реестр `PEP-06`, который и так владеет временем жизни ровно этих виджетов. Второго индекса заводить не нужно.

Отсюда разделение полей эффекта:

| Что | Где | Зачем |
|---|---|---|
| `TargetSessionGeneration`, `TargetUiInstanceId`, `TargetRevision` | `target` | актуальность: три причины отбрасывания `PEP-03` |
| ключ участника, `duration_ms` | `Args` | адресация и параметры |

Эффект строится **целевым**, координаты берутся у координатора в момент публикации. Без этого `ResolveEffectTarget` на нецелевом эффекте всегда возвращает `None`, и три причины отбрасывания остаются синтетическими навсегда: механизм проверяется только собственными тестами и в производстве не срабатывает ни разу.

**Одна точка дренажа.** `TakePendingEffects` сегодня не имеет ни одного производственного вызывающего, а собственный комментарий очереди требует «one counter, one queue, one drain point». Дренирует `UGV2RuntimeSubsystem`: он уже владеет делегированием `Attach`/`DetachHostLocalScreen` и является UE-стороной сессии. Он же резолвит ключ участника в виджет и отдаёт исполнителю `PEP-04`. `GV2PresentationApply` по-прежнему не знает ни `overlay_stack`, ни сессии — тем же маршрутом, которым `PEP-06B` увёл открытие окна в `UGV2PresentationInteractionSink`.

Публикация идёт тем же маршрутом в обратную сторону: `OpenHoverOverlay`/`CloseHoverOverlay` перестают быть прямыми действиями и становятся публикаторами эффекта.

**«Эффект отброшен как stale» и «окно стало stale» — разные механизмы.** Первое означает, что одноразовая команда не доехала, потому что документ сменился между публикацией и дренажом. Второе — правило жизненного цикла [ADR-0048](../../ADR/0048-widget-exit-lifecycle-and-input-gating.md), по которому окно перестаёт принимать ввод. Отброшенный эффект не обязан убивать окно, а ставшее stale окно не обязано ждать отказа эффекта.

**Не считается закрытием:** поставить эффект, попутно отправив Lua уведомление «для удобства»; собственный путь постановки мимо очереди `PEP-03`; hover, меняющий desired-состояние; нецелевой эффект (`bHasTarget == false`) — он обходит отбрасывание вместо того, чтобы ему подчиниться; дать виджету собственный `ui_instance_id` — это копия документного факта, которой негде оставаться верной; завести второй индекс виджетов вместо реестра `PEP-06`; второй дренаж очереди помимо единственного.

**Шаги:**
1. Ввести единственную точку дренажа в `UGV2RuntimeSubsystem`: `TakePendingEffects` → резолв ключа участника через реестр `PEP-06` → исполнитель `PEP-04`.
2. Перевести `OpenHoverOverlay`/`CloseHoverOverlay` из прямых действий в публикаторы эффекта; прямой вызов открытия из `PEP-06B` снять.
3. Заполнить `target` координатами документа от координатора, `Args` — ключом участника; назвать источник каждой величины.
4. Проверить перечислителем, что ни один путь наведения не достигает Lua-биндингов.
5. Проверить критерий `PEP-01`: снять canonical state до и после наведения — он неизменен.
6. Проверить восстановимость: после rebuild презентации окно отсутствует и восстанавливается только наведением.

**Done:**
- Наведение не достигает Lua; перечислитель — обход путей вызова, не просмотр.
- Canonical state до и после наведения побайтово равен.
- После rebuild окно не восстанавливается само; проверено прогоном.
- Постановка идёт через общую очередь `PEP-03`; собственного пути нет, прямой вызов из `PEP-06B` снят.
- Точка дренажа ровно одна; перечислитель — вызывающие `TakePendingEffects` в production-дереве, их число равно единице.
- Виджет адресуется ключом участника из `Args`, а не собственным `ui_instance_id`; ни один виджет такого поля не получил.
- Производственный эффект целевой, и источник каждой координаты назван; хотя бы одна из трёх причин отбрасывания `PEP-03` срабатывает на реальном эффекте, а не только в негативном тесте — иначе отбрасывание остаётся непроверенным в производстве.
- Отброшенный эффект не уничтожает окно: случай «документ сменился между публикацией и дренажом» покрыт тестом и отделён от stale-правила `ADR-0048`.

**Evidence:** перечень вызывающих `TakePendingEffects`, обход путей вызова наведения, сверка canonical state, прогон отброшенного эффекта с живым окном, прогон rebuild.

**Реализация.** `OpenHoverOverlay` и `CloseHoverOverlay` больше не выполняют attach/detach до публикации. Открытие создаёт синхронный host-local request, кладёт его `request_id` и `duration_ms` в `FPresentationEffect`, публикует и запрашивает общий coordinator drain; только accepted effect в `UGV2RuntimeSubsystem::HandlePresentationEffects` выполняет `AttachHostLocalScreen` и возвращает созданный key. Закрытие кладёт существующий `instance_key` в Args; только accepted effect выполняет `DetachHostLocalScreen`, rejected effect оставляет окно живым. Оба источника приходят в тот же handler через `FGV2SessionCoordinator::DrainPresentationEffects`; production call site `TakePendingEffects` ровно один и больше не привязан к событию hover.

Источник координат цели неизменен: `TargetUiInstanceId`/`TargetRevision` читаются из текущего `BindingRegistry` при публикации, `TargetSessionGeneration` ставит `FRuntimeSession::StampAndEnqueueEffect`. `GV2.Runtime.Presentation.HoverEffectQueueContract` отличает apply от одной диагностики: accepted queued close физически снимает адресованное окно; close с `StaleTarget` оставляет его в `overlay_stack`; canonical state остаётся побайтово равен. `GV2.Runtime.Presentation.EffectsDrainAfterRuntimeEntry` отдельно доказывает, что очередь забирается после protected runtime entry без будущего hover.

Восстановимость (`GV2.Runtime.Presentation.HoverEffectQueueContract`, шаг 5): `EndSession` разрушает весь GameShell целиком; `StartSession` не восстанавливает окно наведения — оно появляется только настоящим наведением. Обход путей вызова (`GV2.Runtime.Presentation.HoverEffectNeverCrossesLua`) сканирует тела ровно четырёх функций (`OpenHoverOverlay`, `CloseHoverOverlay`, `PublishHoverEffect`, `DrainPresentationEffects`) на отсутствие Lua-пересекающих символов (`DispatchSemanticInput`, `DispatchCommand`, `SubmitUiInteraction`, `lua_` и т.д.) — подтверждено мутацией: временный второй вызов `TakePendingEffects` красит «ровно один вызывающий» гейт («... to be 1, but it was 2»), откачено. UE `GV2.*` automation suite 203/203 зелёный (201 было + 2 новых теста). Портативный `ctest` не тронут (задача не коснулась `GV2RuntimeCore`, только использовала уже существующие `PublishHostLocalEffect`/`TakePendingEffects`/`ResolveEffectTarget`).

### PEP-08 — Реализовать появление и уход с отменой

- [x] PEP-08 — Реализовать появление и уход с отменой

**Зависимость:** PEP-07. **Файлы:** `PresentationEffectApply.h`/`.cpp` (вид `Transparency`, `Widget`/`Alpha` в `Apply`, `InvalidWidget`); `GV2ScreenAnchorHost.h`/`GV2ScreenWidgetBase.h`/`.cpp` (`GetAnchoredContentScreenRect`); `GV2RichTextWidgetBase.h`/`.cpp` (`EGV2HoverFadeStage`, `HandleHoverTransition`/`TickHoverFade`, тестовый `SimulateHoverTickForAutomationTest`); `GV2PresentationInteractionSink.h`/`GV2RuntimeSubsystem.h`/`.cpp` (`DurationSeconds` в `OpenHoverOverlay`, `duration_ms` в `Args`); `validate_presentation_apply_surface.py` (исключение для `FGV2PresentationEffectApply`); новые тесты `GV2PresentationEffectApplyTests.cpp`, `GV2RichTextHoverFadeTests.cpp`.

**Инвариант:** раздел `Snapshot/effect ordering` контракта: отказ эффекта не инвалидирует snapshot и gameplay state. Дополнительно — правило `PEP-02` про self-dismissal: уход отменяем, и отмена не создаёт второго экземпляра окна.

**Решение:** появление ведёт прозрачность 0 → 100% за авторскую длительность, уход — 100 → 0 за неё же; на нуле окно исчезает. Длительность приходит в `args` как `duration_ms` и задаётся содержимым (для первого потребителя — 2000), а не константой в C++.

Возврат курсора на текст или на само окно во время ухода отменяет уход и ведёт прозрачность обратно к 100% **от текущего значения**, а не от нуля и не скачком; оставшееся время пропорционально остатку.

**Сигнатура `Apply` расширяется виджетом, и это не ослабление `PEP-04`.** Та задача закрыта с `Apply`, принимающим только `Kind`, и на этом держалось утверждение «отказ эффекта структурно не может задеть snapshot и gameplay state». Прозрачности нужен виджет. Гарантия при этом не слабеет: её давал граф сборки `GV2PresentationApply.Build.cs`, который не даёт модулю знать snapshot- и gameplay-типы, а виджеты он знает и так. Расширение обязано быть названо в change set явно — иначе оно прочитается как тихое ослабление уже закрытой задачи.

**Место для длительности заводит `PEP-06C`** — поле в `hover` схемы v4, рядом со `screen_id`. Эта задача его читает и доводит до `args` эффекта; заводить его здесь заново не нужно, но и обойтись без него нельзя: без места в данных длительность неизбежно окажется в C++ и собственный `Done` задачи провалится.

**Не считается закрытием:** задать 2000 мс константой в C++; оставить длительность без места в данных и переписать `Done` по факту; при отмене выставлять 100% одним кадром; при отмене начинать новое появление с нуля; считать уход завершённым по таймеру, не по достигнутой прозрачности.

**Шаги:**
1. Довести длительность из `hover` до `args` эффекта через Prepare владельца — тем же путём, которым туда приходит остальное содержимое окна.
2. Реализовать вид эффекта прозрачности, читающий `duration_ms` из `args`.
3. Реализовать отмену ухода с продолжением от текущей прозрачности и пропорциональным остатком времени.
4. Проверить, что повторные наведение и уход не создают второго экземпляра окна.
5. Снять фактическую кривую прозрачности в прогоне и сверить её с объявленной длительностью на обоих концах.

**Done:**
- Длительность читается из `hover`, а не из C++; два вида окна вправе иметь разную длительность, проверено двумя значениями.
- Длительность берётся из данных; перечислитель — отсутствие числового литерала длительности в C++.
- Изменение длительности в данных меняет наблюдаемую кривую; проверено вторым значением, а не одним.
- Отмена продолжает от текущей прозрачности; проверено сверкой снятого значения в момент отмены с началом обратного хода.
- Многократные наведение/уход не порождают второго окна; проверено прогоном с чередованием.
- Окно исчезает по достижении нуля, а не по истечении таймера; случаи различены тестом.
- Расширение сигнатуры `Apply` названо в change set; граф сборки по-прежнему не даёт модулю знать snapshot- и gameplay-типы, проверено `validate_presentation_apply_module_graph.py`.

**Evidence:** снятая кривая прозрачности, прогон чередования, прогон отмены с зафиксированным значением.

**Реализация.** `EPresentationEffectKind` получил первое значение — `Transparency` (`Count` стало 1); `FGV2PresentationEffectApply::Apply` расширен явно названным `UWidget* Widget` и `float Alpha` (комментарий в заголовке объясняет, почему это не ослабление `PEP-04`: гарантия держалась на графе сборки `GV2PresentationApply.Build.cs`, который не пускает `GV2RuntimeCore`/`GV2ContentCore`, а `UWidget` модуль и так знает через UMG). `EGV2PresentationEffectApplyReject` получил `InvalidWidget` — отдельная, не смешанная с `UnsupportedKind` причина отказа для `Widget == nullptr`. Гейт `validate_presentation_apply_surface.py` расширен именным исключением для `FGV2PresentationEffectApply` (сиблинг `FGV2PresentationApply`, тот же класс защищаемого физического рубежа, только с `UWidget*` вместо `FGV2PreparedPresentationTransaction&`).

Очередь эффектов `PEP-03/07` эту задачу не проходит: appear/leave — не одноразовый сигнал через `TakePendingEffects`, а непрерывная анимация, тикающая каждый кадр. `EGV2HoverFadeStage{None, Appearing, Leaving}` живёт на `UGV2RichTextWidgetBase` (тот же модуль, что и `FGV2PresentationEffectApply` — вызов легален без пересечения границы `GV2RuntimeCore`). Механизм переноса пропорционального остатка — не отдельный расчёт, а следствие константной скорости (`1/HoverFadeDurationSeconds` в секунду): отмена ухода — это просто смена знака направления с той же самой скоростью, продолжая с текущего значения `HoverFadeOpacity`, а не с нуля и не скачком. `NativeTick` разбит на `HandleHoverTransition` (обработка перехода) + `TickHoverFade` (тик анимации); `HandleHoverTransition` вынесен отдельно специально для того, чтобы `GV2.Runtime.Presentation.HoverFadeAppearLeaveCancel` мог прогнать тот же самый продакшен-код через `#if WITH_DEV_AUTOMATION_TESTS`-обёртку `SimulateHoverTickForAutomationTest`, не полагаясь на управляемый курсор ОС (сопоставление курсор→переход уже проверено `GV2RichTextSpanHoverDetectorTests` из `PEP-06A`).

«Наведение на само окно» реализовано не отдельным кросс-виджетным сигналом, а тем же детектором: `CaptureHoverableSpanAnchors` добавляет прямоугольник открытого окна как ещё один якорь для того же `SpanId`, если окно открыто — курсор на попапе засчитывается как «наведение на span» без единой новой связи между виджетами. Прямоугольник — не корневая геометрия окна (она всегда Fill/Fill на весь слой и сделала бы «курсор над попапом» истинным где угодно на экране), а прямоугольник РЕАЛЬНОГО видимого содержимого: новый метод `IGV2ScreenAnchorHost::GetAnchoredContentScreenRect()`.

Длительность: `duration_ms` теперь также кладётся в `Args` эффекта открытия/закрытия (`PublishHoverEffect`, `OpenHoverOverlay` на `UGV2PresentationInteractionSink` получил параметр `DurationSeconds`) — для полноты DTO одноразового сигнала, а не потому что дренаж читает его обратно: сам тикер держит копию из `Span->Hover.Duration` напрямую. Перечислитель `GV2.Runtime.Presentation.HoverFadeDurationHasNoCppLiteral` сканирует `GV2RichTextWidgetBase.cpp` и подтверждён мутацией (замена чтения на литерал `2.0f` красит тест, затем откачена).

`GV2.Runtime.Presentation.HoverFadeAppearLeaveCancel` доказывает прогоном: кривая непрозрачности линейна и совпадает с объявленной длительностью на обоих концах; окно не исчезает по истечении «длительности», пока наведение удерживается (таймер не единственный владелец) — исчезает строго по достижении нуля во время ухода; отмена продолжает точно с зафиксированного значения (0.75 → тот же 0.75, не 0 и не 1) и покрывает остаток пропорционально оставшейся дистанции; переключение между разными span закрывает предыдущее окно прежде, чем открыть новое — второго живого экземпляра не остаётся; два окна с длительностями 2с и 4с после одинакового прошедшего времени показывают разную непрозрачность (0.5, не одинаковое значение) — длительность подтверждена данными, а не рассуждением. UE `GV2.*` automation suite 205/205 зелёный. Портативный `ctest` не тронут (задача не коснулась `GV2RuntimeCore`).

### PEP-09 — Развести ввод при двух видах ухода

- [x] PEP-09 — Развести ввод при двух видах ухода

**Зависимость:** PEP-08. **Файлы:** `GV2PresentationInteractionSink.h` (`FGV2StaleHostLocalDeparture`/`FGV2SelfDismissingHostLocalDeparture`/`FGV2HostLocalDepartureState`, `GV2HostLocalDepartureAcceptsInput`, `SetHoverOverlayDeparture`); `GV2LayeredUiReconciler.h`/`.cpp` (`GetHostLocalScreen`); `GV2RuntimeSubsystem.h`/`.cpp` (`SetHoverOverlayDeparture` override); `GV2RichTextWidgetBase.h`/`.cpp` (`DetectStaleHoverBeforeSpansChange`, `MarkActiveHoverStale`, `bActiveHoverIsStale`); новый тест `GV2HoverDepartureTests.cpp`; `Docs/Status/ImplementationStatus.md`, `Docs/Architecture/BuildAndTooling.md` (снятие `STATUS-003`).

**Инвариант:** [ADR-0041](../../ADR/0041-ui-commit-rollback-model.md) и правило `PEP-02`. Интерактивный stale-виджет — наблюдаемый дефект: клик по тому, чего уже нет, доходит до dispatcher. Именно этот класс отказа появляется впервые вместе с анимацией и до неё существовать не мог.

**Решение:** stale-виджет гасит ввод в момент логического удаления и инвалидирует свои handles тогда же; интерактивный stale-виджет делается невыразимым структурно — состоянием типа, а не проверкой во время исполнения. Self-dismissing виджет остаётся интерактивным до конца ухода, и взаимодействие с ним отменяет уход. `STATUS-003` закрывается обоими случаями.

**Не считается закрытием:** гасить ввод у stale физическим снятием виджета — между логическим удалением и снятием остаётся окно; проверка во время исполнения вместо невыразимости; закрыть только self-dismissal, оставив stale «как было, и так работало».

**Шаги:**
1. Сделать интерактивный stale невыразимым: состояние ухода несёт признак приёма ввода, и stale-ветка не может его выставить.
2. Погасить ввод и инвалидировать handles в момент логического удаления.
3. Проверить мутацией: вернуть приём ввода stale-виджету — красный тест с названной причиной; восстановить.
4. Проверить stale на реальном случае плана: пока окно открыто, реконсиляция убирает его span или экран либо меняется ревизия. Окно становится stale, доигрывает затухание и на клик не отвечает.
5. Проверить self-dismissal: клик по затухающему окну на 40% принят, уход отменён.
6. Снять `STATUS-003` тем же change set, которым закрыта вторая половина.

**Done:**
- Интерактивный stale невыразим структурно; мутационная проба подтверждает красный, а не рассуждение.
- Ввод у stale гаснет в момент логического удаления; промежуток между логическим и физическим снятием проверен на окне, у которого реконсиляция убрала span или экран, — единственном stale-случае в области этого плана.
- Stale-окно доигрывает затухание и ввода не принимает: исчезновение рывком не засчитывается за закрытие, приём клика — тем более.
- Взаимодействие с затухающим окном принято и отменяет уход; проверено на промежуточной прозрачности, а не в начале ухода.
- `STATUS-003` снят этим же change set.

**Evidence:** мутационная проба, прогон stale-окна с убранным span, прогон клика на 40%.

**Реализация.** Различие выражено типом, не флагом: `FGV2StaleHostLocalDeparture`/`FGV2SelfDismissingHostLocalDeparture` — пустые структуры, `FGV2HostLocalDepartureState = TVariant<...>`. `std::is_empty_v<FGV2StaleHostLocalDeparture>` компиляторно фиксирует отсутствие policy-data, а `GV2HostLocalDepartureAcceptsInput` использует `Visit` с отдельным overload для каждой alternative: новый вид ухода без ветки не компилируется. Запрещённый `sizeof`-суррогат из первой редакции теста удалён. Типы объявлены в `GV2PresentationApply` и пересекают границу к `UGV2RuntimeSubsystem` методом `UGV2PresentationInteractionSink::SetHoverOverlayDeparture`.

Логическое удаление — это `UGV2RichTextWidgetBase::ApplySpans` (единственное место, где `CurrentSpans` заменяется, и для настоящего Prepare/Commit пути, и для одношагового Blueprint API): `DetectStaleHoverBeforeSpansChange` проверяет СТАРЫЙ набор против НОВОГО непосредственно перед заменой — если span открытого окна пропал либо его `Hover.ScreenWidget` сменился на другой объект, `MarkActiveHoverStale` немедленно (в том же вызове) публикует `Stale` через `SetHoverOverlayDeparture` и переводит затухание в `Leaving`, не дожидаясь ни следующего тика, ни физического снятия. Обработчик `SetHoverOverlayDeparture` (`UGV2RuntimeSubsystem`) резолвит виджет через новый `FGV2LayeredUiReconciler::GetHostLocalScreen` (тот же реестр `PEP-06`, второго индекса не заведено) и переключает `SetIsEnabled` — это отключает приём ввода для всего поддерева на уровне Slate hit-testing, не соглашением в 24 местах физического снятия.

Self-dismissal (уход, начатый переходом `Ended` в `HandleHoverTransition`) публикует `SelfDismissing` и НЕ трогает `SetIsEnabled` — окно остаётся интерактивным по умолчанию, и взаимодействие с ним на промежуточной непрозрачности отменяет уход (доказано прогоном: зафиксированное значение при отмене — не 0 и не 1). Ветка отмены ухода (`Began` при `HoverFadeStage == Leaving` для того же span) явно исключает `bActiveHoverIsStale`: re-hover на span, который реконсиляция уже убрала, не воскрешает окно — оно доигрывает уход и физически закрывается по достижении нуля, попадание курсора на него игнорируется.

`GV2.Runtime.Presentation.HoverDepartureInputGating` доказывает прогоном: (1) self-dismissal принимает клик на промежуточной (не начальной) непрозрачности и продолжает от неё; (2) stale гасит ввод СИНХРОННО с `ApplySpans`, при этом окно ещё физически лежит в `overlay_stack` (промежуток между логическим и физическим снятием реален, не гипотетичен); (3) stale доигрывает затухание, не принимая ввод ни в одной точке, и повторное наведение на убранный span его не отменяет. `GV2.Runtime.Presentation.HostLocalDepartureAcceptsInputIsExhaustive` проверяет сам диспетчер напрямую и мутационно: временная замена `GV2HostLocalDepartureAcceptsInput` на всегда-`true` покрасила ОБА теста (прямой и поведенческий) — «интерактивный stale» перестаёт быть невыразимым только при ручной порче диспетчера, откачено.

`STATUS-003` снят: строка удалена из `Docs/Status/ImplementationStatus.md` (правило документа — закрытие удаляет строку, не помечает «closed»), ссылка на STATUS-003 в `Docs/Architecture/BuildAndTooling.md` переписана на факт закрытия. ## Правила выполнения и остановки

- Всякая правка C++ виджетов классифицируется в change set до отметки `[x]`: механизм либо отсутствующий маршрут данных. Во втором случае задача обязана добавить маршрут и показать его вторым случаем. Неклассифицируемая правка останавливает задачу.
- Change set не объединяет введение механизма и его первого потребителя: механизм доказывается негативными тестами, потребитель — поведением. Вместе они недоказуемы.
- Задача, потребовавшая изменить архитектурный инвариант, останавливается до ADR.
- Правила про производителя вводимого множества и про проверку границы со следующей задачей — общие для всех планов и живут в [индексе](../README.md). Прецеденты, которыми они введены, найдены в этом плане: `PEP-05` наделил ролью класс, который переселение окна обещало удалить; переселение снимало tooltip-маршрут, который был единственным детектором наведения; `PEP-08` требовал поля в данных, которого не заводил никто.
- Evidence затухания требует прогона UE automation; он конфликтует с живым редактором, задачи M3 выполняются в сессии, где это учтено.

## Критерий выхода

Одноразовый эффект существует как один механизм с двумя равноправными источниками, монотонным `sequence`, типизированным отбрасыванием и отсутствием реплея после загрузки. Всплывающее окно — обычный экземпляр экрана в `overlay_stack`, собранный из declared composites; второй его вид добавлен без единой строки C++. Появление и уход ведут прозрачность 0↔100% за авторскую длительность, уход отменяется возвратом курсора и продолжается от текущей прозрачности. Элемент, удалённый реконсиляцией, не принимает ввод с момента логического удаления, и интерактивный stale невыразим структурно; элемент, уводящий себя сам, интерактивен до конца. `STATUS-002` и `STATUS-003` сняты.
