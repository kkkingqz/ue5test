# Presentation Effect Pipeline: план реализации

> **Материализует:** раздел `Effect` контракта [Presentation Snapshot and Effects](../../UI/PresentationSnapshotAndEffects.md), который объявлен нормативным и не реализован ни одной строкой кода. Первым потребителем механизма становится всплывающее окно по наведению на размеченный текст.
> **Не является нормативным:** единый pipeline эффектов с двумя источниками и жизненный цикл виджета за пределами коммита фиксируются ADR (`ADR-0047`, `ADR-0048`) задачами `PEP-01` и `PEP-02` до реализации.
> **Исполнение:** последовательно по задачам. Checkbox задачи — единственный источник её завершения.

**Цель:** получить один механизм одноразовых эффектов презентации, которым пользуются все будущие эффекты независимо от источника; сделать всплывающее окно обычным ui-блоком, а не особым C++-классом; и довести первый эффект — плавное появление и затухание окна — до состояния, в котором окно остаётся полноценным интерактивным виджетом всё время своего ухода.

**Технологии:** существующий universal UI property pipeline и declared composites ([ADR-0040](../../ADR/0040-universal-ui-property-pipeline.md)), маршрут `NestedScreen` (доказан DUC-09/10/11), слой `overlay_stack` `UGV2GameShellWidgetBase`, `FGV2LayeredUiReconciler`, `FGV2PreparedPresentationTransaction`. Нового runtime-модуля и внешней tween-библиотеки план не требует.

## Измеренное состояние

**Эффектов нет вовсе.** Ни `publish_effect`, ни очереди, ни apply path, ни отбрасывания по stale target в `Scripts/`, `Source/`, `Tests/` не существует. `Scripts/authoring/presentation.lua` публикует только desired UI document. Раздел `Effect` контракта описывает DTO (`effect_id`, `sequence`, `target`, `args`), правила порядка и обязательные тесты — всё это открыто как [`STATUS-002`](../../Status/ImplementationStatus.md).

**Всплывающее окно существует, но устроено как Slate-тултип.** `UGV2RichTextPopoverWidgetBase` (`Source/GV2PresentationApply/Public/UI/GV2RichTextPopoverWidgetBase.h`) создаётся декоратором в `OnOpening()` (`GV2RichTextWidgetBase.cpp:62`) и уничтожается в `OnClosed()` через `SlateToolTip->ResetContentWidget()`. Декоратор объявляет `IsInteractive() == true`, поэтому курсор в окно увести можно, но закрытие безусловно и мгновенно: состояния «окно уходит, но ещё живо» в модели нет.

**Содержимое окна зафиксировано в C++.** `FGV2RichTextHoverViewModel` (`GV2WidgetTypes.h:167`) — ровно `Title`, `Description`, `ImageResourceId` плюс transient `ResolvedImageBrush`. Схема `core:schema.ui_field.rich_text.v3` повторяет эту тройку в поле `hover`. Добавить в окно ещё один элемент сегодня нельзя без правки структуры, виджета, `GV2CentralStylePreparer` и схемы одновременно.

**Окно намеренно вне транзакции.** `PSC-10B`: popover создаётся после commit экрана, поэтому не может быть целью собственной подготовленной операции, ничего не разрешает сам и получает все значения от `UGV2RichTextWidgetBase`, который получил их из Prepare. Он сознательно не реализует `IGV2UiStyleConsumer`, чтобы не попасть в перечислитель стилизуемого поддерева экрана.

**Слой для окна уже есть.** `UGV2GameShellWidgetBase` объявляет `background`, `location_content`, `character_presentation`, `core_interface`, `overlay_stack`, `modal_stack`. Блокировка нижних слоёв — свойство `modal_stack`, а не `overlay_stack`.

**Hover не пересекает границу Lua и не должен.** `SemanticInput.md:110`: открытие, позиционирование, задержка и закрытие popover не вызывают Lua; `WidgetRegistry.md:278`: hover/unhover не пересекают Lua boundary. План это правило сохраняет.

## Почему дешёвые пути не дают результата

| Подход | Результат и цена | Выбор |
|---|---|---|
| Добавить UMG-анимацию в Blueprint окна и остановиться | Затухание появится, но окно останется тултипом: Slate уничтожит его в `OnClosed()` на середине анимации. Интерактивность во время ухода недостижима в принципе | Не исполним как есть |
| Сделать затухание локальным таймером внутри `UGV2RichTextPopoverWidgetBase` | Работает для одного окна и создаёт второй механизм презентации мимо очереди и `sequence`. `STATUS-002` не закрывается, а к нему добавляется расхождение | Недостаточен |
| Реализовать effect pipeline только для Lua-источника | Первый же потребитель — hover — оказывается вне pipeline, потому что hover не пересекает границу Lua. «Единый pipeline» опровергается собственным первым примером | Недостаточен |
| Оставить окно особым C++-классом, добавив ему полей | Каждое следующее окно снова требует C++: структура, виджет, style preparer и схема правятся вместе | Недостаточен |
| Один pipeline с двумя источниками; окно — nested screen в `overlay_stack`; затухание — первый эффект этого pipeline | Закрывает `STATUS-002` механизмом, `STATUS-003` — правилом и реализацией, и снимает C++ с пути добавления нового окна | Основа плана |

## Рекомендуемое устройство

### Один pipeline, два источника

Эффект остаётся тем, чем его описывает контракт: `effect_id`, монотонный `sequence`, optional `target` и `args`. Различаются только точки входа. **Lua-источник** публикует эффект фиксированным биндингом рядом с `publish_snapshot`; DTO schema-валидируется и глубоко копируется в исходящую очередь, reconciler внутри Lua-вызова не запускается. **Host-local источник** — презентационное событие, не имеющее gameplay-смысла и потому не пересекающее границу Lua: наведение курсора на размеченный span. Оба источника кладут эффект в одну очередь, получают `sequence` из одного счётчика и проходят один apply path с одинаковым отбрасыванием по stale target и чужому поколению сессии.

Это расширение контракта, а не его обход: сегодня раздел `Effect` сформулирован как часть «Lua → UE сообщений». `PEP-01` фиксирует, что источник эффекта не входит в его identity, и что host-local эффект не вправе нести gameplay-значимое состояние — иначе он стал бы скрытым каналом авторитета мимо `INV-014`.

### Два вида ухода виджета

Уход виджета со сцены бывает двух разных природ, и до сих пор существовала только первая:

**Stale-удаление.** Реконсиляция убрала экран или элемент, потому что состояние, которое он показывал, исчезло. Ввод гасится немедленно, в момент логического удаления, а не физического: принимать клик по тому, чего уже нет, нельзя ни кадра. Handle удалённого span инвалидируется тогда же.

**Self-dismissal.** Элемент уводит себя сам по собственному таймеру, а состояние, которое он показывает, никуда не делось. Он остаётся полноценным интерактивным виджетом до конца ухода, и взаимодействие с ним уход отменяет. Всплывающее окно — ровно этот случай.

Различение обязано быть выражено в типе, а не в комментарии: `PEP-02` вводит его как состояние жизненного цикла с явным владельцем, `PEP-09` делает невыразимым интерактивный stale-виджет.

### Окно как обычный ui-блок

Всплывающее окно перестаёт быть `UGV2RichTextPopoverWidgetBase` и становится экземпляром экрана в `overlay_stack`, собранным из declared composites — теми же средствами, что и всё остальное. Поле `hover` схемы `rich_text` перестаёт быть фиксированной тройкой и несёт nested screen: маршрут `NestedScreen` уже доказан DUC-09/10/11 и уже selectable в Designer.

Следствие, ради которого это делается: добавление нового вида окна становится авторской работой в данных и Blueprint. Проверяется это не рассуждением, а вторым видом окна, собранным в фикстурах без единой строки C++ (`PEP-06`).

### Правка C++ как классифицируемое событие

План действует под отдельным правилом владельца проекта: **всякая правка C++ виджетов по ходу плана классифицируется в change set до отметки `[x]`.** Два допустимых исхода:

- **Механизм.** Правка добавляет или меняет сам движковый механизм — вид эффекта, состояние жизненного цикла, потребитель свойства. Такая правка законна, и её признак — что она одна обслуживает неограниченное число будущих авторских случаев.
- **Отсутствующий маршрут данных.** Правка понадобилась, потому что конкретный авторский случай не выражается данными. Такая правка не принимается как есть: задача обязана добавить маршрут, после которого этот класс случаев данными выражается, и показать это вторым случаем.

Третьего исхода нет. Правка, которую не удалось отнести ни к одному, останавливает задачу.

## Объём фиксации

План включает 10 задач: `PEP-01…10`. Первая фиксируемая поверхность — раздел `Effect` контракта презентации, схема `core:schema.ui_field.rich_text`, слой `overlay_stack` и widget-поверхность rich text. План закрывает [`STATUS-002`](../../Status/ImplementationStatus.md) целиком и [`STATUS-003`](../../Status/ImplementationStatus.md) обеими половинами — правилом и реализацией.

Вне плана: анимации переходов между экранами, звук, тосты и прочие виды эффектов. План строит механизм и доводит до конца ровно один его вид; остальные виды — авторская и содержательная работа поверх готового pipeline. Gameplay-семантика окна (что именно в нём показано) планом не задаётся.

Множество automation test id план расширяет; удалений не предполагается, кроме тестов `UGV2RichTextPopoverWidgetBase`, чья судьба перечисляется поимённо в `PEP-06`.

| M3 — Затухание | PEP-08…09 | Появление и уход 0↔100% за авторскую длительность с отменой; интерактивность при self-dismissal и невыразимость интерактивного stale |

Зависимости: `01 → 02 → 03 → 04 → 05 → 06 → 07 → 08 → 09 → 10`.

Порядок не переставляется. Оба ADR идут **до** кода, потому что обе задачи меняют архитектурный инвариант: первая — состав канала Lua → UE, вторая — модель владения виджетами и правило ввода [ADR-0041](../../ADR/0041-ui-commit-rollback-model.md). Механизм эффектов идёт **до** переезда окна, иначе переезд не на чем проверять и окно временно получает собственный таймер — ровно тот второй механизм, который план запрещает. Переезд окна идёт **до** затухания, потому что затухание требует виджета, переживающего собственное логическое удаление, а тултип им быть не может.

## M0 — Решения до кода

### PEP-01 — Зафиксировать единый pipeline эффектов с двумя источниками

- [x] PEP-01 — Зафиксировать единый pipeline эффектов с двумя источниками

**Зависимость:** нет. **Файлы:** [`ADR-0047`](../../ADR/0047-one-shot-effect-pipeline-and-origins.md); `Docs/UI/PresentationSnapshotAndEffects.md`.

**Инвариант:** [INV-014](../../Architecture/Invariants.md) — presentation восстановима и не является источником gameplay-истины. Host-local источник эффекта — новый путь, по которому в презентацию попадает сообщение, не пришедшее из Lua. Если такому эффекту разрешить нести gameplay-значимое состояние, он станет каналом авторитета мимо canonical state, и нарушение будет наблюдаемым: значение, пережившее reload, которого нет в сохранении.

**Решение:** ADR фиксирует, что identity эффекта не включает его источник: `effect_id`, `sequence`, `target`, `args` одинаковы для обоих. Lua-источник публикует фиксированным биндингом рядом с `publish_snapshot` со schema-валидацией и глубоким копированием. Host-local источник порождается презентационным событием, не имеющим gameplay-смысла, и обязан быть выводим заново из snapshot плюс состояния устройства ввода. Оба идут в одну очередь с одним счётчиком `sequence`. ADR отвечает, почему host-local источник не нарушает `INV-014`, а не только чем он удобен.

**Не считается закрытием:** ADR, разрешающий host-local эффекты общей формулировкой без критерия, по которому эффект признаётся не несущим gameplay-состояния; два счётчика `sequence`; описание источника как поля DTO — это вернуло бы источник в identity эффекта; ADR, откладывающий правило non-persistence «до реализации».

**Шаги:**
1. Написать ADR: состав DTO, два источника и их равноправие, единый `sequence`, правило отбрасывания по stale target и чужому поколению сессии, non-persistence при save/load.
2. Сформулировать критерий допустимости host-local эффекта проверяемо: эффект допустим, если его отсутствие не меняет ни одного значения canonical state и он восстановим из snapshot и состояния ввода.
3. Обновить `PresentationSnapshotAndEffects.md`: раздел `Effect` перестаёт быть частью «Lua → UE сообщений» и получает оба источника.
4. Назвать ADR в contracts и в `Docs/ADR/README.md`.

**Done:**
- ADR принят и назван в contracts; номер проверен по каталогу в момент записи.
- Критерий допустимости host-local эффекта сформулирован так, что его нарушение наблюдаемо, а не оценочно.
- Раздел `Effect` контракта описывает оба источника и единый `sequence`.
- ADR отвечает, чем прежняя формулировка «Lua → UE сообщения» была неправа, а не только чем новая полнее.

**Evidence:** ADR, diff контракта, `validate_docs`.

### PEP-02 — Зафиксировать жизненный цикл уходящего виджета и правило ввода

- [x] PEP-02 — Зафиксировать жизненный цикл уходящего виджета и правило ввода

**Зависимость:** PEP-01. **Файлы:** [`ADR-0048`](../../ADR/0048-widget-exit-lifecycle-and-input-gating.md); `Docs/UI/UIDocumentAndReconciliation.md`, `Docs/UI/README.md`.

**Инвариант:** [ADR-0041](../../ADR/0041-ui-commit-rollback-model.md) — модель commit/rollback реконсиляции, и владение виджетами, которое перечисляет `validate_session_snapshot_ownership.py`. Виджет, живущий после логического удаления, сегодня не принадлежит ни дереву слоя, ни кандидату; без явного владельца он становится untraced owning-указателем, и гейт с 13 негативными мутациями это обнаружит. Второе следствие: при откате коммита ([ADR-0041](../../ADR/0041-ui-commit-rollback-model.md)) и при замене сессии ([ADR-0044](../../ADR/0044-session-replacement-and-registry-sealing.md)) уходящий виджет обязан иметь определённую судьбу, иначе она окажется разной в разных ветках.

**Решение:** ADR вводит уход как состояние жизненного цикла с двумя различимыми видами. **Stale-удаление**: реконсиляция убрала элемент, показанное им состояние исчезло; ввод гасится в момент логического удаления, handles инвалидируются тогда же, физическое снятие может отстать. **Self-dismissal**: элемент уводит себя по своему таймеру при живом показанном состоянии; остаётся интерактивным до конца, взаимодействие отменяет уход. ADR называет владельца уходящего виджета, его судьбу при rollback и при замене сессии, и фиксирует, что `STATUS-003` закрывается обоими случаями, а не одним.

**Не считается закрытием:** записать различие как соглашение в комментарии; оставить владельца уходящего виджета неназванным «потому что он всё равно скоро исчезнет»; свести правило к «stale не интерактивен», не сказав, в какой момент гаснет ввод; ADR, не отвечающий на rollback и replacement.

**Шаги:**
1. Перечислить фактические места, где сегодня виджет снимается со сцены, — перечислителем, а не списком: обход `CommitReconcile` и его вызывающих.
2. Описать оба вида ухода, момент гашения ввода и владельца на каждом шаге.
3. Определить судьбу уходящего виджета при откате коммита и при замене сессии; обе ветки назвать явно.
4. Обновить `UIDocumentAndReconciliation.md` и `UI/README.md`: правило про «до завершения exit animation» переписывается через два вида ухода.
5. Назвать ADR в contracts.

**Done:**
- Оба вида ухода описаны с моментом гашения ввода, а не только с конечным состоянием.
- Владелец уходящего виджета назван для каждого шага его жизни; правило совместимо с перечислителем `validate_session_snapshot_ownership.py`.
- Судьба уходящего виджета при rollback и при replacement определена явно в обеих ветках.
- `UI/README.md` и `UIDocumentAndReconciliation.md` больше не формулируют инвариант через несуществующий механизм.
- ADR отвечает, чем прежняя формулировка была неправа: она выражала правило ввода через анимацию, которой не было, и потому выполнялась пусто.

**Evidence:** ADR, перечень мест снятия виджета со сцены, diff contracts.

## M1 — Механизм эффектов

### PEP-03 — Реализовать DTO, очередь и порядок эффектов

- [x] PEP-03 — Реализовать DTO, очередь и порядок эффектов

**Зависимость:** PEP-02. **Файлы:** `Source/GV2RuntimeCore/Public/GV2RuntimeCore/GV2RuntimeSession.h` и `.cpp` (`FPresentationEffect`, `EPresentationEffectRejectReason`, `ResolveEffectTarget`, `PublishHostLocalEffect`/`TakePendingEffects`); `Scripts/boundary/outbound.lua` (`publish_effect`/`take_pending_effects`, staged/committed lifecycle); `Source/GV2RuntimeCore/Private/GV2PresentationEffectConformance.cpp` и `Testing/GV2PresentationEffectConformance.h`; `Source/GV2/Private/Tests/GV2PresentationEffectConformanceTests.cpp`; `Tests/Lua/presentation/effect_queue_spec.lua`.

**Инвариант:** [достоверная приёмка](../../Architecture/BuildAndTooling.md) и раздел `Snapshot/effect ordering` контракта. Очередь без монотонного `sequence` и без отбрасывания чужого поколения — это тихая доставка эффекта в сессию, которая его не заказывала: наблюдаемо как всплывающее окно предыдущей сессии поверх новой.

**Решение:** DTO эффекта и очередь в переносимом слое, оба источника публикуют через одну функцию постановки, `sequence` выдаётся одним счётчиком. Отбрасывание по трём причинам — stale target, чужое поколение сессии, устаревшая ревизия — каждая со своей типизированной причиной, а не общим `false`. Lua-биндинг schema-валидирует и глубоко копирует DTO; reconciler внутри Lua-вызова не запускается.

**Не считается закрытием:** очередь без `sequence`; общий булев отказ вместо типизированных причин отбрасывания; постановка эффекта прямо из Lua-вызова; DTO, принимающий произвольный payload без схемы.

**Шаги:**
1. Определить DTO по контракту; реализовать очередь и единый счётчик `sequence`.
2. Реализовать три причины отбрасывания; на каждую — негативный тест.
3. Добавить Lua-биндинг публикации со schema-валидацией и глубоким копированием; проверить, что reconciler не вызывается изнутри Lua.
4. Проверить монотонность `sequence` при чередовании источников: эффекты из Lua и host-local в одной очереди не получают совпадающих номеров.

**Done:**
- `sequence` монотонен при любом чередовании источников; перечислитель — тест с обоими источниками вперемешку, а не по одному.
- Каждая из трёх причин отбрасывания имеет собственную типизированную причину и негативный тест.
- Lua-биндинг schema-валидирует DTO и глубоко копирует его; эффект с лишним или неизвестным полем отвергается до постановки.
- Reconciler не запускается внутри Lua-вызова; проверено, а не заявлено.

**Evidence:** прогоны негативных тестов, тест чередования источников, вывод schema-валидации.

### PEP-04 — Реализовать исполнение эффектов и non-persistence

- [x] PEP-04 — Реализовать исполнение эффектов и non-persistence

**Зависимость:** PEP-03. **Файлы:** `Source/GV2PresentationApply/Public/GV2PresentationApply/PresentationEffectApply.h` и `Private/PresentationEffectApply.cpp` (`EPresentationEffectKind`, `FGV2PresentationEffectApply`); `Source/GV2/Private/Tests/GV2PresentationEffectApplyTests.cpp`; non-persistence case 5 добавлен в `Source/GV2RuntimeCore/Private/GV2PresentationEffectConformance.cpp` (сохранение/загрузка через существующую портативную сессию, рядом с `GV2.Runtime.SaveAndLoad.*`, без правки самого файла).

**Реализация (закрытая с 0 видами эффекта):** перечисление `EPresentationEffectKind` заведено пустым (`Count = 0`) — единственный содержательный вид, прозрачность, явно вынесен в `PEP-08`, чтобы не объединять механизм с первым потребителем в одном change set. Экземплярность гейта полноты доказана мутацией по ходу разработки: временно добавленное значение перечисления (`TestOnlyMutationProbe`) поймано гейтом (`GV2.Runtime.Presentation.PresentationEffectApply` красный: «Zero unhandled effect kind diagnostics» — 1 вместо 0), после чего откачено. Компилятор эту мутацию НЕ ловит (пустой `switch` без `default` не выдаёт предупреждения в текущей сборочной конфигурации) — единственная измеренная гарантия здесь рантайм-гейт, симметричный `FGV2PropertyConsumerFactory::ValidateAllKindsHandled`, с независимой перепроверкой через `IsInapplicableKind` (без неё функция-заглушка `GetKindHandlingStatus` тихо провалила бы найденную мутацию через собственный fallback). `Apply` принимает только `Kind` — ни виджета, ни snapshot, ни gameplay-state в сигнатуре нет в принципе (граф сборки `GV2PresentationApply.Build.cs` не даёт этому модулю знать такие типы), поэтому отказ эффекта структурно не может задеть ни то, ни другое — гарантия ADR-0043 D2, а не тест поведения. Non-persistence проверен реальным `SaveToSlot`/`StartFromSave` над портативной сессией: canonical state hash не меняется при постановке недренированного эффекта, после реального перезапуска сессии из сохранённого слота хэш совпадает с состоянием до эффекта, а очередь эффектов пуста — поведением, а не отсутствием поля в контейнере.

**Инвариант:** [ADR-0043](../../ADR/0043-presentation-apply-boundary.md) — граница применения презентации: физическое применение получает только подготовленные значения и исполняется на Game Thread. Эффект, применяемый вне Game Thread, воспроизводит ровно тот класс отказа, который уже закрыт guard-ом в `FGV2PresentationApply::Apply`.

**Решение:** исполнитель эффектов на Game Thread, принимающий подготовленные значения. Вид эффекта — закрытое перечисление механизма с exhaustive dispatch: новое значение без явной ветки не компилируется либо проваливает гейт полноты, симметрично `FGV2PropertyConsumerFactory::ValidateAllKindsHandled`. Параметры и цель вида — данные. Отказ эффекта не трогает snapshot и gameplay state. Save/load эффекты не реплеит: незавершённый эффект не сохраняется и после загрузки не возобновляется.

**Не считается закрытием:** диспетчеризация по строковому `effect_id` через if-цепочку — при добавлении вида молчит компилятор; применение эффекта вне Game Thread «потому что он косметический»; тест non-persistence, проверяющий отсутствие поля в файле вместо поведения после загрузки.

**Шаги:**
1. Реализовать исполнитель на Game Thread; отклонить off-thread вызов типизированным отказом.
2. Ввести закрытое перечисление видов эффекта и exhaustive dispatch; добавить гейт полноты.
3. Проверить, что отказ эффекта не инвалидирует snapshot и gameplay state.
4. Проверить non-persistence поведением: эффект в процессе → сохранение → загрузка → эффект не возобновлён, состояние презентации восстановлено из snapshot.

**Done:**
- Новый вид эффекта без явной ветки не проходит: гейт полноты либо компилятор; случай покрыт негативным self-test.
- Off-thread применение отклоняется типизированным отказом; случай покрыт тестом.
- Отказ эффекта оставляет snapshot и gameplay state неизменными; проверено внесённым отказом, а не рассуждением.
- Non-persistence проверен поведением после реальной загрузки.

**Evidence:** вывод гейта полноты, негативные прогоны, save/load-прогон с эффектом в процессе.

### PEP-09 — Развести ввод при двух видах ухода

- [ ] PEP-09 — Развести ввод при двух видах ухода

**Зависимость:** PEP-08. **Файлы:** реализация состояний ухода из `PEP-02`; `FGV2LayeredUiReconciler`; binding registry.

**Инвариант:** [ADR-0041](../../ADR/0041-ui-commit-rollback-model.md) и правило `PEP-02`. Интерактивный stale-виджет — наблюдаемый дефект: клик по тому, чего уже нет, доходит до dispatcher. Именно этот класс отказа появляется впервые вместе с анимацией и до неё существовать не мог.

**Решение:** stale-виджет гасит ввод в момент логического удаления и инвалидирует свои handles тогда же; интерактивный stale-виджет делается невыразимым структурно — состоянием типа, а не проверкой во время исполнения. Self-dismissing виджет остаётся интерактивным до конца ухода, и взаимодействие с ним отменяет уход. `STATUS-003` закрывается обоими случаями.

**Не считается закрытием:** гасить ввод у stale физическим снятием виджета — между логическим удалением и снятием остаётся окно; проверка во время исполнения вместо невыразимости; закрыть только self-dismissal, оставив stale «как было, и так работало».

**Шаги:**
1. Сделать интерактивный stale невыразимым: состояние ухода несёт признак приёма ввода, и stale-ветка не может его выставить.
2. Погасить ввод и инвалидировать handles в момент логического удаления.
3. Проверить мутацией: вернуть приём ввода stale-виджету — красный тест с названной причиной; восстановить.
4. Проверить self-dismissal: клик по затухающему окну на 40% принят, уход отменён.
5. Снять `STATUS-003` тем же change set, которым закрыта вторая половина.

**Done:**
- Интерактивный stale невыразим структурно; мутационная проба подтверждает красный, а не рассуждение.
- Ввод у stale гаснет в момент логического удаления; окно между логическим и физическим снятием проверено тестом.
- Взаимодействие с затухающим окном принято и отменяет уход; проверено на промежуточной прозрачности, а не в начале ухода.
- `STATUS-003` снят этим же change set.

**Evidence:** мутационная проба, прогон окна между логическим и физическим снятием, прогон клика на 40%.

## Правила выполнения и остановки

- Всякая правка C++ виджетов классифицируется в change set до отметки `[x]`: механизм либо отсутствующий маршрут данных. Во втором случае задача обязана добавить маршрут и показать его вторым случаем. Неклассифицируемая правка останавливает задачу.
- Change set не объединяет введение механизма и его первого потребителя: механизм доказывается негативными тестами, потребитель — поведением. Вместе они недоказуемы.
- Задача, потребовавшая изменить архитектурный инвариант, останавливается до ADR.
- Evidence затухания требует прогона UE automation; он конфликтует с живым редактором, задачи M3 выполняются в сессии, где это учтено.

## Критерий выхода

Одноразовый эффект существует как один механизм с двумя равноправными источниками, монотонным `sequence`, типизированным отбрасыванием и отсутствием реплея после загрузки. Всплывающее окно — обычный экземпляр экрана в `overlay_stack`, собранный из declared composites; второй его вид добавлен без единой строки C++. Появление и уход ведут прозрачность 0↔100% за авторскую длительность, уход отменяется возвратом курсора и продолжается от текущей прозрачности. Элемент, удалённый реконсиляцией, не принимает ввод с момента логического удаления, и интерактивный stale невыразим структурно; элемент, уводящий себя сам, интерактивен до конца. `STATUS-002` и `STATUS-003` сняты.
