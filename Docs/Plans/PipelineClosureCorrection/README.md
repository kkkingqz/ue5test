# План доведения UI property pipeline

> **Материализует:** находки `UPP-R1`, `UPP-R2`, `UPP-R3`, `UPP-R6`, `UPP-R7` внешнего ревью от [2026-08-27](../../Status/GV2_Universal_UI_Property_Pipeline_Review_2026-08-27.md).
> **Задачи:** PCC-01…12.
> **Результат:** обе фигуры дефектов — «значение принято и выброшено» и «отказ проглочен» — перестают воспроизводиться внутри нового pipeline, а инструмент проверки перестаёт иметь систематические слепые зоны.

## Цель

Закрыть то, что осталось незамкнутым после [UniversalUiPropertyPipeline](../Archive/UniversalUiPropertyPipeline.md), и расширить охват средства измерения.

Пять находок P1 обнаружены на работе, закрытой с полностью зелёной верификацией. Четыре из пяти — это те же две фигуры, ради устранения которых строился весь pipeline. Само по себе это не провал направления: `ADR-0040` подтверждён ревью как верное решение. Но это доказывает, что **инструмент имеет систематические слепые зоны, а не случайные пропуски**.

Harness наблюдаемости доказывает, что объявленные capability существующих виджетов подключены. Он не заходит внутрь элементов коллекций, не видит объявленный, но нереализованный `kind`, и ничего не знает о том, потребляется ли результат `Commit`. Каждая находка ревью лежит ровно там, куда он не наведён. Поэтому план чинит не только экземпляры, но и охват.

## Состояние на входе

| Что | Сейчас |
|---|---|
| Схема элемента коллекции | Строится из capability самого entry-виджета, а не из скомпилированного `Spec.Items`; проверка `Schema ⊆ Capabilities` для элементов истинна по построению |
| Результат `CommitScreenFields` | Отбрасывается реконсилятором документа |
| Валидатор значения | Два: переносимый `ValidateUiFieldValue` и собственный `WalkFieldValue` материализатора; продакшн использует второй |
| `DescribeUiCapabilities` | Пять `const_cast` в композитах локации: const-метод создаёт объекты |
| Reset-мутация | Отсутствие target или consumer не отклоняет Prepare; Commit молча пропускает |
| Охват harness | Только объявленные capability существующих виджетов, верхний уровень |
| `EGV2PreparedUiValueKind::Object` | Вид объявлен, `CreateConsumer` возвращает `nullptr`, вызовов и тестов ноль |
| `WidgetRegistry.md` | Перечисляет классы как реализующие `IGV2ScreenFieldHost`, чего в коде нет |

## Принятые решения

- **Контракт не выводится из реализации.** Схема элемента коллекции обязана приходить из скомпилированной схемы, а не собираться из capability потребителя. Механизм, выводящий ожидание из того, что и так делает код, не может обнаружить расхождение — он и породил `UPP-R1`.
- **Результат операции, способной отказать, обязан быть потреблён.** Это правило проверяется гейтом, а не ревью глазами: отбрасывание результата любого `Commit*`/`Prepare*` краснит сборку.
- **Инструмент расширяется в том же change set, что и починка.** Иначе следующий раунд найдёт пятый экземпляр той же фигуры в очередной непокрытой области.
- **`UPP-R5` в план не входит.** Принадлежность UI-схем closure репозитория и политика отказа для схем мода — отдельная задача, не блокирующая ни одну из находок этого плана. Решение принимается до неё отдельно.

## Границы

Не входят: `UPP-R4` (`screen_fields` end-to-end) и работа по объявляемой из Designer композиции — они принадлежат плану [DataDrivenUiComposition](../DataDrivenUiComposition/README.md). Планы связаны не порядком целиком, а конкретными рёбрами между задачами; список рёбер и разделение файлов — в README того плана. `UPP-R5` — отдельная задача. `STATUS-001` и `STATUS-002` — как и прежде, вне границ.

## Критический путь

```text
PCC-01 ──► PCC-02 ──► PCC-03        (строгий порядок: наблюдаемость, проверка, удаление)
PCC-04, PCC-05                      (независимы друг от друга и от цепочки выше)

M2 независим от M1
M3 выполняется последним: его гейты фиксируют результат M1 и M2
```

`PCC-05` вынесен в M1 намеренно: решение о том, какие виды значения существуют и применимы, нужно рано — от него зависит `DUC-05` из плана [DataDrivenUiComposition](../DataDrivenUiComposition/README.md).

## Общие правила выполнения

1. Задача не отмечается `[x]`, пока не назван тест, который **покраснеет** при откате изменения, и это не продемонстрировано.
2. Расширение охвата инструмента входит в ту же задачу, что и починка соответствующего экземпляра.
3. Тест, доказывающий более слабое свойство, чем его имя, переписывается, а не дополняется.
4. Ассеты меняются только через `unreal-mcp`, с compile, save и прогоном automation.
5. Правки нормативных контрактов выполняются в той же задаче, что и код, делающий утверждение истинным.

## Итоговый Definition of Done

- [x] Схема элемента коллекции приходит из скомпилированной схемы; свойство, объявленное в ней и отсутствующее у entry-виджета, отклоняется, а не теряется. (PCC-01…03)
- [x] Проверка `Schema ⊆ Capabilities` рекурсивно доходит до элементов коллекций и не может быть истинной по построению. (PCC-02)
- [x] Валидация значения выполняется одним переносимым валидатором; второй путь удалён, а не оставлен параллельно. (PCC-04)
- [x] Каждый `EGV2PreparedUiValueKind` имеет consumer либо явно объявлен неприменимым; объявление вида без реализации краснит сборку. (PCC-05)
- [x] Результат каждого `Commit*` и `Prepare*` потребляется; отбрасывание краснит сборку. (PCC-06)
- [x] Отказ commit любого экрана документа оставляет остальные слои и предыдущую ревизию нетронутыми, и это проверено инъекцией отказа. (PCC-07)
- [x] Reset-мутация имеет те же инварианты, что и apply: отсутствие target или consumer — отказ Prepare, а не пропуск. (PCC-08)
- [x] `DescribeUiCapabilities` не создаёт объектов и не меняет состояние хоста. (PCC-09)
- [x] Harness наблюдаемости заходит внутрь элементов коллекций. (PCC-10)
- [ ] `WidgetRegistry.md` и остальные контракты описывают фактический API. (PCC-11)
- [ ] Ни одна находка ревью не закрыта ссылкой на задачу без продемонстрированного красного теста. (PCC-12)
