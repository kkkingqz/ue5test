# План объявляемой композиции UI

> **Материализует:** находку `UPP-R4` и архитектурный пробел, обнаруженный при разборе вопроса «нужен ли C++, чтобы собрать блок из существующих элементов».
> **Задачи:** DUC-01…11.
> **Результат:** новый UI-блок из существующих базовых элементов собирается ассетом, схемой и Lua — без единой строки C++.

## Цель

Сегодня ответ на этот вопрос — «да, нужен», по трём причинам, и все три механические.

Базовые элементы вообще не адресуемы как поля: `IGV2ScreenFieldHost::GetScreenFieldId()` реализован ровно четырьмя композитами локации, а `WBP_Text`, `WBP_Image`, `WBP_ProgressBar` и остальные — нет. Объявление capability недоступно из Blueprint: `DescribeUiCapabilities` — чистый виртуальный C++-метод, а `FGV2UiCapabilityBuilder` не является `BlueprintType`. Наконец, `key` привязан к перечислению пятнадцати конкретных классов в `FGV2KeyPropertyConsumer::Commit`.

Вдобавок средний уровень вложенности `экран → вкладки → блок` не работает: `EUiFieldKind::ScreenFields` в материализаторе проваливается в `default` с ошибкой «not supported» (`UPP-R4`).

## Принятые решения

- **Роль одна, а не две.** Экран и блок различаются только тем, что экран проверяется на матрице разрешений, а блок — нет. Всё остальное совпадает. Поэтому вводится **одно** свойство идентичности со смыслом «идентичность внутри объемлющего хоста»: на уровне экрана это field_id, на уровне блока — имя свойства. Два разных свойства дали бы автору ассета два способа сделать одно и то же.
- **Плоский объявляемый список, а не автоматическое делегирование.** Композит объявляет тройки *(имя свойства, имя дочернего виджета, вид)* — ровно то, что сегодня руками пишут композиты локации. Автоматическое разворачивание дерева ребёнка через `AddObject` дало бы автору схему вида `{ label: { text, key }, value: { percent, label, key } }` с протечкой `key` на каждый уровень. Плоский список даёт `{ label: TextSpec, value: number }`.
- **Ребёнку не нужен собственный идентификатор.** `Cap.TargetName` уже разрешается через `GetWidgetFromName`, то есть дочерний виджет адресуется своим именем в `WidgetTree`, которое UMG даёт бесплатно. Свойство идентичности нужно только тому, кто сам является полем объемлющего хоста.
- **Список живёт в Designer-свойстве.** Объявление лежит рядом с деревом виджетов, которое описывает, и правится тем же человеком в том же инструменте. Data asset и вывод из схемы рассмотрены и отклонены как разносящие объявление и предмет объявления по разным местам.
- **Вложенность не ограничивается.** Рекурсия уже реализована и уже неограниченна: проверка совместимости рекурсивно спускается в `ChildTree`, счётчика глубины нет нигде, обнаружение циклов схем работает. Ограничение в два уровня было бы **новым** правилом поверх работающей рекурсии — строго больше работы, а не меньше. Вместо него закрываются два реальных риска: циклы на уровне виджетов и фикстуры на глубине не меньше двух.

## Состояние на входе

| Что | Сейчас |
|---|---|
| `GetScreenFieldId()` | Реализуют четыре композита локации; ни один базовый элемент и ни `UGV2ScreenWidgetBase` |
| `DescribeUiCapabilities` | Чистый виртуальный C++-метод; `FGV2UiCapabilityBuilder` не `BlueprintType` |
| `EUiFieldKind::ScreenFields` | Материализатор проваливает в `default` с «not supported» |
| Вложенный экран во вкладке | Использует свой протокол, а не обычный envelope `field_id`/`schema_id`/`value` |
| `key` | Перечисление 15 конкретных классов; 13 из них — идентичный `SetKey` |
| Цикл на уровне виджетов | Схемные циклы обнаруживаются; композиционный цикл виджетов не проверяется |

## Границы

Не входят: `UPP-R1`, `UPP-R2`, `UPP-R3`, `UPP-R6`, `UPP-R7` — они принадлежат плану [PipelineClosureCorrection](../Archive/PipelineClosureCorrection.md). `UPP-R5` (принадлежность схем closure репозитория) — отдельная задача; она станет обязательной, когда блоки начнут поставляться модами, но для блоков проекта не требуется.

## Связь с планом доведения

План [PipelineClosureCorrection](../Archive/PipelineClosureCorrection.md) не является предшественником целиком. Связаны конкретные задачи, и весь этап M1 этого плана от него не зависит вовсе.

| Ребро | Тип | Причина |
|---|---|---|
| `DUC-05` → `PCC-05` | жёсткое | Набор видов, разрешённых в объявлении, определяется решением о полноте видов, включая судьбу `AddObject` |
| `DUC-09` → `PCC-04` | жёсткое по порядку | Иначе `ScreenFields` реализуется внутри `WalkFieldValue`, который заменяется единым валидатором |
| `DUC-07` → `PCC-02`, `PCC-03` | содержательное | Композит с коллекцией внутри наследует путь `UPP-R1` напрямую; и правильный образец «сравнение независимых источников» должен существовать до того, как его копируют |
| `DUC-04` ↔ `PCC-10` | только слияние | Один и тот же файл harness |
| `DUC-01`, `DUC-02`, `DUC-03` | нет | Затрагивают заголовки виджетов, общее состояние хоста и свойства ассетов |

При одном исполнителе проще выполнить план доведения целиком, а затем этот. При двух — `DUC-01…04` ведутся параллельно с самого начала, поскольку M1 плана доведения представляет собой строго упорядоченную цепочку и является узким местом по построению.

## Разделение файлов при параллельной работе

Оба плана тяжело правят один набор файлов, поэтому при параллельном ведении владение фиксируется явно.

| Файл | Владелец |
|---|---|
| `GV2PropertyConsumers.cpp` — consumer коллекции, валидация, виды | PipelineClosureCorrection |
| `GV2PropertyConsumers.cpp` — consumer ключа | DataDrivenUiComposition (`DUC-03`) |
| `GV2ScreenFieldMaterializer.cpp` | PipelineClosureCorrection до `PCC-04`, затем DataDrivenUiComposition |
| `GV2LayeredUiReconciler.cpp`, `GV2UiMutationPlan.cpp` | PipelineClosureCorrection |
| `GV2UiCapability.cpp` — рекурсия проверки совместимости | PipelineClosureCorrection (`PCC-02`) |
| `GV2UiCapability.h/.cpp` — построитель и объявляемый список | DataDrivenUiComposition |
| `GV2UiCapabilityObservabilityTests.cpp` | PipelineClosureCorrection до `PCC-10`, затем DataDrivenUiComposition (`DUC-04`) |
| Заголовки базовых виджетов, `GV2UiPropertyHost.h` | DataDrivenUiComposition |
| `GV2LocationCompositeWidgetBases.*` | PipelineClosureCorrection до `PCC-09`, затем DataDrivenUiComposition (`DUC-08`) |
| Ассеты `Content/` | DataDrivenUiComposition |

Разделение внутри `GV2PropertyConsumers.cpp` работает потому, что consumer ключа — обособленная функция, а `DUC-03` её целиком заменяет одной веткой.

## Общие правила выполнения

1. Задача не отмечается `[x]`, пока не назван тест, который **покраснеет** при откате изменения, и это не продемонстрировано.
2. Каждая задача, добавляющая объявляемую поверхность, тем же change set добавляет её в sweep наблюдаемости.
3. Ассеты меняются только через `unreal-mcp`, с compile, save и прогоном automation.
4. Правки нормативных контрактов выполняются в той же задаче, что и код.

## Итоговый Definition of Design

- [x] Базовый элемент может быть полем объемлющего хоста; свойство идентичности одно и задаётся в Designer. (DUC-01, DUC-02)
- [x] `key` не требует правки общего файла при добавлении нового хоста. (DUC-03)
- [x] Композит из существующих элементов объявляется Designer-свойством и не требует C++-класса. (DUC-05…07)
- [x] Схема такого композита плоская: автор пишет `day`, а не `day.text`. (DUC-06)
- [x] `screen_fields` работает через тот же envelope, что и обычное поле экрана. (DUC-09)
- [x] Цепочка `экран → вкладки → блок` собрана из данных и покрыта тестом, включая отказ на третьем уровне. (DUC-10)
- [x] Композиционный цикл виджетов отклоняется до `Ready`. (DUC-11)
- [x] Ни один объявляемый механизм не выводит ожидаемую форму из того, что умеет потребитель. (DUC-07)
