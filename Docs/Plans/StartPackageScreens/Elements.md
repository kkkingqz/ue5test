# Общие элементы

> **Материализует:** этап M0 [плана](README.md): решения по составу экранов, элемент действия с неактивным состоянием и подсказкой, пошаговый просмотр коллекции.

## SPS-01 — Решения по составу экранов

- [ ] SPS-01 — Решения по составу экранов

**Файлы:** `Docs/Status/ScreenRequests.md` (раздел «Решение» в каждой заявке, уточнённые таблицы полей), этот план.

**Зависит от:** —

**Решение:** до первого asset фиксируется, из чего собирается каждый экран. Вопросы:

1. Элемент действия (`key`, `text`, `binding`, `enabled`, `disabled_reason`) — одна схема `ui_value` и один composite для SR-001, кнопки покупки SR-003, вариантов SR-004 и движений SR-005. Владелец namespace — `core`, если элемент не зависит от игры.
2. Подсказка — переиспользовать hover-окно `RichText` (nested screen по `screen_id`) для нетекстового хоста или ввести отдельный механизм.
3. Пошаговый просмотр — отдельный элемент или `TabContainer` со скрытыми заголовками и локальным «Далее».
4. Магазин — `TabContainer` (товар — вкладка, описание и покупка — её nested screen) или описание в строке товара.
5. Диалог — сброс прокрутки при смене шага через `key` блока текста, равный ID шага, или явным сбросом.
6. Сцена с участниками — наибольшее число участников, под которое рассчитан layout.

**Инвариант:** [Core UI Extended Element Set § 4](../../Proposals/CoreUiExtendedElementSetProposal.md#4-правила-включения): элемент вводится вместе с первым потребителем и не дублирует существующий. Нарушение — второй вид кнопки или списка.

**Не считается закрытием:**
- решение «по месту» в задаче экрана;
- новый элемент без сравнения с существующими из таблицы плана.

**Done:**
- По каждому вопросу записано решение, отвергнутый вариант и причина.
- Таблицы полей SR-001…SR-005 соответствуют решениям.
- Для каждого нового C++ класса записан ответ по [When to Write Cpp](../../Guides/WhenToWriteCpp.md); класс без ответа не вводится.

**Evidence:** diff `ScreenRequests.md`; `validate_docs.py`.

## SPS-02 — Элемент действия с неактивным состоянием и подсказкой

- [ ] SPS-02 — Элемент действия с неактивным состоянием и подсказкой

**Файлы:** schema `ui_value` элемента действия в `GameData/<владелец>/schemas/`; composite элемента действия на `UGV2DeclaredCompositeWidgetBase` с дочерним `WBP_Button`; механизм подсказки по решению SPS-01 (C++ — только если решено); стиль `disabled` в `DA_UITheme_Default`; `Docs/UI/WidgetRegistry.md`, `Docs/UI/ScreenTemplates.md`, `Docs/UI/SemanticInput.md`, `Docs/Proposals/CoreUiExtendedElementSetProposal.md` (строка `Tooltip` переходит в план).

**Зависит от:** SPS-01.

**Решение:** `enabled` применяется существующим Boolean consumer к активности кнопки. `disabled_reason` — `TextSpec`, показывается подсказкой при наведении только у неактивного элемента. Подсказка — UE-local surface: открытие, позиционирование и закрытие не вызывают Lua.

**Инвариант:** [Semantic Input](../../UI/SemanticInput.md): неактивный элемент не создаёт Semantic Input; hover не пересекает boundary. Нарушение — отправка handle неактивного элемента или вызов Lua при наведении.

**Не считается закрытием:**
- подсказка, показанная только в тесте без production reconciler;
- текст причины raw string вместо `TextSpec`;
- неактивность, нарисованная цветом без отключения ввода.

**Done:**
- Схема элемента замкнута; `enabled` по умолчанию `true`; лишний ключ, неверный тип и неверный `key` отклоняются.
- Неактивный элемент показан стилем `disabled` и не отправляет Semantic Input при нажатии, даже если `binding` передан.
- Причина появляется при наведении на неактивный элемент и не появляется у активного.
- Наведение не создаёт Semantic Input.
- Смена `enabled` у элемента с тем же `key` обновляет существующий widget, а не создаёт новый.
- Удаление элемента при открытой подсказке закрывает её как stale-удаление.
- Подсказка остаётся в пределах viewport на шести разрешениях матрицы.
- Composite проходит `GV2.UI.CapabilityObservabilityCompositeSweep`.

**Evidence:** contract-тесты на фикстурах `core:` через production reconciler; отказы схемы; sweep; матрица; `compile_and_save_assets.py`; `run_ue_tests.py`.

## SPS-03 — Пошаговый просмотр коллекции

- [ ] SPS-03 — Пошаговый просмотр коллекции

**Файлы:** элемент по решению SPS-01 (`core`); schema `ui_field`/`ui_value`; подпись «Далее» — текст шаблона; `Docs/UI/WidgetRegistry.md`, `Docs/UI/ScreenTemplates.md`, `Docs/UI/UIDocumentAndReconciliation.md` (номер записи — UE-local state).

**Зависит от:** SPS-01.

**Решение:** элемент показывает одну запись keyed-коллекции и кнопку «Далее»; номер текущей записи — UE-local state, как выбранная вкладка. На последней записи вместо «Далее» показываются кнопки из данных.

**Инвариант:** [UI Document § UI-local state](../../UI/UIDocumentAndReconciliation.md#ui-local-state): значение, не влияющее на gameplay, не хранится в Lua. Нарушение — «Далее», отправляющий Semantic Input.

**Не считается закрытием:**
- «Далее» через команду Lua;
- все записи сразу с прокруткой вместо пошагового показа;
- подпись «Далее» из значения поля.

**Done:**
- Показывается одна запись; «Далее» переходит к следующей без Semantic Input и без новой revision.
- На последней записи показаны кнопки из данных с их bindings.
- Новая revision с другим набором `key` записей начинает с первой записи; та же revision с теми же `key` сохраняет текущую.
- Запись с одним элементом сразу показывает кнопки.
- «Далее» доступно с клавиатуры и геймпада через focus navigation CommonUI.

**Evidence:** contract-тесты на фикстурах `core:`; sweep; `run_ue_tests.py`.
